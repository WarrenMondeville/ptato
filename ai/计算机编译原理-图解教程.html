00一句话：编译器就是一台翻译机器

先别管什么文法、自动机、四元式。编译器的全部工作，可以用一句话说完：读进一种语言写的程序，写出另一种语言写的、意思完全等价的程序。

如果你学过英语，这件事你每天都在做。给你一句中文「把窗户打开」，你翻译成 Open the window。你做的动作是：先听出这是几个词（词法），再判断「把」字句的结构（语法），再理解它是在要求别人做一件事而不是描述窗户的状态（语义），最后用英语的习惯说法重新组织出来（生成）。

编译器做一模一样的事，只是输入是 x = a + b * 2;，输出是一堆机器指令、一段字节码、或者另一种高级语言的源码。

听词
词法分析
把一串无差别的字符切成有意义的单词：x 是标识符，= 是赋值号，a 是标识符，+ 是加号……空格和注释在这一步被丢掉。
断句
语法分析
按语言规定的结构，把单词串组织成一棵树：这是一条赋值语句，左边是变量 x，右边是一个加法表达式，加法右边又是一个乘法表达式。
解意
语义分析
检查这句话有没有意义：a 声明过吗？b 是数组还是整数？把整数和字符串相加是不是合法的？
落笔
代码生成
把检查过的意思用目标语言重新写出来，先写成中间形式（四元式），再翻成目标机器上的指令。
润色
代码优化
写出来的东西能跑，但不一定好。把能提前算的提前算、把重复算的合并、把循环里不变的东西挪出去。

01从机器语言到高级语言：为什么必须有翻译这一步

计算机只认一种东西：一串 0 和 1 组成的指令。人写代码的自然方式完全不是这样。这个落差，就是编译器存在的全部理由。

三层语言，和两个翻译方向

先把语言的层次看清楚。最底下是机器语言，就是 CPU 能直接执行的二进制指令；往上一层是汇编语言，用 MOV、ADD 这种助记符代替二进制，本质上一对一；再往上是高级语言，用接近数学记号的方式表达算法。

高层
高级语言　sum = sum + i;
人写起来舒服，机器一个字都看不懂。
中层
汇编语言　MOV R1, sum　ADD R1, i　MOV sum, R1
和机器指令一一对应，只是把二进制换成了人能读的助记符。
底层
机器语言　1001 0110 0011 ...
CPU 唯一真正能执行的东西。
图 1-1 · 语言的三层，越往上越像人话，越往下越像机器话

从高往低走，叫编译（编译程序）。从低往高走，也有人在做，叫反编译或者逆向，但那是另一个领域，而且天然做不到完全还原——编译过程丢掉的信息（变量名、注释、类型结构）是找不回来的。

一句话记住编译的定义

编译程序是这样的一个程序：它把用某一种高级语言写的源程序，翻译成一个等价的、用低级语言（机器语言或汇编语言）写的目标程序。「等价」两个字是全部难点所在——不是「大概意思对」，而是在任何输入下行为完全一致。

中间那条路：先编译到字节码，再交给虚拟机

很多人以为「编译型语言」和「解释型语言」是语言的属性，其实不是。它是实现的属性。C 通常被编译，但也有 C 解释器；Python 通常用解释器执行，但也有把 Python 编译成机器码的实现。

而且今天最主流的做法其实是第三条路：先编译成一种与具体机器无关的中间形式（字节码），运行时再由虚拟机把它翻译成机器指令执行。Java 的 class 文件、.NET 的 IL、WebAssembly 走的都是这条路。

张幸儿这本书在第 6 章专门安排了一节讲虚拟机（6.3.2），正是为了这个目的：让初学者不必先啃完 x86 指令集，也能把代码生成这一环完整地做出来。你造一个假想的机器，定义好它的指令，然后为它生成代码——配套的实践教材里就给了一个能跑的样本程序。

这个思路在工程上极其有用。LLVM 之所以能同时支撑 C、Rust、Swift、Julia，正是因为它把「前端翻译成 IR」和「IR 翻译成某款 CPU 的指令」彻底分开了。N 种语言 × M 种机器，本来要写 N×M 个编译器，有了 IR 只需要 N+M 个。

02编译与解释：两条路线，和一个光谱

编译是「先全部翻好，再去执行」；解释是「边翻边执行」。听起来是二选一，实际上今天几乎所有语言都落在两者之间。

编译方式
先把整个源程序翻译成目标程序，得到一个可以独立运行的东西，然后再运行它。翻译一次，运行多次。
解释方式
不生成独立的目标程序，而是边读源码边执行，读一句执行一句。每次运行都要重新翻译。

启动速度慢。得先编译完快。改完立刻能跑

JIT 是什么，一句话讲清

JIT（Just-In-Time，即时编译）就是：先按解释方式跑起来，同时统计哪些代码跑得次数多，然后把这些热点代码当场编译成机器码缓存起来。下次再跑到这段，直接用编译好的版本。它同时拿到了解释的灵活性和编译的速度，代价是运行时要额外承担编译开销和一份内存。

还有一种：先编译成 C，再让 C 编译器干活

把源语言翻译成 C 代码，再交给现成的 C 编译器去生成机器码。这条路叫源到源翻译（source-to-source），张幸儿在配套著作里专门讨论过 PASCAL 到 C 的转换系统。

它的好处是：不用自己写后端。你只需要把你的语言翻译成 C，寄存器分配、指令选择、目标文件格式这些最脏最累的活，全都由 GCC 或 Clang 替你做了。早期的 C++（Cfront）、很多函数式语言、以及大量 DSL 都走这条路。

代价也要知道

调试信息难做（报错会报到生成的 C 代码行号上）、编译速度慢（走两遍完整编译）、以及 C 语言自身的限制会反过来约束你的语言设计（比如不好实现精确的垃圾回收）。

为什么需要「中间代码」这一层

你可能会问：语法树都有了，为什么不直接生成机器指令？

三个理由。第一，解耦：有了中间代码，前端只管翻译到中间代码，后端只管从中间代码生成指令。换一台机器，只改后端。第二，便于优化：四元式这种线性、结构统一的形式，做数据流分析和代码变换比在树上操作方便得多。第三，便于跨平台：字节码就是一种中间代码，同一份字节码在不同机器上由不同的虚拟机执行。

一个反直觉的事实：中间代码这一层的引入，反而让编译器整体变简单了。看起来多了一道工序，实际省掉了 N×M 的组合爆炸。软件工程里到处都是这个道理——加一层间接，把网状依赖变成星形依赖。

04前端与后端、遍、T 形图：三个绕不开的概念

这三个概念不解决任何具体技术问题，但没有它们，你没法描述一个真实的编译器长什么样。

前端与后端：按「和谁有关」切一刀

编译程序天然可以切成两半：和源语言有关、和目标机器无关的那一半叫前端；和目标机器有关的那一半叫后端。切点就在中间代码上。

前端
词法 + 语法 + 语义+ 中间代码生成换一门源语言，就要换一个前端
中间表示
四元式 / 字节码 / IR这一层是契约，两边都只认它
后端
优化 + 目标代码生成换一款 CPU，就要换一个后端
图 4-1 · 前中后三段的职责划分

这解释了一个你可能注意过的现象：为什么 Clang 能同时编译 C、C++、Objective-C？因为它们共用同一个后端，只是前端不同。为什么 LLVM 能同时支持 x86、ARM、RISC-V、WebAssembly？因为后端是可替换的，前端不用管。

遍：一趟扫描算一遍

遍（pass）的定义很朴素：对源程序或者它的某种中间形式从头到尾扫描一次，并做相应的加工处理，就叫一遍。

一个只做一遍的编译器，读一遍源码，边读边做词法、语法、语义、生成代码，一次搞定。它快、省内存，但做不了什么优化——很多优化需要的信息（比如「这个变量在后面还会不会被用到」）在你扫描到当前位置时根本还没读到。

单遍
一遍扫描，一次成型
内存省、速度快。适合早期内存小、或者要求快速编译的场景。代价是几乎没有优化空间，且要求语言本身设计得「一遍就能定下来」（比如 C 要求先声明后使用）。
多遍
一遍做一件事，前一遍的输出是后一遍的输入
典型：第 1 遍词法，第 2 遍语法，第 3 遍语义与中间代码，第 4 遍优化，第 5 遍目标代码。每遍逻辑清晰、可以充分优化，代价是中间结果要落盘或驻留内存，编译变慢。

06文法的形式定义：G = (Vn, Vt, P, S)

文法就是一套造句规则。它精确地回答一个问题：哪些符号串是「合法的句子」，哪些不是。

四元组：文法由四样东西构成

G = ( Vn, Vt, P, S ) Vn —— 非终结符集合（nonterminal） 语法单位，还要继续往下展开的东西 Vt —— 终结符集合（terminal） 语言里最终的、不可再分的符号 P —— 产生式集合（production） 形如 α → β 的重写规则 S —— 开始符号（start symbol） 一个特殊的非终结符，推导的起点 约定：V = Vn ∪ Vt，且 Vn ∩ Vt = ∅

用一句话解释：Vn 是「还能再拆的语法概念」，Vt 是「拆到底的单词」，P 是「怎么拆」的规则表，S 是「从哪个概念开始拆」。

一个常考的点

不同的文法可以生成同一个语言。如果 L(G₁) = L(G₂)，就说 G₁ 与 G₂ 等价。这不意味着两个文法长得像——它们可以有完全不同的产生式。第 10 节的「文法等价变换」就是在利用这一点：换一个更好用的文法，但语言不变。

08Chomsky 四类文法，以及各自的识别机器

1956 年 Chomsky 把文法分成四类，不是出于分类癖，而是因为每一类恰好对应一种计算能力不同的机器。这条对应关系，直接决定了编译的每个阶段能用什么工具。

改文法（推荐）

加规定（也可以）

一个必须知道的定理

不存在一个算法，能判定任意一个上下文无关文法是不是二义的。更进一步，也不存在算法能判定两个 CFG 是否生成同一个语言。这不是「还没找到」，而是已被证明不可判定。所以别指望有个工具能替你检查文法写得对不对——只能靠人在设计时小心，以及用「无二义的充分条件」（比如后面要讲的 LL(1)、LR(1) 条件）去保证。

变换一：压缩文法（删除无用符号）

文法里可能存在两类垃圾符号，都要删掉：

类型定义怎么找
不可达符号从开始符号 S 出发，用任何产生式都推导不出它从 S 出发做闭包，凡是没被访问到的非终结符都删
不活动（无用）符号从它出发永远推不出一个只含终结符的串反向找：能推出终结符串的留着，其余删
例：G = ( { S, A, B }, { a }, P, S ) P : S → a // S 是好的 A → aA // A 永远推不出终结符串（无限递归）→ 不活动 B → a // B 能推出 a，但从 S 出发到不了 B → 不可达 压缩后：G' = ( { S }, { a }, { S → a }, S )　　　L(G') = L(G) = { a }
删除顺序有讲究

先删不活动符号，再删不可达符号。反过来做可能删不干净：先删不可达的话，某个符号可能因为「它依赖的那个符号被删了」而变成新的不活动符号，但你已经过了这一步。这是教材里专门强调的实现细节。

变换二：消去左递归

这是自顶向下分析的必经步骤。左递归产生式形如 A → Aα，用自顶向下的方式展开它，会陷入死循环：A 展开成 Aα，又展开成 Aαα，永远碰不到终结符。

直接左递归　A → Aα | β ↓ 改写成 A → βA' A' → αA' | ε 直觉：原来是「先来个 A 再跟一串 α」， 改成「先来个 β，后面跟任意多个 α」——用右递归表达「重复」。

看个具体的：表达式文法里的加减法。

原文法（左递归） 改写后（右递归） E → E + T | T E → T E' E' → + T E' | ε 原来 E 想吃掉一串 + T， 现在 T 打头，E' 负责后面 但第一个符号又是自己。 任意多个 + T。语言完全一样。
图 10-2 · 消左递归的实质：把「向左无限展开」改成「向右可终止展开」

间接左递归也是同样的问题，但藏得更深：比如 A → Bα，B → Aβ，绕一圈又回到 A。处理办法是先把非终结符排个序，然后把间接左递归逐步转化成直接左递归再消除。教材里给出了完整的算法，实现时就是两重循环加代入。

变换三：提取左公因子

当同一个非终结符的多条候选式开头相同时，自顶向下分析就没法「看一眼当前符号就知道该选哪条」。解决办法是把公共前缀提出来，把决策往后推。

原文法（有公共前缀 if） S → if E then S S → if E then S else S 提取左公因子 S → if E then S S' S' → else S | ε 现在看到 if 就只有一条路可走， 到底有没有 else，等读完再决定。
三种变换的分工

压缩是为了干净（删垃圾），消左递归是为了不死循环，提取左公因子是为了能做唯一选择。前两个对自顶向下和自底向上都必要，第三个主要是为了 LL(1)。
注意：消左递归会改变语法树的结构（左结合变成右结合），所以做完之后，需要在语义动作里把结合性重新纠正回来。

13DFA 与 NFA：确定与非确定

状态转换图画起来直观，但要让机器自动生成它，得先把它变成严格的数学对象。DFA 每一步只有一条路，NFA 每一步可以有多条路。

确定有穷状态自动机 DFA = ( K, Σ, f, S, Z ) K 有穷的状态集合 Σ 有穷的字母表（输入符号集） f 转换函数，f : K × Σ → K // 单值：一个状态读一个符号，只到一个地方 S 唯一的初态，S ∈ K Z 终态集合，Z ⊆ K 非确定有穷状态自动机 NFA = ( K, Σ, f, S, Z ) f : K × (Σ ∪ { ε }) → 2^K // 多值：一个状态读一个符号，可以到多个地方 S 初态集合（可以有多个） 允许 ε 边：不读任何符号就能转移
DFA 确定
读一个符号，只有一条路不允许 ε 边初态唯一好实现：一个二维数组就能存下整个 f
NFA 非确定
读一个符号，可能有多条路允许 ε 边初态可多个好构造：从正则表达式几乎直接就能画出来
图 13-1 · DFA 好执行，NFA 好构造。第 14 节讲怎么把后者变成前者

一个关键事实：两者识别能力完全相同

定理（子集构造 / 子集法）

对任意一个 NFA，都存在一个与之等价的 DFA，它们识别同一个语言。所以 NFA 的「非确定」并没有带来更强的能力，只是带来了更方便的写法。代价是状态数可能指数级膨胀（n 个状态的 NFA 转成 DFA 最多有 2ⁿ 个状态，实践中通常远小于这个上界）。

图 13-2 · 确定化的核心思想：把「一组可能的状态」当成一个新状态
为什么这个想法能成立？因为 NFA 在运行时，虽然「可能处于多个状态」，但这个可能状态的集合是确定的。所以用集合当状态，非确定就消失了。这就是子集法的全部洞察。

14子集法与分割法：先确定化，再化简

拿到一个 NFA 之后有两步标准操作：先用子集法把它变成 DFA，再用分割法把 DFA 的状态数压到最小。这两步就是词法分析器自动生成器的全部核心。

子集法（NFA → DFA）

对状态集合 I，定义两个操作： ε-closure(I) 从 I 中任一状态出发，只走 ε 边能到达的所有状态的集合 （I 自身也在里面） move(I, a) 从 I 中任一状态出发，读一个符号 a 能直接到达的状态的集合 （只走一步，不含 ε 边） 算法： 1. 令 DFA 的初态 = ε-closure({ NFA 初态 }) 2. 对 DFA 中每个新状态 T，对每个符号 a ∈ Σ： 计算 U = ε-closure( move(T, a) ) 若 U 非空且是新的，就作为 DFA 的新状态加入 记下转换 T --a--> U 3. 重复直到没有新状态 4. DFA 的终态 = 所有含有 NFA 终态的状态集合
第 4 步最容易忘

DFA 的一个状态是一组 NFA 状态的集合。只要这个集合里包含至少一个 NFA 的终态，这个 DFA 状态就是终态——不需要集合里全是终态。直觉是「只要有可能停在接受状态，就算接受」。

分割法（DFA 最小化）

确定化之后往往有一堆冗余状态。最小化的思路是把「表现完全一样」的状态合并成一个。

终止状态与非终止状态是可区分的（一个接受、一个不接受） 可区分：从状态 s 和 t 出发，读同一个符号串 w，一个到终态一个不到 算法： 1. 初始划分：Π = { 终态集, 非终态集 } 2. 反复细分：对当前每个组 G，若组内状态 s、t 读某符号 a 后 落到了不同的组，就把 G 拆开 3. 直到没有组能被拆开 4. 每个组合并成一个状态，重画转换边 最后还要删死状态：从初态不可达的、或者永远到不了终态的状态，直接删掉。

一个实用的理解方式：最小化本质上是在合并「无论后面读什么，命运都相同」的状态。如果两个状态对所有可能的后续输入都给出同样的接受/拒绝判定，那保留两个就是浪费。
为什么要最小化

状态数直接决定词法分析器的转换表大小和运行速度。对真实语言（几十上百个单词模式），做不做最小化，状态数差几倍很常见。而且最小 DFA 是唯一的（同构意义下），这意味着你可以用它来判断两个正则表达式是否等价——都转成最简 DFA，比一下是不是同构。

自顶向下分析的本质：为一个串找一棵树

换个说法：自顶向下分析器就是一个「预测器」。它站在树根，看着输入的第一个符号，猜「这个句子应该是由 S 的哪条候选式来的」，然后往下走一层，再猜一次，直到猜出来的叶子正好和输入串完全对上。

如果猜对了，皆大欢喜；如果猜错了，叶子和输入对不上，就得回到上一层换一条候选式重猜。这个「回到上一层」就是回溯。回溯的代价在最坏情况下是指数级的——第 19 节专门讲为什么必须扔掉它。

20无回溯的前提：FIRST 集与 FOLLOW 集

要做到无回溯，需要回答一个问题：看到当前输入符号 a，能不能唯一确定该用 A 的哪条候选式？两个集合就是为回答这个问题而造的。

FIRST 集：一串符号「可能以什么开头」

FIRST(α) = { a | α ⇒* aβ，a ∈ Vt，β ∈ V* } 若 α ⇒* ε，则 ε ∈ FIRST(α) 人话：FIRST(α) 是「把 α 推导到底，第一个终结符可能是谁」的集合。
情况FIRST 怎么算
α 是终结符 aFIRST(a) = { a }
α 是非终结符 A把 A 的每条候选式的 FIRST 并起来
α = X₁X₂…Xₙ依次加 FIRST(X₁)；若 ε ∈ FIRST(X₁) 就继续加 FIRST(X₂)；以此类推
所有 Xᵢ 都能推出 ε把 ε 加进 FIRST(α)

FOLLOW 集：一个非终结符「后面可能跟着什么」

FOLLOW(A) = { a | S ⇒* αAaβ，a ∈ Vt，α,β ∈ V* } 若 S ⇒* αA（A 在句型最末尾），则 # ∈ FOLLOW(A) （# 是输入串的结束标志，有些教材写作 $） 人话：FOLLOW(A) 是「在所有可能的句型里，紧挨在 A 右边的终结符可能是谁」的集合。
规则操作
规则 1对开始符号 S，把 # 放进 FOLLOW(S)
规则 2若有产生式 B → αAβ，则把 FIRST(β) 中除 ε 以外的所有符号放进 FOLLOW(A)
规则 3若有产生式 B → αA，或者 B → αAβ 且 ε ∈ FIRST(β)，则把 FOLLOW(B) 全部放进 FOLLOW(A)
规则 3 是初学者最常漏的一条

它的含义是：如果 A 在一个产生式的末尾，那么 A 后面能跟什么，取决于「谁用了这个产生式」的后面能跟什么。所以要反复迭代计算，直到所有 FOLLOW 集都不再变化为止。实现上就是一个 do-while 循环，跑到不动点。

LL(1) 的判定条件

文法 G 是 LL(1) 的，当且仅当对每一个非终结符 A 的任意两条不同候选式 A → α 与 A → β，同时满足： ① FIRST(α) ∩ FIRST(β) = ∅ 两条候选式能推出的开头终结符不能重叠 ② 若 ε ∈ FIRST(α)，则 FIRST(β) ∩ FOLLOW(A) = ∅ （反之亦然） 若某条候选式可能推出空串，就还要检查它「该不该用 ε」的时刻 ——那时要看 A 后面能跟什么，不能和另一条的开头撞上
图 20-1 · LL(1) 条件的两种违反方式
一个必须记住的限制

LL(1) 文法不能含左递归（左递归必然违反条件 ①），也不能含公共左因子。所以第 10 节的消左递归和提取左公因子，是 LL(1) 分析的必备前置步骤。
反过来，不是所有文法都能改造成 LL(1)。有些语言结构天生需要更多前瞻（比如前面那个 if-else 二义性，标准做法是用额外的消歧规则，而不是靠 LL(1) 条件）。

21递归下降分析技术

如果文法是 LL(1) 的，那么最自然的实现方式就是：给每个非终结符写一个函数，函数体就是它的候选式。遇到终结符就匹配，遇到非终结符就调用对应函数。这就是递归下降。

图 21-1 · 一条产生式对应一个函数，候选式的选择变成 if 判断

两条固定的编写规则

遇到的东西生成的代码
终结符调用 match(该终结符)：比对当前符号，对上了就读下一个，对不上就报错
非终结符调用它对应的那个函数
多个候选式用 if / switch 按当前符号选择；选择走哪个分支，查 FIRST 集（能推出 ε 的还要看 FOLLOW 集）
ε 候选式什么都不做，直接返回（但要放在 else 分支里，不能无条件返回）
为什么递归下降至今仍然是最常用的手写方案

四个理由：① 直观——代码和文法一一对应，改文法就是改函数；② 好调试——调用栈直接反映语法结构，报错时栈回溯一看就知道在解析什么；③ 好插语义动作——想在哪生成代码就在哪插一行，比表驱动方便得多；④ 报错友好——可以在每个函数里写针对性的错误信息。
GCC 早期、Clang 的 C 前端、Go 早期、以及绝大多数 JSON / DSL 解析器，都是递归下降。

代价：对文法要求高

递归下降要求文法接近 LL(1)。遇到需要多符号前瞻的地方，标准做法是手工前瞻——先读几个符号看看，再决定走哪条，必要时把读过的符号退回。这会牺牲一点优雅，但换来的是可控性和好的错误信息。C++ 这种文法极其复杂的语言，Clang 就是靠大量手工前瞻硬啃下来的。

递归下降与「预测分析」的分工：递归下降把分析表编码进了控制流（if 分支就是表的内容）；预测分析则把表显式存成二维数组，配一个通用的驱动循环。前者手写方便，后者适合自动生成。

句柄和规范归约

回忆第 9 节：句柄 = 最左直接短语。如果每次归约都归约当前句型的句柄，这样的一系列归约叫规范归约（也叫最左归约），它正好是最右推导（规范推导）的逆过程。

永远在栈顶。这是自底向上分析能用栈实现的根本原因。 （严格说是「规范句型的活前缀」加上句柄，见第 26 节）

为什么自底向上比自顶向下强？因为它在决定动作之前，已经看到了句柄的全部（都已经进栈了），而自顶向下在决定候选式时，后面的输入还没看到。所以 LR 类文法能覆盖的语言，严格多于 LL 类。几乎所有程序设计语言的语法结构都能用 LR 描述，但有些用 LL 描述不了。

24简单优先分析技术

最简单的找句柄办法：给每两个符号之间定义一个优先关系，然后用「关系模式」把句柄的左右边界找出来。

三种优先关系

对文法中的任意两个符号 a、b（可以是终结符也可以是非终结符）： a =· b 当且仅当文法中存在产生式形如 … a b … 或 … a Q b … // a 和 b 属于同一个句柄，要一起归约 a <· b 当且仅当存在产生式 … a P …，且 b ∈ FIRSTVT(P) // b 比 a 后归约，a 在句柄的左边外面 a ·> b 当且仅当存在产生式 … P b …，且 a ∈ LASTVT(P) // a 比 b 先归约，b 在句柄的右边外面 （FIRSTVT / LASTVT 的定义见下一节，这里先理解为 「P 能推出的串的第一个 / 最后一个终结符」）
第一个 ·> 就是句柄的右端； 再从那里往左扫，找到最后一个 <· ，它右边第一个符号就是句柄的左端。
图 24-1 · 句柄被夹在 <· 和 ·> 之间，内部全是 =·

分析算法

设栈顶符号是 a，当前输入符号是 b： 1. 若 a <· b 或 a =· b → 移进：把 b 压入栈 2. 若 a ·> b → 归约：往回找句柄的左端，用对应产生式归约 3. 若 a = b = # → 接受 4. 其余情况 → 报错
简单优先的苛刻条件

要求文法满足：① 任意两个符号之间至多有一种优先关系（不能既 <· 又 ·>）；② 不含 ε 产生式；③ 任意两个产生式的右部不相同。这些条件相当严格，真实语言的文法很难全部满足。所以简单优先教学价值大于实用价值——它把「找句柄」这件事讲清楚了，后面的技术都是它的升级版。

简单优先的名字是相对「算符优先」来的：它对终结符和非终结符一视同仁，统一定义优先关系。而算符优先只看终结符（算符），不管非终结符。

25算符优先分析技术

算符优先把注意力只放在终结符（算符）上，非终结符一概不管。这样优先矩阵立刻小很多，代价是归约的不再严格是句柄，而是「最左素短语」。

算符文法与两个集合

算符文法（OG）：任一产生式的右部都不含相邻的两个非终结符 形如 … Q R … 的右部是不允许的 （允许 … a Q b …，不允许 … Q R …） FIRSTVT(P) = { a | P ⇒⁺ a… 或 P ⇒⁺ Q a… } // P 能推出的串中，第一个终结符的集合 LASTVT(P) = { a | P ⇒⁺ …a 或 P ⇒⁺ …a Q } // P 能推出的串中，最后一个终结符的集合

a <· b 等价于 f(a) < g(b) a =· b 等价于 f(a) = g(b) a ·> b 等价于 f(a) > g(b) 空间从 O(n²) 降到 O(n)。 代价：不是所有优先关系矩阵都能表示成优先函数； 而且原来矩阵里的「无关系」（即出错）会被强行赋予一个数值关系， 于是错误发现会变晚——本该立刻报错的，可能要再读几个符号才报。

两个核心概念：项目与活前缀

项目（item）：在产生式右部的某个位置点一个圆点，表示「分析进展到哪了」 A → α · β 已经看到了 α，还期待看到 β A → α β · β 也看完了 → 归约项目 A → · α β 什么都没看到 → 待约项目 A → α · X β 移进项目（X 是终结符时） 活前缀（viable prefix）：规范句型的一个前缀，它不含句柄之后的任何符号 人话：分析栈里的符号串，任何时候都必须是某个活前缀 ——因为一旦越过了句柄右端，就应该归约了 关键定理：所有活前缀的集合，恰好可以被一个 DFA 识别， 这个 DFA 的状态就是「LR(0) 项目集」。LR 分析表就是从这个 DFA 造出来的。
一句话理解 LR 的全部思想

把所有「可能已经看到的部分」记成一个状态，每读一个符号就跳到下一个状态；当状态告诉你「已经凑齐一条产生式的右部」时，就归约。状态机记住了所有历史，所以决策永远唯一，不需要回溯。这就是 LR 强于 LL 的原因——它把「看过什么」编码进了状态。

28LR(1) 与 LALR(1)：为什么要多看一格

SLR(1) 用 FOLLOW 集决定归约，但 FOLLOW 集是「全文法范围内」算出来的，太粗。把展望符精确到「这个具体项目后面能跟什么」，就是 LR(1)。

SLR 为什么会不够

问题在于：FOLLOW(A) 是「A 在所有句型里后面可能跟的所有符号」，但某个具体的项目 A → α· 出现的那个上下文里，A 后面能跟的往往只是其中的一部分。

一个比喻

FOLLOW 集像是「全国所有姓张的人可能出现的城市」，而 LR(1) 的展望符是「这个具体的张三人此刻所在的城市」。用前者做判断，就会在一些不该归约的地方也允许归约，从而可能和移进动作撞车——这就是 SLR 会报冲突、而 LR(1) 不报的原因。

LR(1) 项目：带上自己的展望符

LR(1) 项目的形式：[ A → α · β , a ] a 叫搜索符 / 展望符，含义是： 「当栈顶是 α、并且下一个输入符号是 a 时，才允许用 A → αβ 归约」 CLOSURE：若 [ A → α · Bβ , a ] ∈ I， 则对每个产生式 B → γ 和每个 b ∈ FIRST(βa)， 把 [ B → · γ , b ] 加入 I // 注意展望符是算出来的，不是照抄的 填表：归约项目 [ A → α · , a ] 只在 ACTION[k, a] 上填 r —— 而不是像 SLR 那样在整个 FOLLOW(A) 上都填

好消息：真实语言的文法很少碰上这种情况。这也是为什么 Yacc 系列几十年来一直用 LALR(1)——用最小的状态数，拿到了几乎全部的能力。

为什么类型检查是语义分析的核心

30属性文法与语法制导翻译

语义分析不是另起炉灶做一遍遍历，而是挂在语法分析的过程中——每用一次产生式，就执行一段附带的语义动作。这就是语法制导翻译。

结构体 / 记录类型把它当成一个小的作用域：内部成员从 offset=0 开始排；整个类型的宽度 = 成员宽度之和（还要考虑对齐）
作用域：符号表天生是分层的

内层作用域可以看见外层的名字，外层看不见内层的。同名时内层屏蔽外层。实现上就是一张栈式的符号表：进入作用域压一层，退出弹一层，查表从栈顶往栈底找。第 7 章的栈式存储分配和第 36 节的符号表组织，都是这个结构。

四元式：最主流的一种

形式：( op , arg1 , arg2 , result ) op 运算符（+ - * / := j< jnz =[] call ……） arg1 第一操作数 arg2 第二操作数（一元运算时为空） result 运算结果存放的地方（通常是临时变量 T1、T2） 每个四元式只有一个运算符，所以复杂表达式必须拆成一串。 它是「三地址码」的一种写法：一条指令最多涉及三个地址。

把 a = b * c + b * d 翻译成四元式序列：

( 1 ) ( * , b , c , T1 ) // T1 = b * c ( 2 ) ( * , b , d , T2 ) // T2 = b * d ( 3 ) ( + , T1, T2, T3 ) // T3 = T1 + T2 ( 4 ) ( := , T3, _ , a ) // a = T3

三元式与间接三元式

三元式：( op , arg1 , arg2 ) 结果不写名字，而是用这条三元式的编号引用 ( 1 ) ( * , b , c ) // (1) = b * c ( 2 ) ( * , b , d ) // (2) = b * d ( 3 ) ( + , (1), (2) ) // (3) = (1) + (2) ( 4 ) ( := , (3), a ) // a = (3) 问题：优化时经常要插入或删除指令，一改编号就全乱了， 所有引用都要跟着改。 间接三元式：加一张执行表，表里存三元式的编号。 优化时只改执行表（顺序、增删），三元式本身不动。 相当于把「代码」和「执行顺序」解耦。

逆波兰表示

中缀（人写的） 后缀（逆波兰） a + b a b + a + b * c a b c * + ( a + b ) * c a b + c * a = b * c + b * d a b c * b d * + := 优点：不需要括号，优先级天然由顺序表达 用一个栈就能求值：遇操作数压栈，遇运算符弹两个算一个再压回去 用途：早期栈式虚拟机（如 Pascal 的 P-code）、老式计算器、Forth / PostScript
为什么四元式赢过三元式

因为优化需要频繁地增删和重排指令。四元式用显式的临时变量名引用结果，删掉一条指令不影响其他指令的编号；三元式用编号引用，一动就全乱。多花一点空间存名字，换来的可操作性完全值。这也是软件设计里反复出现的取舍：显式命名比隐式位置更抗变更。

控制语句的翻译：回填技术

翻译 if a < b then S1 else S2 时会碰到一个矛盾：生成「条件为假就跳转」这条指令时，还不知道要跳到哪里——因为 S1 还没翻译，长度未知。

解决办法叫回填（backpatching）： 1. 先生成跳转指令，目标地址暂时空着，记下这条指令的编号 2. 继续翻译，等翻译到目标位置了，回头把地址填进去 实现上用两个语义函数： nxq 下一条四元式的编号（一个全局计数器） makelist(i) 建一张只含编号 i 的链表 merge(p1,p2) 把两张链表接起来 backpatch(p, t) 把链表 p 里所有编号对应的四元式的跳转目标填成 t 布尔表达式还要维护真链 TC 和假链 FC： 条件为真时该跳到哪（一坨待填的指令） 条件为假时该跳到哪（另一坨待填的指令）
①
翻译条件 a < b
生成 (j<, a, b, ?) 和 (j, _, _, ?)，两条跳转的目标都暂时是问号，把编号记进真链和假链。
②
翻译 then 分支 S1
翻译前把真链的跳转目标回填成「这里」；翻译完 S1 后生成一条无条件跳转（目标还不知道，待填）。
③
翻译 else 分支 S2
把假链回填成 else 分支的开头；翻译完 S2 后，把第 ② 步那条无条件跳转的目标回填成「S2 之后」。
✓
所有问号都填上了
控制流正确，且只扫了一遍——不需要先翻译一遍算长度再回填。
图 32-2 · 回填：先把坑挖好并记账，等地址确定了再统一填
回填是编译里一个非常通用的技巧。除了控制流，函数调用的返回地址、数组的地址计算、向前引用的符号地址，凡是「生成时还不知道、之后才知道」的信息，都用这套「先占位 + 链表记账 + 后回填」的模式处理。汇编器里的重定位表、链接器里的符号解析，本质上也是同一套思路。

34三种存储分配策略

程序跑起来之前，编译器必须回答一个问题：每个变量放在内存的哪里？三种策略，对应三种不同的生命周期。

静态存储分配
编译时就定死地址整个运行期不变适合：全局变量、常量、静态变量不能递归（因为没有「再来一份」的机制）
栈式存储分配
进入一个过程就在栈上压一块退出就弹掉适合：局部变量、形参、临时变量支持递归
堆式存储分配
运行时按需申请手动或自动回收适合：大小未知、生命周期跨越多次调用的对象需要 GC 或手动释放
图 34-1 · 三种策略的分界，本质是「什么时候能确定地址和生命周期」

静态分配：最简单，也最受限

编译时为每个变量算出一个绝对地址，全程不变。好处是零运行时开销、访问极快；代价是它要求：

要求原因
数组上下界必须是常量否则编译期算不出要留多大
不允许递归调用递归需要同一份变量有多个副本，静态地址只有一个
不允许动态创建数据对象大小在运行前必须已知

FORTRAN 77 及更早的版本就是纯静态分配——这也是为什么那个年代的 FORTRAN 不支持递归。

栈式分配：过程调用的骨架

每次调用一个过程，就在栈上分配一块活动记录（activation record），也叫栈帧（frame）；过程返回时整块回收。递归之所以能工作，就是因为每次调用有自己的一份活动记录。

图 34-2 · 递归调用在运行栈上就是「同一份代码，多份活动记录」

堆式分配：跨越调用边界的活对象

栈的问题是生命周期被绑死在调用上——过程一返回，里面的东西就没了。但很多时候我们需要「这个函数返回了，但它造出来的数据还得活着」。

回收方式怎么做代表代价
手动释放程序员显式调用 free / deleteC / C++（RAII）忘记释放 → 内存泄漏；释放后还用 → 悬垂指针
垃圾回收运行时自动找出「不再被引用」的对象回收Java / Go / C# / PythonGC 停顿、额外内存开销
引用计数每个对象记着有多少人引用它，归零就回收Python / Swift / Objective-C循环引用处理不了，需要额外机制
所有权/借用编译期用类型系统静态证明何时该释放Rust学习曲线陡，但零运行时开销
一句话概括三者的分工

静态区放「程序活着它就活着」的东西（全局变量、字符串常量）；
栈放「跟着调用走」的东西（局部变量、参数）；
堆放「寿命我自己说了算」的东西（动态数据结构）。
你写的每一行代码，编译器都要替它在这三者之间做出选择。

两条链：静态链与动态链

静态链（访问链）
指向定义它的外层过程的最新活动记录用途：访问非局部名字由程序的嵌套结构决定
动态链（控制链）

为什么两者会不一样

假设 P 里嵌套定义了 Q，而 Q 被一个完全无关的 R 调用。那么 Q 的动态链指向 R（谁调用我），而静态链指向 P（谁定义我）。
静态链的长度（要跳几层）在编译时就能算出来：等于嵌套深度之差，记作 nd。运行时只要沿着静态链跳 nd 次，就到了目标变量所在的帧。

display 表：用空间换时间

沿静态链跳 nd 次，嵌套深了就慢。替代方案是维护一张全局数组 display：第 i 项存放「嵌套深度为 i 的那个过程」的当前活动记录地址。

访问嵌套深度为 i 的外层变量： 静态链做法 沿链跳 nd 次，每次一次内存访问 display 做法 直接读 display[i]，一次内存访问 + 一次偏移计算 维护：进入深度为 k 的过程时， 把旧的第 k 项存进新帧（保存）， 再把 display[k] 改成当前帧地址； 退出时恢复。 取舍：display 快，但多一张全局表要维护， 而且在多任务 / 多线程环境里这张表得按线程各存一份。
现代语言为什么不太讲这个了？因为主流语言（C、Java、Go、Python）不支持过程嵌套定义——所有函数都是顶层的，非局部变量只有「全局」和「局部」两级，不需要访问链。C 之所以没有嵌套函数（GCC 有个扩展，但很少用），正是为了省掉这套机制。而 Pascal、Ada、早期的 ML 支持嵌套，就必须实现静态链或 display。

37优化的概念、分类与结构

优化的唯一目标：在保持程序语义完全不变的前提下，让它跑得更快、占得更少。前提永远是「语义不变」，这是优化的红线。

优化的三条原则（原书 8.1.1）

① 等价原则：优化后和优化前，程序在任何输入下的行为必须一致。这是底线，违反它就是 bug。
② 有效原则：优化后确实要更快或更小。有些变换在理论上「更优」，但在现代 CPU 上反而更慢（比如过度展开循环会撑爆指令缓存）。
③ 合算原则：优化本身要花编译时间，还要增加编译器复杂度。如果一个优化只在极少数程序上生效，可能不值得做。

局部
基本块内的优化

38基本块与流图

基本块是一段「只能从第一句进去、从最后一句出来」的顺序代码。它是局部优化的作用范围，也是构造流图的节点。

怎么找基本块的入口

三条规则，满足任一就是入口语句： ① 程序的第一条语句 ② 任何条件转移或无条件转移语句的目标语句 （也就是被跳到的那一句） ③ 紧跟在条件转移语句后面的那一条语句 （因为条件不满足时会顺序落到这里） 基本块 = 从一个入口语句开始， 到下一个入口语句之前（或到转移语句、停语句为止）的所有语句。
图 38-1 · 按三条入口规则，四元式序列被切成四个基本块

流图：把基本块连成有向图

流图（flow graph）的构造： 节点 = 基本块 边 = 块 B1 → B2，当且仅当 ① B1 的最后一句是转移语句，目标是 B2 的第一句；或 ② B2 紧跟在 B1 后面，且 B1 的最后一句不是无条件转移 入口节点：包含程序第一条语句的基本块
回边（回到已访问的块），它标识出一个循环
图 38-2 · 流图中的回边标识循环：{ B2, B3 } 构成一个循环
怎么在流图上找循环

用支配节点（dominator）的概念：如果从入口到 B 的每一条路径都必须经过 D，就说 D 支配 B。
有了它，一条回边 B → D（D 支配 B）确定的循环就是：D 加上所有「不经过 D 就能到达 B」的节点。这个算法叫自然循环（natural loop）。
循环识别之所以重要，是因为程序 90% 的时间花在 10% 的代码上，而那 10% 几乎都是循环。

39基本块内的优化

基本块是顺序执行的，没有跳转，所以「这个变量在这一句之后还会不会被用到」这类问题在块内可以算得很精确。这是最稳的一类优化。

优化种类做什么例子
删除公共子表达式同一个表达式算过一次了，后面再算就直接复用t1 = b*c; t2 = b*c; → t2 = t1;
复写传播x = y 之后，用到 x 的地方直接换成 yx = y; z = x + 1; → z = y + 1;
删除无用赋值赋了值之后从来没被用过（也没有后续出口用到）x = 1; ...; x = 3; → 删掉 x = 1;
常量合并（常量折叠）编译期就把常量表达式算出来x = 2 * 3; → x = 6;
代数化简用等价的、更便宜的运算替换x * 1 → x；x * 0 → 0；x + 0 → x
强度削弱用便宜的运算代替贵的x * 2 → x + x；x / 2 → x * 0.5；x² → x * x

DAG：基本块优化的标准工具

把基本块里的四元式画成一张有向无环图（DAG），公共子表达式会自然合并，无用赋值会自然暴露。

两个变量挂在同一节点上 = 它们值相同

DAG 为什么好用

它把「哪些计算是重复的」这个问题，变成了图上的节点是否相同这个几何问题。构造 DAG 时，遇到 x op y 就先查「有没有一个节点是 op、左右孩子分别是 x 和 y」——有就直接复用（这就是删除公共子表达式），没有才新建。一次遍历，顺手完成多项优化。

一个限制

块内优化看不到块外的情况，所以「删除无用赋值」要保守：如果一个变量在基本块出口处还是活跃的（后面可能会用），就不能删最后一次对它的赋值。判断活跃性需要跨块的数据流分析，属于全局优化的范畴。

40循环优化三件套

循环是优化收益最大的地方。原书讲的三件套是：代码外提、强度削弱、删除归纳变量。

一、代码外提（循环不变运算外提）

如果循环里某个表达式的值每一轮都完全一样，就把它搬到循环外面算一次。 优化前 优化后 for (i = 0; i < n; i++) t = x * y; // 提到外面 a[i] = b[i] + x * y; for (i = 0; i < n; i++) a[i] = b[i] + t; 关键：怎么判断「不变」？ 该表达式的所有操作数，要么在循环外定值， 要么在循环内被定值但定值点唯一且值不随轮次变化。
不能无脑外提的两种情况

① 循环一次都不执行时：把可能出错的运算（如除法、数组访问）外提，会让「本来不会执行」的代码被执行，引入原本不存在的错误。
② 该定值点不唯一：如果变量在循环内有多个赋值点，且来自不同分支，就不能判断它是否不变。
这就是为什么代码外提需要到达定义分析（reaching definitions）作为支撑。

二、强度削弱

把循环里代价高的运算替换成代价低的，前提是两者结果等价。典型场景：把「乘法」变成「加法」。

优化前 优化后 for (i = 0; i < n; i++) t = 0; // 归纳变量 a[i] = b[i] + i * 4; for (i = 0; i < n; i++) { a[i] = b[i] + t; t = t + 4; // 加代替乘 } 原理：i 每轮 +1，那么 i*4 每轮 +4。 与其每轮重新算一遍乘法，不如增量累加。 在多数 CPU 上，加法比乘法快得多。
常见强度削弱
乘法 → 加法（归纳变量）乘法 → 移位（乘 2 的幂）除法 → 乘法（除以常数）取模 → 位与（模 2 的幂）乘方 → 连乘
现代编译器要小心
现代 CPU 上乘法已经很快，而多一个变量可能多占一个寄存器，反而引发寄存器溢出。所以是否做强度削弱，要由目标机的代价模型决定，不能无条件开。
图 40-1 · 强度削弱的适用范围取决于目标机，不是永远划算

三、删除归纳变量

归纳变量：随循环轮次线性变化的变量。 基本归纳变量 i：每轮 i = i ± c 派生归纳变量 j：j = c1 * i + c2（跟着 i 线性变） 优化前 优化后 for (i = 0; i < n; i++) { t = 0; j = i * 4; while (t < 4 * n) { // 用 t 控制循环 a[j] = 0; a[t] = 0; } t = t + 4; } 结果：基本归纳变量 i 不再被使用，整个删掉。 循环控制改用派生归纳变量，少一个变量的维护和一次乘法。
图 40-2 · 三件套的收益层次
还有两类常见的循环优化教材里也常提：循环展开（把循环体复制几份，减少分支判断次数，代价是代码变大）和循环合并（两个循环变量范围相同的循环合成一个，减少一次循环开销）。它们属于「用空间换时间」，是否划算由目标机的缓存和分支预测特性决定。

窥孔优化的视角极其朴素：在已经生成的目标代码上开一个小窗口（几條指令），看看能不能局部地改好一点点。它不需要任何全局分析，性价比极高。

窥孔优化的独特价值

前面几节的优化都在中间代码层面做，看不到目标机的具体指令。而中间代码层面看起来已经最优的东西，翻译成指令后往往会露出破绽——因为翻译是机械的、一对多的。
窥孔优化正好补上这最后一环：它工作在目标代码上，能利用具体机器的指令特性，而且实现简单（就是一张模式匹配表）。投入产出比极高，是任何代码生成器都值得加上的一个 pass。

42错误的种类与各阶段的职责

编译器大部分时间面对的不是正确的程序，而是写错了的程序。出错处理做得好不好，直接决定一门语言的开发体验。

错误种类谁发现典型症状例子
词法错误词法分析出现了语言里不存在的字符序列int 3abc;　@#$　字符串没闭合
语法（句法）错误语法分析单词序列不符合文法括号不匹配、缺分号、if 后面没条件
语义错误语义分析结构合法但没有意义未声明的标识符、类型不匹配、参数个数不对
违反环境限制编译的各个阶段超出实现规定的范围数组维数太大、标识符太长、嵌套层数超限
一个常被忽略的第四类

「违反环境限制」和真正的错误不一样。程序本身完全合法，只是这个编译器实现不支持（比如规定标识符最多 31 个字符、结构体嵌套最多 10 层）。这类问题不会在其他编译器上出现，所以报错信息应该明确说清是实现限制，而不是「你的程序错了」。

出错处理要达成的五个目标

清晰
报告准确
错误信息要让用户一眼看懂：哪一行、哪个位置、什么问题。含糊的 syntax error 是最差的。
准确
位置要对
报错位置要尽可能接近真正出错的地方，而不是「发现不对的地方」。这两者常常差很远。
不雪崩
一次错误只报一次
一个拼写错误不该引发几十条错误。虚假错误（spurious error）是评价编译器好坏的关键指标。
继续
尽量走完
发现错误后要能恢复，继续检查后面的代码，一次编译找出全部问题，而不是改一个编译一次。
不拖累
正常路径零开销
出错处理的代价不能让正确程序的编译变慢。错误处理必须只在出错时才付出成本。

这五个目标之间有张力。最典型的是「继续检查」和「不产生虚假错误」：恢复得越激进，就越容易因为状态错乱而误报。设计一个好的恢复策略，本质上就是在这两者之间找平衡。

43复原与校正：从恐慌模式到最小距离

「复原（recovery）」是让分析能继续下去；「校正（correction）」是猜出用户本来想写什么并改正。后者难得多，也危险得多。

词法错误的复原与校正

策略做法评价
恐慌模式发现非法字符就跳过，一直跳到一个「同步符号」（分号、换行、空白）为止，从那里继续最简单，最常用。跳过的内容不做检查
删除一个字符试着删掉当前字符，看能不能继续识别能处理多打了一个字符的情况
插入一个字符试着插入一个缺失的字符（如闭合引号、分号）能处理少打了字符的情况
替换一个字符把当前字符换成另一个（如 ： 换成 :）能处理打错字符
交换相邻字符试着把相邻两个字符调换能处理手快打反的情况（如 =+ → +=）
最小距离校正：把「猜」变成「算」

上面后四种策略可以统一成一个框架：找一个与错误串「编辑距离」最小的合法单词。编辑距离的定义就是上面四种操作的最少步数——插入、删除、替换、交换各算一步。
碰到 whlie，算出它到 while 的距离是 1（交换 l 和 i），于是提示「是否想写 while」。这正是很多现代编译器/IDE 给出「did you mean...」提示的原理。

语法错误的复原

恐慌
恐慌模式恢复
发现错误后，丢弃输入符号直到遇到某个同步符号集（通常是语句结束符、右花括号这类「重新开始」的标志），然后从那里继续分析。
优点：简单、绝不无限循环。缺点：会跳过一段代码不做检查。
短语级
短语级恢复
在出错位置做局部修补：插入一个缺失的分号、删掉一个多余的逗号、替换一个错词。修补完接着分析，不跳过任何输入。
优点：检查覆盖完整。缺点：修补动作的设计非常依赖对语言的了解。
产生式
出错产生式
在文法里预先加入一些「错误产生式」，比如 stmt → error ;。分析器遇到错误就走这条产生式，把错误当成一个合法成分处理。
优点：机制优雅，可以直接复用分析器的归约动作。缺点：文法被污染。
全局
全局校正
理论上最优的做法：找出「与错误输入串编辑距离最小的那个合法串」。
理论上完美，实际上代价太高，几乎不用。只在个别工具（如某些代码格式化器）里有限使用。

同步符号集怎么选？一个好的经验是：把这个语言里「能开始一个新结构」的符号都放进去——语句开头的关键字（if、while、int）、分号、右花括号。这样恢复后重新分析时，最可能落在一个真正的语句边界上，从而避免雪崩式误报。

语义错误

语义错误的处理思路和前两类不同：绝大多数语义错误无法自动校正，只能报告。因为「把 int 赋给 string」到底是你写错了类型、还是你想做转换，编译器无从判断。

语义错误能否校正常见做法
标识符未声明部分可以用最小距离法提示「是否想写 xxx」；也可以提示「是否忘了 include」
标识符重复声明不能报「重复定义」，指出第一次定义的位置
类型不匹配一般不能报「无法从 A 转换到 B」，有些语言会提示「是否需要显式转换」
实参形参不匹配不能报「期望 n 个参数，得到 m 个」，列出期望的类型
控制流错误不能break 不在循环内、函数缺 return
好的错误信息长什么样

对比一下：
差的：error: syntax error at line 42
好的：42:7: 缺少分号　int x = 5　加一个指向第 7 列的小箭头。
再进一步（Rust 的做法）：指出错误、标出位置、给出建议、附上理由。错误信息是编译器最容易被低估的部分——它是每时每刻都在用的用户界面。

46常见误区与反直觉点

这些是学编译原理时几乎人人都会踩的坑，也是考试和面试最爱问的地方。

误区正确说法
「编译型语言」和「解释型语言」是语言属性是实现属性。同一个语言可以有编译器也可以有解释器。C 有解释器，Python 也有编译器
ε 就是空格ε 是空串，长度为 0；空格是一个实实在在的符号，长度为 1
句子和句型是一回事句子是不含非终结符的句型。句子 ⊂ 句型
一个文法只能对应一种推导一棵树可以对应多种推导顺序。所以要规定最左 / 最右，让分析过程确定
二义文法可以靠工具检测出来已被证明不可判定。没有任何算法能判断任意 CFG 是否二义
NFA 比 DFA 识别能力更强完全等价。NFA 只是写起来方便，子集法总能转成 DFA（状态数可能涨）
正则表达式能匹配括号嵌套不能。嵌套需要计数，有穷状态机没有计数器。工程里的「正则」加了扩展已不是正则语言
LL 和 LR 能力差不多LR 严格强于 LL。因为自底向上在决策前已经看到了句柄全部，自顶向下还没看到后面
消左递归不改变语义语言不变，但语法树结构变了（左结合变右结合）。必须在语义动作里把结合性纠正回来
算符优先归约的是句柄归约的是最左素短语，非终结符名字不可靠，可能放过文法和语言之外的串
LALR(1) 是 LR(1) 的简化，所以能力更弱但不会更糟合并同心集可能引入新的归约-归约冲突，这种冲突是 LR(1) 里原本没有的
声明语句会生成代码不生成。只填符号表。这是「可执行语句」和「说明性语句」的根本区别
优化后代码一定变快不一定。过度展开循环会撑爆指令缓存；强度削弱多占寄存器反而可能引发溢出
递归需要特殊支持，所以 C 天生支持递归递归靠栈式存储分配。纯静态分配的语言（如 FORTRAN 77）不支持递归
语法正确等于程序合法不等于。「变量必须先声明后使用」这类上下文有关约束，交给语义分析而不是语法分析
一个贯穿全书的方法论

凡是「上下文有关」的东西，都被从语法分析里赶了出去，交给语义分析用符号表处理。这是编译工程史上最重要的一个分工决策：它让语法分析能停在 2 型文法（高效、可自动构造），把难题集中到语义分析里用表驱动的方式解决。理解了这一点，整本书的章节安排就顺了。

47从零到跑通：九步上机清单

这本书配了《编译程序构造实践》，每章都有上机实习题。如果想自己做一个能跑的小编译器，按这个顺序走最省力。

01
先定义语言，只定义一小块
不要一上来就想支持完整的 C。一个够用的最小集：整数类型、变量声明、赋值、四则运算、if、while、函数。把它写成 BNF，并明确优先级和结合性。
02
写词法分析器
可以先手写状态转换图（第 12 节），跑通了再改用自动构造。输出属性字序列，先打印出来看对不对——这一步的输出要能肉眼验证。
03
建符号表
哈希表 + 分层。先只存名字、类型、offset。词法分析阶段就开始往里填标识符。
04
写语法分析器：递归下降优先
用递归下降（第 21 节）而不是 LR。理由：好写、好调试、好插语义动作。等全跑通了再考虑换 LR。
05
构造 AST 并打印它
先不做翻译，只把树建出来，用缩进打印检查结构是否正确。这是最有价值的一次中间验证。
06
加语义分析：类型检查
遍历 AST，查声明、查类型、算 offset。此时应该能报出「未声明」「类型不匹配」。
07
生成四元式
按第 32 节的规则翻译。控制语句用回填（第 32 节）。输出四元式序列，人工核对自己算的结果。
08
写虚拟机解释器
按第 33 节造一个十几条指令的虚拟机，把四元式翻成指令并执行。能跑出正确结果，这一关就算过了。
09
最后才加优化
先做基本块划分（第 38 节）和块内优化（第 39 节），再考虑循环优化（第 40 节）。优化永远最后做，而且每次做完都要跑同一组测试对比结果。

一条经验

每一步都要有可肉眼验证的输出。属性字序列、AST 缩进打印、四元式序列、虚拟机指令流——这四样东西打印出来，任何 bug 都能定位到具体是哪一步出的。反过来，如果四个阶段一口气写完再测，出问题时会完全无从下手。

48思考题

这些问题没有标准答案，但想清楚它们，比背下所有定义更有用。

#问题提示方向
1为什么词法分析用 3 型文法就够，而语法分析必须用 2 型？想想单词和句子分别有没有「嵌套/配对」结构
2如果一门语言允许「变量未声明就使用」，它的编译器实现会多出哪些麻烦？想想第一次遇到这个名字时，你不知道它的类型
3为什么 C 语言要求「先声明后使用」？是为了方便程序员，还是为了方便编译器？联系「一遍扫描能不能完成编译」
4LL(1) 文法能不能描述 C 语言的全部语法？如果不能，差在哪里？想想类型声明和表达式的歧义，typedef 带来的问题
5为什么算符优先分析快，却几乎没人用它做整个语言的语法分析？见第 25 节：它可能放过文法不生成的串
6消左递归把左结合改成了右结合，具体应该在语义动作里怎么补回来？对比改写前后两棵 AST 的形状
7如果让你给一门新语言做编译器，你会先做前端还是先做后端？为什么？想想「编译到 C」这条捷径，以及 LLVM 的思路
8为什么现代 CPU 上，强度削弱未必总是划算？多一个变量意味着多占一个寄存器
9垃圾回收解决了什么问题，又引入了什么问题？Rust 的所有权是从哪个角度绕开它的？把「何时释放」从运行时判定，变成编译期证明
10如果让你设计报错信息，你会给「未声明标识符」这条错误加哪些内容？想想 Rust 的四段式：错误、位置、建议、理由
最后一句

编译原理这门课真正留给你的，不是那几十个算法，而是一种看程序的方式：任何一段代码，在你眼里都应该能自动展开成一棵树、一串属性字、一段中间表示。有了这个视角，写解析器、做 DSL、读编译器报错、评估语言特性，都会变得容易得多。
