00一道题：两台手机，同一场战斗

两个人各自拿着一台手机，在同一局对战里厮杀。网络往返 60ms，设备一台是骁龙旗舰，一台是三年前的千元机。十分钟后，两边画面里的血量、冷却、胜负判断，完全一致。这一致性是怎么来的？

最直觉的答案是：服务器算好了，把结果发下来。这就是状态同步。它很好用，但有两个代价：服务器要扛全部运算；带宽要传全部物体状态。

帧同步给了另一条路，而且是把思路反过来的：服务器什么都不算，只转发指令；每个客户端自己算，而且必须算出完全一样的结果。

前提假设
「相同的初始状态 ＋ 相同的输入序列 ＋ 相同的逻辑代码」 ⇒ 必然得到相同的结果
↓ 只要守住这一条
那么网络上根本不需要传「谁在哪里、还剩多少血」
只需要传「A 在第 120 帧按下攻击、B 在第 121 帧往左走」
图 0 · 帧同步的全部信仰，就压在这一条假设上。后面所有工程手段，都是在拼命维持它

这一个换位换来了三个巨大的好处，也埋下了三个致命的坑。整个教程就是围绕这张对照表展开的。

换来代价

只传按键，单帧几十字节。屏幕上有 200 个单位还是 20 个，带宽几乎一样。		 必须绝对确定性
任意两台机器上，任何一次浮点误差、任意一次遍历顺序不同，都会让两边世界分叉。

状态同步传「结果」，帧同步传「原因」。传原因省带宽、省算力，但要付出一个远比结果更苛刻的要求：两台完全不同的机器，必须每一步都算得一模一样。这就是整篇文章的主线。

01三种同步模型，一张图分清

谈同步必须先把三个模型并列摆好，否则后面所有讨论都是混的。它们不是「新与旧」的关系，而是分别解决不同的问题。

模型一：帧同步（确定性锁步 / Deterministic Lockstep）

所有客户端并行跑同一份模拟。每一帧，每个客户端把自己的输入广播给所有人；谁的输入没到齐，谁就卡住等 —— 所有人一起停。因为大家跑的是同一份代码、同一组输入，结果自然一致。

它要的是「绝对的公平」：要卡一起卡，要快一起快。这是局域网时代的天然选择，也是 Doom、星际争霸、帝国时代的做法。

模型二：状态同步 / 快照插值（Snapshot Interpolation）

服务器跑唯一权威的模拟。它每几十毫秒给客户端发一份世界快照（谁在哪、多少血），客户端在两张快照之间插值，画出平滑画面。客户端的操作上行给服务器，本地靠预测先动起来。

它要的是「体验的连续性」：客户端渲染的其实是过去的、被抹平的世界。网络抖动被插值缓冲吃掉了，代价是你看到的是一百毫秒前的世界。

模型三：预测回滚（Rollback Netcode）

它是帧同步的激进改良：不等了。远端输入还没到，就按「他应该还会继续按着方向键」来猜，先往下算。等真实输入到了，如果猜错了，就把世界回滚到分歧那一帧，用真输入重新算一遍，再快进到当前帧。

它要的是「零感延迟」：GGPO 能把一百毫秒左右的延迟藏到几乎察觉不到。代价是模拟一帧可能要跑好几遍，CPU 开销与实现复杂度都上一个台阶。

别硬上帧同步的三种情况

03逻辑帧：这个世界唯一的时钟

帧同步的第一个决定，是把「时间」从真实世界里抢出来。游戏世界不再按真实时间前进，而是按逻辑帧前进。渲染帧率可以是 30／60／120，逻辑帧率必须死板得像心跳。

为什么不能用真实时间

如果用引擎的帧间隔（deltaTime）驱动逻辑，两台机器上每帧的 dt 都不一样：一台是 16.7ms，另一台因为卡顿是 33ms。哪怕物理公式完全相同，position += velocity * dt 的累加路径也完全不同，几十帧后位置就分叉了。

所以帧同步的第一条规矩：逻辑层只认帧号，不认时间。任何一次位移、冷却、动画推进，都用「第 N 帧到第 N+1 帧」来表达，而不是「过去了 16.7 毫秒」。

dt // 逻辑层里永远是一个常量 dt = 1 / LOGIC_FPS // 例如 LOGIC_FPS = 30 → dt 固定为 1/30 秒 // 任何时候都写成： pos += vel * DT_FIXED // 确定性写法 pos += vel * deltaTime // 帧同步里的自杀写法

逻辑帧率该选多少

帧率越低，带宽越省、算力越省，但操作响应越迟钝；帧率越高，响应越好，但服务器广播压力越大。行业里常见的落点是 10 ～ 30Hz。

渲染帧 ≠ 逻辑帧

这是初学者最容易混的一处。假设逻辑帧 15Hz（每 66ms 一步），而渲染跑 60fps（每 16.6ms 一帧）。那么平均每渲染 4 次，逻辑才走一步。如果直接拿逻辑状态去画，画面就是「跳一次、停三下」，非常卡。

解法是表现层插值：逻辑层每步给出目标状态，表现层在两步之间用浮点数平滑地把物体挪过去。逻辑是台阶，渲染是斜坡。

逻辑帧 15Hz · 每 66ms 走一步
只算「到哪儿了」：frame 100 → 101 → 102 …… 状态是离散的
↓ 插值
渲染帧 60fps · 每 16.6ms 画一次
在 frame 100 与 101 之间取 t = 0.25 / 0.5 / 0.75，用浮点算出中间位置 → 看起来是连续移动
↓
关键约束
插值只允许改变「看起来在哪」，绝不能改变「逻辑上在哪」。渲染层的漂亮特效，一行都不能回流进逻辑层。
图 3 · 逻辑给台阶，渲染铺斜坡。两者一旦互相污染，帧同步就完了
一个反直觉的推论

因为逻辑帧率固定，所以「技能冷却 0.5 秒」在帧同步里应该写成「冷却 15 帧」（15Hz 下）。所有数值配置表都应该用帧数表达。这不只是为了确定性，也让策划与程序说的是同一种语言：讨论平衡时讲「快 3 帧」，比讲「快 0.2 秒」精确得多。

04指令：只传「按了哪个键」

既然世界由每个客户端自己算，那么网络上唯一需要走的东西，就是「这一帧，每个玩家按了什么」。这就是指令（Command / Input）。整条帧同步链路的带宽成本全在这里。

指令长什么样

一个玩家的操作，本质上是有限的几个键的状态。用位掩码（bitmask）打包，8 个玩家一帧的全部操作，可以塞进几个 32 位整数里。

// 用 1 个 int 描述一名玩家这一帧的全部按键
public struct FrameInput
{
    public uint Buttons;   // 低 16 位放按键
    public sbyte MoveX;    // 摇杆：-127 ~ 127，或量化成 8 个方位
    public sbyte MoveY;
}

// 按键定义：每一路占一个 bit
public static class Btn
{
    public const uint Up     = 1 << 0;
    public const uint Down   = 1 << 1;
    public const uint Left   = 1 << 2;
    public const uint Right  = 1 << 3;
    public const uint Attack = 1 << 4;
    public const uint Skill1 = 1 << 5;
}

// 一帧的完整数据：帧号 + 每个玩家的操作
public struct FrameCommand
{
    public int  Frame;              // 逻辑帧号，全局自增
    public uint[] PlayerButtons;    // 长度 = 房间人数，10 人 = 40 字节
}

算一下带宽：10 人房间，每人每帧 1 个 32 位按键 ＋ 帧号，30Hz 下每秒广播 30 次 ——下行不到 2KB/s。同样场景如果走状态同步，每个单位每帧同步位置／朝向／血量／状态机，轻松上到几十 KB/s。

指令有三种来源，必须分清

① 本地玩家指令
从设备读到的真实操作。上行给服务器。这一路有自己的时间戳，需要对齐到帧。
↓
② 远端玩家指令
从服务器下发。可能迟到、可能丢包、可能乱序 —— 网络层要负责补齐与去重。
↓
③ 系统指令
不是人按的，但同样改变世界：掉线托管（AI 接管）、超时默认空指令、开局随机种子。它们也必须是被所有客户端一致接受的输入。
图 4 · 三类指令在逻辑层里是同一种东西：某个帧号上的一个操作。逻辑层不关心它从哪来
「玩家没操作」也要发指令

一个常见 bug：只有玩家按键时才发包，导致远端玩家不知道「对面这一帧什么都没按」，状态机一直沿用上一帧。正确做法是每帧都要有值，没操作就是全 0 的空指令。服务器在没人操作时也必须按节奏持续广播，哪怕内容完全一样 —— 因为帧号本身在推进，它就是这个世界的节拍器。

05经典锁步：最朴素也最刚硬的做法

最早的帧同步实现简单粗暴：这一帧所有玩家的输入没到齐，谁都不许往下走。Doom、早期的局域网 RTS 都是这个形态。理解它的缺陷，才能理解后面所有改良的动机。

流程拆解

每个客户端都有一个内部时钟，按固定间隔（比如 100ms，即 10Hz）触发一次「回合」。回合开始时：

  1. 把本地这一回合的操作打包，发给其他所有人（对等网络里直接发，C/S 下发给服务器）。
  2. 同时把操作写进本地缓冲。
  3. 等到所有人的这一回合指令都到齐，把大家（包括自己）的指令一起交给逻辑层，推进到下一回合。
  4. 如果本地时钟已经到点，但别人的指令还没来 —— 停住，等。画面卡住，进度不动。

注意第 4 条：这是关键。所有人的帧号永远一致，代价是所有人的速度被最慢的那个人拉平。

它的优点，其实不少

  • 绝对公平：所有人的时间线严格对齐，没有谁快谁慢；
  • 实现极简：只有一条「等齐再走」的规则，不需要预测、不需要插值、不需要回滚；
  • 天然可回放：每个回合的指令都有留痕，按序重演就是整场比赛；
  • 带宽极低：还是只传指令。

它的致命伤

致命伤只有一个，但足以杀死产品：网络体验的短板效应。四个人里只要有一个人在地铁里，另外三个人就要陪着一起卡。更糟的是，这种卡不是「画面卡一下」，而是「整个世界停止推进」—— 因为帧号不动，连本地输入都会被吞掉。

为什么今天几乎不用纯经典锁步

因为玩家的耐心只有几百毫秒。经典锁步可以理解为「把网络质量最差的那个人的体验，强加给所有人」。它只在两种环境里成立：局域网（延迟稳定在几十毫秒内），或者玩家愿意接受整局卡顿的回合制序列同步。公网产品必须改良。

06乐观帧锁定与时间桶：不让慢的人拖住全场

改良的方向非常明确：把「等人」改成「定时」。服务器不再等谁，而是像广播电台一样，每 66ms（15Hz）固定播出一帧，收到谁的指令就算谁的，没收到就留空。慢的人自己掉队，快的人不受影响。

每隔 Interval（例如 66ms）: frame++ // 帧号无条件自增 把当前已收集到的所有玩家指令打包 广播给所有客户端 // 没收到的人 → 该帧补「空指令」

配套的一个安全补丁：预提交哈希

乐观帧锁定放宽了同步约束，也开出了一个很狡猾的作弊口子 —— 偷看（Lookahead Cheat）：如果我把操作故意晚发一帧，就能先看到对手这一帧做了什么，再决定自己做什么。这在实时性要求高的对战里就是降维打击。

对抗手段是「先押注、再开牌」：

第 K 帧： 1. 本地生成指令 → 立刻算哈希 H(指令) → 广播哈希 // 先押注，不泄露内容 2. 等收到所有人的哈希 3. 再广播明文指令 4. 收到所有人明文 → 各自算哈希，与第 1 步收到的对比 不一致 → 判定该客户端作弊

代价是带宽翻倍（哈希 ＋ 明文两轮）与延迟增加（要等两轮）。所以实际项目里通常是抽样使用：只在关键帧启用，或者干脆不在客户端做，交给服务器事后验算录像。

术语小抄

「锁步同步 / 严格帧锁定 / 确定性锁步」指的是要等齐的那一种；「乐观帧锁定 / 定时不等待 / 时间桶 / Bucket Synchronization」指的是不等的那一种。中文社区常把两者都叫「帧同步」，讨论问题时最好先对齐说的是哪一个。

07确定性的四条腿

架构聊完，进入帧同步真正的深水区。只要你写了帧同步，确定性就是你每天都要还的债。它不是某个函数写对了就行，而是四条腿同时立住 —— 缺一条，两边世界就会分叉。

「分叉」（Desync）到底有多严重

分叉不是「画面有点不同」，而是世界模型的彻底分裂：A 客户端认为自己的技能命中了、已经回血；B 客户端认为那次没打中。从这一帧起，两边的后续一切都不同 —— 伤害、走位、AI、胜负。而且没有自动收敛的可能，因为双方都「按规则算得没错」。

一个真实的教训

曾有人排查很久的一次分叉，最后定位到：某个逻辑模块在遍历一个列表时会条件性地执行一次排序，而排序的比较器里用到了浮点数。两台设备的浮点舍入不同，排序结果就不同，后面所有依赖顺序的逻辑全变了。这类 bug 的特点是：复现率极低、越查越像玄学。

所以帧同步团队必须建立一种肌肉记忆：写逻辑层的每一行代码，都要先问一句「这行在两个平台上会算出一样的东西吗？」 下面是具体的雷区。

08头号敌人：浮点数，与定点数解法

确定性四大雷里，浮点数排第一，因为它看起来人畜无害。你在两台机器上写 0.1f + 0.2f，直觉上必然相等，实际上在很多链路里不保证逐位相同。

浮点为什么不保险

  • 编译器会做优化：把 a*b+c 融合成一条 FMA 指令，中间结果的舍入位置就变了；不同平台编出的指令不同。
  • 数学库不是同一份实现：各平台的 sin／cos／sqrt 精度与算法不同，同一个输入可能返回最后一位不同的结果。
  • 舍入模式与扩展精度：x86 的 80 位扩展寄存器、不同 ARM 版本的指令集，都会影响中间值的保留位数。
  • 浮点加法不满足结合律：(a+b)+c 与 a+(b+c) 可能不等。累加顺序一变，结果就变。

注意：这些问题在「同一台设备、同一份构建」里通常不会暴露。所以最常见的现象是 —— 开发期一切正常，一上真机、一混平台（iOS ＋ Android）就开始偶发分叉。

解法：定点数（Fixed-Point）

核心思路一句话：用整数表示小数。约定一个缩放因子，把「真实值 × 2^n」存成整数，所有运算都在整数域里做。整数加减乘在全世界所有 CPU 上都是逐位精确的。

图 8 · 定点数的两难：小数位多则精度高但范围小、乘法易溢出；小数位少则反之。Q48.16 是 3D 场景的常见折中

整数部分存的是「真实值 × 2^16」。比如 1.5 存成 1.5 × 65536 = 98304。加减直接算，乘法要先把中间结果扩大、再右移回来。

// 一个够用的 64 位定点数实现（Q48.16）
public struct Fix64
{
    public const int  FRAC = 16;
    public const long ONE  = 1L << FRAC;        // 表示 1.0
    public long Raw;                              // 真实值乘 65536

    public static Fix64 operator +(Fix64 a, Fix64 b) => FromRaw(a.Raw + b.Raw);
    public static Fix64 operator -(Fix64 a, Fix64 b) => FromRaw(a.Raw - b.Raw);

    // 乘法：用宽中间类型防溢出，再右移 FRAC 位
    public static Fix64 operator *(Fix64 a, Fix64 b)
    {
        Int128 t = (Int128)a.Raw * b.Raw;
        return FromRaw((long)(t >> FRAC));   // 舍入策略必须全局统一
    }

    public static Fix64 operator /(Fix64 a, Fix64 b)
        => FromRaw((long)(((Int128)a.Raw << FRAC) / b.Raw));

    public static Fix64 FromRaw(long v) => new Fix64 { Raw = v };

    // 只在渲染前转换，逻辑层绝不调用
    public float ToFloat() => Raw / (float)ONE;
}
两条铁律

一、绝不在逻辑层里从浮点转定点。形如 FromFloat(1.1f) 的转换本身就是不确定的 —— 编译器可能把它算成 1.0999999 或 1.1000001，转出来的整数值就不一样。定点数只能来自整数常量、字符串解析（注意固定区域设置），或者由前面步骤的定点运算得出。Photon Quantum 干脆把这类函数命名成 FromFloat_UNSAFE，就是在提醒这件事。

二、舍入策略必须统一。右移是「截断」还是「四舍五入」，正负数怎么处理，全项目只能用同一套。中途换一次策略，等于制造一次全量分叉。

三角函数、开方：查表 ＋ 迭代

定点数本身不解决 sin／sqrt／atan2。这些在逻辑层里必须自己实现：

  • sin / cos：预计算一张查找表（比如 1024 或 4096 项），用线性插值取中间值。表是常量，所有客户端一致；插值也全在定点域内完成。
  • sqrt：整数牛顿迭代，固定迭代次数（比如 4 次或 8 次）。次数固定很重要 —— 如果按「误差小于阈值就停」，两端停在不同次数上就会算出不同结果。
  • atan2：同样用查表 ＋ 定点插值，或多项式逼近但系数与运算顺序完全固定。
  • 向量归一化：v / sqrt(v·v)，全部走定点版本，别图省事调引擎的数学库。
性能上其实是划算的

定点数四则运算确实比原生浮点慢（每次乘法多了移位与宽整数运算），但查表版三角函数往往比系统 sin 更快，因为省掉了函数调用与内部的多项式展开。在每秒几十次逻辑帧、每帧几万个运算的游戏里，这个差距通常完全吃得下 —— 真正的成本是「改写代码」这件事，而不是运行时的 CPU。

09另外五个雷：随机、容器、时间、物理、第三方库

把浮点换成定点，只堵住了一个洞。下面这五处，每一处都能独立制造分叉，而且症状往往比浮点更难查。

雷一：随机数

引擎的全局随机数是天生的不确定性来源：它内部有状态，调用次数不同、顺序不同，取到的值就不同。解法是自建随机器，并且把它当成世界状态的一部分：

// 确定性随机器：状态属于「世界状态」，可存档、可回滚
public struct DeterministicRandom
{
    private ulong _state;

    public DeterministicRandom(ulong seed)
        => _state = seed == 0 ? 88172645463325252UL : seed;

    // xorshift64*：纯整数运算，跨平台逐位一致
    public ulong NextULong()
    {
        _state ^= _state >> 12;
        _state ^= _state << 25;
        _state ^= _state >> 27;
        return _state * 2685821657736338717UL;
    }

    // 取模用无符号整数，避免负数取模的符号差异
    public int Range(int minInc, int maxExc)
        => minInc + (int)(NextULong() % (ulong)(maxExc - minInc));
}

还有三条配套规矩：① 每局开局由服务器下发同一个种子；② 按用途分开多个随机器实例（战斗随机、表现随机、掉落随机）—— 表现随机不该消耗逻辑随机的状态，否则「多播了一次粒子」就会改变后面的暴击判定；③ 它必须能被存档与回滚，否则回滚重算时随机序列接不上。

雷二：容器与遍历顺序

用哈希字典／哈希集合存游戏对象，是帧同步里最隐蔽的坑之一。哈希容器的遍历顺序依赖内部哈希分布与插入历史，两端可能不同。

  • 逻辑层只用数组／有序列表，或者用「对象 ID 作键 ＋ 每帧按 ID 排序后遍历」。
  • 对象增删改必须走缓冲队列：本帧只记录意图，统一在下一帧初按 ID 排序后批量处理，避免「遍历中改容器」。
  • 排序要用稳定排序 ＋ 确定性比较器（比较器里只能有整数）。注意大部分语言的默认排序是不稳定排序，等价元素的前后关系不保证，这一点尤其要留心。

雷三：时间与时序

  • 逻辑层禁止访问系统时间（DateTime.Now、真实运行时长、帧计数器以外的任何时间源）。
  • 禁止协程／异步回调参与逻辑推进 —— 它们的执行时机与帧的对应关系不可控。
  • 禁止「物理帧」与「逻辑帧」各自独立计时（例如引擎的 FixedUpdate 与自定义逻辑帧并行跑）。
  • 所有「每隔 N 秒」的逻辑，改写成「每隔 N 帧」。

雷四：物理

这是帧同步项目最容易翻车的地方。Unity 的 2D／3D 物理系统、以及绝大多数商用物理库，都不保证跨平台逐位一致：它们内部用浮点、用可能并行的宽相检测与迭代求解。

结论很硬：帧同步项目通常要自己写移动与碰撞。而好消息是，大多数竞技游戏需要的那点物理并不复杂：

你想要的确定性做法
角色移动用定点数做运动学积分，每帧固定步长；不要用刚体
碰撞检测自己写 AABB／圆／胶囊等基础形状检测，全整数或定点运算
阻挡与推挤固定迭代次数的位置修正（如 4 次），不允许「收敛即停」
寻路A* 用整数代价；取最小节点要按 (代价, 节点 ID) 双键比较，避免同代价时随机取
浮空、抛物线定点重力 ＋ 定点速度积分；不要用引擎的施力接口

雷五：第三方库与「顺手」的引擎 API

物理引擎只是最显眼的一个。凡是逻辑层里调用的东西，都在责任范围内：

  • 数学库：引擎的向量、四元数、数学常量都是浮点实现，逻辑层不能用。
  • 动画系统：动画驱动的位移（Root Motion）、动画事件回调如果不确定性，就必须挪到表现层；逻辑层只接受「技能进入第 K 帧」这类整数状态。
  • 序列化／反射：反射遍历成员的顺序不保证稳定，逻辑层应显式手写序列化。
  • 对象池与分配顺序：池化本身没问题，但如果「谁先被分配」影响了逻辑，就出事了。
  • 异常：被悄悄吞掉的异常会让一段逻辑「在一端跑了、在另一端没跑」。逻辑层里任何异常都应当被当成致命错误暴露出来。
一个判断标准

问自己：「这段代码在两个不同平台、不同编译器、不同帧率下跑，会不会给出最后一位不同的结果？」 只要答案不确定，它就不该出现在逻辑层。判断力比清单更重要 —— 清单永远列不全。

10确定性自查清单

把上面的雷区压成一张可以贴墙上的清单。开新模块前过一遍，能省掉后面几周的玄学排查。

数值

  • 逻辑层无 float／double；全部使用定点数类型。
  • 没有任何浮点转定点的操作进入逻辑层。
  • 除法的舍入策略、右移的舍入策略全项目统一，并有单元测试覆盖负数情况。
  • 定点乘法使用宽中间类型，并明确溢出边界与饱和策略。
  • 三角函数、开方、atan2 全部是自实现的查表／迭代版本，迭代次数固定。

数据与顺序

  • 逻辑层的随机数来自固定种子的确定性随机器，且随机器状态可存档、可回滚。
  • 遍历顺序固定；容器增删走缓冲队列，遍历过程不修改容器。
  • 排序使用稳定排序 ＋ 只含整数的比较器（多键要比较到「唯一 ID」为止）。
  • 同一帧内的更新顺序被显式定义（先系统 A 再系统 B 再对象 C），并写进文档。
  • 所有逻辑实体有确定性的唯一 ID 生成器（不能用内存地址或随机 GUID）。

时间与环境

  • 逻辑推进只依赖帧号；帧间隔是常量。
  • 逻辑层没有任何系统时间、协程、异步调用。
  • 没有使用引擎物理系统做逻辑判定。
  • 逻辑层不读取任何设备信息（分辨率、语言、机型、时区）。

机制

  • 每 N 帧计算一次世界状态校验和（CRC32／xxHash）并与服务器比对。
  • 有「逻辑帧调试器」：能暂停、单步、查看每帧输入与该帧状态。
  • 有网络模拟开关：可注入固定延迟、抖动与丢包率。
  • 有本地回放工具：能把一局的指令流重演出来，用于复现分叉。
最后一条最重要

清单的价值不在「写代码时看」，而在新人入职时看。确定性是被整个团队共同维护的：任何一个人随手写的一行浮点，都可能毁掉几个月的调试成果。把这份清单做成代码审查里的固定检查项，比事后排查便宜一百倍。

11分层：逻辑层与表现层必须离婚

确定性解决「算得一样」，架构要解决的是「算得干净」。帧同步项目的架构可以浓缩成一句话：逻辑层是一台没有画面的机器，表现层是一个只读的观众。

一条清晰的分界线

为什么必须这么绝

因为一旦表现层能改状态，确定性就失守了。举三个真实会发生的场景：

  • 表现层为了「打击感」在命中时加了一点位移 —— 这在逻辑上改变了距离，后续判定全变。
  • 动画系统在播放结束时触发一个事件改血条 —— 事件触发时机依赖渲染帧率，两端不同。
  • 为了省事，UI 直接读逻辑对象并顺手四舍五入写回 —— 浮点污染了整个数值链。

工程上的三个实操建议

  1. 逻辑层独立成程序集／独立目录，不引用引擎命名空间。Unity 项目里可以用单独的 asmdef，让编译器帮你拦住「不小心用了引擎数学库」。
  2. 逻辑层提供「单机模式」入口。不联机、不联网、直接喂指令就能跑。做得到，说明分层是干净的；做不到，说明逻辑层还粘着表现层。
  3. 服务器能跑同一份逻辑层代码。这是帧同步最划算的一笔投资：服务器能跑逻辑，就能验算录像、就能做权威校验、就能在服务端复现线上 bug。同一份代码，三处复用。
反过来看：这层分离也是帧同步最值钱的部分

很多团队当初为了联机才做分层，最后发现真正的收益在别处：战斗回放、观战、断线重连、AI 训练、自动化战斗回归测试 —— 逻辑层一旦干净，这些都变成「顺手做掉」的小功能。

12主循环：帧率控制、追帧与抖动缓冲

逻辑帧率固定，但真实设备每秒的渲染次数会上下浮动，网络包的到达时间更是忽快忽慢。主循环的任务就是在这两者之间做一道缓冲坝：把不规律的输入，变成规律的输出。

主循环的骨架

// 帧同步主循环（简化版）
void Update()
{
    // 1) 采样本地输入，量化到「待执行帧号」
    CollectLocalInput();

    // 2) 累加真实时间，换算成「应该已经跑了几帧」
    _accumulator += Time.unscaledDeltaTime;

    int steps = 0;

    // 3) 攒够一帧、且该帧输入已就位，就推进一帧
    while (_accumulator >= DT && steps < MAX_STEPS_PER_FRAME)
    {
        int frame = _currentFrame + 1;

        if (!_inputBuffer.Has(frame))          // 输入还没到
        {
            if (IsHanging(frame)) break;        // 还在容忍窗口内 → 等一等
            _inputBuffer.FillMissing(frame);      // 超时 → 用空指令补齐，继续跑
        }

        _simulation.Step(frame, _inputBuffer.Get(frame));  // 纯确定性逻辑
        _currentFrame = frame;
        _accumulator -= DT;
        steps++;
    }

    // 4) 表现层：用两次逻辑状态插值，画连续画面
    _presentation.Render(_currentFrame, _accumulator / DT);
}

这段代码里有三个关键点，值得单独说。

关键点一：单帧最多跑几步

如果设备卡了 500ms，累加器会攒下十几帧的量。若不限制，一次 Update 里要跑十几帧逻辑，只会更卡，形成雪崩。所以要设上限（常见 5～10 帧），剩下的留给后面的帧慢慢消化。这也自然形成了「追赶」。

关键点二：追帧（Catch-up）

断线重连、长时间卡顿之后，客户端落后了几百帧。系统的处理方式像「快放录像」：加速跑逻辑帧，但不渲染。

正常节奏: 每秒 15 帧 ← 每 66ms 一帧，配合渲染插值 追帧模式: 每秒 150 帧 ← 一帧里连续跑很多步，跳过全部表现层开销

追帧期间必须屏蔽所有表现层的副作用：不播音效、不放特效、不弹 UI、不触发需要玩家交互的剧情。要是一边快放三百帧一边播技能音效，玩家会以为手机坏了。这就要求前面那条「逻辑与表现分离」做得足够彻底 —— 能不能干净地追帧，是分层的验收标准。

关键点三：抖动缓冲（Jitter Buffer）

网络包的到达时间是不均匀的。如果来一帧跑一帧，逻辑推进就会忽快忽慢，画面一顿一顿。解法是在客户端留一个滞后缓冲：

  • 不要「收到第 N 帧就跑第 N 帧」，而是始终落后网络最新帧 2～4 帧再执行。
  • 这样即使某一帧晚到 100ms，也不会打断当前的执行节奏。
  • 缓冲深度可以自适应：网络抖动大就加深，网络稳就减浅，减少延迟。
网络到达: ─N───N+1──────N+2─N+3────────N+4──→ （忽快忽慢） ↓ 放进缓冲 缓冲区: [N][N+1][N+2][N+3][N+4] ... （排队，抹平抖动） ↓ 按本地稳定节奏取 本地执行: ─N─────N+1─────N+2─────N+3─────N+4──→ （每 66ms 一步，恒定）
图 10 · 抖动缓冲的作用：用一点延迟（几帧）换一个稳定的世界节拍。这笔交易几乎总是划算的
「等等看」与「直接跳过」的取舍

输入没到齐时，主循环有两个选择：挂起等待（像经典锁步，画面会停）或补齐继续（流畅，但那个玩家的操作会丢失）。实践中通常是分档处理：落后 1～2 帧时等一等（多是网络抖动，马上就到）；超过容忍窗口就补齐继续，并在客户端侧做「输入补发」补偿。这个容忍窗口的大小，就是这款游戏「手感 vs 严格同步」的调参旋钮。

13网络层：为什么帧同步最终都会离开 TCP

帧同步对网络只有一个硬要求：按序、可靠、低延迟地送达每一帧数据。听起来这正是 TCP 的卖点，但实践下来，几乎所有的实时帧同步项目都会换成「可靠 UDP」。

可靠 UDP 的三件套

自己基于 UDP 造一层轻量可靠协议（KCP、ENet 是常见选择，也可以自己写），核心是三招。

① 冗余发包：把「重传」提前成「提前发」

与其等丢包后重传，不如每次都多发一点。帧数据很小，代价极低。

// 每个包都带上最近 3 帧的数据（N-2, N-1, N）
// 收包方按帧号去重，任何一帧都能从后续包里被「救」回来
void SendFrameWindow(int currentFrame)
{
    var pkt = new Packet();
    for (int i = Math.Max(0, currentFrame - 2); i <= currentFrame; i++)
        pkt.Append(_frameBuffer[i]);      // 附带冗余帧
    _socket.Send(pkt);
}

这样设计的妙处：丢一个包最多影响一帧，而这一帧几乎必然被下一个包带上。用带宽换延迟，在帧同步里非常划算（一帧数据才几十字节）。

② 帧号单调推进：用序号做去重、排序与断包检测

// 接收侧：只接受比当前大的帧号，重复帧直接丢
void OnReceive(FrameCommand fc)
{
    if (fc.Frame <= _lastReceivedFrame) return;      // 冗余帧，丢掉

    if (fc.Frame > _lastReceivedFrame + 1)             // 中间有缺口 → 请求补发
        RequestRetransmit(_lastReceivedFrame + 1, fc.Frame - 1);

    _inputBuffer.Put(fc);
    _lastReceivedFrame = fc.Frame;
}

③ 帧聚合：把多帧合成一个包

15Hz 的逻辑帧，每帧只有一个几十字节的小包 —— 网络利用率极低，每个包还要背二十多字节的 IP／UDP 头。常见优化是把 2～3 帧攒成一个包发（比如每 100～200ms 发一次），进一步省带宽。代价是增加了「攒包」的延迟，所以要控制聚合深度。

UDP 还是 TCP？一个实用的结论

把可靠性做在 UDP 之上以后，网络层实现与上层逻辑可以解耦：上层只看到「按序到达的帧流」，底下是 TCP 还是可靠 UDP，变成一个配置参数。

  • 追求操作延迟最低 → 可靠 UDP（把重传超时压到很短、丢包立即快速重发、容忍有界乱序）。
  • 追求服务器承载最大、网络环境最杂 → 用 TCP 也常常可行，尤其当逻辑帧率较低（10～15Hz）且客户端已有抖动缓冲时，队头阻塞的影响会被缓冲吸收一部分。
  • 主流组合：客户端与网关之间走 UDP（KCP 之类），网关到游戏服之间走内网可靠通道。
别忘了一条最容易被忽视的规则

不管底层是什么，「断线」都必须被显式处理。要有心跳（比如每 500ms 一次）、要有超时判定、要有超时后的托管逻辑（AI 接管或空指令），还要有重连恢复流程。否则一次地铁进隧道，就会让整局陷入「所有人陪着等一个已经不在的人」的僵局 —— 而这正是帧同步最怕的事。

14服务器：中转站、裁判与录像机

帧同步里的服务器看起来「什么都不算」，但它其实承担了四件不能少的事：收集与广播、时序控制、存档与重连、事后验算。它不管世界怎么变，它管「世界按什么节奏变，以及历史有没有被篡改」。

职责一：指令中转与节奏控制

服务器维护房间的帧状态机，每 1/LogicFps 秒推进一次帧号，把当前收集到的所有玩家指令打包广播。两个设计要点：

  • 服务器是唯一的时钟源。帧号由服务器定义并下发，客户端不许自己发明帧号。客户端只做「我在第 N 帧，请把 N 之后的数据给我」这类请求。
  • 指令必须归属到确定的帧。玩家点击「攻击」时，这个指令落在哪一帧必须由服务器裁决（客户端带的时间戳只作参考），否则同一操作在不同客户端会落到不同帧上，直接分叉。

职责二：全帧历史存档

服务器把从开局到当前的每一帧广播内容都存下来。这份历史一物多用，是整个系统最值钱的数据：

职责三：权威裁判（补上帧同步最大的短板）

帧同步的逻辑在客户端跑，外挂可以改内存、改数值、改结果。服务器不需要在战斗过程中实时拦截（那样延迟太高），而是在关键节点验算：

  • 校验和比对：客户端每 N 帧上报一次世界状态的哈希；服务器可以用自己那份逻辑重算，或者至少比对多个客户端上报的哈希是否一致，不一致就标记本局异常。
  • 结果验算：一局结束时，服务器拿这局的指令流跑一遍权威逻辑，得到「标准答案」，与客户端上报的胜负／经济／伤害比对。
  • 行为统计检测：命中率、反应时间、操作间隔等统计特征，异常值（比如永远零失误、反应快过人眼极限）可用于标记可疑账号。

这套机制之所以成立，前提还是那句老话：逻辑层代码能在服务器上跑。所以服务器验算不是额外工程，而是分层架构的自然红利。

职责四：匹配与房间管理

这部分与同步模型关系不大，但帧同步对它有额外要求：尽量把网络质量接近的玩家匹配到一起。理由很直接 —— 在时间桶模型里，延迟高的玩家会持续丢帧、持续被托管，体验很差；把他和同延迟区间的玩家放一起，这个问题会显著缓解。

一个常见的误解

「帧同步不需要服务器」是错的。准确说法是：帧同步不需要服务器算游戏逻辑。服务器要管的时序、存档、重连、验算、匹配一样都不能少 —— 只是它的负载模型从「算世界」变成了「搬数据 ＋ 存历史」，容量估算的维度完全不同。

三把常见的斧头

  1. 提高逻辑帧率：15Hz → 30Hz，采样与等待各减半，代价是带宽与算力翻倍。这是最直接的一刀。
  2. 抖动缓冲自适应：网络好的时候不要一直背着 4 帧的缓冲。把「缓冲深度」做成动态的，可以让好网络玩家白赚 100ms。
  3. 本地输入先行：这是最大的一刀 —— 本地操作不再等服务器确认，直接就地生效。代价是可能与最终真相反，所以要配上「预测 ＋ 回滚」或者「预表现 ＋ 掩盖」。这就是接下来两章的内容。

16回滚（GGPO）：预测，然后重算

回滚是帧同步最漂亮的一次进化。它的出发点是一句反问：为什么要等？ 远端玩家的输入虽然还没到，但我可以猜 —— 而且大概率猜得对。猜对了没有代价，猜错了就倒回去重算。

三个概念，先把牌摆清楚

帧延迟（Input Delay）
我按下攻击，但游戏规定它要到第 N+2 帧才生效。用一点点人为延迟，换取「远端输入有更大概率及时赶到」。GGPO 允许 0～8 帧可调。
＋
预测（Prediction）
远端输入没到，就假设「和上一帧一样」。人在连续操作时，输入是高度重复的 —— 按住方向键、连打普攻，这个猜测命中率很高。
＋
回滚（Rollback）
真输入到了、发现猜错，就把世界恢复到「最后一个全程确定的帧」，用真输入重算一遍，再一路快进到现在。

// 回滚核心逻辑（概念版）
void OnRemoteInputArrived(int frame, FrameCommand real)
{
    if (_predictions[frame] == real) return;      // 猜对了，什么都不用做

    int rollbackTo = FindLastConfirmedFrame(frame);  // 回退到仍未过期的确定帧

    // 1) 恢复状态：从环形缓冲里取出那一帧的世界快照
    _simulation.Restore(_snapshotRing[rollbackTo]);

    // 2) 用真输入重算，一路跑到当前帧
    for (int f = rollbackTo + 1; f <= _currentFrame; f++)
    {
        FrameCommand cmd = _inputBuffer.Has(f)
            ? _inputBuffer.Get(f)                    // 已确认的真输入
            : _inputBuffer.Predict(f);               // 还没到的，继续猜
        _simulation.Step(f, cmd);
    }

    // 3) 表现层不需要重新播动画，只需接受「位置被修正了」
    _presentation.SmoothCorrectTo(_simulation.State);
}

为什么这招能成立

因为它吃的是两笔便宜：

  • 模拟很便宜。格斗游戏一帧的逻辑通常是几十个对象的位置与状态机，重算 5 帧的成本远低于一帧渲染。只要游戏逻辑够轻，回滚在 CPU 上完全吃得消。
  • 预测命中率很高。真人对战里的输入是「连续信号」：按住方向、连按攻击、蓄力不放。沿用上一帧的输入，命中率通常能到很高的水平，所以平均回滚次数并不多。

代价：三件必须提前做好的事

前提要求
状态可序列化整个游戏状态必须能一键「存」和「取」。不能有藏在引擎对象里、散落在闭包中、或者依赖外部引用的状态。这是最难的一条，通常要求逻辑层本来就是纯数据结构
快照要快每帧一次内存拷贝。常用做法是「环形缓冲 ＋ 预分配固定大小的结构体」，避免任何运行时分配；状态变化少时可以用差分快照优化
逻辑与表现彻底分离回滚重算时绝不能重复播放音效、特效、动画。要用一个「是否正在重演」的开关把所有副作用关掉，重演结束后由表现层按差值平滑修正
回滚的两个典型副作用

橡皮筋：预测错得离谱时（比如对手突然反向跳），画面会出现角色被「拉回」的瞬间。缓解办法是表现层做平滑修正（在 100～200ms 内渐变到正确位置），而不是瞬间硬切。

观感抖动：回滚本身会带来微小的视觉不一致（比如一次本该命中的攻击被判成未命中）。这类问题只能靠提高预测准确度（例如记录玩家的操作习惯）与控制回滚窗口深度（超过 7～8 帧就不预测、转为轻微等待）来缓解。

GGPO 的调参旋钮：帧延迟

帧延迟是「延迟」和「回滚频率」之间的滑杆：

帧延迟适用网络回滚频率
0 帧任意（延迟全交给预测承担）高
1～2 帧延迟在 2 帧以内中
3～5 帧延迟在 5 帧以内低
动态可调根据实测往返延迟自动选择自适应

实践中，帧延迟通常取「两端玩家设置值的较大者」，因为延迟小的一方多做一点预测就行，而延迟大的一方如果被强行要求零延迟，回滚会爆炸。

一句话总结回滚的性价比

它用 CPU（多跑几遍模拟） 换来了 手感（零等待），代价是对架构的要求变得苛刻 —— 状态必须可存可取、逻辑必须与表现绝缘。对 2～8 人、逻辑轻、精度要求高的游戏，这是目前最划算的方案。

17不回滚也能跟手：预表现与掩盖

回滚不是唯一的答案，而且它的实现成本不低。如果不想动架构，还有一批更「轻」的手段可以用来改善手感 —— 它们的共同思路是：逻辑上老实等着，但画面上先演给你看。

手段一：本地预表现（Prediction Presentation）

本地玩家按下攻击键，逻辑层老老实实等到第 N+2 帧才真正执行；但表现层立刻播放「抬手」动画与音效。等逻辑真正执行时，动画刚好走到出招的那一帧 —— 玩家感觉是「立刻响应」，而世界状态没有任何提前。

它和回滚的区别是：回滚是在逻辑上抢跑，预表现只是在视觉上抢跑。 所以预表现不需要状态可回滚，但它的可用范围有限 —— 只适合那些「结果几乎必然如此」的操作（比如走路、普攻），不适合胜负判定（技能命中、格挡成功）。

手段二：输入提前量 ＋ 前摇动画

  • 把操作提前到最早的合法帧。服务器收到「我要在第 N 帧攻击」这类意图时，只要该帧还没被广播，就把它插进去，而不是排到下一帧。
  • 前摇动画当缓冲。把技能设计成「有起手动作」的形态：起手 6～10 帧再判定。这段起手时间天然吸收了网络延迟，玩家感觉不到等，只觉得「这招有分量」。
  • 连招预输入缓冲。记录玩家在硬直期间按下的按键，硬直结束立刻消费掉，避免「按了没反应」。

手段三：表现层平滑修正

当逻辑状态与表现状态出现偏差（服务器纠偏、回滚重演、追帧结束），不要瞬间硬切 —— 那会看到「瞬移」。正确做法是在一段短时间（100～200ms）里把表现位置渐变到正确位置，并且优先修正位置、尽量不修正在播的动画。

每渲染帧: visualPos = Lerp(visualPos, logicPos, k) // k 由修正时间反推 偏差 > 阈值（例如 2 米）: 直接瞬移 // 差太多时平滑反而诡异

手段四：让请求延迟变成「设计选择」

这条最容易被忽略：游戏设计本身可以吃掉一部分延迟。

设计手法为什么有效
技能有可见的前摇给双方公平的反应窗口，延迟被「规则」而不是「网络」解释
判定宽容（命中范围略大于视觉）几十毫秒的误差被宽容度吸收，玩家不会觉得「明明打中了」
不需要精确到帧的玩法帧同步的延迟在宽松玩法里几乎无感；硬要 1v1 拼帧，就必须上回滚
把「即死」改成「有血量空间」单次判定的误差不再直接决定胜负，体验容错更高
四种手段的适用边界

预表现只用于「结果几乎确定」的操作；前摇与宽容是设计层手段，越早定越好改；平滑修正是万能兜底，但要注意「偏差过大时改为瞬移」。三者都不需要回滚那么重的架构，是性价比很高的第一步。

18不同步了怎么查：校验和与录像定位

分叉这件事，一定会在某个时刻发生。团队之间的差距，不在于是否能避免它，而在于从「玩家反馈不同步」到「定位到那一行代码」要花多久。这一章讲怎么把这段时间从「两周」压缩到「两小时」。

第一步：让它自己开口说话 —— 校验和

逻辑层每 N 帧（例如 30 帧）计算一次整个世界的哈希值，上报给服务器。服务器把同一局、同一帧、不同客户端上报的哈希排在一起比对：

哈希要覆盖所有影响后续的字段：对象 ID、位置、速度、血量、状态机状态、计时器、随机器内部状态。别只哈希位置 —— 那样会把「随机器状态不同」这类分叉藏起来。

第二步：拿到「案发时段的录像」

因为帧历史存在服务器上，你可以把这一局从开局（或从某个快照点）到分叉帧的指令流完整取下来，在本地重演：

回放模式: 1. 用同一颗种子初始化世界 2. 逐帧喂入服务器存档的指令 3. 每到 30 帧的倍数，打印一次校验和 4. 在「本地校验和 ≠ 线上校验和」的那一帧停下来 5. 此时对比该帧的所有对象属性，逐字段找出第一个不同的值

这套流程能进行的前提，是帧历史 + 同一个逻辑层 + 可复现的初始化。所以前面反复强调的那三件事（分离、存档、服务器能跑逻辑），在排查阶段全部变现。

第三步：准备四个工具

工具作用
确定性校验仪每 N 帧打印世界哈希；能对比两份运行的哈希序列，直接指出第一处不同
逻辑帧调试器能暂停、单步执行逻辑帧、查看该帧输入与全量状态。配上断点，就能盯着分叉那一刻
指令流回放器输入一份录像，重现整局。线上 bug 在本地 100% 复现的唯一途径
网络模拟器注入延迟、抖动、丢包、乱序，用来复现「只有在弱网下才出现」的问题

自动化：让它自己找出分叉

光有工具还不够，还要让它持续跑。一个成熟的做法是搭建自动化战斗回归：

  • 让多台真机（不同芯片、不同系统版本）跑同一批脚本对局，每天固定轮次；
  • 每局结束自动比对各方校验和序列，一旦发现分叉，自动保存「录像 ＋ 差异文档」并上传；
  • 差异文档里打印每个对象的每个属性，并用标记指出哪些相同、哪些不同。

这样分叉就会从「线上偶发、无法复现」变成「早上上班就看到一份现成的案卷」。把不确定性从生产环境挪到测试环境，是帧同步最值钱的一笔工程投资。

常见的分叉凶手排行

按经验，排查结果大致集中在：① 某处偷偷用了浮点（尤其是排序比较器、插值、距离判定）；② 哈希字典的遍历顺序；③ 某个随机数消耗次数与另一端不同；④ 一段「按条件触发」的代码在两端走了不同分支；⑤ 对象 ID 分配顺序不同。这五类能覆盖绝大多数案例，可以在排查时优先怀疑。

19断线重连、观战、录像与反作弊

这四件事在帧同步里其实是同一件事的四个用法：都是「按帧号重演历史」。因为世界由指令流决定，所以只要能拿到历史指令，就能重构出任何一个过去时刻。

断线重连与追帧

玩家断线重连后需要快速赶上。做法是：

  1. 客户端告诉服务器「我最后确认收到的帧号是 N」；
  2. 服务器把这局从 N 到最新帧的全部指令发给它（帧数据很小，几百上千帧也就几十 KB）；
  3. 客户端进入追帧模式：以远高于实时的速度连续演算，直到追上当前帧；
  4. 追帧期间关闭所有表现层副作用（不播音效、不弹 UI、不放特效），追平后无缝切回实时。

更快的做法是「快照 ＋ 追帧」：服务器或房主定期保存世界状态快照，重连时直接给「最近的快照 ＋ 之后的少量指令」，落后几百帧的情况可以在瞬间补齐。

观战与录像

观战本质就是「以慢一档的速率播同一份指令流」，所以它几乎不需要额外开发 —— 只是多一个不发送输入的客户端。录像同理：把整局的指令序列按帧号存储、去掉空帧、整体压缩，一局对战的体量常常能小到几 KB 级别。

这也是帧同步在内容生态上的一件隐形福利：回放、观战、剪辑、精彩时刻、AI 训练数据，全部共用同一套机制。

20上线清单

把前面 19 章压成一张可以逐条打勾的清单。如果你的帧同步项目要上线，这几项没有一项是可选。

开工前（架构决策）

  • 确认玩法适合帧同步（单位多／操作精度要求高／需要回放），而不是硬套。
  • 逻辑层独立成模块，不引用引擎命名空间；能单机跑、能在服务器跑。
  • 选好定点数精度（2D 用 Q16.16，3D 用 Q48.16 之类），写进团队规范。
  • 定好逻辑帧率（10／15／30）与协议格式，帧率越早定越好改。

开发中（确定性纪律）

  • 逻辑层没有浮点、没有系统时间、没有引擎物理、没有哈希容器遍历。
  • 随机数走自建随机器；随机器状态纳入存档。
  • 同帧更新顺序被显式定义并落在文档里。
  • 代码审查里有「确定性检查」一项；新人有自查清单。

联调前（工程能力）

  • 有校验和机制，每 N 帧上报一次。
  • 有指令流回放器与逻辑帧调试器。
  • 有网络模拟（延迟／抖动／丢包／乱序）。
  • 有自动化战斗回归，多机型跑同一批脚本并比对结果。

上线前（体验与安全）

  • 抖动缓冲自适应；弱网下不崩、不无限等。
  • 断线重连能追帧；长时间无输入有托管逻辑。
  • 追帧与重演期间屏蔽所有表现层副作用。
  • 输入延迟经过实测（真机、弱网），在可接受范围。
  • 服务器有全帧历史存档；结算有权威验算。
  • 校验和异常会自动告警并留存案卷。
上线后的第一条守则

永远不要为了「性能」或「省事」在逻辑层里打开一个口子。帧同步的确定性像一间无菌室：一次侥幸的浮点、一次顺手的字典遍历、一次「就这一次」的时间调用，都可能在两周后变成一个查不出来的线上分叉。守住纪律本身，就是这个技术方案的核心成本。

B常见误区与反直觉点

误区一：「帧同步就是同步每一帧的状态」

恰恰相反。帧同步同步的是输入，状态是自己算出来的。名字里的「帧」指的是逻辑帧号，不是「把帧里的状态发过去」。很多沟通事故都源于这个名字的误导。

误区二：「帧同步不需要服务器」

不需要服务器算逻辑，但极度需要服务器定节奏、存历史、做验算、管重连。少了这些，一个掉线就能让整局僵死。

误区三：「浮点只要精度够高就没问题」

问题不在精度，而在一致性。float128 该分叉还是会分叉。定点数的价值不是「更准」，而是「在哪儿算都一样」。

误区四：「先做功能，最后再统一处理确定性」

这是最常见的致命顺序。确定性必须从第一天就作为架构约束存在 —— 等逻辑层写完再回头改定点数，代价接近于重写。这也是为什么很多团队在中后期评估时，最终选择放弃帧同步。

误区五：「卡顿是网络问题，加带宽就好」

帧同步的卡顿大多是时序问题：抖动缓冲太浅、追帧没做、没有超时托管、聚包延迟太大。加带宽解决不了「慢的人拖住别人」，只有时间桶、缓冲与托管能解决。

误区六：「回滚能解决一切延迟」

回滚能藏住延迟，但不能藏住连续大幅抖动。如果对手忽然改变操作方向，预测必然错，回滚窗口会持续加深；超过一定深度就必须转为「轻微等待」，否则画面会变成橡皮筋。回滚是「概率性地藏延迟」，不是魔法。

一句话反直觉总结

三条最值得记住的

① 帧同步省的是带宽与服务器算力，付出的是确定性的长期税；
② 帧同步项目里最难的不是网络代码，而是纪律 —— 让二十个人的每一行逻辑代码都守同一套规矩；
③ 帧同步最大的隐形红利是「世界可重演」：回放、观战、重连、AI 训练、自动化回归测试，全部白送。

  2. 逻辑帧率从 15Hz 提到 30Hz，输入延迟能降多少？代价是什么？在什么情况下不值得？
  3. 为什么「玩家没操作」也必须按帧发送空指令？不发会产生什么连锁后果？
  4. 时间桶模型下，一个玩家的指令连续丢了三帧。从玩家视角、其他玩家视角、以及最终结算三个角度，分别会发生什么？
  5. 如果让你只保留一个调试工具来排查分叉，你选校验和还是指令流回放器？为什么？（提示：两者的作用其实互补）
  6. 回滚要求「整个状态可序列化」。请举出三个在真实项目里很难序列化的东西，并说明怎么隔离它们。
  7. 为什么说帧同步的反作弊目标是「可审计」而不是「防住」？这个判断在什么前提下成立？
  8. 假设你们要把游戏搬到服务端权威的帧同步（服务器跑逻辑），架构上需要额外做哪些事？服务器成本会怎么变？

✦写在最后

帧同步是一条把复杂度从服务器搬到客户端的路线。它用一条优雅的假设 —— 「相同的输入必然得到相同的结果」—— 换来了极低的带宽、极轻的服务器和天然的录像能力，但也换来了一份必须长期偿还的债：确定性。

它不像状态同步那样「随便写写也能跑」，更像是一种纪律：每一行逻辑代码都要经得起「两台不同机器会算出一样吗」这一问。理解了这一点，你就能理解为什么这种看起来古老的技术，至今仍站在 RTS、MOBA 和格斗游戏的底层。

传原因，还是传结果 —— 这是网络同步的第一个问题，也是最重要的那个。
