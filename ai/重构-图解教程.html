01

什么叫重构：两顶帽子What is Refactoring

先给结论。Fowler 把“重构”当成两个词来定义，缺一个都容易走偏：

重构（名词）

对软件内部结构的一种调整，目的是在不改变软件可观察行为的前提下，提高它的可理解性，降低修改成本。

重构（动词）

使用一系列重构手法，在不改变软件可观察行为的前提下，调整它的结构。

两个定义都咬住同一句话：不改变可观察行为。这不是修辞，这是分界线。

一条硬判据

如果你顺手改了外部行为，那你不是在重构，你只是在写代码。如果你没有自动化测试，你根本不知道行为有没有变——那么严格来说，你也没有在重构。

重构改的是哪一层
为什么强调“不改变行为”？因为它把一次大改动拆成了无数个可验证的小步，每一步做完，系统都还是能跑的那个系统。

两顶帽子：Kent Beck 的心法

重构最容易被搞砸的地方，是把“改结构”和“加功能”混在一起做。于是你一口气改了 200 行，测试红了，你不知道是哪一步坏的。

两顶帽子：一次只戴一顶
你正在写的这段代码，是“我要它做件新事”还是“我要它更好懂”？如果答案是“两个都要”，停一下，先摘一顶。
真实工作流是这样的

你想加个新功能 → 发现现在的代码结构不好加 → 摘下功能帽，戴上重构帽，把它整理成“容易加”的样子 → 换回功能帽，三下五除二把功能加上去。
所以重构不是额外的工作，它是加功能的前置动作。

02

为什么值得重构：设计耐久性假说Why Refactor

反对重构最常见的说法是“没时间”。Fowler 的回应是四个理由，其中最后一个最狠：

改进设计

代码腐化是默认状态，不是意外。重构是唯一持续对抗它的手段：它消除重复，把“能跑但乱”拉回“干净”。

让代码更容易理解

代码是写给人看的。你花二十分钟把一段费解的逻辑改成能读懂的样子，下一个人省下的是两小时。

帮你找到 bug

“要真正理解代码在干什么，你不得不重构它。”整理结构的过程本身就是一次代码审查，bug 往往在这时候自己冒出来。

提高编程速度（最重要）

前三条都服务于这条。重构不是牺牲速度换美感，它是唯一能让速度长期维持在高位的方法。

设计耐久性假说：两条速度曲线
红线和绿线交叉的位置，就是“这破系统没法维护了”和“这系统还行”的分界线。它不会突然出现，是从第一次“先这样吧”开始积累的。
一个反直觉的推论

如果重构真能加速，那“没时间重构”这个理由就站不住——你只是把今天的成本挪到了下周的高利贷上。Fowler 说得更不客气：如果不重构也能轻松加功能，那说明设计本来就够好，确实不用重构；可一旦你开始觉得“每次改这里都提心吊胆”，那笔账已经在还了。

顺便说清两件容易混的事

重构 ≠ 性能优化

重构让代码更好懂，性能优化让代码更快——两者目标不同，甚至会互相打架（优化常引入缓存、特化分支，破坏结构的清晰）。所以：先重构到清晰，再针对 profiler 报出的热点做优化，分开做。

重构 ≠ 预先设计

Fowler 现在更倾向 YAGNI（You Aren't Gonna Need It）：只按当前需求构建，把设计质量做高，等需求真来了再重构去应对。唯一例外——当你判断“以后再重构会非常困难”时，才值得现在就留那个灵活的钩子。

03

什么时候动手：三次法则When to Refactor

Don Roberts 给了一条流传最广的判据，Fowler 把它放在“何时重构”的第一句：

三次法则 The Rule of Three
第一次做这件事
直接做，别想太多
↓
第二次做类似的事
有点烦，但还是照做一遍
↓
第三次再做
停，重构
重复出现“第三次”，就是在告诉你：这里有一个还没被命名、还没被提取出来的抽象。

五种重构时机，按价值排序

时机怎么做为什么排这个位置
① 预备性重构
加功能之前		 先把代码整理成“新功能容易插进去”的形状，再动手写功能 性价比最高。整理完你会惊讶地发现新功能只要几行
② 帮助理解的重构
读不懂的时候		 先重构到你读得懂，再做你本来要做的修改 读不懂还硬改，是把“没搞清的东西”变成“改坏的东西”
③ 捡垃圾式重构
路过的时候		 顺手把眼前这一小块收拾干净，不刻意扩大范围 童子军军规：让营地比你到达时更干净。不贪心，才做得久
④ 有计划的重构
还技术债		 专门排时间，针对长期积累的结构问题做系统性调整 应该有，但应该很少。绝大多数重构是见机行事的
⑤ 复审代码时
Code Review		 review 出坏味道就地重构，而不是只留一句“这里不太好” Fowler 认为这是最好的重构时机：有人已经读过并理解了这段代码
“先往北开 20 公里”

Fowler 用开车比喻预备性重构：你要往东开 100 公里，但没有从当前位置向东的路。于是你先向北开 20 公里上高速，再从高速向东 100 公里——绕了路，总用时反而更短。
重构看起来是“先做了一件不是需求的事”，实际上是把后面的路铺平了。

什么时候不该重构

代码一团乱麻，改不动了

如果代码已经烂到重构无从下手，重写可能比重构更划算。重构的前提是你还能理解它、还能小步走。

这段代码不需要改，也没人需要读懂它

比如一段稳定得像块石头的底层库、一段只被调用一次且永不修改的脚本。没有修改需求，重构就没有回报。

你还没搞懂自己的设计

如果你连“这段代码应该长什么样”都还不知道，先停下来想清楚。盲目重构 = 换个姿势继续乱。

项目在交付死线上

最后冲刺阶段强行重构，是在赌。可以先记录下来，等这一轮交付完再回头处理。

04

安全绳：没有测试就没有重构Self-Testing Code

这一条必须单独成节，因为它决定了重构能不能做。

重构的第一块基石

重构的整个逻辑建立在“行为没有变”之上。而“行为没有变”这句话，你只有靠自动化测试才有资格说。没有测试，你只是在满怀希望地改代码。

重构的循环：小步 + 绿测试
注意“改一小步”的措辞：不是“改一块”，是一个手法。手法小到“改个名字”“把三行提成一个函数”这种程度。

没有测试的遗留代码怎么办

现实里更多的是“一坨没人敢动的老代码，还没有测试”。Fowler 给的路径是找接缝：

  1. 找接缝（seam）——哪里有可以插入测试而不牵动全局的边界？一个对外函数、一个纯计算模块、一段没有副作用的逻辑。
  2. 在接缝处插测试——不用覆盖全部，先锁住你即将要改的那部分行为。
  3. 用重构造接缝——如果压根找不到接缝，就用重构手法造一个。这一步有风险（此时还没有测试保护），但它是取得进展必须付出的代价。
  4. 让它变好一点点——每次触碰一块代码，就顺手改善它一点点。频繁使用的代码，改善可理解性的回报最大。
关于测试的一句话

书里第 4 章专门讲怎么搭测试体系：从待测代码出发，写出第一个会失败的测试，再补第二个，再改测试夹具。核心不是覆盖率数字，而是你改完之后敢不敢按提交键。

06

坏味道精讲 · 膨胀与变化阻碍Bloaters & Change Preventers

这七种味道是最常见、也最该优先处理的：它们让代码变大、变难懂，并且让每一次改动的代价成倍增长。

① 过长函数 Long Function

Fowler 的立场非常鲜明：如果你觉得需要写注释来解释一段代码在做什么，就该把它提炼成一个函数，用注释当函数名。

  • 越长的函数越难理解，越难理解就越不敢改，越不敢改就越长——正向反馈的死亡螺旋。
  • 哪怕是只有一行的代码，只要它需要解释，就值得被提炼出来。
  • 小函数带来的真正好处是：命名。函数名本身就是一层可以读的文档。

处方

提炼函数（Extract Function）是首选。如果函数里有大量局部变量和参数互相纠缠、提不动，改用 以查询取代临时变量 拆掉临时变量，再 引入参数对象 收拢参数，最后还有终极手段：以函数对象取代函数（Replace Method with Method Object）。如果只是条件分支和循环太长，直接 分解条件表达式 / 提炼循环。

② 过大类 Large Class

一个类里塞了太多字段、太多方法、太多职责。它通常是“什么都能干”的上帝类，也是发散式变化的温床。

识别信号

看字段：几个字段总是成组出现、成组被使用，说明它们其实属于另一个还没被创建出来的类。看方法：如果一组方法只操作同一批字段，那就是一个天然的 提炼类 候选。

③ 基本类型偏执 Primitive Obsession

该有自己的类型时，却一直用 int、string、float 硬撑。典型场景：

  • 钱用 int cents 存，汇率和币种散落在各处判断；
  • 坐标用两个 float 到处传；
  • 区号 / 电话号码 / 温度区间 全用字符串，校验逻辑重复十几遍。

处方是 以对象取代基本类型。如果这个基本类型其实是个类型码、还控制着条件分支，那就更进一步：以子类取代类型码 → 再 以多态取代条件表达式。

④ 过长参数列表 Long Parameter List

参数多到调用的时候要数着位置、还容易传错顺序。

症状处方
参数可以从另一个对象身上问到以查询取代参数，别让调用者替你查
传进来的是一堆“筛选项”布尔值移除标记参数，按行为拆成两个函数
参数是同一个对象被拆散的几个字段保持对象完整，整个传进去
几个参数总是成群结队一起出现引入参数对象

⑤ 数据泥团 Data Clumps

同样的三四个数据项，成天在好多地方一起出现：既作为几个类的字段，又作为好几个方法的参数。

判断方法很简单：把其中一个删掉，其他几个还有意义吗？如果没有，它们就该被打包成一个对象。—— 这其实就是“提炼类”和“引入参数对象”的标准触发信号。

⑥ 发散式变化 Divergent Change

发散式变化：一个类，多种原因的修改
“一个类应该只因同一种原因被修改” —— 这就是单一职责原则在重构语境下的说法。

⑦ 霰弹式修改 Shotgun Surgery

它是发散式变化的反面。发散式变化是“一个类因为很多原因被改”，霰弹式修改是“一个原因让很多类都被改”。你加一个字段，结果要在七八个文件里各补一小段——这就是“霰弹”，改动像散弹一样打得到处都是。

发散式变化

某个类很忙，什么都改它。
处方：拆开它（提炼类）

霰弹式修改

某个改动很忙，到处都要动。
处方：合并进来（搬移函数/字段、内联类）

两者的处方正好相反，这也说明：坏味道清单是用来帮你判断方向的，不是拿来对着抄答案的。

07

坏味道精讲 · 可有可无与耦合Dispensables & Couplers

⑧ 重复代码 Duplicated Code

所有坏味道里最出名的一个。它意味着一次业务规则的变更要在多个地方同步，而人一定会漏掉一处。

  • 同一个类里两段相似代码 → 提炼函数；
  • 两个兄弟类里相似代码 → 提炼函数 + 函数上移；
  • 只有算法结构相同但细节不同 → 提炼超类 或 塑造模板函数；
  • 两种方式表达同一件事 → 选一种，另一种用替换算法清掉。

⑨ 冗余的元素 Lazy Element

一个类、一个函数、一个变量没做够事来证明自己存在的价值。典型：只转发一层的方法、只被用一次的类、名字比内容还长的工具函数。

处方很简单：内联函数 / 内联类 / 折叠继承体系，把它拆掉。Fowler 的态度是：结构不是越多越好，多余的结构本身就是成本。

⑩ 夸夸其谈通用性 Speculative Generality

为了“以后可能会用到”，提前加了一堆钩子、抽象层、特殊分支。结果是：现在没人用，将来也没人用，但所有人都得读它、绕过它、维护它。

这是 YAGNI 的反面教材

处方：折叠继承体系、内联类、移除参数、改名（把“万能”的名字改回它真正做的事）。
判断标准是 Fowler 的原话：只有当“以后再重构会很困难”时，才值得现在就加灵活性。否则——现在就删。

⑪ 临时字段 Temporary Field

一个实例变量只在特定情况下被赋值，其他时候是 null。读代码的人看到这个字段，会困惑“它到底什么时候有值”。这通常说明：这个字段其实属于一个还没被提炼出来的对象。

⑫ 注释 Comments

Fowler 最容易被误解的一条

他不是说注释是坏味道。他说的是：注释常常被用来遮盖代码的坏味道——当你想写“这里是在计算折扣”的时候，其实应该把那段代码提炼成一个叫 计算折扣() 的函数。
注释真正的正当用途，是记录你无法在代码里表达的东西：为什么这里必须这么写、这段历史为什么绕开了一个坑、这个看似多余的判断在防哪种数据。这些不是遮盖，是补充。

⑬ 依恋情结 Feature Envy

一个函数跟另一个模块的数据/函数打得火热，跟自己所在的模块反而不怎么说话。最经典的形态：一个函数调了另一个对象的一堆 getter 来算出某个值。

模组化的目标：内部多说话，之间少说话
如果数据真的跨两个模块都要用，那答案可能是提炼类，而不是硬搬。手法选择永远取决于“为什么”，不是“套模板”。

⑭⑮⑯ 剩下的三种耦合味道

内幕交易

Insider Trading

两个类私下里交换太多数据，明明可以光明正大地做成一个体系。处方：搬移函数/字段，或以委托取代继承。

过长的消息链

Message Chains

a.b().c().d().e() —— 客户代码追着一串对象问下去，中间任何一段关系变动，客户就得跟着改。处方：隐藏委托关系，或提炼函数把这条链包起来。

中间人

Middle Man

一个类里大半方法都只是转发给另一个对象。封装是好的，但过度委托就成了纯粹的噪音。处方：移除中间人——如果只剩少量转发，干脆内联函数掉。

注意这组味道的张力

“过长的消息链”让你加一层（隐藏委托），“中间人”让你减一层（移除中间人）。它们是一对拔河——层数没有绝对正确的值，只有当前这段代码看起来更好懂的那个值。这句话几乎可以作为整本书的方法论：手法之间会互相抵消，判断永远依赖上下文。

第 2 版新增的四个

味道症状处方
神秘命名
Mysterious Name		函数名、变量名、类名看不出意图，要靠读实现才能猜改名。如果改不出好名字，说明这段代码的职责还没想清楚——那先重构结构，再回头命名
全局数据

可变数据
Mutable Data		一块数据在 A 处被改，B 处读到时已经不是你期望的值封装变量；考虑以查询取代派生变量；趋向不可变——更新时返回新副本，旧数据保持不动
循环语句
Loops		用 for/while 手工做筛选、映射、累加，循环体里塞了一堆控制逻辑以管道取代循环（filter / map / reduce），把“做什么”和“怎么遍历”分开

基本功：提炼、内联、改名Composing Functions

第 6 章“第一组重构”里的这一批，是日常使用频率最高的手法。如果只学五个，就学这五个。

提炼函数 Extract Function

整本书最基础、也最常用的一个。它的做法值得完整看一遍，因为它示范了“机械步骤”到底是什么感觉：

  1. 创建一个新函数，以“它做什么”命名（不是“它怎么做”）。
  2. 把要提炼的代码复制进新函数，调整其中的变量引用为参数。
  3. 处理局部变量：只被读的当参数传入，被赋值的当返回值传出。如果被赋值的变量不止一个，说明这段代码做了不止一件事，考虑拆成多次提炼。
  4. 在原位置调用新函数。
  5. 跑测试。
  6. 检查新函数里有没有可以继续提炼的部分，以及新函数名是否准确反映了它的行为；必要时改名。
提炼函数前后
注意：代码量没有变少，甚至变多了。重构买的不是行数，是“能不能在三秒内看懂这段在干什么”。

内联函数 / 内联变量：反方向的清理

它们和提炼是一对反向操作，用来对付“冗余的元素”：

内联函数 Inline Function

当函数体比它的名字还清楚，或者一堆函数被拆得过于零碎、看不出整体逻辑时，把它们合并回去。典型场景：一堆只做简单委托的转发函数。

内联变量 Inline Variable

当变量名并不比它所赋的表达式更能说明问题时，直接内联掉。命名确实是好的，但一个名不副实的名字比没有名字更糟。

提炼变量与拆分变量

// 改动前：这个表达式什么鬼
if (order.quantity * order.itemPrice > 1000) return 0.05;

// 提炼变量：给表达式一个名字，意义立刻显形
const basePrice = order.quantity * order.itemPrice;
if (basePrice > 1000) return 0.05;
提炼变量有一个陷阱

如果这个变量被赋值了不止一次（比如在循环里累加、在条件分支里改），千万别急着提炼——先做 拆分变量（Split Variable）：给每个不同的赋值含义各起一个独立的名字。一个变量被赋了三次不同含义的值，是 bug 的高发区。

改变函数声明 Change Function Declaration

也就是改名、加参数、删参数、调整参数顺序。听起来最无聊，实际威力最大——因为名字是代码里成本最低、收益最高的文档。

一个好用的技巧

如果改名字会牵动很多调用点怎么办？先用旧名字创建新函数，内部委托给老的实现；把调用点一个个迁到新名字；全部迁完后再删掉旧的。这样整个过程随时可停、随时可回滚。

三个“组合”手法

手法什么时候用效果
引入参数对象
Introduce Parameter Object		 几个参数总是成组出现（数据泥团） 把一团参数变成一个概念，函数签名立刻变短、变清楚
函数组合成类
Combine Functions into Class		 一组函数总是在操作同一份数据，把这份数据传来传去 把数据变成字段，函数变成方法 —— 少传参数，多一层内聚
函数组合成变换
Combine Functions into Transform		 一份原始数据被多个函数反复加工，每次都重新算一遍派生值 一次算好，把派生数据附加到数据本身，后续函数直接读
拆分阶段
Split Phase		 一段代码里混了两类不同的事（如“算”和“展示”） 切分成两个阶段，中间用一个明确的数据结构沟通 —— 案例的主角

搬移与封装：代码该待在哪Moving & Encapsulating

第 7、8 两章合起来的主题是一个问题：这段逻辑放对地方了吗？搬移解决“放错位置”，封装解决“暴露太多”。

搬移函数 Move Function

这是面向对象设计里最重要的一次动作之一。判断标准只有一条：这个函数引用了谁的数据最多，它就该住在谁那里。

搬家决策：往哪搬
这个函数里，哪个类的数据被引用得最多？
↓
是另一个类 → 搬过去
「依恋情结」的标准处方。搬完你会发现它用到的参数少了一大半
↓
散落在好几个类 → 先看它是不是在协调
如果它主要是在编排多个对象的动作，那它本来就是“服务层”，留在原地是对的
↓
哪边都不合适 → 提炼一个新类
把数据一起搬进去。这已经不是搬移，是提炼类了
注意最后两档：手法会在半路变成另一个手法。这是常态，不是走偏。

另外几种搬移

搬移字段 Move Field

字段住错了类。判断方式和搬函数一样：哪个类的方法最常用它，它就搬去哪。搬字段通常要用封装变量先把读写都收进函数，再整体迁移。

移动语句 Slide Statements

把相关的代码凑到一起。这是所有重构里最不起眼、却最常用的一步：把变量声明挪到第一次使用它之前，把相关的几行聚拢，为后续的提炼铺路。

拆分循环 Split Loop

一个循环里做了两件不相干的事。拆成两个循环——性能上的那点损耗，换来的是每一步都能被独立理解、独立提炼。Fowler 明确说：先拆，真成为瓶颈了再合并优化。

以管道取代循环
Replace Loop with Pipeline

用 filter / map / reduce 表达“做什么”，把“怎么遍历”交给语言。适合那种“筛一遍、转一下、加起来”的循环。

// 拆分循环 + 以管道取代循环
// 改动前：一个循环干三件事，每件事都得通读整段才能看懂
let total = 0, count = 0, cheapest = null;
for (const p of products) {
  total += p.price;
  if (p.quantity > 0) count++;
  if (!cheapest || p.price < cheapest.price) cheapest = p;
}

// 改动后：三件事，各说各的
const total    = products.reduce((s, p) => s + p.price, 0);
const count    = products.filter(p => p.quantity > 0).length;
const cheapest = products.reduce((a, b) => a.price < b.price ? a : b);

封装：把“能改的地方”收窄

封装变量：真正要封住的是什么
尤其对集合：不要只封装集合本身，还要封装集合里元素的增删（提供 add/remove 而不是返回裸数组）。否则调用者仍然可以随意改内部。

以查询取代临时变量 Replace Temp with Query

把只算一次的临时变量，换成每次调用都重算一遍的函数。

// 改动前
const basePrice = quantity * itemPrice;
if (basePrice > 1000) return basePrice * 0.95;
return basePrice * 0.98;

// 改动后：变量没了，但这段逻辑可以被别处复用了
function basePrice() { return quantity * itemPrice; }
if (basePrice() > 1000) return basePrice() * 0.95;
return basePrice() * 0.98;
性能怎么办

这是最常被质疑的手法：本来算一次，现在算三次。
Fowler 的回答很直接：先让它可读，绝大多数情况下这点开销无感；真的成为热点，再把它改回去。重构和优化是两件事，别在这里打架。

简化条件逻辑：干掉 switchSimplifying Conditional Logic

条件逻辑是复杂度最集中的地方。第 10 章给的六个手法，几乎覆盖了所有“if 写得看不清”的情况。

四步阶梯：从最轻到最重

条件逻辑的化简阶梯

以卫语句取代嵌套条件表达式

把“正常情况埋在 if 里面、异常情况写在 else”的写法，翻成“异常情况先挡掉，正常情况走直线”。

// 改动前：要读到最里面才知道正常流程是什么
function payAmount() {
  let result;
  if (isDead) {
    result = 0;
  } else {
    if (isSeparated) {
      result = separatedAmount();
    } else {
      if (isRetired) result = retiredAmount();
      else result = normalPayAmount();
    }
  }
  return result;
}

// 改动后：特殊情况一句句挡掉，最后一行就是主流程
function payAmount() {
  if (isDead)      return 0;
  if (isSeparated) return separatedAmount();
  if (isRetired)   return retiredAmount();
  return normalPayAmount();
}

以多态取代条件表达式

这是这一章的重头戏，也是第 1 章案例的终点。它的目标：把“按类型分支”这种散落各处的 switch，变成一次分发。

为什么 switch 是坏味道
多态的解法：把“类型”变成一个对象，把“每个类型下该怎么做”各自关进自己的类里。新增一个剧种 = 新增一个子类，一个 switch 都不用碰。
// 以多态取代条件：把分支收进子类
class PerformanceCalculator {
  get amount()        { throw new Error("子类负责"); }
  get volumeCredits() { return Math.max(this.performance.audience - 30, 0); }
}

class TragedyCalculator extends PerformanceCalculator {
  get amount() {
    let result = 40000;
    if (this.performance.audience > 30)
      result += 1000 * (this.performance.audience - 30);
    return result;
  }
}

class ComedyCalculator extends PerformanceCalculator {
  get amount() { /* 喜剧的算法 */ }
  get volumeCredits() {
    return super.volumeCredits
         + Math.floor(this.performance.audience / 5);   // 复用父类 + 自己的差异
  }
}
还有一个更轻的替代品

引入特例（Introduce Special Case，旧称“引入 Null 对象”）：当一个特殊值让调用方到处写 if (customer === null) 的时候，创造出一个“不存在的客户”对象，它也响应同样的消息，只是行为是“什么都不做”。
它做不到多态那么彻底，但便宜得多。又回到了那条方法论：选最轻的那一档。

完整走一遍：戏剧团计费案例The First Example

第 1 章是全书最值得反复读的一章。Fowler 没有讲任何理论，而是打开一个真实的程序，从头改到尾——用了大约 30 分钟、改了二十来处，全程测试都是绿的。

起点：一个函数，三件事

一个给剧团打印账单的函数。输入是账单发票（客户的每一次演出、观众人数）和剧目表（每个剧的 ID、名称、类型），输出是一段文本账单。

// 起点：约 40 行，把三件事混在一个函数里
function statement(invoice, plays) {
  let totalAmount = 0;
  let volumeCredits = 0;
  let result = `账单：${invoice.customer}\n`;
  const format = new Intl.NumberFormat("en-US",
    { style: "currency", currency: "USD" }).format;

  for (let perf of invoice.performances) {
    const play = plays[perf.playID];
    let thisAmount = 0;

    // ① 按剧种算这一场的钱
    switch (play.type) {
      case "tragedy": /* 40000 + 超 30 人每人 1000 */
      case "comedy":  /* 30000 + ... + 每人 300 */
      default: throw new Error(`未知剧种：${play.type}`);
    }

    // ② 攒积分（喜剧规则不同）
    volumeCredits += Math.max(perf.audience - 30, 0);
    if ("comedy" === play.type) volumeCredits += Math.floor(perf.audience / 5);

    // ③ 拼这一行的文本
    result += `  ${play.name}：${format(thisAmount / 100)}`
            + `（${perf.audience} 人）\n`;
    totalAmount += thisAmount;
  }

  result += `应付：${format(totalAmount / 100)}\n`;
  result += `积分：${volumeCredits}\n`;
  return result;
}

Fowler 对这个起点的评价很有意思：它不算烂。不重复、命名还行、结构清楚、长度也就一屏。他写这段话的目的恰恰是——如果连这样“还行”的代码都能被重构变得更好，那你手上那些真正难看的代码就更没有理由不动。

真正的问题有三个：

问题 1 · 三件事混在一起

算钱、算积分、拼字符串。任何一件变化，都要在同一个函数里小心地动刀。

问题 2 · 逻辑无法复用

如果现在要出一个 HTML 版账单，整个函数得复制一份再改——重复代码的经典开场。

问题 3 · switch 会越长越多

剧情类型分支散在函数里，加一个剧种就要改多处，而且每处都得记得改。

重构路径：五步走完

从 40 行单函数，到可扩展的多态结构
第 1 步 · 提炼函数
把“算一场的钱”“算积分”“取剧目”分别提炼出去。一个手法、一次测试、一次提交
↓
第 2 步 · 拆掉临时变量
用「以查询取代临时变量」把 format、play 等变量清掉，让结构浮出水面
↓
第 3 步 · 拆分阶段（最关键的一刀）
切出「组装数据」阶段 createStatementData()，与原函数的「渲染文本」阶段分离。中间的账单数据用一份明确的中间结构传递
↓
第 4 步 · 按类型重组计算
把「按剧种算钱/算积分」的逻辑搬进一个计算器，再用工厂函数根据剧种返回不同的计算器
↓
第 5 步 · 让计算器变成多态
提炼出父类，把差异放进子类；switch 消失，只剩一次分发
每一步都是一个独立的重构手法，每一步之后测试都是绿的 —— 所以整个过程随时可以停下来。

终点：statement 只剩两行

// 计算与渲染分家：statement 只负责"渲染"
function statement(invoice, plays) {
  return renderPlainText(createStatementData(invoice, plays));
}

// 组装数据的阶段：把所有派生值一次算好，交给渲染阶段
function createStatementData(invoice, plays) {
  const result = {};
  result.customer  = invoice.customer;
  result.performances = invoice.performances.map(enrichPerformance);
  result.totalAmount        = total(result.performances, "amount");
  result.totalVolumeCredits = total(result.performances, "volumeCredits");
  return result;

  function enrichPerformance(aPerformance) {
    const calculator = createPerformanceCalculator(aPerformance, playFor(aPerformance));
    const result = Object.assign({}, aPerformance);   // 浅拷贝，别改原对象
    result.play          = calculator.play;
    result.amount        = calculator.amount;
    result.volumeCredits = calculator.volumeCredits;
    return result;
  }
}

// 唯一的那个"switch"，而且只有它知道有哪些剧种
function createPerformanceCalculator(aPerformance, aPlay) {
  switch (aPlay.type) {
    case "tragedy": return new TragedyCalculator(aPerformance, aPlay);
    case "comedy":  return new ComedyCalculator(aPerformance, aPlay);
    default: throw new Error(`未知剧种：${aPlay.type}`);
  }
}

改动前：要出 HTML 账单

把整个 statement 复制一份，改掉字符串拼接部分——算钱和算积分的逻辑从此有了两份，从此开始分叉。

改动后：要出 HTML 账单

写一个 htmlStatement()，同样调用 createStatementData()，只换渲染部分。计算逻辑一份，不重复。

改动前：要加“历史剧”

找到那个 switch，加一个 case；再去改积分逻辑里的 if；如果别处还有按类型的分支，也得一个个找。漏一处就是 bug。

改动后：要加“历史剧”

写一个 HistoryCalculator 继承父类，实现 amount（和可选的 volumeCredits），在工厂函数里加一行。其他代码一行不用碰。

这一章真正想教的东西

不是“多态很好”，而是——这个漂亮的终点，是一步一步走出来的，中间没有哪一步需要你先想清楚终点。
Fowler 在过程中好几次走岔了（比如一开始把 play 变量删得过头，后来发现不合适又加回来），这些都是真实的。他的原话大意是：重构的过程就是这样，你会来回试探；有测试保护，试探的成本极低，所以你可以放心地走错再走回来。

在真实项目里重构 + 速查Challenges & Cheatsheet

书里的例子永远是干净的。现实里有六个绕不过去的障碍，第 2 章专门讨论了它们。

障碍为什么会卡住Fowler 的回应
被认为拖慢进度 产品经理看到你在“改代码”而不是“做功能” 重构的唯一目的就是让开发更快。沟通时不要讲“我在整理代码”，要讲“我在把这块整理成好加新功能的样子”
代码所有权 这块代码归另一个团队，你说不上话 保留旧接口、标记为废弃，新旧并存逐步迁移（新东西用新的，老调用点慢慢改）
长期分支 你的重构和别人的改动在两条分支上各自跑了三个月 分支持续得越久，合并越痛。倾向持续集成，每天向主干合并
没有测试 改完不知道有没有坏 没有测试就不要做大规模重构。先补测试，哪怕是覆盖即将改动的那一小块
遗留系统 一坨巨大、没有测试、没人完全懂的老代码 找接缝 → 在接缝处插测试 → 小步重构。每次触碰就改善一点点，让营地比你到达时更干净
数据库 数据结构一改，全世界的代码和线上数据都受影响 用数据迁移脚本把结构改动和代码改动绑在一起；每次迁移都很小且完整，迁移后系统仍可运行；串联多次小迁移完成大改造。能拆到多次生产发布就拆开，一次出问题容易回滚

如果你的项目是 Unity / C#

几条对游戏工程特别对得上的建议

① 先给纯逻辑层加测试。MonoBehaviour 难测不是借口——把伤害计算、掉落表、商店定价、数值公式从 MonoBehaviour 里提炼成普通 C# 类，这些就能直接单测。“提炼类”这个手法在 Unity 里往往就是“把逻辑从 MonoBehaviour 挪到 POCO”，收益极高。
② Prefab 和序列化是隐形的接口。改字段名会打断 Prefab 引用、动画曲线、ScriptableObject 资产。所以改名前先确认引用范围——这相当于书里“代码所有权”问题在 Unity 里的变体。
③ “万能管理器”是过大类重灾区：上千行的 GameManager、UIManager。用提炼类把职责切出去（音频 / 存档 / 输入各归各处），比整篇重写安全得多。
④ 枚举 + switch 的配置表就是“重复的 switch”：按类型分支的玩法逻辑，最值得用以多态取代条件表达式或策略对象整理一遍，加新玩法时才不用改核心代码。

动手之前，过一遍这份清单

  • 这段代码有测试保护吗？没有就先补，或者只做最小的、能立刻验证的那一步
  • 我现在戴的是哪顶帽子？是在改结构，还是在加功能
  • 我能不能说出这次重构对应哪个手法？说不出名字，多半是没想清楚
  • 这一步多大？大到不能一分钟内回滚，就该再切小一点
  • 我改完之后行为真的一点没变吗？（如果变了，那这不是重构，得按加功能的方式验收）
  • 如果这次重构做到一半被打断，仓库里的代码是能跑的吗
一句话带走

把大改动拆成一个个小到“不值得做”的步骤，每一步之后代码都还能跑，于是你永远有退路。 重构的全部魔力就在这里——它不是让你更勇敢，而是让“动老代码”这件事，终于不再需要勇敢。
