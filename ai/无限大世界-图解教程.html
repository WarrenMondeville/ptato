00一个反直觉的真相：大世界不是「把地图做大」

所有大世界技术，本质上都是同一个问题的不同答案：如何在有限的内存、带宽、浮点精度里，假装整个世界都在。

先泼一盆冷水。我们直觉里「无限大世界」的画面是：一个巨无霸的地图文件，游戏一启动就全部载入，玩家走到哪都是真的。但现实是——不管是 Switch 上的海拉鲁，还是 PS5 上的交界地，内存里永远只装着玩家周围那一小圈。所谓「无缝」，不是「全都存在」，而是「你还没看的地方，刚好在你看之前被偷偷换上去了」。

所以这篇文章不按「这是哪个游戏」讲技术，而是先讲清楚所有大世界共用的底层零件（流送、地形、剔除、精度、程序化），再去看五款游戏各自怎么组合这些零件交出答卷。你会发现：塞尔达和虚幻引擎 5，其实在解同一道题，只是解法一个像艺术家、一个像工业化流水线。

这一篇你该记住的一条

「无限大世界」是演出，不是容量。它的全部工程，都围绕三个词：加载、卸载、以及让这两件事发生在玩家视线之外。

01世界分区与流送：永远只把身边那一圈装进内存

这是大世界的地基。把整张地图切成格子，按玩家位置动态加载、卸载，内存里永远只有九宫格那一点东西。

它解决什么问题

一个 80 km² 的世界里，可能有上万个可交互物体：敌人、草、树、宝箱、呀哈哈、武器、NPC。全部常驻内存？Switch 的 4GB 统一内存当场爆炸。而且只按距离砍也不行——因为很多机关是联动的（树倒了 → 桥出现），你不能把有关系的对象拆散到不同内存块里。

怎么做：以塞尔达的「九宫格」为例

《旷野之息》把世界切成带字母 + 数字的方格（A-1、B-3、H-5…），每个叫一个 Map unit。玩家站在 H-5 时，系统加载周围 3×3 = 9 个 Dynamic unit（G-4 到 I-6）。这不是比喻，是逆向工程实锤的加载策略。

关键在有两个互相独立的半径，这是最容易搞混的地方：

  • 加载半径（九宫格 / Loading Range）：决定这块内容进不进内存；
  • 显示半径（TraverseDist / 剔除距离）：决定它画不画、跑不跑 AI。

也就是说「加载 ≠ 显示」。一个物体可以躺在内存里睡觉，也可以明明在内存里却被判「太远，别画」。理论上只要美术给它配够大的 TraverseDist，你在海拉鲁的这头能看见那头的东西。

通用引擎的同一件事：World Partition 与 Addressables

Unity / 虚幻把这套思路做成了自动化工具。UE5 的 World Partition：整个世界存在一个持久关卡里，自动按网格切成 cell（默认 128 m 一格），按玩家到流送源的距离自动加载卸载。每个 Actor 存成独立文件（OFPA），彻底解决多人协作时的版本冲突。Unity 侧则是把世界切成 additive scene，用 Addressables 按引用计数异步加载、自动释放。

02地形：脚下要细、地平线要远

地形是大世界里唯一永远在视野里、永远不能卸载的东西。它的核心矛盾是：脚下要够细，地平线要够远——两者的三角形数量差好几个数量级。

第一步：高度图切成块

地形底层是一张二维「高度表」（Heightmap）。一张 4096×4096 的 16-bit 高度图不压缩约 32 MB，永远不一次性全载，而是切成 64~128 m 见方的小块（Chunk）。

第二步：几何 LOD，三种流派

远处地形用低精度模型，靠近才换高精度。问题是不同精度的相邻块之间会出现裂缝（T-junction）。三种主流解法：

流派结构接缝处理特点
Chunked LOD四叉树 + 预生成块插入 stitching 补丁几何经典，但要额外补丁
CDLOD四叉树 + 全场景统一 LOD 函数不需要 stitching，用顶点 morph连续缩放、无 pop
GeoClipmap以相机为中心的同心环靠 skirt（裙边）一个 draw call 一环，适合无限地形

CDLOD（Strugar, 2010）是现在最常被引用的方案：它按「观察者到地面的真实三维距离」决定 LOD，在每层最后 15~30% 的 morph 区让顶点连续变过去，所以既不用补丁，也不会有「啪」地弹一下的跳变。GeoClipmap 则像一个以你为中心的靶子，中心最清晰、越往外越粗，内存恒定，特别适合盗贼之海那种「望不到边」的海面。

03剔除与 HLOD：瓶颈是 draw call 不是三角形

视锥剔除只解决了「画面外的不画」。但开放世界里，你面前隔着一座山——山后那一万个物体在视锥里，却根本看不见。而且真正的瓶颈往往不是三角形数，是提交次数。

三级剔除

  • 视锥剔除（Frustum Culling）：不在相机视野锥里的直接不画；
  • 遮挡剔除（Occlusion Culling）：被山、楼挡住的也不画。常用 HZB（层级深度图）——一张金字塔状的深度图，判断「这个包围盒是不是被完全挡住」只需采样几个像素，极快；
  • GPU Driven Rendering：把剔除、LOD 选择、绘制调用全搬到 GPU 批量裁决，CPU 不再一个个问 GPU。

HLOD 与 Imposter：把一堆物体变成一个

单个物体的 LOD 解决了「每个东西自己变粗」，但解决不了「东西太多、draw call 太多」。远处一片 5000 棵树的森林 = 5000 次 draw call，哪怕每棵只有 12 个三角形。这时用 HLOD（层级 LOD）：把一组相邻静态物体合并成一个低模代理。

Nanite 的双 Pass 遮挡

UE5 的 Nanite（虚拟化几何）把网格切成固定 128 三角形的 Cluster，用 BVH + 双 Pass 遮挡 + 软光栅化。它先用上一帧的 HZB 剔除（假设上一帧可见的这帧大概率还可见），光栅化后再构建本帧 HZB；再用本帧 HZB 把刚才被「误杀」的物体补回来。为什么两遍？因为单靠上一帧会把相机转角瞬间刚露出来的模型漏掉。

04浮点精度的诅咒：21 km 与坐标重定位

新手最常踩、最难 debug 的坑：世界越大，离原点越远，物体开始抖动、贴图错位、物理飘移。地图没错，是数字本身的精度不够了。

为什么会出现

虚幻的单位是 cm，坐标用 float32 存。float32 尾数 24 位，当物体离原点距离为 x 时，最小可分辨距离约为 Δx = x·2⁻²³。在 x ≈ 21 km 处，Δx 已经到 0.25 cm 级别——肉眼可见的抖动。这就是 UE4 时代「世界半径硬上限约 21 km」的来历。

# 达摩克利斯之剑：精度随距离线性变差 Δx = x · 2⁻²³ x = 2²¹ cm ≈ 20.97 km → Δx = 0.25 cm # 抖动的临界

三条解决路线

方案做法代价
Origin Rebasing玩家走远，整个世界的 Actor 反向平移，让原点重新贴回脚下绝不能手动改偏移值，否则坐标漂移极难查
Camera-relative提交 GPU 的顶点坐标先减相机世界位置，GPU 永远看到贴近零的小数后处理材质里用绝对世界坐标仍可能出问题
LWC（UE5）引擎层 FVector 升为 double，只在提交 GPU 前转回 float老代码的隐式 float 转换会静默丢精度

UE5 起默认开启 LWC（Large World Coordinates）：世界坐标用 double，GPU 相关（顶点、粒子、骨骼）用单精度 FVector3f。但别以为开了就万事大吉——网络复制仍是量化 float；FVector → FVector3f 的隐式转换能编译通过却静默丢精度；Niagara 粒子、物理子系统内部仍是 float 路径；后处理材质里的绝对世界坐标在离原点几十公里处仍会偏差。

一句话记住

LWC 没有让坐标变准，它只是把「不准」挪到了看不见的地方。三种解法分别对应：把整套房子搬到你们中间（Rebasing）、永远用「离你几米」报地址（Camera-relative）、直接换一把 64 位游标卡尺（LWC）。

05虚拟纹理与 IO：PS5 的 SSD 到底改变了什么

流式加载的终极瓶颈通常不是「文件多大」，而是「把这块内容弄进内存要多少毫秒」。PS5 的 SSD 把这条瓶颈砍掉了一大截——但也没砍掉全部。

虚拟纹理：给地形一层「无限大但有分辨率」的皮

地形叠了 8 层材质（草 / 岩 / 土 / 沙 / 雪 / 过渡…），如果每帧每像素采样 8 张贴图再混合，纹理常驻内存会被推到 4~8 GB，然后疯狂换页。虚拟纹理的思路是：先把「最终颜色」烘进一张巨大的虚拟贴图，再按可见性只把需要的 tile 分页进物理内存——把「每帧 8 次采样」变成「一次采样」。UE5 有 RVT（GPU 实时生成）和 SVT（从磁盘按需加载）两种。

Mark Cerny 的话很直白：PS5 可以在 0.27 秒加载 2 GB，游戏启动只要 1 秒，没有读盘画面，快速旅行快到眨眼。它解锁的是新的设计空间——关卡不用再为了藏加载而被扭曲成电梯、窄走廊、慢开门。

最容易高估的一点

SSD 解决的是带宽，不是内存、也不是实例化 / GC 开销。PS4 时代开发者用叙事技巧藏加载，是 HDD 逼出来的。但社区大量优化记录显示：卡顿大头常常在 Instantiation（实例化）、GC、PSO 编译，而不是文件读取。Unreal 的 GC 默认 60 秒一次全量可达性分析，几十万 UObject 的开放世界每次都要 game thread 停十几毫秒——这跟 SSD 多快一点关系都没有。

06程序化生成：Houdini、PCG 与「无菌感」

手工摆 80 km² 的树石村落会累垮美术；纯程序化又有另一个问题——玩家察觉重复的速度，比你以为的快得多。最佳形态永远是混合。

它是什么：不是「替你做关卡」，是「把你定的规则套到百万个对象上」

业界标准工具是 Houdini，把节点网络打包成 HDA 进引擎当黑盒；UE5 自带 PCG 框架，用节点图画点云流水线：在表面 / 样条上采样点 → 按坡度 / 高度 / 噪声筛选 → Poisson Disk 保证最小间距 → 带上属性表 → 用 ISM / HISM 批量生成。

生态分布规则：让自然「看起来对」

真实生态被非生物因素约束：海拔（每升 1000 m 降温约 6.5°C）、坡度朝向（北半球南坡更暖更干）、湿度（靠近水体、迎风坡更湿）。游戏把这些变成 scatter 的 mask——先生成 heightmap，算 humidity / temperature，查表选 biome，每个 biome 定义可放置资产与密度，再分层撒。这一步让「山脚雨林、山顶苔原」自然成立。

什么时候不该用 PCG

三件程序化做不好的事：叙事精度（推开门第一次看到龙的机位）、难度曲线（boss 前的治疗道具）、独特记忆点（黑魂的篝火、时之笛的神庙）。BotW 的米津真在 CEDEC 2017 明说：海拉鲁不是自动生成的，是做完之后走一遍、再做一遍再走一遍。

三种典型翻车

① 重复疲劳：5 种树 + 随机缩放，玩几小时就腻，解法不是加随机而是加密基础资产与参数空间；② 无菌感：程序化放桶是「覆盖率最大化」，手放桶是「有人把桶落在这儿了」，后者有叙事；③ 美术方向漂移：规则保证一致性，但规则没有审美，没有能翻译成参数的 Art Bible 系统就会跑偏。

07海洋、天空与「空的恐惧」

水、云、引导和密度，是让大世界「活」起来也最容易露怯的地方。这一节把三件横向技术一次讲清。

海洋：Gerstner 波与 FFT

朴素正弦波叠加只让顶点上下动，波峰波谷对称，像果冻。真实海浪波峰尖、波谷平，因为水粒子在走圆周轨道。1802 年 Gerstner 给出的摆线波，让顶点既上下也左右位移，把顶点「聚到波峰、散到波谷」，自然得到尖峰平谷。色散关系 ω = √(g·k)，g ≈ 9.81 m/s²——常见错误是随手定 ω 而不从波长 k 推出，导致所有波同速、像人造波浪池。实践上 steepness 总和预算 0.6~0.8，Q 过大波峰会自交翻面。

# Gerstner 单波：顶点同时做上下 + 水平位移 P(x,z,t) = ( x + Σ Qᵢ Aᵢ Dₓ cos(ωᵢ D̂·p₀ + φ t) , Σ Aᵢ sin(ωᵢ D̂·p₀ + φ t) , z + Σ Qᵢ Aᵢ D_z cos(ωᵢ D̂·p₀ + φ t) ) ωᵢ = √(g·kᵢ) # 深水色散：长波跑得快

近景用 Gerstner（几条波手调形状），远景大面用 FFT 海洋（Tessendorf 电影级方法，盗贼之海用的就是它）：在频域按 Phillips 谱给每个频率分量分配能量，GPU 上做 IFFT 合成高度场，波峰相遇叠加、波谷相遇抵消，所以永不重复。水面网格用 CDLOD / Clipmap 让近密远疏，避免多边形爆炸。浮力就是每帧问水面「我脚下 y 是多少」再施加上推与阻力；泡沫用 Jacobian（表面是否折叠）判据。

天空与昼夜：最贵的是实时全局光照

蓝天来自 Rayleigh 散射（短波蓝散得多），太阳晕来自 Mie 散射（大颗粒向前散射强）。体积云用 ray marching 真 3D 累积，能自投影。但完整昼夜循环最大的成本不是画天空，是每帧重算反弹光的实时全局光照：Lumen（UE5 实时 GI）在密集森林约 2.5~4.5 ms，而烘焙光照同场景 < 0.5 ms。所以很多游戏（如 Firewatch）宁可锁一个被精心打光的「黄金时刻」做视觉签名，而不是真做完整日夜——那不是偷懒，是艺术控制。

「空的恐惧」：地图大 ≠ 空

开放世界显空，不是因为面积大，而是因为玩家视线里没有值得走过去的东西。BotW 的「三角法则」：用三角状地形（山 / 丘）遮蔽视线，给玩家「翻还是绕」的选择，并让新目标在行进中才揭晓，形成无限发现的循环；再用「引力点」（神庙、塔、敌营）像磁铁一样把玩家吸过去。早期 BotW 用「点 + 线」导航测试，80% 玩家沿线性路径走、20% 乱逛，都没好好接触核心内容——改成地标吸引模型后才成功。

密度三把尺（来自 BotW 设计）

① 距离感：以京都实际步行感受定世界大小；② 密度感：以「遇见邮筒 / 便利店的频率」类比怪物 / 神庙密度；③ 间隔感：每处要素耗时——小迷宫 5~20 分、大迷宫 40 分、支线 20 分、主线 100 分。

08塞尔达 旷野之息：聪明的谎言 + 九宫格 + 化学引擎

塞尔达的答案是艺术家的：用一个约 10×8 km、手工雕出来而非程序化生成的小地图换密度；用「有限的聪明谎言」换自由度，而不是真实模拟。

两套引擎：物理 + 化学

GDC 2017《Change and Constant》里，技术总监堂田卓宏给出极漂亮的框架：动作游戏 = 碰撞 + 运动 + 状态。前两项叫物理，后一项叫化学。物理基于改动过的 Havok，但不用它做真实模拟——堂田称之为「贤い嘘（聪明的谎言）」：配上特效后视觉像真的，计算量小一个数量级。化学引擎把世界分两类：

元素
火 / 水 / 冰 / 电 / 风 —— 无固定形状，可改变别的东西
物质
树 / 石 / 武器 / 林克 —— 有形状，是「被改变」的对象
图 5 · 化学引擎的铁律：① 元素可改物质；② 元素可改元素；③ 物质不可改物质

第三条是灵魂——它把「组合爆炸」从 N² 砍成 N×M + M²。物质之间不互相影响，一棵树永远不必关心旁边另一棵树的状态。结果就是「可推演的规则」，玩家能自己预判、自己组合出无数解。堂田的原话是：希望玩家玩《旷野之息》时觉得自己是天才。

乘法式玩法与 120 座祠堂

塞尔达不做「有趣的交互」，做「会产生有趣交互的系统」——堂田叫它乘法式玩法（Multiplicative Gameplay）。结果是一个约 80 km²（datamine，常被误传成 827.8 km² 的京都参照面积）的小世界塞进 120 座祠堂，密度参考是「现实里便利店、邮筒的频率」。它感觉比 80 km² 大得多，靠的是地形起伏让表面积远超平面投影，以及「看得到就去得了」的设计胜利。

《王国之泪》：把「谎言」推到极致

GDC 2024《Tunes of the Kingdom》披露：TotK 废弃了「运动学刚体控制」（质量视为无限、容易互相打架），把所有物体改成物理驱动；质量 / 惯量由材质 / 尺寸 / 形状自动算出，而非手工赋值；连音效都是每个零件各自发声再合成。一句话总结它的取舍：兼容性 > 真实性。同一个世界观、同一套工具磨了 6 年才做出 TotK——任天堂的做法是先把地基磨到极致，再在同一地基上加层。

最反直觉的一条

BotW 的 Havok 是被特意关掉了一部分真实性的。如果真按教科书物理跑，玩家反而会失去自由度——因为真实物理往往只有唯一解；而「假物理 + 可推演规则」能给出无数解。做大世界最难的技术，常常不是技术，是管理：把需求做成世界里的一块告示牌、用颜色做进度视图、停工一周让 300 人亲自玩游戏。

09荒野大镖客2：把硬盘当内存 + 会呼吸的大气

Rockstar 用自研 RAGE 引擎的「实时流送 + 把硬盘当二级内存 + 距离分级 AI」三板斧，在 2013 年的 PS4 上硬塞进一个无加载画面、草木会动、马会自己停悬崖的活着的世界。

无读盘是怎么做到的

PS4 只有 8GB 共享内存、5400 转机械盘，不可能常驻整个约 75 km² 世界（社区估计，官方未公布）。RAGE 按玩家位置实时流送：只把附近城镇、NPC、地形完全载入，远处留低精度占位；硬盘被当成「二级内存」，纹理音频按需从盘读。一个反直觉的细节：RDR2 安装体积超 100GB、故意少压缩多冗余拷贝，正是为了让机械盘磁头更快找到数据、避免卡顿——「无缝」的代价就是磁盘占用。

RDR2 的天空不是贴图，是真的在体积里累积光。云用覆盖全图的 Cloud Map（多层密度）定义分布，沿视线 ray marching 累积散射；天空散射查 32×16×32 的 LUT；地图铺 32×32 的 3 阶球谐探针，每个覆盖 256m×256m 作环境光。所以风暴前地面泛起冷光、云被夕阳切片，都是物理算出来的——代价是贵，靠分帧、降分辨率、探针来省，目标所有平台 30fps。

马匹：3000 个动画拼出来的生命感（GDC 2021）

RDR2 不靠一段段过场动画，而是准备约 3000 个可拼接的小动画片段，按地形类型 / 速度 / 负重 / 情绪实时缝合。内部原则「Don't stop moving」让马减速时仍保持循环、像不想停；临近悬崖触发「stop matching」插入最佳刹车动画——悬崖由美术手工标记。Euphoria 动态动作合成再叠加被击 / 失衡的物理反应。马因此能对任何地形组合做出自然反应，而不是机械执行指令。

10艾尔登法环：水平大地图 + 垂直地下世界

FromSoftware 把魂系「箱庭」改造成「水平大地图 + 垂直分层地下世界」，用雾门 / 加载区 / 电梯竖井 / 传送棺连接一张连续的竖轴地图，以 30fps 锁帧换全平台稳定的超大无缝体验。

箱庭 vs 无缝：鱼与熊掌兼得

魂系（《恶魔之魂》《黑魂》《血源》）靠「垂直互联箱庭」营造密度与谜题感，但世界显得小。法环想做「大」又不丢魂味：把水平大地图（The Lands Between）作主舞台，保留 6 个 Legacy Dungeon（史东薇尔、魔法学院等）作封闭、带雾门、垂直秘密重的传统魂关，嵌在开放世界里。VICE 的分析点出：黑魂用「上下堆叠」假装大，法环干脆把世界做大，用 Torrent（灵感来自塞尔达）解决 traversable 问题。

引擎、内存与 30fps 锁帧

PC 端帧率被硬编码上限 60fps（变量 fFrameTick ≈ 1/60 写在进程内存，改配置文件无效），且物理与帧率强耦合——只解锁渲染会让移动 / 攻击 / 重力随帧率异常加速，需物理解耦。写死节拍让全平台行为一致、好调试，代价是高刷屏被浪费，且引擎线程调度古早，在 Intel 大小核上易卡。长会话里敌人 AI、粒子、流送资源不一定干净卸载，45~90 分钟后可能撞内存天花板冻结。

别被面积数字带跑

RDR2 与法环的 km² 数字都来自社区测量 / 估算，官方从未公布精确值。法环地表约 79 km²、含垂直层「可导航」超 120 km²，属社区数据挖掘，引用时标 [待核]。

11原神：Unity 深度改造 + 多端统一的卡通 PBR

原神是在 Unity 基础上做了深度定制改造的跨平台开放世界：一套「基于 PBR 的风格化（卡通）渲染」管线，配合分块流式加载和激进的分辨率 / LOD 缩放，让同一份内容在手机、PC、主机上都能跑出无缝、有昼夜天气的大世界。

为什么「用了 Unity」不等于「套壳」

米哈游技术总监易任重（Yi Zhenzhong）在 Unity 技术分享中明确说：团队在 Unity 上做了「深度开发」，手机和主机用不同的渲染管线但保持同一基调（基于 PBR 的风格化渲染）。PS4 上大量使用 compute shader，借 Async compute 隐藏开销。刻意「成熟技术优先、不过度炫技」——因为开发周期短。卡通渲染本身比写实 PBR 轻，配合 PBR 又能保证 24 小时光照循环下光影不翻车。

跑图不读条：分块流式加载

世界切成网格 Cell，只保留「玩家所在 + 周围预备区块」，远景用 impostor。根据玩家位置异步加载、卸载远处区块；社区文章提到「每帧最多加载 3 个 Cell、分帧执行」避免卡顿，并用 Job System 在后台线程解压、用「视野预测」按移动方向提前 1~2 秒加载。本质像图书馆——不把整馆书堆桌上，只摊开眼前几排，走过道时馆员提前递下一排。

移动端优化：把最贵的东西降分辨率

绝大多数安卓设备 3D 渲染长边不超过 1280 像素，半透明特效甚至只在半分辨率算。阴影用 8 级 CSM 级联（比通常 4 级更暴力），前 4 级每帧更新、后 4 级逐帧轮替，再用全屏 mask 只对半影区算软阴影，把 GPU 耗时从 2~2.6 ms 降到 1.3~1.7 ms（约降 35%）。代价是画面发虚、仍有上千 Draw Call 和严重 overdraw——移动端其实「优化得很苦」。

12盗贼之海：FFT 真海 + 确定性跨服迁移

Rare 在 Unreal Engine 4 上打造「共享世界」海盗游戏，最难的技术点是全程零加载画面——靠关卡流送 + 一套确定性模拟的服务器网格，让玩家在无缝海洋里航行、遭遇其他真人船队时，能在不被察觉的情况下被悄悄迁移到更热闹的海里。

为什么「全程零加载」是它最难的点

传统开放世界在区域间会黑屏读条。盗贼之海要让玩家从出港、航行、遭遇风暴、撞见敌船到沉没中间一次都不打断。世界切成 chunk：海、天空、岛屿、岛上物体分别管理；岛屿用 Level Streaming 按距离加载高模（所有平台同距离加载，避免不公平）；海洋是「无限」的，所以海本身不加载，而是程序化模拟实时生成。难点不在不黑屏，而在于任何一帧都不能因为突然要读一块地而卡住——流送必须永远领先视野。

海洋：FFT 电影级实时模拟

多数游戏用 Gerstner 波（几条正弦叠加，久看会露规律）。盗贼之海走的是 FFT Ocean（Tessendorf 2001，用于《泰坦尼克号》《加勒比海盗》）：不是手摆几个波，而是问「真实海洋里都有哪些尺度的波」，一次算出成百上千个波分量经 IFFT 合成高度场，GPU 每帧据此把海面网格捏出起伏。大涌浪慢、小涟漪快，波峰相遇叠加、波谷相遇抵消，永不重复。泡沫用 Jacobian 判据（表面折叠处即碎浪），反射用几何反射而非 SSR。

服务器权威：确定性模拟让迁移无察觉

14给你的选型清单与动手建议

假设你是个独立或小团队开发者，想做自己的开放世界。下面是按优先级排的清单。

第一优先：流送是地基，先做对

  • 用引擎现成的方案（UE5 World Partition / Unity Addressables + Additive Scene），别自己造轮子；
  • 明确区分加载半径与显示半径两个半径；边界留 hysteresis 缓冲，吸收相机抖动导致的反复加载；
  • Unity 记得利用 AsyncOperation.progress 在 0.9 时做转场，再激活；忘记 Release 是内存泄漏头号原因。

第二优先：地形与精度

  • 地形用 CDLOD / GeoClipmap 做连续 LOD，别让玩家看到裂缝和 pop；
  • 世界超过 ~20 km 就要认真考虑 LWC / Camera-relative；UE5 默认开 LWC，但老代码的 float 隐式转换会静默丢精度，重点查；
  • 别高估 SSD：卡顿大头常在实例化、GC、PSO，不是 IO。

第三优先：密度与引导

  • 程序化只填「之间」的荒野，Hero 场景和 POI 手工做；给每个 POI 实在收益，做面包屑引导；
  • 用三角地形遮蔽视线、用引力点吸玩家，弱化 UI 箭头；
  • 昼夜循环想清楚：真日夜 = 实时 GI（贵），不如锁一个精心打光的固定时刻做视觉签名。
小团队最该抄的一课

塞尔达的「做完之后走一遍，再做一遍再走一遍」——大地图的问题只有走过才能发现。哪怕没有 300 人停工一周的排场，自己多走几遍、录热力图、看哪些路没人走，比堆技术参数有用得多。

B思考题

合上页面之前，试着自己答一遍。

  1. 「加载」和「显示」为什么必须分成两个独立半径？如果只用一个半径会出什么问题？
  2. 塞尔达的化学引擎第三定律（物质不可改物质）砍掉了哪一类组合爆炸？如果去掉这条规定，开发成本会怎么变？
  3. 浮点精度在 21 km 处开始抖动的公式是什么？Origin Rebasing、Camera-relative、LWC 三者分别把「不准」藏到了哪里？
  4. 为什么 Nanite 不总是最快？草、小石这种极小实例为什么经典 HISM 反而更好？
  5. 盗贼之海的「确定性跨服迁移」靠什么保证玩家无察觉？如果两服务器用了不同 seed 会怎样？
  6. 艾尔登法环的地下世界为什么推断「与地表同 X/Z 坐标」？这个设计对遮挡剔除有什么好处？
  7. 假如你只有 3 人做开放世界，你会在哪三件事上押注？哪三件事敢用程序化？
写在最后

无限大世界从来不是「把地图做大」，而是「把玩家周围那一小圈做好，并让它在每一帧都无缝地换血」。五款游戏作答不同，但地基零件一模一样：流送、地形、剔除、精度、程序化、引导。技术会换代，这套零件不会——理解了它们，你再看任何一款开放世界，都能拆出它的零件清单。
