1

核心公式：大脑 + 眼睛 + 手脚第 1 章

整本书的骨架只有一个公式，也只有一个比喻：

Agent = LLM + 上下文 + 工具
🧠 LLM —— 大脑 理解 · 思考 · 规划 · 决策 预训练给知识，后训练给策略
👁 上下文 —— 眼睛 指令 · 记忆 · 知识 · 轨迹 它能看到的一切信息
🖐 工具 —— 手脚 感知 · 执行 · 协作 · 代码 它能把什么变成行动
三者缺一不可：没有眼睛是瞎猜，没有手脚是空谈，没有大脑是脚本

再往外看一层，Agent 和一个叫 Environment（环境）的东西构成闭环。搞清楚这个边界很重要，因为后面所有"权限、沙箱、验证"都长在这条线上：

一个反直觉但极其重要的推论

书里有一个很有力的判断：当模型固定时，提升 Agent 表现最有效的手段，往往不是换更强的模型，而是重新定义它的观察空间和动作空间。很多"看起来需要更聪明模型"的问题，其实只是接口问题——该看到的数据没进上下文，该做的操作没封成工具。

书里用两家产品的演进做了证据：Manus 把"深度调研、写代码、操控电脑"三条原本独立的路线合进一个 Agent，靠的是把三类观察/动作空间取并集；OpenClaw 再往外推一层，把用户日常在用的 WhatsApp、Telegram、Slack 等消息渠道和本地文件系统接进来，让分散在不同账号设备上的数据都能被同一个 Agent 处理。

对，但要注意代价

接口每扩大一圈，出错和攻击面也跟着扩大一圈。扩大必须按需进行，并配合权限控制和验证——这是第 4 章反复强调的主题。

三条被反复引用的工程原则

  1. 保持简单——从最简单的方案开始。直接的 API 调用优于复杂的框架，清晰的代码优于聪明的抽象。每多一层抽象，都是以后调试时的新盲区。
  2. 保持透明——明确显示规划步骤、执行日志和决策轨迹。黑箱里的错误，外部观察者既无法定位也无法纠正。
  3. 设计好工具接口（ACI）——从 Agent 的视角设计接口。核心思路叫 防呆（Poka-yoke）：像 SIM 卡的缺角让卡片只能从一个方向插入、微波炉门没关好就绝不加热。用设计让错误无法发生，而不是靠说明书提醒。

书里给出的决策顺序非常实用：先优化提示词 → 再考虑工作流 → 最后才引入自主 Agent。反过来做的典型反面例子是：一上来就设计一条六七步的多 Agent 流水线，每个部件单看都有道理，组合起来又低效又不可靠，因为执行拓扑是固定的，遇到例外只会继续加节点。

Manus 的取舍

"Less structure, more intelligence." —— 先给能力足够的 Agent 清晰的目标、必要的上下文和可组合的工具，用自然语言告诉它该怎么做；程序只固化那些必须始终成立的边界（权限、不得覆盖原始材料、原子发布）。好的结构不是替 Agent 预演全部思考，而是守住边界，把边界内的决策空间还给模型。

这是全书安全讨论的总骨架。注意它的排序逻辑——不是按处理先后，而是按被绕过的难度：越靠下的层越不依赖模型自己的判断。

4

上下文工程：决定能力上限的"眼睛"第 2 章

书里给了一个特别贴切的类比：你招来一位天才工程师，理论功底深厚、编程能力卓越，但对你们的产品架构、业务逻辑、技术债务、团队规范一无所知，而且关键决策散落在不同人的记忆里、代码库没有文档——这位天才再聪明也难发挥价值。

模型就是这样。所以第 2 章的核心命题是：Agent 的能力上限，不是模型参数量决定的，而是它在每个决策点"看到了什么"决定的。上下文工程就是系统性地设计、组织、压缩这份"视野"。

4.1 为什么要"KV Cache 友好"：一个真实事故

先看一个故事：某客服 Agent 每天处理 10 万次对话，一切正常。某天工程师为了让 Agent"知道"当前时间，在系统提示词里加了一行 Current time: {{now}}。第二天告警——首 token 延迟从 0.5 秒涨到 3–5 秒，月度推理账单几乎翻倍。代码没问题，模型也没换。

原因：模型每生成一个 token 都要回头看前文所有 token（注意力机制）。如果每轮都从头算，开销随长度平方级增长。KV Cache 的做法是把前文的中间计算结果缓存下来，下一轮只算新增部分。而大模型是几十上百层 Transformer 串联的，改动点越靠前，需要重算和计费的 token 越多——系统提示词在最前面，所以插入一行时间戳，等于后面几乎全部重算。

三条不读原理也必须记住的结论

  1. 系统提示词和工具定义一旦确定就别改。哪怕多一个空格，都可能让首个不同 token 及其后的缓存无法复用。
  2. 动态信息永远追加到末尾。时间戳、用户状态这些变化内容，作为新消息追加，而不是回头修改系统提示词。
  3. 用标准 API 格式，不要自己拼消息。自己拼 "USER: … ASSISTANT: …" 的根本问题是偏离了模型训练时见过的格式，会削弱它的多步思考能力。

书里给出一个量级：Anthropic、DeepSeek、GPT-5 等的缓存读取成本约为首次计算的十分之一。当这个差距足够大时，缓存一致性会反过来主导架构选择——Claude Code 就把系统提示词按缓存边界切成两半：边界之前跨用户跨会话全局缓存，边界之后才放用户/会话特定信息。缓存经济性不是事后优化，而是前置约束。

层次 4 的真实案例：为什么"模糊规则"会出事

一个替用户打电话谈账单的 Agent，产品诉求是"办不成就退款"（让人愿意尝试）+ 防止薅羊毛。于是设计三种计费：按省钱提成、按服务收小费、困难任务预收款不退。

问题来了："帮我退掉上个月买的衣服"是"帮用户省钱"还是"取回本属于他的钱"？"取消 Netflix 订阅"算省钱吗？同样的任务在不同时间可能得到完全不同的分类。书里给出的细化方式是：把提成严格限定为"通过谈判降低现有账单"，退款与取消服务只能用固定费用；成功率按固定流程分步评估，高于 60% 用可退款模式、低于 30% 直接拒绝；金额粒度写死（每分钟 0.05 美元，四舍五入到整数美元），并且明确"节省"只基于现有账单——否则模型会想："不砍价明年涨到 180，我帮他维持 150 就省了 30。"

设计哲学

LLM 的优势在于遵循复杂指令和从长上下文提取信息，但不应该在业务规则制定上被赋予过多自由裁量权。优秀 Agent 公司里，提示词一般由产品经理基于线上数据与用户反馈来设计。

4.3 提示注入：Agent 时代最危险的攻击

普通聊天机器人被攻击，最坏是输出不当内容。但 Agent 有工具调用能力——被注入的指令可能导致删除文件、发送邮件、泄露隐私，且不可逆。而且每一个感知工具都是潜在的注入入口：网页的不可见元素、PDF 元数据，甚至连图片的 EXIF 信息都能藏指令。

两个容易被忽略的新注入面

1. Skill 本身也是一种注入面。Skill 的本质是"把外部内容当作指令加载"的制度化形式——第三方 Skill 里藏的恶意指令，效果比网页隐藏文本更直接。安装来源不明的 Skill 前必须审查内容，如同审查将要执行的代码。
2. Agent 状态栏同理。状态栏信息被模型高度信任，一旦它的内容来自可被外部污染的数据源（比如把网页片段直接写进状态栏），这种信任就会被反向利用。

4.5 上下文压缩：什么时候压、怎么压、为什么"隔离"更好

先分清三个概念：上下文腐化（窗口没满，但无关内容太多导致模型找不到关键信息）、上下文溢出（真装不下了）、上下文焦虑（模型觉得窗口快用完，任务没完成就提前收尾）。压缩要对付的是前两个，而第三个要靠明确的"还剩多少预算"来安抚。

书里还有个反直觉的发现：上下文学习更像"检索"而不是"推理"——模型不是把上下文里所有内容都推理一遍，而是像查资料一样去取。这解释了为什么"塞得越多越好"是错的。

隔离优于压缩
压缩 把臃肿记录蒸馏成结论 但摘要本身会丢信息，且要花 LLM 成本
隔离 让大体积中间信息根本不进主上下文 派个子 Agent 去翻档案室，只带结论回来
书里的原则：能隔离就不要压缩；压缩要分层、要保留原文可回溯、要用当前查询意图来指导摘要

第 2 章的视野是"一次会话"。当它扩展到跨会话、跨用户，就有了两条线：用户记忆（记住一个人）和知识库（记住一个领域）。两者共用同一套检索底层技术。

5.2 RAG：让 Agent"开卷考试"

RAG（检索增强生成）解决的是模型不知道的东西：训练截止后的信息、私有领域知识。流程是一条管道：

① 分块
↓
② 嵌入
↓
③ 混合检索
↓
④ 融合重排
↓

"开卷考试"——先翻资料，再答题

为什么要"两路都跑"

稠密嵌入 Dense稀疏嵌入 Sparse / BM25
原理把文本映射成每个维度都有值的向量，语义近则向量近极高维向量，绝大多数维度为 0，只有出现的词对应维度非零
优势能理解"意思"，换个说法也找得到精确匹配关键词、型号、专有名词很准
弱点对罕见专有名词、编号容易失手不懂同义词；词频要饱和、长文要归一化
类比给每个词在地图上标个坐标一张超长的勾选表，只勾中出现的词

两路结果怎么合并？书里介绍了 RRF（倒数排名融合）——不看原始得分，只看名次：得分 = Σ 1/(k + rank)，k 常取 60。这个"不看分数看名次"的思路很重要，因为稠密和稀疏的分数根本不在一个量纲上。

之后再上神经重排序：用跨编码器（Cross-Encoder，把查询和文档拼在一起逐词比对，慢但准）对融合后的前 N 个候选精排。书里用的比喻很形象——双编码器像猎头按简历关键字快速筛，跨编码器像面试官和人选面对面深谈。

知识怎么组织：从"扁平文本"往上走

  • 结构化索引：RAPTOR 自下而上递归抽象——叶子文本块 → 聚类 → 摘要父节点 → 递归到根，形成一棵树，既能查细节也能查总览
  • 图谱：GraphRAG 把知识建成实体—关系—实体三元组，支持多跳推理和实体消歧
  • 文件系统范式：把记忆/资源/技能映射成虚拟目录与 URI，用 L0/L1/L2 三层（约 100 tokens 摘要 / 约 2000 tokens 概览 / 全文）按需加载
  • 智能体化 RAG（Agentic RAG）：把检索变成 Agent 可以随时调用的工具，用 ReAct 循环反复检索——不是搜一次就写报告，而是像研究员那样反复查资料
  • 上下文感知检索：索引前先用 LLM 给每个文本块生成一段"上下文前缀"（这段摘自哪份文件哪一章），再拼接索引——相当于给每张卡片贴上出处标签
最终收敛成的架构：双层记忆

常驻上下文的结构化概览（要点卡）+ 按需检索的细节（档案室）。书里还提到一个记忆框架的演进很有意思：Mem0 v2 在写入时就做消歧，v3 改成"只追加 + 检索时融合排序"——从"当场改"变成"先都记下、查的时候再判断"，这正好呼应了全书的"只增不改"原则。

6.1 五类工具

6.2 能力该做成什么形态：专用工具 / 通用执行器 / Skill

同一件事（比如"部署应用"），可以做成一个 deploy_app 专用工具，可以拆成三个细粒度工具，也可以干脆不做工具、只写一份 Skill 文档让 Agent 用 bash 逐步执行。选哪种形态，决定了每条能力常驻多少 token、参数怎么传、谁能改。

默认取向：通用工具优于专用工具——一个 Python 解释器可以替代数十个特定功能工具

但通用并不总是更好。书里给的退回专用工具的四种情况：安全/权限/审计（生产数据库写操作需要精细授权与留痕）、屏蔽平台差异并给出更好反馈（Mac/Windows/Linux 的 grep 语法不同，专门工具能给清晰的行号）、使用频率极高、参数结构复杂（嵌套对象、多字段联合校验）。

一个容易被忽视的对比

专用工具用 JSON schema 规定输入输出，便于模型遵循、生成合法参数并解析；Skill 完全用自然语言描述，模型要自己生成合法的命令行参数、还要处理引号转义——转义规则比 JSON 复杂得多，而且三个系统各不相同。所以 Skill 对模型要求更高，参数复杂时更容易出错。
反过来，Skill 对人类编写者更友好：不会因为一处语法错误就让整个 Agent 跑不起来。

6.3 工具描述的艺术（本章最值得反复咀嚼的一节）

大多数人写工具描述只写"这个工具能干什么"，而真正决定成败的是"什么时候该用"和"什么时候不该用"。

要点❌ 差✓ 好
写"何时用"而非"能做什么""搜索相关内容""当需要获取实时信息或查找未知事实时使用"
边界比能力更重要只说能按文件名匹配明确说明"不能搜索文件内容"——大多数调用失败不是模型不知道工具能做什么，而是不知道它不能做什么
用具体例子代替抽象规范"timestamp：RFC3339 格式""RFC3339 格式，例如 2024-03-15T14:30:00Z"
描述返回值 + 标注执行代价只写参数"返回 JSON 数组，含 title/url/snippet"；"此工具需下载完整网页，可能 5–10 秒，只要元信息请用 get_page_metadata"

为什么例子这么关键？模型在专注处理一个问题时能理解这些术语，但在执行复杂任务时——要同时处理多个工具、从历史轨迹里提取信息、权衡多个决策——只能分出一小部分注意力去确认参数格式。具体例子让它可以照搬，省掉一次推理。

72% → 90%
给每个工具附上 1–5 个真实调用示例后，工具调用准确率在一些基准上的典型提升（书中注明具体数值因任务而异）
最实用的一条调试原则

当 Agent 频繁选错工具时，先检查工具描述，而不是怀疑模型能力。大多数工具选择错误的根因是描述不准确。修正描述的投入产出比，通常远高于换一个更强的模型。
类比：你招了个聪明的实习生，他总是做错事——多数时候不是他笨，是你没告诉他"投诉金额超过 5000 就别自己处理，转给主管"。

附：参数保真性——一种比功能缺失更隐蔽的 bug

书里给了两个真实案例，都很值得警惕：

  • 静默输入转换：某版本编辑工具的参数传递层，把中文弯引号（""）静默转成了英文直引号（"）。于是模型看到的是弯引号、传进去的也是弯引号，但实际比对时变成了直引号 → 匹配失败 → 模型反复尝试、反复失败，它无法理解为什么工具找不到自己明明看到的内容。
  • 静默参数注入：某 IDE 的 bash 工具在执行所有 git commit 时自动附加一个额外参数。如果用户的 Git 版本较旧不支持该参数，就会报错——模型无论怎么改提交信息措辞都会失败。

由此提炼出一条基本原则：模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差。如果确实需要规范化输入，必须在描述里说明、并在返回中明确告知模型。

6.5 安全：执行工具的四道防线

书里给的最重要的提醒之一是：venv 不是沙盒。Python 虚拟环境只隔离包依赖，对文件系统、网络、进程毫无约束——换了工具箱，但没锁门。

另外两个概念也值得记住：幂等性（同一操作执行一次与执行多次，对外界影响完全相同——电梯按钮按一次和按十次都只来一趟）、致命三要素（Simon Willison 提出：能访问私有数据 + 暴露于不受信任内容 + 具备外部通信能力；三者齐备，数据外泄只是时间问题）。书里还补充了第四要素：持久记忆——恶意指令写进长期记忆后可以跨会话潜伏，不是多了一把钥匙，而是把钥匙藏在了枕头底下。

7.1 为什么"让代码来编排工具调用"能省两个数量级

传统方式是"一次调用一个工具，每个中间结果都搬进上下文"。更好的方式是让模型一次性生成一段脚本，把中间变量留在执行环境里，只有最终结果返回模型。

书里的类比

传统方式就像你每做完一步都要写一封邮件汇报给领导，领导读完再回信告诉你下一步做什么——这些来回的邮件就是 token 消耗。代码编排则像领导一次性写好完整的操作手册，你照着做就行，只在全部完成后汇报最终结果。
效果：抓取多个网页再批量提取字段时，页面全文只存在于执行环境的变量中，返回上下文的只有汇总结果，token 消耗可降低约两个数量级。

7.3 提议者—审核者：解决"Agent 过早认为任务完成"

这是全书的明星模式，也是作者说"早在 loop engineering 概念流行之前，我们就在用"的方法。它成立的前提是：自审不可靠。

退回时必须给出可定位的修复条件；审核者不能修改测试、证据采集器或发布门槛
为什么必须两个 Agent 而不是一个？

单 Agent 做的话，渲染图 × N 轮会让上下文爆炸（1080p 截图 = 数千 token × 14 页 × 5 轮）。双 Agent 时：Reviewer 只看当前版本，Proposer 只累积文本反馈，两边上下文都干净。
而且 Reviewer 的价值不在于"用同一个模型再看一遍代码"，而在于它渲染了 PPT 并截取了画面——截图承载着提议者生成代码时完全无法获得的视觉信息。这就是书里反复强调的"审核者必须读取独立证据"。

书里还提到这一模式的只读变体 Sidecar：与主模型并行运行的轻量级 LLM 旁路，对单次工具调用做安全门控——像摩托旁挂的边车，独立运行但跟着你跑。

7.4 错误恢复：最能拉开工程差距的一块

  • 警惕"死亡螺旋"：错误处理逻辑本身又调用 LLM、再次出错引发的连锁反应——灭火器自己着火了
  • 看门狗（watchdog timer）：超过设定时间没有新输出就判定卡死。书里的类比很好——"水管断了会立刻知道，水管不出水也得有人盯着"
  • 中立轨迹格式：轨迹不要按某家厂商的接口格式存储，思考要拆成"可移植文字 + 不可移植凭证"，否则换模型接力时直接报错

关于最后一点，书里有一段很有价值的提醒：各家对"历史思维链要不要回传"的策略差异很大。DeepSeek R1 官方做法是剥离全部历史思考（因为训练时历史 CoT 从不出现在输入里），但这对 Agent 有缺陷——中间思考承载着"为什么调这个工具、排除了哪些假设"，剥离后模型每轮从零推理。而 DeepSeek V4 彻底反转：只要请求带 tools 参数，每条 assistant 消息都必须原样回传 reasoning_content，否则 API 直接 400 报错；Kimi K2、GLM-5 采用同样协议。

书里还讨论了一个容易混淆的点：不能仅凭代码用了 asyncio 就认定模型具备原生异步能力——前者是"运行时在安排节奏"，后者是"模型理解等待与中途变化"。截至 2026 年 9 月，GPT-6 Astra 已提供原生异步工具调用与回合中途引导：查询会议场地时可以继续整理议程，用户中途说"预算减少了"，系统保留已完成的工作、把新约束带入后续处理。

8.3 Computer Use：让 AI 坐在你的椅子上用电脑

三个关键问题：动作空间怎么设计（鼠标、键盘、滚动、截图、等待、bash……）、怎么在截图上找到要点的位置（视觉定位 Grounding）、怎么把连续观察变成离散事件。

另一个工程细节是坐标双向缩放：截图缩小到模型训练分辨率送入，模型输出坐标再按比例放大回真实分辨率——在小地图上量距离，再换算到真实地图。书里还提到 AOI（Agent–Computer Observation Interface）：给 Agent 配一个"只在有变化时眨眼"的眼睛和一只耳朵（关键帧截图 + 音量门控语音转写 + 画面文字描述）。

8.4 机器人：VLA 与世界模型

书里以 XLeRobot 整理桌面为例讲了三层结构：长程规划与任务分解（LLM 做）→ VLA 控制（视觉—语言—动作模型，接收画面 + 技能指令输出动作）→ 世界模型（预测"当前状态 + 候选动作 → 下一状态"，用于比较候选动作的后果）。

有一个工程上很实用的技巧叫动作分块（Action Chunking）：模型一次生成一小段未来动作，控制线程高频回放——把推理延迟藏在执行时间里，像提前写好 25 个八拍的舞步，身体按节奏跳。

评估：为什么"跑通一次"不算数第 7 章

构建完成不等于构建正确。没有评估，你无法判断一次改动带来的提升究竟源于设计本身，还是仅仅来自随机波动。这一章是全书最"硬"的一章，也是最容易被跳过、但最影响实战的。

9.1 先看这条最简单的判断口径

假设你的 Agent 单次成功率是 90%，看起来相当高了。跑 5 次会怎样？

Pass@5 vs Pass^5（单次成功率 p = 0.9）
Pass@5 · 5 次里至少成功 1 次
99.999%
"能力上限"——这件事原则上做不做得到
Pass^5 · 连续 5 次每次都成功
59%
"业务可靠性"——能否稳定可靠地交付
公式：Pass@k = 1 − (1−p)k ；Pass^k = pk
请把这段话读两遍

单次成功率做到 90%，连续 5 次不出错的概率也只有约 59%。如果这是一个每天跑 5 笔的退款流程，平均差不多每两天就会出一次错。这就是为什么"我试了一次，通了"完全不能说明系统可用。

书里还有一个更极端的例子（p = 0.6，k = 5）：Pass@5 ≈ 99%，看起来很美好；Pass^5 ≈ 7.8%——一个"十次能成六次"的 Agent，给它五次机会几乎必然能成一次，但要它连着五次都别出错，概率不到 8%。

指标含义适用场景
Pass@kk 次中至少一次通过 = 能力上限科研发现、漏洞挖掘、开放式创作（人类可以从 k 条候选里挑最好的）
Best@kk 次中取最好的一次得分（连续分数时）同上
Pass^k连续 k 次每次都必须通过，且不触发安全/合规/幻觉等一票否决项支付、退款、权限变更、生产部署
Pass@1单次平均成功率日常最常用的口径
报告口径必须写清

k 次尝试是"同一任务的 k 次独立采样"，还是"生产流水线上连续 k 个任务"？对于会产生副作用的操作，不能简单地"重试直到成功"，而应在沙盒或可回滚环境中采样，并把每一次失败都记入可靠性指标。

9.2 什么算"技术奇观"

书里用了一个很精准的词：当前许多 Agent 仍处在技术奇观阶段——在大量尝试、充足时间和人工筛选下展示能力上限，只要其中一次成功，就足以证明"这件事原则上做得到"。早期 Manus 和 OpenClaw 完成复杂任务的成功率并不高、token 成本也很高，但因为框架通用、Pass@k 高，在社交网络上被大量分享，这些"技术奇观"正是它们成功的关键。

这不是贬义。Anthropic 讨论长时运行 Agent 时举的例子就是这样：让 Agent 自主工作一周从头写出一个 C 编译器、持续探索直到找到某个数学猜想的反例、反复审查开源软件发现已存在几十年的重大安全漏洞——展示的通常不是"每次都做对"，而是把探索预算拉长后终于出现一条突破性轨迹。

9.5 失败归因：找第一案发现场

评估的价值不在打分，而在知道该改哪里。所以书里强调：归因对象是"轨迹中首个导致偏离的错误"，因为后续错误多是连锁反应——第一次走错路口才是根因，后面绕远是后果。

另外两种回归任务值得记住：端到端回归任务（从初始状态跑完整任务，检查最终状态/输出/安全条件——每次发版跑一遍全流程冒烟测试）和轨迹前缀回归任务（冻结已有上下文与状态，只让 Agent 输出下一步或下几步动作）。后者的答案不是唯一正确解，而是"哪些动作可接受 + 哪些禁止"——"先问清楚再做"和"先查规则再做"都算对，直接删库算错。这种回归便宜得多，也能隔离问题。

9.6 从外部评估到内部评估

书里最后一节讲生产级评估基础设施，三个概念特别实用：

  • 消融基础设施：内置总开关，可一键禁用多个主要特性，创造"裸模型"基线，量化每个特性的真实贡献——拆掉汽车零件再跑一圈，看少了谁真的不行。
  • 双层特性开关：编译时 + 运行时两层，用于实验、渐进发布、紧急熔断——配电箱里的总闸。
  • 机制指标 vs 目标指标：你直接改变的东西（缩短计划文件）vs 你真正关心的东西（降低会话成本）。A/B 测试必须以目标指标为准。

书里提醒：不要只看排行榜。除了准确率、价格、速度，还要考虑三个容易被忽略的维度——策略边界（模型在基准上具备某种能力，不代表承载它的产品允许你调用；同一任务在聊天产品、Coding Agent 和 API 中可能结果不同）、输出速度（Agent 往往需要 20 轮推理，每轮慢 2 秒就意味着总共多等 40 秒）、多模态能力。另外，绝大多数 Agent 需要支持思考（Reasoning）的模型。

后训练：模型是怎么"学会干活"的第 8 章

这一章偏技术，但它的判断框架对做产品的人也极有用——因为它回答了"我该用哪一招"，而不是"哪个算法更炫"。

先记住一句贯穿全章的话：模型的输出本质上是一个概率分布。所谓"训练"，归根结底就是调整这个概率分布——让想要的 token 概率更高、不想要的更低。四个环节的区别，只在于"想要什么"，以及"用什么信号来定义想要"。

10.2 SFT 与 RL 的本质区别（全书主线之一）

一句话

SFT 拟合的是"答案长什么样"，RL 拟合的是"什么才算赢"。

更深的区别在于它们在概率分布上做的事完全不同。一个问题往往存在多类合理回答，每一类都对应分布中的一个"峰"：

mass-covering vs mode-seeking
SFT = 覆盖式
把菜谱上所有变体都背下来
客人点哪道都能做
RL = 寻峰式
反复琢磨哪道菜回头客最多
然后把精力集中在那几道上
最终是保持多样性还是收缩到少数模式，取决于示范分布、奖励函数、KL 方向与系数、熵正则和采样温度——不是由算法名字单独决定的
必须讲清适用边界（原书特意自我限定）

"SFT 记忆、RL 泛化"是特定实验条件下测得的对照实验结论，不是 SFT/RL 的普遍属性。数据足够多样、正则化得当时 SFT 也能泛化；奖励或环境有偏时 RL 同样会过拟合。
真正的差别在于：RL 能评估示范之外的候选行为——而这些候选，SFT 的数据集里永远看不到。

持续进化：经验该往哪放第 9 章

书里开头就抛出一个尖锐的悖论：今天的 Agent 可以零样本解决从未见过的复杂任务，却可能在处理了一万次相似任务之后，第二天仍然犯下第一天的错误。

为什么不让它每次任务后自己学？因为生产环境很少提供干净的学习信号：用户满意不意味着合规；局部参数更新可能造成能力遗忘、策略漂移或安全退化；若允许模型依据未经验证的反馈直接改自身参数，错误经验和提示注入就可能被固化，并在后续任务中持续放大。

本章最重要的一个辨析

保存经历 ≠ 从经历中学习。把一百条轨迹放进长上下文或向量库，可以帮助模型在需要时找回某个案例，却不会自动完成跨案例比较——哪些步骤在成功轨迹中反复出现，哪些做法只在旧版接口上有效，某次成功究竟来自正确策略还是环境偶然。
学习发生在系统主动完成"评价、对照、归纳、验证"之后，而不是发生在日志写入磁盘的那一刻。

还有一组对照必须记住：第 3 章的用户记忆沉淀的是"用户与世界是什么样的"；本章的经验学习要沉淀"在什么条件下应该怎样行动"。前者让 Agent 记得更多，后者才让它从聪明变得熟练。

一句话验收标准：只有改变后续行为且通过验证的更新，才构成持续进化。

12.4 跨组织协作：A2A 协议

以上都假设所有 Agent 由同一团队开发、运行在同一系统内。当协作跨越组织边界时，就需要标准化的互操作协议——A2A 之于 Agent，就是网络协议之于进程。

  • Agent Card：描述能力的元数据文档（能做什么、支持哪些输入输出模态、如何认证）—— Agent 的"名片"
  • 任务生命周期：已提交 → 进行中 → 需要输入 → 已完成 → 失败的状态机，原生支持长时间运行和流式进度
  • 不透明协作：Agent 之间只交换任务与产物，不暴露内部提示词、思考过程和工具实现
MCP 与 A2A 的分工

MCP 解决 Agent 与工具之间的互操作，A2A 解决 Agent 与 Agent 之间的互操作。同一团队内部的多 Agent 系统直接用消息总线即可，只有当协作方互不信任、实现互不可见时，才需要 A2A 这样的公开协议。

12.5 Agent 社会：一个很好玩的观察窗口

书里最后一节把视角拉远：当 Agent 数量从几个扩展到成百上千、交互足够自由时会涌现什么？三个维度很有意思：社交涌现（斯坦福 AI 小镇、十年尺度的长期生活模拟、Agent 自己的社交网络）、经济涌现（虚拟市场竞争、Agent 之间互相雇佣、甚至雇真人）、策略博弈（信息不对称下的狼人杀）。

其中一个实验结论特别耐人寻味：移除所有直接通信后，逐利的 Agent 仍会通过公开报价板来达成价格合谋。

结语：两朵乌云与一条飞轮后记

书的后记借了开尔文 1900 年的比喻：当年物理学晴朗的天空上飘着两朵乌云，后来一朵变成了相对论，另一朵变成了量子力学。今天 Agent 的天空同样称不上晴朗。

作者看到的两朵乌云
第一朵：实时交互 今天绝大多数 Agent 仍是按轮次的"请求—应答"模式——你说完一句，它想一整段，再一次性吐出结果。但真实世界不会停下来等它想完。 两条路并行推进：架构上做快慢分离（前台快模型维持节奏、后台慢模型深度思考）；把推理本身做快（当 decode 足够快，按轮次的等待就短到近乎消失）
第二朵：持续学习 今天的模型更像一个记性极好、却学不会新东西的天才：训练时把人类知识背得滚瓜烂熟，上岗后却几乎不再成长。 争论在"小世界假设"（足够大的模型一次学够）与"大世界假设"（属于某个具体用户、某家具体公司的知识不在任何训练语料里，只能上岗后持续学）之间
书里的结论：模型最强的能力，终将不是记住，而是学习与适应

B. 动手清单：从今天就能做起的 15 件事

  1. 先确定静态前缀再动工。系统提示词和工具定义定下来就不轻易改，动态信息一律追加到末尾。
  2. 给上下文加"预算感"。告诉模型还剩多少窗口/预算，避免它因为"快满了"而提前收尾。
  3. 给工具描述补三样东西：什么时候用、什么时候不该用（反例）、一个真实的参数示例。
  4. Agent 选错工具时，先改描述，别急着换模型。
  5. 检查工具的"静默行为"。有没有偷偷改参数、偷偷加参数、偷偷截断输出？有就显式写出来。
  6. 感知工具要"克制地看"：支持 offset/limit、分页或游标，截断时明确标注"已显示 1–200 行，共 5000 行"。
  7. 通用工具优先，但高风险操作退回专用工具（支付、删除、发邮件、生产部署），配权限、预览和人工确认。
  8. 把外部内容用显式标记包裹（如 <external_content source="webpage">），并禁止自拼消息格式。
  9. 给工具分级风险，高风险操作必须由上下文之外的机制复核（独立进程/最小权限/沙盒/人在回路）。
  10. 用提议者—审核者替换"自己检查自己"：审核者只看产物和独立证据，不看产出方的推理过程。
  11. 建立三层验证器：先有结果验证器（最优先），再加过程验证器，最后才上 LLM 评委。
  12. 改用 Pass^k 口径评估有副作用的流程，并在报告里写清 k 次尝试的口径（独立采样 vs 连续任务）。
  13. 失败归因找"首个错误"，而不是最后一处痕迹。给验证器配"证据不足时拒绝评分"的开关。
  14. 经验分流四问：能写成事实吗（知识）？能说清判断原则吗（Skill）？能确定性执行吗（程序）？都不能才考虑训练（参数）。
  15. 每次更新都带边界集 + 保留集：既看失败的那类任务是否改善，也看本来能做的任务有没有退化。

C. 精选思考题（来自原书，不设标准答案）

Q1. 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——你会选哪个？在什么条件下你的选择会改变？
Q2. "模型即 Agent"意味着模型在工具调用决策上越来越自主。但本书论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？
Q3. 消融实验里"工具结果缺失"会让 Agent 反复重试直到耗尽迭代预算。生产环境中还有哪些情况会这样？你会设计怎样的检测和终止机制？
Q4. 如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 delete_file 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？
Q5. 人工干预机制要求 Agent 能"优雅地移交控制"。但用户可能不在线、响应很慢、或者给出模糊指令。此时 Agent 应该怎么办？
