00先想清楚：你要的不是聪明，是可读

一句话：Boss AI 的第一评价标准不是「它多聪明」，而是「玩家能不能看懂它」。这一条会决定你后面所有架构选择。

先破除一个最常见的误解。很多开发者一上手就想给 Boss 装「智能」——让它预判玩家、绕后包抄、根据血量动态调整策略。结果做出来的 Boss 不是难，是烦。

这里有一个很反直觉的结论：玩家对 Boss 的挫败感，绝大部分不来自「打不过」，而来自「不知道为什么挨打」。

一个攻击前摇只有 3 帧、没有特效提示、伤害判定框还比视觉模型大一圈的招式，玩家会骂「这游戏有病」。同样难度的招式，只要把前摇拉到 15 帧、加一道白光、把判定框收进模型里，玩家死了会说「我贪刀了」——这是完全不同的两种情绪。

最该记住的一条

AI 架构的选择，本质上是在回答一个问题：这套逻辑，能不能被人看懂、能不能被人改。「人」既包括玩家（看得懂行为），也包括三个月后回来改数据的你自己（看得懂代码）。所有架构争论的答案都在这一条里。

Boss 和杂兵，根本不是同一个问题

杂兵 AI 的目标是「制造压力」，它可以是廉价的、可替换的、允许有 bug 的——反正玩家两刀砍死就走了。

Boss AI 完全不同。它有三个杂兵没有的硬约束：

约束一
要被反复看几百次
一个杂兵的动作玩家可能只看到 10 秒。一个卡关的 Boss，玩家会盯着它重复 20 分钟。任何「有点怪」的细节都会被放大 100 倍。
约束二
必须可以被学习
Boss 的乐趣在于「模式识别 → 掌握 → 通关」。如果你的 AI 随机到无法预测，玩家学不到任何东西，剩下的只是运气。
约束三
要撑起一段叙事
Boss 是关卡的高潮，它的行为要有「性格」：狂暴的战士不该用优雅的法师蓄力。AI 结构必须能承载这种表达。
图 0-1 · Boss AI 与杂兵 AI 的三个本质差别

这三条约束，会直接推导出后面所有技术选型：

  • 因为要被反复看——所以需要能精确控制时序的架构，不能靠「大概差不多」的权重调参。
  • 因为要可以被学——所以随机性必须是「有序中的无序」（这点第 14 节展开）。
  • 因为要撑叙事——所以需要「阶段」这种结构性概念，而不是一条平铺的状态链。

先给结论，免得你读到最后才发现

绝大多数独立游戏和中小团队的动作游戏，正确的答案既不是纯 FSM 也不是纯行为树，而是「行为树做决策 + 状态机做表现」的混合架构。第 10 节会把这条讲透，但你现在就可以知道靶子在哪。

01有限状态机：一个 Boss 同时只能做一件事

一句话：FSM 的全部思想就是「此刻我只能是其中之一」。这个约束看起来是限制，其实是它最大的价值。

它要解决的问题

不用 FSM 写 AI，代码会长这样：

// 一个没有状态机的敌人 —— 一开始能跑，三天后变成噩梦
void Update() {
    float dist = Vector2.Distance(transform.position, player.position);
    if (dist < 2f && attackCooldown <= 0) { Attack(); }
    if (dist < 8f) { MoveToward(player.position); }
    if (dist > 12f) { Patrol(); }
    if (isHurt) { Knockback(); }
    // ... 后来有人加了「狂暴」，有人加了「召唤」，有人加了「破防」
}

这段代码有三个致命问题，而且会随着需求增加越来越糟：

  1. 没有互斥：Attack() 和 MoveToward() 可能在同一帧都执行。Boss 会边后退边挥刀。
  2. 没有进出的概念：攻击结束要关掉判定框、要重置计时器。放在哪？没人知道，最后散落在各个 if 里。
  3. 条件会互相打架：玩家在 1.9 距离时进入攻击，后退到 2.1 又变回追击，来回抖动。

FSM 用一句话把这些全解决了：把每一段「互斥的行为」包装成一个状态，同一时刻只允许一个状态活着，并且每个状态都有明确的进入和退出口。

关键的思维转变

从「每帧检查所有条件该做什么」转成「我现在是什么状态，以及什么条件下我要换到别的状态」。前者是散的条件堆，后者是一张有向图。图能画出来，就能讨论、能改、能评审。

状态机的三件套

1
状态接口 —— 定义 Enter / Tick / Exit 三个入口。它规定了「每个状态必须自己负责收拾自己的场面」。
2
具体状态类 —— 每个状态一个类：IdleState、ChaseState、AttackState、StaggerState。逻辑各自独立，互不污染。
3
状态机控制器 —— 持有当前状态，负责切换、负责 Tick，是唯一有权改状态的地方。

最小可用的 C# 实现

先看接口和状态机本体。注意 ChangeState 里那个「先 Exit 再 Enter」的顺序——这是 FSM 最重要的三行代码：

public interface IBossState {
    void Enter();
    void Tick(float dt);      // 先这么叫：需要时再换成 FixedTick
    void Exit();
}

public class StateMachine {
    public IBossState Current { get; private set; }

    public void Initialize(IBossState initial) {
        Current = initial;
        Current.Enter();
    }

    public void ChangeState(IBossState next) {
        if (next == null || next == Current) return;  // 幂等，防抖动
        Current.Exit();          // ← 收场：关判定框、停音效、清计时器
        Current = next;
        Current.Enter();         // ← 登场：播动画、开判定框、设朝向
    }

    public void Tick(float dt) => Current?.Tick(dt);
}

然后是具体状态。这里用 Boss 的「攻击」状态举例，注意它是怎么在 Exit 里把攻击判定框关掉的：

public class AttackState : IBossState {
    private readonly Boss boss;
    private float timer;

    public AttackState(Boss boss) { this.boss = boss; }

    public void Enter() {
        timer = 0f;
        boss.animator.SetTrigger("Attack");   // 动画交接放在 Enter，不要放 Tick
        boss.StopMoving();                       // 攻击时锁定位移
    }

    public void Tick(float dt) {
        timer += dt;
        // 只在「活跃帧」区间开启攻击判定
        boss.hitbox.SetActive(timer > 0.25f && timer < 0.45f);

        if (timer >= 0.9f) {                     // 后摇结束 → 回到决策
            boss.fsm.ChangeState(new RecoverState(boss));
        }
    }

    public void Exit() {
        boss.hitbox.SetActive(false);          // 关判定框，否则切走后还会打到人
        timer = 0f;
    }
}
这一行是真会出 bug 的

Exit() 里不关判定框，是动作游戏里最经典的「莫名其妙被打中」。Boss 已经从攻击状态切到受击状态了，上一个攻击的判定框还开着——玩家贴脸就被打。写 FSM 时，只要 Enter 里开了什么，Exit 里就必须对称地关掉什么。

02状态爆炸：FSM 从哪一行代码开始崩

一句话：FSM 的维护成本随「状态对的数量」增长，不是随状态数。这就是它崩掉的数学原因。

20 个状态，意味着 380 条潜在转移。这时候你会开始看到三种典型的崩坏症状。

症状一：条件打架（状态抖动）

最典型的是距离阈值。你的 Chase 状态里写「距离 < 2 就攻击」，Attack 状态里写「距离 > 2.5 就回去追」。

玩家站在 2.2 的位置前后微调，Boss 就会在 Chase 和 Attack 之间以每秒十几次的频率疯狂切换——动画抽搐，音效连播，玩家看着像 Bug。

解法：滞回（Hysteresis）

让「进入条件」和「退出条件」用两个不同的阈值。Chase → Attack 用 2.0，Attack → Chase 用 3.0。中间 1.0 的缓冲区就是防抖带。
这个技巧在任何「基于连续量做状态切换」的地方都适用：视野范围、血量阈值、士气值，全都要留滞回带。

症状二：交叉连线（这也不对，那也不对）

当 Boss 有十几个状态时，你会开始需要「从任何状态都能进入」和「从任何状态都能被打断」两类转移：

  • 玩家打出硬直 → 无论 Boss 在干什么，都必须切到 Stagger
  • Boss 血量归零 → 无论在哪，都必须切到 Death
  • 阶段转换触发 → 无论在哪，都必须切到 PhaseTransition

于是每个状态里都要复制一遍这些判断。15 个状态 × 3 个全局规则 = 45 处重复代码。改一条规则要改 15 个文件。

症状三：改一处、炸三处

这是最贵的代价。你想改「硬直的触发阈值」，结果发现这个阈值在 6 个文件里各写了一遍，数值还都不一样。你想加一个「三阶段」，发现要在 15 个状态里都插入一条 if (hp < 0.3f)。

拐点判断：什么时候必须换架构

不用等状态数到 20 才动。看到下面任意两条同时成立，就该考虑 HFSM 或行为树了：
· 状态数超过 8~10 个，且还在加；
· 出现了「任意状态都能进入」的全局打断规则；
· 需要「阶段」这种对状态分组的概念；
· 同一个判定条件在 3 个以上地方重复出现。

值得说清楚：FSM 没有「过时」

这里有个常见误解，值得专门澄清一下。状态爆炸不是 FSM 的失败，而是「用一个扁平结构去装一个分层问题」的失败。

下面这些场景，FSM 到今天仍然是最优解，别急着上行为树：

Opsive 在对比自家两套工具时给了一句很干净的判据：「如果主要问题是『哪个模式处于激活状态、什么能让它切走』，用状态机；如果主要问题是『现在该尝试哪个动作、失败之后怎么办』，用行为树。」这句话基本概括了下面两节的全部内容。

03分层状态机 HFSM：给状态分组

一句话：HFSM 只是承认了一件事——「追击」和「追击时闪避」不是同一个层级的概念。

它要解决的问题

回到上一节那个痛点：全局规则被复制到每个状态里。HFSM 的解法非常朴素——把状态装进组里，让共同的规则写在组上，而不是写在每个成员上。

更本质的说法是：扁平 FSM 只有一个「当前状态」，而 HFSM 有一串「当前状态路径」。比如同时是「战斗中的 → 近战子行为中的 → 正在挥刀」。外层的规则管打断，内层的规则管具体动作。

图 3-1 · 分层之后，「当前状态」变成了一条路径：战斗中 → 交战 → 突刺 → 活跃

HFSM 的两个实际收益

规则下沉到组
「受击打断」写在 Disabled 组的进入条件上，所有子状态自动继承。改一条，全组生效。
子状态可复用
「前摇→活跃→后摇」这个三段结构，横扫、跳劈、突刺都能用同一套子状态机，只是参数不同。
图 3-2 · HFSM 的两个实际收益

第二种收益往往被低估。在真实项目里，一个 Boss 的十几种招式，有八种共享「前摇 → 活跃 → 后摇 → 返回」这个骨架，差异只在动画、判定框、时长和位移。一旦把它们提成一个可参数化的子状态机，代码量会塌掉一大半。

HFSM 的代价

层级引入后，「当前状态」不再是单个值而是路径，调试时不能只问「它在哪个状态」，要问「它在哪条路径上」。另外层级一旦定错（比如把「闪避」放在 Engage 组里而不是顶层），后面迁移会很痛。分层要按「谁的规则管谁」来分，不要按「看起来像一类」来分。

状态机家族的全景

形态核心机制适合的状态规模主要痛点
扁平 FSM一个当前状态，显式转移3~8 个全局规则重复；连接数平方增长
HFSM状态带层级，规则分组继承10~30 个层级定错难迁移；调试需看路径
栈式状态机用栈管理，「返回上一状态」是天然操作需要频繁返回的场合栈深度失控；跨层通信麻烦
并行状态机多个正交子机同时运行（位移 / 攻击 / 表情各一套）关注点须真正正交子机之间的仲裁逻辑容易变复杂

栈式状态机值得单独说一句：它的典型场景是「Boss 被打断 → 插播受击动画 → 播完自动回到刚才那个招式」。用普通 FSM 你得手动记「刚才是什么状态」，用栈就是 Push / Pop 两个操作。但栈深度一乱就很难查，慎用。

04行为树：从「我在哪」换到「我该做什么」

一句话：状态机的中心问题是「当前模式」，行为树的中心问题是「下一件要尝试的事」。这一个视角的切换，带来了模块化和可中断这两个决定性优势。

它要解决的问题

先看一个真实需求。你的 Boss 该表现成这样：

  • 血量低于 30% 时，优先放濒死大招；
  • 否则如果玩家在危险区域，优先用反击；
  • 否则如果玩家在近身范围，用近战连段；
  • 否则如果玩家在远处，远程压制；
  • 否则追击；
  • 而且每一帧都要重新检查这些优先级——一旦条件成立，立刻打断当前行为。

用状态机做这件事，你需要在每一个状态里都写一遍上面这整条判断链，否则打断不及时。用行为树，这就是一次从根节点的自上而下遍历，天然每帧重算。

最关键的一句话

「按优先级找出第一个能执行的行为」是行为树的核心操作。它在结构上等价于一串 if / else if / else if，但每个分支可以是一整棵子树，而且可以复用到别的地方。这就是「模块化」的真正含义。

行为树的三个组成部分

组合
Composite 组合节点 —— 有多个子节点，决定它们的执行顺序。最常见的是 Sequence（顺序）和 Selector（选择）。
装饰
Decorator 装饰节点 —— 只有一个子节点，修改它的执行方式或返回值。比如取反、循环、加时间限制、加条件门。
叶子
Task 叶节点 —— 没有子节点，真正干活或真正做判断的那个。分两种：Action（做事）和 Condition（判断）。

行为树的出身

行为树不是学术产物，它是在工业里被逼出来的。它由《光环 2》（Halo 2）普及——当时 Bungie 需要让 AI 表现出「有优先级的、能被打断的、由大量可复用小队件组成的行为」，状态机已经撑不住了。

今天它已经是主流引擎和中间件的标配：Unreal 的 Behavior Tree 是内置模块，Unity 侧有 Behavior Designer、NodeCanvas 这类成熟插件，开源方案也有 BehaviorTree.CPP、LimboAI 等。你如果不想自己造轮子，直接上插件是理性的选择——但自己手写一遍最小实现，是理解它的最快路径，下面的代码就是为了这个目的。

05节点的三种返回值：Success / Failure / Running

一句话：行为树的全部魔法，都建立在「每个节点都必须返回三个值之一」这个约定上。尤其是第三个值。

这三个值分别是什么

Success
做完了，而且成功了
比如「走到玩家身边」——抵达就是成功。父节点会认为「这个分支搞定了」。
Failure
做不了，或做失败了
比如「检查玩家是否在视野内」——玩家不在，返回失败。父节点会认为「这个分支不成立」，转去试下一个。
Running
正在做，还没完
比如「播放大招动画」——它要 2 秒，这一帧才过 0.3 秒，就返回 Running。父节点会记住「我停在这个孩子上」，下一帧从这里继续。
图 5-1 · 三个返回值，缺一不可

前两个值很直觉，第三个才是关键。没有 Running，行为树就退化成了一棵「每帧重算的条件判断树」，无法表达跨越多个帧的持续行为。

想想「施放一个 2 秒的持续光束」。它不可能在一帧内完成，也不能每帧都从头开始播。Running 就是那个「别忘了，我还在忙」的信号——它把一次 Tick 的瞬时判断，变成了跨帧的状态维持。

一条极易踩的坑

如果一个动作节点返回 Running，那么整条路径上的父节点都必须原样把 Running 往上传，并且记住自己停在了哪个孩子。Sequence 和 Selector 的内部索引必须能正确恢复——这是手写行为树时最多 bug 的地方。写完之后一定要专门测试「跨帧继续」这个路径。

最小实现

整个行为树的核心不到 40 行。先看节点基类和两种返回值的定义：

public enum Status { Success, Failure, Running }

public abstract class Node {
    public abstract Status Tick(BossContext ctx);
}

// 组合节点：有孩子，要记住停在哪一个
public abstract class Composite : Node {
    protected readonly Node[] children;
    protected int current;                 // ← 这个字段是「跨帧继续」的关键
    public Composite(params Node[] children) { this.children = children; }
}

// 叶节点：没有孩子，只有一个 Tick 行为
public class Action : Node {
    private readonly Func<BossContext, Status> onTick;
    public Action(Func<BossContext, Status> onTick) { this.onTick = onTick; }
    public override Status Tick(BossContext ctx) => onTick(ctx);
}

// 条件节点：只返回 Success 或 Failure，永远不返回 Running
public class Condition : Node {
    private readonly Func<BossContext, bool> check;
    public Condition(Func<BossContext, bool> check) { this.check = check; }
    public override Status Tick(BossContext ctx) => check(ctx) ? Status.Success : Status.Failure;
}

然后是两种组合节点的实现。请注意 Sequence 里对 current 的处理——返回 Failure 时要把 current 重置为 0，这行代码就是「下次从头再来」：

public class Sequence : Composite {         // 与：全部成功才算成功
    public Sequence(params Node[] children) : base(children) { }

    public override Status Tick(BossContext ctx) {
        while (current < children.Length) {
            Status s = children[current].Tick(ctx);
            if (s == Status.Failure) { current = 0; return Status.Failure; }
            if (s == Status.Running) return Status.Running;  // 停在这，下次继续
            current++;                                   // 这个孩子成功了，试下一个
        }
        current = 0;
        return Status.Success;
    }
}

public class Selector : Composite {         // 或：有一个成功就算成功
    public Selector(params Node[] children) : base(children) { }

    public override Status Tick(BossContext ctx) {
        while (current < children.Length) {
            Status s = children[current].Tick(ctx);
            if (s == Status.Success) { current = 0; return Status.Success; }
            if (s == Status.Running) return Status.Running;
            current++;                                   // 这个孩子失败了，试下一个
        }
        current = 0;
        return Status.Failure;
    }
}
注意这两段的对称性

Sequence 遇 Failure 就整体失败，遇 Success 就 current++；Selector 遇 Success 就整体成功，遇 Failure 就 current++。就这一个符号的差别，决定了「与」还是「或」。理解这一点，行为树就没有黑箱了。

一个思考题：如果 Sequence 的某个孩子返回 Running，下一帧是从这个孩子继续，还是从头开始？
答案是从这个孩子继续——因为 current 没有被重置。这正是「播放一段多步连招时，不会每帧重播第一步」的原因。

06Sequence 与 Selector：与、或、以及优先级

一句话：你需要的所有决策结构，都是这两种节点的组合。它们分别对应逻辑上的「与」和「或」。

两种节点的心智模型

Sequence = AND（与）
从左到右依次执行，全部成功才成功，中途失败立即整体失败。「看见玩家并且够近并且冷却好了 → 才出招」
Selector = OR（或）
从左到右依次尝试，第一个成功就整体成功并停止。「能放大招或者能反击或者能近战 → 挑第一个能用的」

把一段策划需求翻译成树

用这一节的方法论考验一下自己。给一段很典型的需求：

需求原文

玩家进入 8 米内，Boss 开始接近；接近到 2.5 米内且攻击冷却结束后，打一套三连斩；如果中途被打断，重新判断；如果没有玩家，就回到巡逻点。另外，任何时候血量低于 30%，都优先打断一切去放濒死大招。

翻译方式：「任意时候都优先」放在最高的 Selector 的第一个分支；每一步「并且」用 Sequence 串起来。

图 6-2 · 翻译是机械的：见到「并且」就套 Sequence，见到「或者 / 优先」就套 Selector
把这条翻译规则记住，你就掌握了 80% 的行为树

「必须全部满足」→ Sequence　「随便满足一个就行」→ Selector　「任何时候都要优先」→ 提到更高的层级。
这三句话能覆盖绝大多数策划需求。翻译完还记得请策划确认一遍——因为如果翻译错了，代码是完全按错的方式在跑的，而且看起来还挺像那么回事。

实践中最容易搞混的地方

看到的需求应该用理由
「先接近，再挥刀」Sequence两步都必须完成，第二步依赖第一步的结果
「能打就打，打不到就追」Selector挑第一个可行的方案，前面成功就不看后面
「检查玩家是否在视野内」Condition 叶节点它是个判断，不是动作，永远不返回 Running
「播放大招动画（2 秒）」Action 叶节点 + Running跨越多个帧的持续行为
「连续挥砍 3 次」Repeater 装饰器 + Action同一个动作重复，不需要写三个节点
「没写条件的兜底行为」AlwaysSucceed 装饰器保证最后有一个分支会执行，防止 AI 发呆

07装饰器与并行：中断才是行为树的杀手锏

一句话：组合节点负责「顺序」，装饰器负责「条件、循环、打断」——而打断是行为树区别于状态机的核心竞争力。

常备的五个装饰器

Inverter
取反 —— 把孩子的 Success 变成 Failure，反之亦然。Running 原样透传。
用途：省掉一堆「条件不成立」的反向节点。
Repeat
重复 —— 重复执行孩子 N 次，或「重复到失败为止」。
用途：三连斩、连续弹幕轮次。
Condition
条件门 —— 只有条件成立时才允许孩子执行，否则直接返回 Failure。
用途：给整个子树加一个前置门槛，比在每个叶子上都写检查干净。
TimeLimit
限时 —— 孩子在规定时间内没完成就强制中断。
用途：防止某个行为卡死，比如「追击最多追 5 秒就放弃」。
Cooldown
冷却 —— 执行过一次后，在冷却期内一律返回 Failure。
用途：控制招式频率，这是 Boss 手感调节的主力旋钮。
图 7-1 · 五个能覆盖九成需求的装饰器

装饰器的实现要简单得多，因为它只包一个孩子：

public abstract class Decorator : Node {
    protected readonly Node child;
    public Decorator(Node child) { this.child = child; }
}

// 取反：把 Success / Failure 对调，Running 不动
public class Inverter : Decorator {
    public Inverter(Node child) : base(child) { }
    public override Status Tick(BossContext ctx) {
        var s = child.Tick(ctx);
        return s == Status.Success ? Status.Failure
             : s == Status.Failure ? Status.Success
             : Status.Running;
    }
}

// 冷却门：冷却期内直接失败（也就是「这个分支不可用」）
public class CooldownGate : Decorator {
    private readonly float duration;
    private float readyAt;

    public CooldownGate(Node child, float duration) : base(child) {
        this.duration = duration;
    }

    public override Status Tick(BossContext ctx) {
        if (Time.time < readyAt) return Status.Failure;   // 还在冷却，让位给后面的分支
        var s = child.Tick(ctx);
        if (s == Status.Success) readyAt = Time.time + duration;  // 成功才进冷却
        return s;
    }
}
冷却门的一个细节，很多人写反了

冷却应该在「成功执行之后」才开始计时，而不是「一开始 tick」就计时。否则会出现「因为它在冷却所以它失败，因为失败所以不进冷却」这类诡异循环。另外，冷却期内返回 Failure 而不是 Running——前者意味着「这个分支现在不用考虑，去看下一个」，后者意味着「这个分支正忙，别动」。选错会让 Boss 卡在冷却里发呆。

并行节点：同时做两件事

Parallel 节点在同一帧 tick 所有孩子，并按某种策略汇总结果——比如「必须全部成功」「任意一个成功即可」。它适合表达真正正交的事情：

Parallel
同时运行下面两支
↓
分支 A
朝玩家移动（持续 Running）
分支 B
检查是否该发射弹幕（条件）
图 7-2 · 并行适合「一边做 A 一边盯着 B」的正交行为

但要小心：Parallel 的「成功判定策略」很容易变成坑。如果两支都返回 Running，整体永远是 Running，父级 Sequence 就永远推进不下去。用它的时候，一定想清楚「什么条件下这个并行块算完成」。

真正的杀手锏：条件中断

这是行为树最值得专门学的一块，也是它和状态机拉开差距的地方。

场景：Boss 正在放一套 3 秒的连续斩击。第 1.5 秒时，玩家跑进了一个危险区域，按照设计，Boss 应该立刻放弃连斩，改用反击。

用状态机你要写：在攻击状态的 Tick 里检查危险区域条件，然后手动中断、手动清理、手动切换。

用行为树，你只需要给这个分支挂一个「可中断的观察者」。它的机制是这样：

1
分支 A（反击）在根 Selector 中排位更靠前。它上面挂了一个条件观察者，条件是「玩家在危险区域」。
2
当前正在执行分支 B（连斩）。每一帧，树从根重新遍历，会先 tick 分支 A 的观察者。
3
某个瞬间条件成立。观察者返回 Success，于是分支 A 开始执行，并向上发出中断信号。
4
中断信号沿路径传播到分支 B，触发它的 Abort——B 的整棵子树被通知「你被取消了」，各节点清理自己的现场（关判定框、停动画）。
5
根 Selector 返回分支 A 的结果。下一帧一切从新状态继续。
图 7-3 · 条件中断的五个步骤。关键在第四步：中断必须能清理现场

实现上，节点需要一个 Abort 钩子，和 Tick 配对：

public abstract class Node {
    public abstract Status Tick(BossContext ctx);
    public virtual void Abort(BossContext ctx) { }   // ← 被取消时清理现场
}

// 组合节点要把 Abort 往下传
public class Sequence : Composite {
    public override void Abort(BossContext ctx) {
        if (current < children.Length) children[current].Abort(ctx);
        current = 0;
    }
}

// 动作节点在这里关掉判定框、停掉音效
public class PlayAttackAction : Node {
    public override void Abort(BossContext ctx) {
        ctx.hitbox.SetActive(false);
        ctx.animator.SetTrigger("Interrupt");
        ctx.ReleaseAttackLock();
    }
}
Abort 不写，就会出现「幽灵判定框」

这是行为树项目里最常见的 Bug 类型，和 FSM 里 Exit 不关判定框是同一个病。只要一个节点在 Tick 里开启了什么持续性状态，就必须在 Abort（以及正常结束的分支）里关掉它。建议把这条写进团队代码规范，比事后调试划算得多。

真实项目里，中断还分「自己打断别人」和「别人打断自己」两种方向（有的实现叫 self-abort / lower-priority-abort）。手写引擎时先只支持一种，用最简单能跑通的方式，等真的遇到需求再补。过度完备的中断系统是新手最容易陷进去的泥潭。

08黑板：节点的共享内存

一句话：黑板让节点之间不必互相认识，就能共享「Boss 现在知道什么」。

它要解决的问题

行为树的节点是独立的小积木，但「条件节点」和「动作节点」经常要读同一份数据。比如：

  • 条件节点判断「玩家是否在视野内」——需要知道玩家位置；
  • 动作节点「朝最后已知位置移动」——需要知道玩家最后一次被看见在哪；
  • 装饰器「追击超过 5 秒就放弃」——需要知道已经追了多久。

如果让节点自己去 FindObjectOfType<Player>()，会有三个后果：性能灾难（每帧每个节点都找一遍）、逻辑不一致（不同节点算出的距离可能不同）、测试困难（没法伪造玩家）。

黑板把这件事收拢成一处：感知层（Perception）每帧统一更新一次黑板，所有节点只读黑板。

图 8-1 · 黑板是树的「工作记忆」，感知层是唯一的写入者

一个够用的黑板

public class BossContext {              // 这就是黑板，叫 Context 也常见
    // —— 引用 ——
    public Transform self;
    public Transform target;
    public Animator animator;
    public Collider2D hitbox;

    // —— 每帧由感知层刷新 ——
    public float distanceToTarget;
    public Vector2 lastKnownTargetPos;
    public bool canSeeTarget;

    // —— 长期记忆 ——
    public float healthPercent;
    public int hitsTakenSinceStagger;   // 硬直计数，见第 13 节
    public float timeInCurrentBranch;
}
黑板上该放什么、不该放什么

放：每帧要读多次的数据（距离、血量、目标引用）。
不放：只有单个节点自己用的临时变量（某个动画的播放进度）——那属于节点私有状态，放黑板上反而会让节点之间产生隐式耦合。
判断标准很简单：如果一个字段只有一个节点会读，它就不该出现在黑板上。

黑板之所以叫「黑板」，是因为它借用了「黑板系统」这个经典 AI 架构的比喻：一群人围着一块黑板，谁都看得见谁写上去的东西，但彼此不必直接对话。在行为树里，这个比喻的落地非常实用——它就是一棵树跨越所有节点的共享内存。

09FSM 还是 BT：一张能直接照着用的判别表

一句话：看你问的是「我在哪」还是「我该做什么」。这不是风格偏好，而是问题类型决定的。

先看思维模型的差别

状态机：状态驱动
核心问题 ——我在哪？脑子里想的是「现在是追击状态，什么条件下切到攻击」。注意力在当前所处的模式，以及能离开它的那几条边。
行为树：任务驱动
核心问题 ——我想做什么？脑子里想的是「按优先级，现在最该尝试哪件事，失败了退到哪件」。注意力在评估顺序和回退路径。
图 9-1 · 同一个 Boss，用两种架构思考时的心理活动完全不同

这个差别看起来很虚，但它会决定你的代码在什么情况下变得难改：

  • 你要频繁调整行为之间的优先级（「濒死大招应该排在反击前面还是后面」）——行为树只需要挪动节点的位置，状态机要改一堆转移条件。
  • 你要精确控制某个模式的进出规则（「硬直期间绝对不能出招」）——状态机一行进入条件就完事，行为树要靠装饰器拦住每个分支。

维度有限状态机 FSM / HFSM行为树 BT

扩展性差。加状态会让连线成平方增长强。加一个分支、子树直接挂上去

一句提醒，来自踩过坑的人

很多开发者的第一反应是「行为树更先进，那就用行为树」。这是错的。行为树解决的是「优先级和组合」问题，如果你的 Boss 根本没有这两个问题，它带来的只有额外的抽象层、更难查的 Bug 和一个多出来的编辑器窗口。
「最优雅的代码不是最复杂的，而是最恰好能解决问题的」——这句话在游戏 AI 上格外成立。

表现层（状态机 + 动画）留在程序手里，负责时序精确性。这条分工线一旦画对，团队的迭代速度会有质变。

唯一的禁忌：不要让两套系统都管同一件事

「谁有权决定 Boss 该出什么招」这个问题，必须只有一个答案。如果行为树决定了要打突刺，同时状态机里还留着一个「距离够近就自动攻击」的逻辑，你会得到最糟糕的结果：两个系统互相覆盖，出现只在特定时序下才复现的神奇 Bug。

11攻击的解剖：前摇 / 活跃帧 / 后摇

一句话：一个攻击动作的全部手感，都由三个时间段的长度比例决定。而这恰好是行为树和状态机都帮不了你的地方——它必须由人来定数字。

三段时间

无论多复杂的招式，拆开都只有这三段。这是动作游戏设计里最基础、也最被低估的一组概念：

图 11-1 · 所有招式都是这个模板，区别只在三段的比例和特效

三段时间各自在解决什么问题

前摇
它决定「公平感」
前摇是唯一把「即将发生什么」告诉玩家的窗口。太长则失去压迫感，太短则玩家来不及反应——战斗会从「读招」退化成「拼反应」。前摇必须配合独立的视觉信号：不一样的抬手姿势、不一样的特效颜色、不一样的身体轮廓。这是让玩家记住招式的关键。
活跃
它决定「危险度」
判定框开着的时段。这个时长要和视觉表现严格对齐——判定框比刀光宽一圈，玩家就会觉得「明明躲开了还被打中」。
后摇
它决定「节奏」
后摇是给玩家的奖励窗口，也是战斗呼吸感所在。后摇的设计有一个反直觉的原则：连续攻击之后，必须留一段明显的、让玩家能确认「现在安全了」的停顿。这段时间里玩家在输出、在回血、在思考下一步——它是战斗「张弛」里的「弛」。

真实数据：《空洞骑士》大黄蜂的招式拆解

《空洞骑士》里第一场大黄蜂（Hornet）战斗，是被反复研究过的教学级案例。她只有四个招式，但几乎每个动作游戏开发者都会把她当范本分析——因为她在极小的角色体型上，做出了一套完全可读、可学的招式体系。

把这组数字放在一起读，就能看出设计的精妙：

  • 突刺的前摇只有 15 帧，刚好够玩家看到动作、然后跳开——难度缓冲极小，但不等于零。
  • 活跃和后摇都只有 10 帧，意味着这一招几乎不给玩家反击机会。它是纯粹的压力招式。
  • 而玩家治疗需要 45 帧。对比一下：突刺全程只有 35 帧。你不可能在突刺间隙里治疗。
这才是「帧数据设计」的真正含义

不是设计一个攻击「多快」，而是设计它与玩家所有能力之间的关系：这招之后玩家能不能回血？能不能偷一刀？能不能安全翻滚出去？
先把玩家侧的三个数字定下来（最短攻击帧、治疗所需帧、闪避无敌帧），每个 Boss 招式就都有了参照系。

两个可以直接抄的参照值

《漫威蜘蛛侠 2》的战斗设计师 Adam Noonchester 在分享里给过两组很实用的数字，都是从玩家感知能力倒推回来的：

0.25 秒
人看提示到按键的本能反应时间。攻击开始后 0.25 秒内不应造成伤害，否则玩家来不及做出反应，会觉得「这招躲不了」。
前摇 ≥ 闪避时长
蜘蛛侠闪避落地需要 0.5 秒，于是攻击前摇定在 0.75 秒——1.25 秒减去 0.5 秒。这样玩家看到提示立刻按闪避，落地时攻击刚好结束。

同一套分享里还有一个更聪明的小设计：后摇长度取决于攻击是否命中。

攻击结果Boss 后摇玩家获得的机会
攻击落空（玩家躲开了）1.5 ~ 3 秒充裕的反击窗口——「你躲得好，这是奖励」
攻击命中0.5 ~ 1 秒窗口很短——「你挨打了，就该收惩罚」

这个设计的价值在于：它用同一套动画，制造了完全不同的两种节奏。玩家躲开的每一次，都会获得更长的输出时间——于是「精准闪避」和「莽着挨打」在收益上被拉开了差距。而且它是自平衡的：越熟练的玩家，Boss 表现出的后摇越多，战斗越流畅。

一个可以直接用的实现思路

后摇时长不是动画的固有属性，而是「命中检测结果」的函数。在动作状态机的后摇阶段开始前做一次判定：recoverTime = hasHitPlayer ? 0.75f : 2.2f。
实现成本很低，但对战斗节奏的改善非常明显。这类「低实现成本、高感知收益」的调整，是性价比最高的一类改动。

攻击频率的参照区间

招式之间的间隔（也就是行为树里那个 Cooldown 装饰器的参数）也有经验区间可以参照。下面这组数字来自多个动作游戏的测试数据汇总，适合作为起点：

难度档位平均攻击间隔设计意图
休闲每 3 ~ 5 秒一次玩家有充足时间观察、试错、治疗
普通每 2 ~ 3 秒一次标准节奏，留出输出与闪避的循环空间
困难每 1 ~ 2 秒一次压缩决策时间，要求玩家形成肌肉记忆
专家每 0.8 ~ 1.2 秒一次，且混合多种攻击接近极限，通常只用于可选 Boss

有一个相关的平衡公式值得记下来，它把「玩家能力」和「Boss 压力」挂上了钩：

玩家可承受的极限频率 = 玩家操作速度 × 角色无敌帧覆盖率 × 容错容忍度

这个公式的实用价值在于：当你觉得「Boss 太密了」的时候，先别急着改 Boss 的攻击间隔——先看玩家的无敌帧覆盖率。如果闪避的无敌帧覆盖率是 25%，那么理论上 75% 的时间玩家是暴露的。提高一点无敌帧覆盖率（哪怕只是多给几帧），往往比削弱 Boss 更好，因为它同时提高了玩家的操作成就感。

12阶段转换：不要只把数值翻倍

一句话：阶段转换要改的是「战斗逻辑」，不是「数值」。玩家感受到的成长感，来自规则变了，而不是数字变了。

最常见的错误

「二阶段血量翻倍、伤害提高 30%」——这是最容易做、也最没意思的阶段转换。玩家的体验是：什么都没变，只是更累了。

判断一个阶段转换是否合格的标准

问自己一句：「如果我把两个阶段的招式表给玩家看，他能说出这两个阶段的打法有什么不同吗？」
如果答案只是「二阶段它打得更疼」，那这个阶段转换是不成立的。合格的阶段转换应该改变玩家的应对方式——比如从「贴身压制」变成「拉开距离躲弹幕」。

一次合格的阶段转换带来什么

解锁
新招式加入 —— 玩家面对的是新的信息，需要重新学习。这是「新鲜感」的来源。
剥夺
旧招式退场 —— 这条经常被忽略，但它极重要。老招式消失会让战斗的节奏和空间感整体改变，而不是简单的叠加。
重构
节奏整体变化 —— 攻击更频繁，或者反而变慢；位移方式改变；战场本身变化（地板碎裂、掉落一层）。
演出
一段无法被跳过的仪式 —— 站起来、嘶吼、场地剧变。它给玩家一个明确的「过了一关」的心理标记。

注意第二条「剥夺」。设计者天然倾向于「二阶段 = 一阶段 + 新招式」，但真正的经典设计往往是「替换」：拿走一部分旧招式，换上新招式，让两个阶段的战斗气质完全不同。

完整案例：《空洞骑士》最终 Boss 的四阶段阶梯

这是教科书级别的阶段设计，四个阶段每一个都在改变玩家的应对方式。数据来自空洞骑士 Wiki 与社区整理：

阶段触发条件招式变化玩家应对方式如何改变

二阶段 血量降至 750 保留一阶段全部招式，新增俯冲火柱 + 感染弹幕；行动与攻击频率明显提高 弹幕覆盖约 75% 场地，且弹幕轨迹固定不追踪——从「贴身踩头」被迫转向「找安全区站位」
三阶段 血量降至 400 新增自残插胸 + 浮空散射，但移除突刺与三连斩（除传送后偶尔使用）；攻击与移动频率反而下降；且此阶段开始无法再被打出硬直 Boss 变慢了，但失去硬直意味着玩家失去了「靠输出压制」的选项。自残动作成为主要输出窗口，节奏从「追击」变成「等机会」

三个阶段，三次「玩法重构」

把右侧那一列连起来读：贴身压制 → 找安全区 → 等破绽。三个阶段对应三种完全不同的战斗方式。
而且注意第三阶段那个反直觉设计：Boss 变慢了，但对玩家来说反而更难——因为它拿走了硬直这个机制。这就是「改逻辑而非改数值」的正面案例。

还有一个值得单独看的细节：这个 Boss 的硬直参数是「受击 13 次、连击 5 次、连击判定窗口 9」，并且三阶段开始后硬直机制被整个禁用。也就是说「硬直」不是固定属性，而是随阶段可被关闭的系统——这需要在架构里把硬直做成独立的、可配置的子系统，而不是写死在受击状态里。

方案 B 是工程上的标准答案——把每个阶段的配置数据抽出来：

// 用 ScriptableObject 承载一个阶段的全部配置，策划可直接调
[CreateAssetMenu(fileName = "BossPhase")]
public class BossPhaseData : ScriptableObject {
    public string phaseName;
    [Header("触发条件")]
    public float healthThreshold;      // 血量降到多少进入本阶段
    public float maxDuration;          // 可选：超时强制进入（防卡死）

    [Header("招式池")]
    public AttackData[] attacks;        // 本阶段可用的招式
    public float attackInterval;      // 攻击间隔（第 11 节的频率参数）

    [Header("机制开关")]
    public bool allowStagger;          // 本阶段是否可被打出硬直
    public float damageMultiplier;

    [Header("转场演出")]
    public AnimationClip transitionAnim;
    public AudioClip transitionSfx;
    public bool reshuffleArena;         // 是否改变战场（地板碎裂等）
}
为什么一定要抽成数据

因为阶段的阈值是必然会反复调的东西。策划会说「750 血太早了，改 650 试试」「三阶段的硬直别删了，改成延长 50%」。如果这些写在代码里，每一次调整都是一次编译、一次提交、一次回归测试。
抽成 ScriptableObject 之后，这些调整变成了在 Inspector 里改数字、存盘、点运行。这类「配置外置」的收益，在项目进入平衡期之后会放大十倍。

方案 C 是行为树方案：每个阶段是一棵独立的子树，阶段切换＝换根选择器的激活分支。前面第 9 节的表格里已经列过这个用法。它的优势是阶段内的决策也能用优先级系统表达；代价是要处理「切阶段时正在执行的行为如何取消」——也就是第 7 节讲过的 Abort 传播。

转场演出有一件事必须做对

转场期间，Boss 必须完全免疫伤害，也完全不接受任何决策输入。玩家在转场时能偷伤害，会让这个「仪式」失去意义；Boss 在转场时还能出招，会让玩家感到被骗。
实现上，转场是一个独占状态（对应第 3 节 HFSM 里的 Disabled 组），期间除它之外的一切都进不来。这个「独占」语义，正是状态机比行为树更擅长表达的东西。

13硬直与破防：给玩家一个能喘气的奖励

一句话：硬直是玩家持续输出的回报，也是战斗节奏里的「呼吸」。它必须有明确的积累、触发、演出、退出四个阶段。

先明确它解决什么问题

一场没有任何硬直的 Boss 战，玩家的体验是「我在打一堵墙」。而一场硬直太频繁的 Boss 战，Boss 变成了靶子，又失去了威胁。

硬直的核心作用是把「持续输出」这个行为变成一个有意义的选择：玩家知道只要稳定命中足够多次，就能换来一段安全的输出窗口——于是他愿意冒风险贴身，而不是远远地磨。

硬直在设计上属于「正反馈」

玩家做对了事（持续命中）→ 得到奖励（Boss 跪地、可以安全输出或回血）。
这类设计对手感的贡献极大，因为它把玩家从「被动躲招」变成「主动制造机会」。没有硬直的战斗，玩家的角色是纯粹的防御者。

为什么是「两个计数」而不是一个

只用一个「总受击次数」会有问题：玩家用低伤害但高攻速的武器，可以轻松刷满计数，硬直变成无成本。
加上「连击次数 + 判定窗口」就解决了——它要求玩家在限定时间内连续命中，攻击间隔太长就会断连、计数重置。这一条把「攻速流」和「单发高伤流」拉回了相对公平的位置。

把它做成可配置的子系统

硬直不应该写死在受击状态里，而应该是一个独立订阅「命中事件」的组件。这样它才能被阶段配置开关（第 12 节提到过三阶段禁用硬直这件事）：

public class StaggerSystem : MonoBehaviour {
    [SerializeField] private int hitsToStagger = 13;      // 总受击次数阈值
    [SerializeField] private int comboToStagger = 5;    // 连击次数阈值
    [SerializeField] private float comboWindow = 0.9f;  // 连击判定窗口（秒）

    private int hitCount, comboCount;
    private float lastHitTime;
    private bool enabled = true;                  // 阶段配置可关掉它

    public void SetEnabled(bool v) {
        enabled = v;
        if (!v) ResetCounters();
    }

    // 由受击逻辑在每次成功命中时调用
    public void OnHit() {
        if (!enabled) return;

        if (Time.time - lastHitTime <= comboWindow) comboCount++;  // 在窗口内 → 连击累积
        else comboCount = 1;                                      // 断连 → 从 1 重新开始
        lastHitTime = Time.time;
        hitCount++;

        if (hitCount >= hitsToStagger || comboCount >= comboToStagger) {
            TriggerStagger();
        }
    }

    private void TriggerStagger() {
        ResetCounters();                                  // ← 图 13-1 第④步，绝不能漏
        BossEvents.Raise(BossEvent.Stagger);              // 通知状态机切到硬直状态
    }

    private void ResetCounters() { hitCount = 0; comboCount = 0; lastHitTime = -999f; }
}
用事件而不是轮询

注意上面这个组件不发散也不轮询——它只在「被命中」这个事件发生时算一次。这比在 Update 里每帧检查 hitCount 要干净得多，也更省。
同样的思路应该贯穿整个 Boss AI：血量过阈值、玩家进出区域、机关被激活——这些都应该用事件驱动，而不是每帧轮询。只有「距离、朝向」这类连续量才需要每帧算。

硬直窗口的长度怎么定

这是最需要实测的参数。给出一个可用的推导方法：

硬直窗口 = 玩家一次攻击总时长 × 期望连击数 + 缓冲 举例：单次攻击 0.35 秒，希望玩家能安全打 4 刀 0.35 × 4 = 1.4 秒，再加 0.2 秒缓冲 → 硬直窗口约 1.6 秒

这个长度刚好让玩家「打得爽，但来不及回满血」。如果硬直窗口长到玩家能回满血，这场战斗的难度曲线就被彻底破坏了——所以窗口长度还要和玩家的治疗时长做交叉验证（回想第 11 节里那个 45 帧的治疗数据：空洞骑士里治疗需要 1.5 秒，而硬直窗口刚好允许一到两次治疗，这就是刻意算过的）。

14读完你的招：反制、假动作与随机性

一句话：随机性要用来让玩家「学不完」，而不是让玩家「学不会」。这两者之间有一道很窄的界线。

先说那条界线

玩家在 Boss 战里获得的乐趣，来自「模式识别 → 形成预期 → 验证预期」。这个循环一旦被破坏，乐趣就消失了：

坏随机：从选项里抽一个
同一位置、同一时机，Boss 完全随机地选出招。玩家学不到任何规律——只剩运气。表现：死了会觉得「被坑了」。
好随机：在一个已学会的模式里加变化
整体循环是固定的，但每一环里有可预期的变化范围。玩家能学会「它这一轮会做什么」——只是每次细节不同。表现：死了会觉得「我判断错了」。
图 14-1 · 「被坑了」和「我判断错了」是完全不同的两种情绪

一句很准确的说法是：「有序中的无序」。它有明确的骨架让人学，也有一点变化让人不能背板。具体到实现，就是三条硬约束：

约束一
招式本身不能随机 —— 一个招式的时长、位移、判定范围必须固定。玩家需要靠这些稳定特征去识别它。
约束二
变化放在「参数」上 —— 冲撞的方向、弹幕的弧度、落点的位置可以有随机性，因为它们不改变招式的认知识别。
约束三
必须有一段可预期的循环 —— 「连续攻击三次 → 短暂停顿 → 再连击两轮」这种循环骨架要固定，让玩家能建立节奏感。
图 14-2 · 随机性的三条边界
一个能直接照做的模式设计

用真实案例说明「有序中的无序」：某个 Boss 的循环是「召唤 → 冲撞三次 → 停顿 → 酸液喷射两轮 → 疲惫期」。
骨架完全固定，玩家可以学会整轮流程；但冲撞方向、酸液弧度带随机，所以每一轮的处理细节都不同。
更关键的是最后那个「疲惫期」——它给了玩家一个明确的安全窗口，让整场战斗有张有弛。节奏感不是来自招式的复杂，而是来自「紧张段 + 放松段」的交替。

反制：让 Boss「读懂」玩家

另一个提升「有想法」感觉的手法，是让 Boss 对玩家的特定行为做出针对性反应。这不是让 AI 真的变聪明，而是把玩家最常用的几个套路，各自配一个专门的回应。

玩家的行为Boss 的反制效果
一直贴着 Boss 猛砍后撤步 + 范围横扫，或短距离弹开惩罚「只会莽」的打法，逼玩家学会后撤观察
一直远远地放风筝突进技 / 远程压制 / 场地边缘封锁惩罚「不敢近身」，让远程打法也有压力
在固定位置反复治疗朝治疗动作的起始位置发远程攻击玩家学会「治疗要看时机」，而不是随时嗑药
规律性地翻滚/闪避同一个方向招式落点偏移、延迟出手把「无脑滚」变成需要判断的操作
趁硬直期疯狂输出硬直结束瞬间的快速反击让玩家在「贪刀」和「保守」之间做取舍
反制的红线：不能变成「读指令耍赖」

反制机制做过头，玩家会明确感觉到「AI 在针对我」——尤其是当 Boss 在玩家按下按键的同一帧做出反应时，这种「作弊感」极其强烈，会直接摧毁公平感。
三条防线：
① 反制必须有和普通招式一样长的前摇，不能「瞬发」；
② 反制应该有冷却，不能每次都触发；
③ 反制的触发条件要基于玩家已完成的动作（比如连续 N 次同方向闪避），而不是「玩家即将按键」。

一个具体的反制陷阱案例

「假后摇」是反制手法里最精妙也最危险的一种。看这个设计（来自《卡赞》Boss 沙克图卡的分析）：

第一段
一个前摇极长、动作幅度极大的蓄力单爪拍击。幅度大是为了让这个招式足够显眼、容易被识别；速度慢是给玩家充足的反应时间，降低第一段的处理难度。
陷阱
爪子落地后约 30 帧（约 0.5 秒），Boss 把爪子向后拉，打出一记反向伤害。这 30 帧是伪装成后摇的前摇——玩家以为技能结束了，上前抓后摇，正好被第二段打中。
为什么是 30 帧
这是「刚好能反应、但容易误判」的数值。20 帧太短，大部分玩家还没意识到可以进攻，陷阱起不到作用；40~50 帧太长，玩家会目押出第二段，陷阱失效。
图 14-3 · 假后摇：把第二段的前摇藏进第一段的后摇里

这个案例最有价值的地方是它给出了一条可计算的推导公式，用来决定「给高手留多少操作空间」：

第二段前摇 = 主角完成一次攻击的最短帧数 + 防御生效的前摇帧数 + 要求玩家最短反应时间（帧） + 冗余帧数 举例：【15 + 0 + 20】= 35 帧起步 → 实际定 40 帧 效果：反应时间在 20 帧以内的玩家可以偷一刀再防御取消， 普通玩家按住防御也能安全处理 —— 同一招对不同水平玩家有不同深度
这条公式的通用价值

它把「给高手留操作空间」这件很虚的事，变成了一个加法。关键洞察是：一个招式应该对普通玩家有保底解法，对高手有额外收益的解法。
保底解法是「按住防御」，额外收益是「偷一刀再取消」。两者都能处理同一个招式，但回报不同——这就是「难度不代表不公平」的实现方式。

15从零搭一个 Boss：三阶段 + 硬直 + 反制

把前面十四个小节全部串起来，完整推演一个 Boss。为了可复制，这里用一个虚构的 Boss「锈铁哨卫」，但每一个决策都标注了参照来源。

第一步：先把设计目标写下来

不要一上来就建脚本。先写清楚这个 Boss 要制造什么样的体验——这份文档会决定后面所有参数。

锈铁哨卫 · 设计目标

定位：中期关底 Boss，玩家此时已掌握基础移动、单次攻击、闪避。
体验目标：教会玩家「硬直」这个概念。一阶段宽容、节奏慢，让玩家学会抓后摇；三阶段收回宽容度，检验他是否真的学会了。
时长目标：熟练玩家 2~3 分钟，首次通关 5~8 次尝试。
一句话描述：一台生锈的守卫机械，动作迟缓但招招沉重；越打越破，最后连自己的手臂都握不住。

注意最后那句「一句话描述」。它同时是叙事设定和机制设定——「动作迟缓但沉重」决定了前摇长、伤害高；「越打越破」决定了三阶段应该是「变慢但更危险」，而不是「变快」。这正是第 12 节讲的「阶段转换改逻辑」。

第二，检查每个招式是否都有独立的视觉信号。前摇列里的「臂甲红光」「后倾蓄力」「地面预示圈」不是装饰，它们就是第 11 节说的「必须配合独立的视觉信号」——玩家靠这些区分招式，而不是靠记帧数。

第五步：写行为树的核心分支

把决策逻辑落到代码上。注意这里的关键设计：所有阈值都从黑板读，不要写死；每个分支都挂冷却门，这样「攻击间隔」这个参数才有地方生效。

// 组装根 Selector —— 顺序就是优先级，从上往下试
var tree = new Selector(
    // 1. 濒死重击：血量低于 25% 且没用过
    new Sequence(
        new Condition(c => c.healthPercent <= 0.25f && !c.ultimateUsed),
        new PlayAttackAction(AttackId.DyingSmash)
    ),

    // 2. 反击横扫：玩家在背后连击时，直接横扫惩罚
    new Sequence(
        new Condition(c => c.comboHitsTaken >= 3 && c.distanceToTarget < 2.5f),
        new CooldownGate(new PlayAttackAction(AttackId.Sweep), 4f)
    ),

    // 3. 近身连击：贴身时的主攻手段（三阶段会被阶段配置禁用）
    new Sequence(
        new Condition(c => c.phase.HasAttack(AttackId.Combo)),
        new Condition(c => c.distanceToTarget < 2.5f),
        new CooldownGate(new PlayAttackAction(AttackId.Combo), 3.2f)
    ),

    // 4. 中距离冲锋
    new Sequence(
        new Condition(c => c.distanceToTarget >= 4f && c.distanceToTarget < 9f),
        new CooldownGate(new PlayAttackAction(AttackId.Charge), 3.5f)
    ),

    // 5. 远程投掷：只在二阶段后可用
    new Sequence(
        new Condition(c => c.phase.HasAttack(AttackId.Throw)),
        new Condition(c => c.distanceToTarget > 6f),
        new CooldownGate(new PlayAttackAction(AttackId.Throw), 4f)
    ),

    // 6. 追击
    new Action(c => c.MoveToward(c.lastKnownTargetPos, c.phase.moveSpeed)),

    // 7. 兜底：巡视（AlwaysSucceed 保证总有一个在跑）
    new AlwaysSucceed(new Action(c => c.IdleScan()))
);
注意第 3 个分支里那行 HasAttack

这是「阶段控制招式池」的落地方式——用条件节点读阶段配置，而不是把阶段写成三棵不同的树。好处是新增阶段只需要加一份 BossPhaseData，行为树完全不用动。
这比「一阶段一棵树」的方案更省维护成本，代价是树上多了一层条件判断。对于五个以内的阶段，这是更划算的选择。

16调试与可视化：看不见的 AI 永远调不好

一句话：行为树和状态机的复杂度是「看不见的复杂度」，所以工具不是加分项，是必需品。

为什么 AI 调试特别难

普通 Bug 有报错、有堆栈、有复现步骤。AI 的 Bug 长这样：

  • 「Boss 有时候会在原地发呆两秒」——什么条件下？没有报错。
  • 「它偶尔会连着放两次同一个招式」——是冷却没生效还是节点没重置？
  • 「第二个 Boss 比第一个笨」——两棵树结构一样，就是感觉不对。

这类问题的共同点是：它们不产生错误，只产生「不对的感觉」。如果你看不到 AI 内部的决策过程，就只能靠猜。

一个可以省下大量时间的原则

「如果 AI 会在某个状态下卡住，就必须能一眼看出它卡在哪个节点。」
把这句话当作调试基建的验收标准。做到这一点，前面那些「看起来像玄学」的问题，会有一大半变成「哦，它卡在第四个分支的冷却门上」。

四层调试基建，从便宜到贵

第 1 层
状态变化日志（最便宜）
在状态机的 ChangeState 和行为树节点进入时打一行日志，带时间戳。
成本：十分钟。收益：能回答「它什么时候切了、切到哪」。
第 2 层
屏上文字（Screen HUD）

成本：一小时。收益：不用切窗口就能边玩边看。
第 3 层
Gizmos 范围可视化
把感知范围、攻击范围、巡逻路径点画在场景里。
成本：半天。收益：立刻看出「为什么它没发现玩家」——通常是因为范围画错了。
第 4 层
行为树可视化面板
在编辑器里高亮显示当前激活的节点路径，节点上标出返回值。
成本：几天，或用现成插件的成本。收益：复杂树的唯一可维护方式。

public class BossDebugHud : MonoBehaviour {

    [SerializeField] private bool showHud = true;

    private void OnGUI() {
        if (!showHud || boss == null) return;

        GUILayout.BeginArea(new Rect(10, 10, 320, 160));
        GUILayout.Label($"阶段  : {boss.phase.phaseName}");
        GUILayout.Label($"模式  : {boss.modeFsm.Current?.GetType().Name}");
        GUILayout.Label($"招式  : {boss.currentAttackName}");
        GUILayout.Label($"节点  : {boss.tree.ActivePath}");   // 高亮的节点路径
        GUILayout.Label($"距离  : {boss.ctx.distanceToTarget:F2}");
        GUILayout.Label($"受击  : {boss.stagger.hitCount} / {boss.stagger.hitsToStagger}");
        GUILayout.Label($"硬直  : {(boss.phase.allowStagger ? "可用" : "已禁用")}");

「节点路径」这一行是最关键的

它告诉你当前激活的是第几个分支、卡在哪个节点的哪个返回值。
有了它，「Boss 发呆两秒」这类问题会变成一个很具体的排查：是第 6 个分支返回了 Running 一直没结束？还是所有条件都不成立落到了兜底分支？不用再看代码猜了。

    Gizmos.color = new Color(0.23f, 0.36f, 0.86f, 0.35f);   // 蓝
    Gizmos.DrawWireSphere(transform.position, detectRadius);

    // 攻击范围：进入这个圈才有攻击欲望
    Gizmos.color = new Color(0.75f, 0.07f, 0.24f, 0.5f);    // 红
    Gizmos.DrawWireSphere(transform.position, attackRadius);

    // 视野锥（朝向相关）
    Gizmos.color = new Color(0.09f, 0.58f, 0.53f, 0.4f);    // 青
    Gizmos.DrawLine(transform.position,
        transform.position + new Vector3(Mathf.Cos(-halfFov) * detectRadius,
                                          Mathf.Sin(-halfFov) * detectRadius, 0));
    Gizmos.DrawLine(transform.position,
        transform.position + new Vector3(Mathf.Cos(+halfFov) * detectRadius,
                                          Mathf.Sin(+halfFov) * detectRadius, 0));
}

画出来之后，你会经常发现一个现象：「攻击范围」和「感知范围」的圆形关系不对劲——比如攻击范围比感知范围还大，导致 Boss 在看不见玩家的地方乱挥刀。这类问题在数字上看不出来，画出来一眼就发现了。

一份可用的验收清单

Boss 做完之后，花半小时过一遍这份清单，能解决大部分「感觉不对但说不清哪不对」的问题：

检查 1
发呆检查 —— 把玩家放在各种位置（贴身 / 中距 / 超远 / 背后 / 视野边缘），观察 Boss 会不会出现无意义的停顿。
检查 2
抖动检查 —— 在状态切换的边界距离上反复移动（比如 2.4 ↔ 2.6），观察有没有高频切换。（对应第 2 节的滞回带）
检查 3
打断检查 —— 在每个招式的每个阶段尝试打断它，确认没有残留的判定框、特效、音效。（对应第 7 节的 Abort）
检查 4
阶段检查 —— 在血量刚好卡在阈值上反复攻击，确认阶段切换不会重复触发或来回跳。
检查 5
硬直检查 —— 连续触发两次硬直，确认第二次的计数是重新累积的，不是瞬间到达。（对应第 13 节的清零）
检查 6
无法通关检查 —— 这个最容易被忘：让 Boss 的技能配置出错时，玩家还有没有可能不被卡死？比如 Boss 卡在障碍物后面出不来、或者玩家被挤进死角。

D常见误区与反直觉点

这一节收集的都是「第一次做 Boss AI 几乎一定会踩」的坑。

误区为什么错正确做法
「行为树更先进，所以我该用它」 行为树只解决「优先级与组合」问题。没有这两个问题，它只带来抽象层和更多 Bug 状态数 ≤ 5 且转移简单就用 FSM。别为了技术而技术
「AI 越聪明，Boss 越好玩」 Boss 的乐趣来自「可学习的模式」。过度智能的设计会让玩家学不到东西 先问「玩家能学会它吗」，再问「它够不够聪明」
「随机出招让战斗更有趣」 纯随机会摧毁模式识别，玩家死了会觉得「被坑」而不是「我错了」 固定循环骨架，只让参数带随机（方向、弧度、落点）
「二阶段就加数值」 玩家感受不到变化，只觉得更累了。阶段转换应该改战斗逻辑 解锁新招式 + 剥夺旧招式 + 改变节奏，让打法真的变
「状态切换不用管退出」 最常见的一类 Bug：切走后判定框还开着、音效还在播 Enter 里开了什么，Exit 就必须对称关掉什么。写成团队规范
「行为树不需要 Abort」 被中断的分支不清理现场，会留下幽灵判定框和卡死的节点 每个持久性节点都实现 Abort。测试时专门测打断路径
「距离判断直接用同一个阈值」 边界上会高频切换，动画抽搐、音效连播 进入和退出用两个阈值，中间留滞回带
「硬直触发后计数不用清零」 第二次硬直会立刻到达，Boss 变成永跪的靶子 触发时立刻清零，并专门测试连续两次硬直
「前摇短一点更难更有挑战」 前摇过短会从「读招」退化成「拼反应」，玩家只会感到不可控 前摇 ≥ 玩家闪避时长 + 0.25s，必须配独立视觉信号
「数值直接写代码里」 平衡期每次调整都要编译、提交、回归测试 所有可调数值放 ScriptableObject，让策划自己改
「调试靠看代码猜」 AI 的 Bug 不报错，只产生「感觉不对」。看不见就调不好 先做屏上 HUD 显示当前节点路径，再谈优化
「AI 逻辑一定要每帧轮询」 性能浪费，而且逻辑散落。距离这类连续量才需要每帧算 血量阈值、区域进出、机关触发都用事件驱动
最后一条，也是最容易忘的

「Boss 的最大弱点必须是可以被利用的。」
《空洞骑士》最终 Boss 的弱点是「上方攻击特别有效」；灵魂暴君的弱点是「传送后总有一段静止」。这些不是 Bug，是设计出来的解法。
如果一个 Boss 没有任何明确的弱点，玩家就只能靠硬拼血量和反复试错——那不是难，那是不友好。设计 Boss 时，请像设计它的招式一样认真地设计它的弱点。

E思考题

如果你能答上这七个问题，这套东西就是真掌握了。

1. 请用一句话分别说出 FSM 和 BT 各自在回答什么问题。然后，拿你正在做的那个敌人，分别用这两种视角描述一遍它的行为。
2. 一个 Boss 有 12 个状态。用扁平 FSM 实现会遇到什么具体问题？HFSM 能解决其中哪些、不能解决哪些？
3. 行为树节点的 Running 返回值为什么不可省略？如果去掉它，只保留 Success / Failure，「播放 2 秒大招」这件事要怎么实现？代价是什么？
4. 「濒死大招必须能随时打断当前行为」这个需求，用状态机和行为树分别怎么实现？哪一种的代码更少、更容易改？为什么？
5. 某个 Boss 的突刺前摇只有 15 帧，而玩家治疗需要 45 帧。请解释这组数字之间的关系，以及它制造了什么样的战斗压力。
6. 为什么《空洞骑士》最终 Boss 在三阶段的攻击频率下降、看起来更慢了，但对玩家来说反而更难？请从「机制被收回」这个角度回答。
7. 你的 Boss 在测试中出现「偶尔发呆两秒」。请设计一套调试流程，说明你会先做什么、看什么、如何定位到具体原因。

架构是手段，不是目的。

状态机和行为树，最终都只是在回答同一个问题：
这一帧，这个 Boss 应该做什么。
而真正决定它好不好玩的，是它「做」的那件事，玩家能不能看懂。
