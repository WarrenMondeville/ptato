01

敌人在哪：腐烂软件的七个症状Design Smells

先说结论：设计原则本身不产生价值，消除症状才产生价值。所以在背诵任何一条原则之前，得先知道它是对着哪种病开的药。

Robert C. Martin 在《敏捷软件开发》里列了七种「设计腐烂」的症状。它们和 Fowler 的「代码坏味道」是同一类东西，只是层级更高——代码坏味道出现在某一段代码里，设计症状弥漫在整个系统结构上。

僵化

Rigidity

系统难以修改。你动手做一个看起来很小的改动，结果发现它影响到的地方远超预期；你改完那些地方，又牵出更多模块。

脆弱

Fragility

系统容易被改坏。改动导致程序中毫无概念关联的地方出错。修好这些地方，又给以后埋了更大的雷。

不动性

Immobility

系统难以复用。某一块代码其实在别的系统里也用得上，但要把它拆出来比重新写一遍还费劲，于是大家都选择重写。

粘滞

Viscosity

做正确的事比做错误的事更难。面对一个改动需求，保持设计原貌的路走起来很吃力，而 hack 一下很轻松——于是 hack 总是赢。

不必要的复杂

Needless Complexity

设计里包含当前并不需要的结构。典型来源是「以后可能会用到」——开发者提前为想象中的需求搭好了基础设施。

不必要的重复

Needless Repetition

设计里存在本可以统一到同一个抽象下的重复结构。最常见的来源是复制粘贴。

晦涩

Opacity

难以阅读和理解，表达不出意图。代码会随时间越来越晦涩，因为再没有人真正熟悉它了。

这七条里，僵化和脆弱是最容易被感受到的——它们直接表现为「我不敢动这段代码」。而它们有个共同机制：

僵化是怎么形成的：一次改动，一圈涟漪
设计原则干的全部事情，就是把涟漪圈住：让一次改动只在一个圈里扩散，而这个圈的大小是可预测的。
一句话记住这一节

七种症状里，有五种都能归到一个根因：变化的影响范围大于变化的意图范围。设计原则不是在追求「优雅」，是在追求「改一处，只崩一处」。

为什么「能跑」从来不是及格线

软件和硬件的根本差别在于：硬件的成本主要在制造，软件的成本主要在修改。一个能跑的系统，生命周期里 70% 到 90% 的成本发生在它第一次上线之后。

所以「代码能跑」只说明它通过了第一关。真正的评分项是：半年后，一个没写过这段代码的人，加一个新功能需要多久，需要多大的心理准备。

02

全景：七条原则不是七条平行线The Big Picture

先交代来历，因为这件事直接决定了它们之间的关系。

时间事件谁
1987提出「行为子类型」：子类型必须能替换基类型Barbara Liskov（后于 2008 年获图灵奖）
1987美国东北大学 Demeter 项目提出「只和直接朋友说话」Ian Holland / Karl Lieberherr
1988《面向对象软件构造》首次提出「对扩展开放，对修改关闭」Bertrand Meyer
1996在 Xerox 咨询时总结出接口隔离、依赖倒置；并重新诠释开闭原则Robert C. Martin
2000论文《Design Principles and Design Patterns》把五条原则放到一起讲Robert C. Martin
约 2004把这五条的首字母拼成 SOLID 这个助记词Michael Feathers

注意一个关键事实：SOLID 这个缩写是一个助记词，不是一套理论。五条原则来自不同的人、不同的年代、不同的失败案例。Martin 只是把它们收拢到一起，因为它们在实践里互相咬合。

而中文教材通常还会再加两条——迪米特法则和合成复用原则，凑成「七大设计原则」。这两条同样是几十年前的真金白银，不该被漏掉。

真正的关系：一个目标，四种手段

绝大多数教程把它们写成七条并列的清单，于是读者只能靠背诵和意志力去遵守。但换个角度看，这七条其实有明确的分工：

七条原则的分工
🎯 目标：开闭原则 OCP
让「加一个新功能」的边际成本接近于「只写字，不改字」
↑ 靠下面四组手段共同支撑
① 切分粒度：SRP 单一职责
先把系统切成「一个变化原因 = 一个单元」。这是地基——单元没切对，后面所有原则都没有作用对象
↓
② 继承的形态：LSP 里氏替换
子类必须能替换基类，否则「扩展」这个动作本身就不安全
↓
③ 接口的形态：ISP 接口隔离
接口要按客户端的角色切，不能按方法的集合切，否则抽象会变成一个更大的枷锁
↓
④ 依赖的方向：DIP 依赖倒置 + LoD 迪米特法则
DIP 管「依赖指向抽象还是指向实现」，LoD 管「依赖要不要穿过对象去够别人的内部」。方向定错，扩展点和复用都无从谈起
↓
⑤ 复用的方式：CRP 合成复用
同样能实现扩展，用继承还是用组合，代价差一个数量级
读的时候记住这张分工表：SRP 是地基，LSP / ISP / CRP 决定边界的形态，DIP / LoD 决定依赖的方向，OCP 是所有努力最终要换来的那个结果。

中文教材里有一句话总结得很准：开闭原则是目标，里氏替换原则是基础，依赖倒转原则是手段。这就是为什么违反任何一条，最终都会表现为「加功能变难了」——因为所有路都通向 OCP。

原则一句话违反时最典型的信号
SRP 单一职责一个类只应有一个引起它变化的原因一个类里同时出现业务规则、SQL 语句、邮件发送
OCP 开闭原则对扩展开放，对修改关闭加一个新类型，必须回到同一个 switch 里加分支
LSP 里氏替换子类型必须能替换它们的基类型调用处出现 if (x is XxxSub) 判断
ISP 接口隔离不应强迫客户端依赖它不使用的方法实现接口时写出抛异常或空的空方法
DIP 依赖倒置依赖抽象，而不是依赖具体实现业务代码里直接 new 数据库/HTTP 客户端
LoD 迪米特法则只和你的直接朋友说话a.GetB().GetC().Do() 这样的长链
CRP 合成复用优先用组合/聚合，而不是继承来复用为了拿到一个方法而继承一个语义不相关的类
这张表怎么用

把它当成体检表而不是考纲。你不需要记住定义，只需要在写完一段代码之后，用右边那列去扫一眼自己的代码——这七个信号里，有没有出现哪怕一个。

03

SRP 单一职责：一个类几个老板Single Responsibility Principle

一句话：一个类应该只有一个引起它变化的原因。
Martin 在后来的《架构整洁之道》里把它改写得更精确：一个模块应该只对一个角色（actor）负责。

这条原则被误解的次数，大概是其他六条的总和。最常见的误解是把它读成「一个类只能干一件事」——于是写出几百个 5 行的类，谁也不敢碰。

「原因」指的是谁在提要求，不是代码有几行。Martin 自己给过一个非常实用的口诀：

Gather together the things that change for the same reasons. Separate those things that change for different reasons.
把因相同原因而变化的东西聚在一起，把因不同原因而变化的东西分离开。 —— Robert C. Martin，《敏捷软件开发》

一个真实代价：被偷偷焊死的两条变更路径

Martin 举过一个教科书级的例子。公司里有个 Employee 类，三个方法分别服务于三个不同的部门：

  • CalculatePay() —— 计算薪资，规则由财务部门（汇报给 CFO）制定
  • ReportHours() —— 统计工时，规则由人事部门（汇报给 COO）制定
  • Save() —— 持久化，由数据库管理员（汇报给 CTO）制定

看起来还算合理，对吧？真正的问题藏在暗处：CalculatePay() 和 ReportHours() 内部都调用了同一个私有方法 RegularHours()（计算非加班工时）。这个共享，看上去是消除重复——其实是灾难的开始。

一次看似无关的改动，半年后炸在另一个部门
财务团队要调整加班口径
负责人改了 CalculatePay()，顺手也改了它依赖的私有方法 RegularHours()
↓
但他没注意到 ReportHours() 也在用同一个方法
没有任何编译错误，没有任何测试变红——因为两边都由测试覆盖，而它们看起来是独立的
↓
财务测完，一切正常；人事毫不知情
工时报表已经算错了，但没人去看
↓
某个深夜，工资算错了，或者审计发现了工时对不上
根因追溯到半年前那行改动
共享一个私有方法，就是把两条本来独立的变更路径偷偷焊在了一起。SRP 要防的就是这个：不是类太大，而是它同时被多个「老板」指挥。
SRP 的真正定义

一个类之所以违反 SRP，不是因为它方法多，而是因为它必须服务于多个变化动因（actor）。判断方法只有一个：能用两个不同的主语给「这个类要改」造句吗？
「因为财务改了薪资规则，所以要改它」 + 「因为数据库换了表结构，所以要改它」——两个主语，两个原因，违反。

代码里的样子

违例：一个方法伺候四个老板

public class OrderService
{
    public void Submit(Order order)
    {
        // ① 校验规则变化 —— 产品经理说了算
        if (order.Items.Count == 0)
            throw new ArgumentException("订单不能为空");

        // ② 计价规则变化 —— 财务说了算
        var total = order.Items.Sum(i => i.Price * i.Qty) * 0.9m;

        // ③ 表结构变化 —— DBA 说了算
        _conn.Execute("INSERT INTO orders (id, total) VALUES (?, ?)", order.Id, total);

        // ④ 触达策略变化 —— 运营说了算
        new SmtpClient("smtp.corp.com").Send(order.Customer.Email, "下单成功");

        // ⑤ 日志格式变化 —— 运维说了算
        _logger.Info($"order {order.Id} submitted");
    }
}

五个部门，五个变化原因，全挤在一个方法里。任何一个部门改需求，这段代码都要动，而它同时又被其他四个部门依赖着——这就是僵化（Rigidity）的最小可复现样本。

拆完：Service 只做编排

// 每个类一个变化原因，互不知晓
public class OrderValidator   { /* 只关心规则变化 */ }
public class PriceCalculator  { /* 只关心计价变化 */ }
public class OrderRepository   { /* 只关心存取变化 */ }
public class OrderNotifier     { /* 只关心触达变化 */ }

// Service 的职责只剩一件事：按顺序协调它们
public class OrderService
{
    public void Submit(Order order)
    {
        _validator.Validate(order);
        order.Total = _calculator.Calculate(order);
        _repository.Save(order);
        _notifier.OrderSubmitted(order);
    }
}
注意 OrderService 没有被删掉

它留下了，而且它自己的职责非常单一：编排顺序。如果某天「先发货再通知」变成「先通知再发货」，改了它也不违反 SRP——因为变的始终是同一件事（流程顺序），只有一个原因。
很多人拆 SRP 时会把这类「协调者」也拆掉，结果是调用方被迫自己按顺序调用四个对象——编排逻辑被复制到了每一个调用点。那才是更大的灾难。

职责的三个层次

SRP 说的「单元」可以是三种粒度，中文教材据此把它和另一条原则区分开：

类级：SRP

一个类一个变化原因。这是最常被讨论的一层。

接口级：ISP

接口按客户端角色切。当「职责」落在接口上时，SRP 就变成了接口隔离原则。

方法级

一个方法只做一件事——这正是《重构》里「提炼函数」的判据：如果一段代码能用一句不含「和」的话描述它，就不用拆。

反向警告

Martin 本人也提醒过：这条原则很容易走过头，类太多也是坏味道。判断标准永远是「变化原因是否相同」，而不是「类是不是够小」。
一个 300 行、但全部服务于同一件事的类，是好设计；十个各 30 行、但每次改需求都要同时改这十个的类，是坏设计。

04

OCP 开闭原则：加功能要动几个文件Open-Closed Principle

一句话：软件实体（类、模块、函数）应该对扩展开放，对修改关闭。
能靠「新增代码」实现的，就不要靠「修改已有代码」实现。

这一条是七条里唯一称得上「目标」的原则——前面那节的分工图里，其他六条最终都在为它服务。原因很朴素：

修改已有代码的真实成本

改一行代码，成本不是「打字的时间」，而是三件事：① 回归风险（原本能用的功能可能被改坏）、② 重新验证成本（所有依赖它的模块都要重测）、③ 认知负担（读代码的人必须先理解这段逻辑的全部历史用途，才敢动手）。
而新增一个类，这三项成本几乎都是零。

一个几乎没人提的事实：OCP 有两个版本

这条原则在几十年里被重新定义过一次，两个版本的实现手段完全不同：

Meyer 版（1988）

靠实现继承。一个类编译好、放进库里、被客户使用，它就是「关闭」的；但任何人都可以继承它来添加新特性，所以它同时是「开放」的。

问题：子类依赖父类的实现细节，父类一改，子类跟着遭殃。

Martin 版（1990s）

靠抽象接口 + 多态。接口的规约是关闭的，任何人都不能改；而实现是开放的，谁都可以提供新的实现。

这是今天绝大多数人说的 OCP，也是更耐用的那个版本。

知道这段历史的价值在于：当有人说「用继承就能满足 OCP」时，你清楚那只说对了一半——继承只是 Meyer 的答案，而且是个有副作用的答案。

代码里的样子：一条永远在长的 if-else

违例：每加一种方式，都要回到这里

public PaymentResult Pay(string method, decimal amount)
{
    if (method == "alipay")   { /* 支付宝 SDK 调用 */ }
    else if (method == "wechat") { /* 微信 SDK 调用 */ }
    else if (method == "card")  { /* 银行卡网关调用 */ }
    else throw new NotSupportedException(method);
    // 明天要接 Apple Pay —— 又要回来改这个已经测试过的函数
}

问题不在于它写得不好看，而在于每次扩展都在修改一段所有人都依赖的代码。它每被改一次，之前所有的测试结果都作废。

改完：扩展 = 新增一个文件

public interface IPaymentGateway
{
    string Method { get; }
    PaymentResult Pay(decimal amount);
}

public class AlipayGateway : IPaymentGateway { /* ... */ }
public class WechatGateway : IPaymentGateway { /* ... */ }

// 接入 Apple Pay：只新增 ApplePayGateway.cs
// 下面这个函数一个字都不会变
public PaymentResult Pay(string method, decimal amount)
    => _gateways[method].Pay(amount);
最实用的一条判据

不要问「这个类是否符合 OCP」。要问：「加一个新功能，我需要修改几个已经测试过的文件？」
答案里每多一个数字，就是一处 OCP 债务。理想值是 0。
这个方法比任何定义都好用，因为它可以量化：下次需求来了，数一下 diff 里改动的文件数。

OCP 的常见实现手段

设计模式里有一大半其实都是「怎么在某个具体场景下做到 OCP」的答案：

场景典型手段扩展点在哪
算法/策略有多个变体，运行时切换策略模式 Strategy新增一个策略实现类
流程骨架固定，某些步骤可变模板方法 Template Method子类重写钩子方法
一个变动需要通知多个下游观察者模式 Observer新增订阅者
需要在不改原类的前提下叠加功能装饰器模式 Decorator新增一个装饰器
对稳定类型集合反复添加新操作访问者模式 Visitor新增一个访问者（代价是类型集合必须稳定）
宿主程序加载外部模块插件架构 / 事件驱动外部提供实现并注册
但这条原则的陷阱最深

你无法为所有维度预留扩展点。为想象中可能发生的扩展而建的抽象，正是第 01 节里那个「不必要的复杂」症状。
判断依据不是「将来可能会变」，而是「它已经变过两三次了」。OCP 应该开在已经被验证过的变化方向上，而不是开在想象里。这条界限的具体划法，在第 10 节展开。

05

LSP 里氏替换：能被替换才叫子类Liskov Substitution Principle

一句话：子类型必须能够替换它们的基类型，而不改变程序的正确性。
所有引用父类的地方，换成一个子类对象，程序都应该照常工作——而且不需要知道换过。

它来自 Barbara Liskov 1987 年在 OOPSLA 上的主题演讲《Data Abstraction and Hierarchy》，1994 年她与 Jeannette Wing 给出了形式化版本，2008 年 Liskov 因此获得图灵奖。

注意原文里最关键的那个词：行为子类型（behavioral subtyping）。LSP 说的从来不是语法上的继承关系，而是行为契约的兼容性。

契约的四条规矩

把父类方法看成一纸合同：调用方有义务满足「前置条件」，方法方有责任兑现「后置条件」。子类重写方法时，只能让合同变得更宽松，不能更苛刻：

规矩允许违反
前置条件
不能加强		父类要求「传个正数」，子类放宽成「传任意整数」父类说「正数就行」，子类说「必须大于 100」
后置条件
不能减弱		父类承诺「返回一条记录」，子类承诺「返回一个非 null 的完整对象」父类保证「一定有结果」，子类可能返回 null
异常
不能新引入		子类不抛异常，或只抛父类已声明的异常的子类父类方法没声明异常，子类抛出 NotSupportedException
不变式
必须保持		子类维持父类的所有恒定约束父类保证「宽高独立可变」，子类让它们互相影响

那个被讲烂、但依然最准的例子

正方形继承长方形。数学上正方形是长方形，所以很多人的第一反应是「这继承天经地义」。但把它放到代码里：

public class Rectangle
{
    public virtual int Width  { get; set; }
    public virtual int Height { get; set; }
    public int Area => Width * Height;
    // 隐含契约：设置 Width 不会影响 Height
}

public class Square : Rectangle
{
    public override int Width  { set { base.Width = value; base.Height = value; } }
    public override int Height { set { base.Width = value; base.Height = value; } }
    // 为了保住「四边相等」，它必须破坏父类的契约
}

然后某段代码这样用：

// 这段代码只认识 Rectangle，它会以为自己拿到的是矩形
void Resize(Rectangle r)
{
    r.Width  = 4;
    r.Height = 5;
    Assert(r.Area == 20);   // 传 Square 进来 → 实际是 25
}
替换之后，谁的预期被打破了
调用方 Resize() 的预期
我拿到的是 Rectangle。Width = 4 之后，Height 还是原来那个值
↓ 传入 Square 之后
实际发生
Width = 4 把 Height 也改成了 4；Height = 5 又把 Width 也改成了 5
↓
代码没有报错，没有编译警告
只是结果悄悄错了
契约视角看得很清楚：Square 的前置条件更强（必须 width == height），后置条件更弱（setWidth 不再保证 height 不变）。两头都违规。
根因一句话

面向对象里的继承表达的是行为契约的可替换性，不是数学集合的包含关系。
「正方形是长方形」在集合论里成立，在代码契约里不成立——因为长方形的契约核心是「宽高独立可变」，而这恰恰是正方形无法兑现的。

同理还有那个经典的鸟类例子：Ostrich : Bird，但 Fly() 只能抛异常或什么都不做。只要代码里有一处 foreach (var b in birds) b.Fly();，这个继承体系就塌了。

最灵的报警器：类型判断

LSP 违例的伤口长什么样

代码里出现这类写法，基本可以直接判定 LSP 已经破了：

if (x is Square)　if (x.GetType() == typeof(...))
var s = x as SpecialSub;　if (bird is Ostrich) { /* 不让它飞 */ }

逻辑很直白：调用方不得不回头确认「你到底是哪一种」，说明它已经不能信任基类的契约了。本来多态的目的就是让调用方不用做这个判断。

修法：三条路，按优先级

  1. 抽出真正的共同抽象。让 Shape 只声明两者都诚实做到的事（Area()），Rectangle 和 Square 各自独立实现。注意：这样它们之间不再是继承关系——因为本来就不该是。
  2. 把可变性拿掉，改成不可变值对象。WithWidth(4) 返回一个新矩形，任何一次设置都不会有副作用。副作用一消失，契约冲突自然消失——这也是函数式设计里最常用的解法。
  3. 改用组合（见第 09 节）。如果继承只是为了白拿几个方法，那它从一开始就不该存在。
这条原则真正的工程含义

LSP 实际在说：继承绝不应该是「代码复用的便利工具」，而必须是一种严格的行为子类型关系。
如果你只是因为「B 想用 A 里的那几个方法」而让 B 继承 A，同时又得在 B 里禁用或覆盖 A 的部分方法——那你已经违约了，改用组合。

06

ISP 接口隔离：那些抛异常的方法Interface Segregation Principle

一句话：不应该强迫客户端依赖它不使用的方法。
多个客户专用的接口，好过一个通用的总接口。

它是被一台打印机逼出来的

ISP 不是坐在书桌前想出来的，是 Martin 在 Xerox 做咨询时从一个真实的烂摊子里总结的。这个故事的细节值得完整讲一遍，因为它是「设计问题如何变成工程灾难」的范本：

Xerox 打印机系统：一台机器，九个功能，一个 Job 类
背景
Xerox 开发新的打印机系统，要支持打印、装订、传真等多种任务。软件从头写起，早期跑得挺好
↓
问题
几乎所有任务都经由同一个 Job 类。它逐渐长成一个「胖类」，塞满了面向各种不同客户的方法
↓
后果
一个装订任务也得「知道」打印任务的全部方法。改这里的任何一处，都要把整个 Job 重新编译、重新部署 —— 一次部署循环长达一小时，开发几乎停摆
↓
Martin 的解法
在 Job 和它的客户之间加一层接口，按任务类型切开：打印任务只看到 IPrintJob，装订任务只看到 IStapleJob。这就是今天的 ISP —— 而他用的手段，正是 DIP
注意这个因果链：设计缺陷 → 部署代价飙升 → 开发效率归零。ISP 不是为了好看，是为了让无关的客户之间不互相牵连。

代码里的样子

违例：胖接口

public interface IWorker
{
    void Work();
    void Eat();      // 机器人员工不需要
    void Sleep();    // 机器人员工也不需要
}

public class Robot : IWorker
{
    public void Work()  { /* ... */ }

    // 这两行就是 ISP 在报警
    public void Eat()   => throw new NotSupportedException();
    public void Sleep() => throw new NotSupportedException();
}

改完：按角色切，不按方法切

public interface IWorkable { void Work(); }
public interface IFeedable { void Eat(); void Sleep(); }

public class Robot : IWorkable                       // 只实现它真正能兑现的
{ public void Work() { /* ... */ } }

public class Human : IWorkable, IFeedable
{ public void Work()  { /* ... */ }
  public void Eat()   { /* ... */ }
  public void Sleep() { /* ... */ } }
两个最好用的违例信号

信号一：实现接口时写出 throw new NotImplementedException() / NotSupportedException / 一个空方法体。空实现不是「占位」，是在告诉你「这个接口里混进了不属于这个客户端的东西」。
信号二：同一个接口被多个客户端依赖，而每个客户端都只用其中两三个方法。这说明它其实已经是好几个接口叠在一起了。

游戏开发里最常踩的版本

写游戏时这条特别容易踩，因为大家都想搞一个万能的 IEntity：

// ❌ 万能接口：炮台和宝箱都被迫实现一堆用不上的东西
public interface IEntity
{
    void TakeDamage(int dmg);
    void Heal(int hp);
    void Interact(Player p);
    void PickUp(Item item);
}

// ✅ 按角色切：谁能挨打、谁能被治疗、谁能交互，是三种独立能力
public interface IDamageable   { void TakeDamage(int dmg); }
public interface IHealable     { void Heal(int hp); }
public interface IInteractable { void Interact(Player p); }

// 炮台：只挨打     宝箱：只交互     可破坏的治疗点：挨打 + 可治疗
public class Turret   : IDamageable { }
public class Treasure : IInteractable { }
public class HealPad  : IDamageable, IHealable { }

这样做的直接收益是：碰撞检测写 if (col is IDamageable d)，交互系统写 if (col is IInteractable i)——每个系统只认识自己需要的那一种能力，加一种新实体类型时，所有已有系统的代码都不用动。这又回到 OCP 了。

但别切碎

ISP 的目标是高内聚的分组，不是「粒度最大化」。把每个方法都拆成一个单方法接口，会带来接口数量爆炸、难以发现和组合的问题。
正确的切法只有一个依据：客户端是谁，它们各自需要哪一组能力。切分的依据是调用方的角色，不是方法的数量。
这也是 ISP 常被称作「角色接口（role interface）」的原因。

ISP 和 SRP 的关系

SRP 管类，ISP 管接口。同样一句「一个变化原因」，落在类上是单一职责，落在接口上是接口隔离。 —— 这也是中文教材里把两者分开列的原因

另外注意它们和 DIP 的连带关系：ISP 提供的那些窄接口，正好就是 DIP 需要的抽象——越窄的接口越容易替换，也越容易测试。这三条在实践里几乎总是一起出现的。

07

DIP 依赖倒置：倒过来的到底是什么Dependency Inversion Principle

两句话，缺一不可：
① 高层模块不应该依赖低层模块，两者都应该依赖抽象。
② 抽象不应该依赖细节，细节应该依赖抽象。

这是七条里名字起得最糟的一条——「倒置」这个词让无数人以为它说的是调用顺序反过来，或者控制流反转。不是。

倒的是「编译期的依赖方向」

传统分层里，业务代码必须 import 数据库驱动的类型才能写 SQL。于是业务层在编译期依赖了基础设施层——数据库换版本、换厂商、换 ORM，业务层就要跟着改。
DIP 之后，业务层自己定义它需要的接口（IOrderRepository），数据库层来实现这个接口。依赖箭头反过来了：不是业务层依赖基础设施，而是基础设施依赖业务层定下的契约。
调用方向一点没变（业务层照样调用数据库），变的是谁在编译期认识谁。

依赖倒置前 vs 后
左边那个箭头是「焊死」的：换数据库要改业务代码。右边那个箭头是「插拔」的：换实现只需要提供一个新的实现类，业务代码一个字都不动 —— 又一次回到 OCP。

代码里的样子

// ❌ 高层模块自己决定了要用什么
public class OrderService
{
    private readonly MySqlOrderRepository _repo = new MySqlOrderRepository();

    public void Submit(Order order)
    {
        _repo.Save(order);      // 业务代码里出现了 SQL 专属类型
    }
}
// 后果：单测必须连真数据库；换 ORM 要改业务层；换云厂商要改业务层
// ① 由高层定义它需要的契约（放在业务/领域层）
public interface IOrderRepository
{
    void Save(Order order);
    Order FindById(string id);
}

// ② 高层只认识抽象，具体实现从外面送进来（构造器注入）
public class OrderService
{
    private readonly IOrderRepository _repo;

    public OrderService(IOrderRepository repo) => _repo = repo;

    public void Submit(Order order) => _repo.Save(order);
}

// ③ 低层实现去实现它（放在基础设施层）
public class MySqlOrderRepository : IOrderRepository { /* ... */ }
public class InMemoryOrderRepository : IOrderRepository { /* 单元测试用 */ }
必须澄清的一组混淆：DIP ≠ DI ≠ IoC 容器

这三个词被混用得极其严重，但它们不在一个层面上：

DIP 是设计原则——规定依赖应该指向抽象。它管的是「谁认识谁」。
DI（依赖注入）是实现手段——把依赖从外部传进来，而不是在内部创建。它管的是「对象怎么拿到它的协作者」。
IoC 容器是工具——自动帮你完成装配。它管的是「谁来 new」。

关键推论：你完全可以不引入任何容器、手写构造器注入，就完整地满足 DIP；反过来，一个用了 Spring / 各种 DI 框架的项目，如果业务类里到处 new 具体实现，它照样违反 DIP。装了容器不等于做对了设计。

判据与实践收益

扫描方法：在业务层/领域层的代码里搜索 new，看它后面跟的是什么。如果跟的是 SqlConnection、HttpClient、FileStream、某个云厂商 SDK 的 Client——那就是 DIP 违例。另一个信号：业务方法的参数或返回值里出现了第三方 SDK 的类型。

可测试

单测时注入内存实现或 mock，测试跑在毫秒级，不依赖任何外部环境。这是最立竿见影的收益。

可替换

换数据库、换消息队列、换云厂商，改的只是基础设施层的一个实现类。

可并行

接口一旦定下，两个人可以同时开工——一个写业务，一个写实现，互不阻塞。

反过来的代价

抽象的引入是有成本的：多一层间接、多一个文件、新人需要多跳一次才能看懂调用链。
所以不是所有依赖都值得倒置。判断标准是那条依赖是否稳定、是否可能被替换：领域模型依赖 string、DateTime 这类语言内置类型完全合理，没有人会去为它们抽接口。抽象应该开在真正会变、或者需要被隔离的地方。

08

LoD 迪米特法则：数一数你的点号Law of Demeter

一句话：只和你的直接朋友说话。
也叫最少知识原则（Principle of Least Knowledge）——一个软件实体应当尽可能少地与其他实体发生相互作用。

它的出身很特别，不是从设计理论里推出来的，而是一个学术项目的副产品：1987 年秋，美国东北大学的 Demeter 项目里，研究者 Ian Holland 提出了这条风格规则；1989 年 Karl Lieberherr 与 Holland 在 IEEE Software 上将它正式发表。

名字的由来有个小八卦：项目组当时用的硬件描述语言叫 Zeus（宙斯），于是这个工具就顺手取了宙斯姐姐的名字 —— 希腊神话里的农业女神得墨忒耳（Demeter），寓意软件像作物一样「生长」。

谁是「朋友」

一个方法 f 里，允许调用的对象只有四类，其余全算「陌生人」：

可以调例子为什么
对象自己this.Method()自己的方法当然可以调
f 的参数方法签名里传进来的对象调用方主动交到你手上的，关系明确
f 里自己创建的对象var tmp = new Foo();生命周期完全由你掌握
对象的直接成员_repository.Save()它就是你的一部分
✗ 成员对象的内部对象_customer.GetAddress().GetCity()这是陌生人，你正在伸手掏别人的口袋

代码里的样子：火车残骸

// ❌ 一串点号组成的「火车残骸」（train wreck）
var city = order.GetCustomer().GetAddress().GetCity();

// 这一行代码，让 OrderService 知道了三件事：
//   1. Order 里有一个 Customer
//   2. Customer 里有一个 Address
//   3. Address 上有个 GetCity()
// 任何一条变了，这行都会崩 —— 而且崩在一个离得很远的类里
// ✅ 让 Order 自己回答这个问题
public class Order
{
    public string GetShippingCity() => _customer.GetShippingCity();
}

// Customer 再往下委托一层，每一层只知道自己的直接伙伴
public class Customer
{
    public string GetShippingCity() => _address.GetCity();
}

// 调用方一句话，且完全不关心内部结构
var city = order.GetShippingCity();

现在如果 Customer 改成支持多个地址（收货地址、账单地址），需要改的只是 Customer.GetShippingCity() 一处——所有调用方毫发无伤。这就是 LoD 的全部价值。

判据：数点号

很多面向对象语言用 . 表示成员访问，所以这条原则可以被压成一句极简的口诀：一个方法里，尽量只用一个 .。
a.Method() —— 不违反。
a.GetB().Method() —— 违反。
a.GetB().GetC().Method() —— 严重违反。
（严格来说这不是官方判据，但它异常好用，因为它可以机械地执行。）

但别教条化：点号不是罪证

Fluent API、Builder、LINQ 查询都是刻意的链式设计，它们完全合法。区别在于：链上每一步返回的对象，是不是「同一个逻辑对象的延续」，还是「另一个对象的内部零件」。
query.Where(x).OrderBy(y).ToList() —— 这是同一条查询流水线的延续，没问题。
order.GetCustomer().GetAddress().GetCity() —— 这是穿越了三层对象去掏出别人的内部结构，有问题。
LoD 的本意是不要穿越对象去访问它内部的零件，不是「禁止点号」。

代价也要说清楚

LoD 在方法层面会让接口变窄（每个方法只需要知道很少几个伙伴），但在类层面会让接口变宽——因为你必须为每种转发需求写一个包装方法。Order 上会多出 GetShippingCity()、GetShippingZip()、GetCustomerLevel()……

所以它有时会被抱怨「写了一堆无脑转发」。这确实是成本，但换来的是封装边界不被击穿。经验做法是：为真实存在的业务问题写转发，而不是为了「把所有点号都消掉」而写。

一个顺手的好处

很多分层架构（Controller / Service / Repository、MVC 的三层）本质上就是在系统级别执行迪米特法则：每层只能调用自己这层和下一层，跨层调用（跳层）被视为违规。
所以当你在代码规范里写「Controller 不许直接调 Repository」时，你其实是在引用 LoD。

09

CRP 合成复用：白箱与黑箱Composite Reuse Principle

一句话：优先使用对象组合/聚合，而不是继承，来达到复用的目的。
注意它说的是「复用」，不是「禁止继承」。

为什么复用要分两种？因为「拿到一段现成的实现」这件事，有两种完全不同的拿法，代价差一个数量级。

白箱复用 vs 黑箱复用
继承 = 白箱复用
父类的内部细节对子类可见。就像把一个零件的内部结构图交给你，你可以改它，但它一改，你也得跟着改
vs
组合/聚合 = 黑箱复用
成员对象的内部细节不可见，只能通过公开接口交互。就像拿到一个封装好的模块，你只管插上、只管调，它内部怎么实现与你无关
「白箱 / 黑箱」说的就是可视性：你能不能看到、进而依赖上对方的实现细节。
对比维度继承（白箱复用）组合 / 聚合（黑箱复用）
封装性破坏——基类实现细节对子类可见保持——只通过公开接口交互
耦合度高，编译期强耦合低，可面向抽象
绑定时机静态，编译期就定死可动态，运行时替换组件
复用范围全盘继承——用不上的方法也得扛着按需取用——只用需要的那几个方法
基类/成员变化的影响基类一改，所有子类都可能被波及成员对象变化对使用方影响很小
灵活性低高

继承的四个坑

  1. 破坏封装。子类可以看到 protected 成员，于是基类的内部细节变成了「事实上公开的 API」。你以后想重构基类内部，得先问问所有子类答不答应。
  2. 静态绑定。继承关系在编译期就定死了，运行时换不了。而组合可以在运行时注入不同实现——这正是策略模式、装饰器模式的基础。
  3. 全盘接收。继承是「全部拿走」，没有选择余地。你为了复用基类里一个方法，得连它另外十个方法一起继承过来——而这十个方法你一个都不用。
  4. 脆弱基类（Fragile Base Class）。基类改一个看起来人畜无害的方法，所有子类的行为都可能悄悄变掉。这是继承体系里最难排查的一类 bug。

代码里的样子

// ❌ 为了白拿「发通知」的代码而继承 —— 短信不是一个邮件
public class EmailNotifier
{
    public void Send(string to, string msg) { /* SMTP 逻辑 */ }
}

public class SmsNotifier : EmailNotifier   // 语义上完全不成立
{
    public new void Send(string to, string msg) { /* 短信逻辑 */ }
    // 顺带继承了 EmailNotifier 全部内部细节，包括那些只有邮件才需要的字段
}
// ✅ 抽出「通知方式」这个抽象，用组合 + 注入
public interface INotifier { void Send(string to, string msg); }

public class EmailNotifier : INotifier { public void Send(string to, string msg) { } }
public class SmsNotifier   : INotifier { public void Send(string to, string msg) { } }

public class OrderService
{
    private readonly INotifier _notifier;      // 组合，而且依赖的是抽象
    public OrderService(INotifier notifier) => _notifier = notifier;
}

Is-A 与 Has-A

教材给的判断标准是：「是一个」用继承，「有一个」用组合。

  • 狗是一种动物 → 可以用继承
  • 汽车有一个发动机 → 必须用组合
但 Is-A 还不够，必须再过 LSP 那一关

这是最容易漏掉的一步。即使确实是 Is-A，也要问一句：子类能不能完全兑现父类的契约？

「圆是一种椭圆」——数学上成立（Is-A ✓），但椭圆类宣称「长轴短轴独立可变」，圆做不到（LSP ✗），所以「圆不该继承椭圆」。
同理「正方形是一种长方形」也是 Is-A 成立、LSP 不成立。

所以完整的判断是两步：先问 Is-A，再问 LSP。两步都过，才用继承；否则用组合。

用一句人话来记

继承是「生下来就定了」——你是这种船，你这辈子就是这种船。
组合是「出门前再挑」——今天装蒸汽机，明天换核动力，船还是那条船。
另一句关键区别：继承是「全部拿走」，组合是「按需取用」。

顺带一提，「优先使用对象组合，而不是类继承」这个建议在《设计模式》（GoF）那本书的开篇就写着了——它比 SOLID 的流行还早。

边界：什么时候该停下来When Not To

前面九节讲的都是「该怎么做」。但只讲这一半是不负责任的——这些原则被滥用时造成的破坏，和违反它们时一样大。Martin 自己列的设计症状里就有两条（不必要的复杂、不必要的重复），专门用来形容「太努力遵守原则」的后果。

刹车一：YAGNI —— 别为想象的需求留口子

YAGNI（You Aren't Gonna Need It，你不会需要它）是极限编程的口号。它针对的正是 OCP 最常见的误用：

「以后可能会用到」是最贵的五个字

为想象中的扩展点建抽象，代价是现在就要支付（多一层间接、多一个接口、多一份认知负担），而收益可能永远不发生。更糟的是，抽象一旦落地，它就会绑架真实需求——后来的需求会被硬塞进这个形状不对的抽象里，于是走向第 10 节下面那个「错误的抽象」。

判断标准：这个扩展点，被真实需求验证过两次了吗？没有的话，就先写直白的 if，等第三次出现时再抽象。

刹车二：DRY 的误用 —— 长得一样 ≠ 该合并

DRY（Don't Repeat Yourself）的原意是「每一份知识，在系统里只应该有一个权威的表述」。它说的是知识不要重复，不是代码文本不要重复。

这两者的差别是致命的：两段代码今天看起来一模一样，但如果它们的变化方向不同——比如一段跟着税率变，另一段跟着汇率变——把它们合并成一个函数，就是在制造一颗定时炸弹。

Duplication is far cheaper than the wrong abstraction.
重复远比错误的抽象便宜。宁可重复，也不要错误的抽象。 —— Sandi Metz，RailsConf 2014 演讲 / 2016 博客《The Wrong Abstraction》

她描述的那个过程，几乎每个团队都经历过一遍：

一个抽象是怎么烂掉的
程序员 A 看到了重复
提取出来，起个名字，替换掉所有重复。代码很完美，A 愉快地走了
↓
程序员 B 接到一个新需求
这个抽象「几乎正好合适」。B 觉得自己有义务维护它，于是给它加了个参数，再加个条件分支
↓
又来一个需求，又一个人
再加一个参数，再加一个条件分支…… 循环下去
↓
直到代码变得无法理解
「它已经不是一个抽象了，而是一段布满条件的流程，把一堆隐约相关的想法交织在一起，难以理解，且极易改坏」
Metz 指出的关键机制是沉没成本谬误：代码越复杂、越难以理解，我们越舍不得删它——「能搞成这样肯定花了不少功夫，删掉太可惜了」。但正确的做法恰恰是往回走。
错误的抽象怎么修：往回走

Metz 给的方子非常具体，只有三步：

① 把抽象重新内联回每一个调用方；② 在每个调用方里，根据它实际传的参数，只保留它真正需要的那部分代码，把用不到的删掉；③ 删完再重新观察——你会发现那些调用方其实跑的是相当不同的代码，然后从干净的状态重新提取抽象。

「面对错误的抽象，最快的前进方式是往回走。」

刹车三：抽象税

每一层接口、每一个工厂、每一个容器都有认知成本。当一个新人需要跨 5 个文件才能看懂「保存订单」这件事时，你收的税已经超过了收益。

一条定调的话：设计原则描述的是代价的方向，不是必须执行的命令。
违反原则不犯法——它意味着你选择把成本挪到未来去支付。如果你清楚自己在借这笔债、并且知道利息是多少，那这就是一个合格的工程决策。真正危险的是不知道自己借了债。

一张决策图：这里到底该不该抽抽象

抽象决策流程
① 这段代码，你确定它会变吗？
不确定 → 别抽象，先写直白；确定 → 往下
↓
② 它已经真实变过两次以上吗？
没有（只是「将来可能」）→ 别抽象；有 → 往下
↓
③ 这些变化是同一个原因引起的吗？
不同原因 → 别合并（DRY 误用），分开；相同原因 → 往下
↓
④ 抽象出来之后，调用方会变简单吗？
会不会只是把复杂度从调用方搬到了接口层？如果是，再想想
↓
⑤ 那就抽象它 —— 并且只抽象这一个维度
不要顺手为「别的可能变化」也留口子。留下一个你自己都说不清用途的扩展点，等于留下一个 bug 温床
这五问其实就是 「三次法则」（Refactoring 里那条）在抽象层面的展开：第一次直接做，第二次照做一遍，第三次才抽象。

完整走一遍：120 行的上帝类A Full Walkthrough

前面每节都是单独讲一条。但真实的重构不是逐条打卡，而是一条原则的修复会自然牵引出下一条。这一节用一个订单提交的案例，完整走一遍这个过程。

起点：一个方法干六件事

public class OrderProcessor
{
    public void Submit(Order order, string payMethod)
    {
        // 1. 校验
        if (order.Items.Count == 0) throw new Exception("空订单");
        if (order.Customer == null) throw new Exception("缺客户");

        // 2. 计价
        decimal total = 0;
        foreach (var item in order.Items)
            total += item.Price * item.Qty;
        if (order.Customer.IsVip) total *= 0.9m;
        order.Total = total;

        // 3. 支付 —— 每接一家就要回来加一个分支
        if (payMethod == "alipay")       { /* ... */ }
        else if (payMethod == "wechat")  { /* ... */ }
        else if (payMethod == "card")    { /* ... */ }

        // 4. 持久化
        var conn = new SqlConnection("Server=...");
        conn.Execute("INSERT INTO orders ...");

        // 5. 通知
        var email = order.Customer.GetAddress().GetEmail();   // 伸手掏了三层
        new SmtpClient().Send(email, "下单成功");

        // 6. 日志
        Console.WriteLine("submitted: " + order.Id);
    }
}

这段代码能跑，测试也挺好写。但把它放到六个变化方向上来检验，全中：产品改校验规则要改它、财务改折扣要改它、接新的支付渠道要改它、DBA 换表要改它、运营改通知文案要改它、运维改日志格式也要改它。

第 1 步：按「变化原因」切开 —— SRP

这是所有工作的起点。先给每个变化原因找一个落脚点：

变化原因（谁在提要求）落到哪个类
校验规则 —— 产品OrderValidator
计价规则 —— 财务PriceCalculator
支付渠道 —— 商务IPaymentGateway 的实现
表结构 —— DBAOrderRepository
触达策略 —— 运营INotifier 的实现
流程顺序 —— 业务本身OrderService（唯一保留的编排者）

注意最后一行：流程顺序本身就是一个独立的变化原因。所以 OrderService 不是「没拆干净的残留」，它是一个职责明确的协调者。

第 2 步：支付渠道要从「分支」变成「可扩展」—— OCP

拆完之后立刻撞上下一个问题：if (payMethod == ...) 这条链还在。每接一家新渠道，都要回来改这个已经测试过的函数——违反 OCP。

public interface IPaymentGateway
{
    string Method { get; }
    PaymentResult Pay(Order order);
}

// 接入 Apple Pay 只需新增一个文件，上面这段代码完全不动
public class ApplePayGateway : IPaymentGateway { /* ... */ }

第 3 步：通知接口不要长胖 —— ISP

做通知时一个很自然的冲动是写个万能接口：SendEmail() + SendSms() + SendPush()。但短信渠道根本不需要实现推送——于是又出现抛异常的空方法。

// 按「通知渠道的能力」切，而不是按「通知」这个概念切一个大的
public interface IOfflineNotifier { void Send(Contact to, string msg); }   // 邮件/短信
public interface IPushNotifier    { void Push(string deviceId, string msg); } // 推送

第 4 步：让业务层不再认识数据库 —— DIP

public class OrderService
{
    private readonly OrderValidator  _validator;
    private readonly PriceCalculator _calculator;
    private readonly IOrderRepository _repo;      // 抽象
    private readonly IPaymentGateway  _payment;   // 抽象
    private readonly INotifier        _notifier;  // 抽象

    public void Submit(Order order)
    {
        _validator.Validate(order);
        order.Total = _calculator.Calculate(order);
        _payment.Pay(order);
        _repo.Save(order);
        _notifier.Send(order.Customer.Contact, "下单成功");
    }
}

注意 Submit 现在只有四行，而且只能通过接口看到协作者。这段代码可以直接跑单元测试——注入假实现即可，不需要数据库、不需要网络、不需要邮件服务器。

第 5 步：收尾的两个小修

LoD：order.Customer.GetAddress().GetEmail() 这条链穿过三层。改成让 Order 自己回答：

// Order 上提供语义化的方法，内部结构变化不外泄
public Contact GetCustomerContact() => _customer.Contact;

// 调用方
_notifier.Send(order.GetCustomerContact(), "下单成功");

CRP：如果 SmsNotifier 当时是继承 EmailNotifier 拿到的代码，把它改成实现 INotifier。同时这也顺手修掉了一个 LSP 隐患——一个「短信不是邮件」的类继承邮件类，迟早会有调用方踩坑。

改完之后的账

来一个需求改之前要动改之后要动
接入一家新支付渠道1 个方法 + 重测整条下单链路新增 1 个文件，已有代码 0 改动
改折扣规则同一段大方法，需确认不影响其他 5 件事只改 PriceCalculator
换数据库改业务代码里的 SQL新增一个 Repository 实现
加一种通知方式改下单流程新增一个 INotifier 实现
给下单流程写单元测试需要真数据库 + SMTP + 支付沙箱注入 5 个假对象，毫秒级跑完
最后的结构长这样

一个薄薄的编排层 OrderService，下面挂着五个各管一件事的协作者，其中三个是接口（IOrderRepository / IPaymentGateway / INotifier）。
没有一行代码知道另一行代码的具体实现是什么——这既是 DIP 的定义，也是 OCP 能成立的前提，还是所有测试能跑得飞快的原因。

顺带说：这个例子不需要一次性做完

真实项目里，你几乎不可能有时间把这五步一口气做完。正确做法是按需要做：接到「要接 Apple Pay」的需求时，顺便做第 2 步；要给下单流程补测试时，顺便做第 4 步。
这就是《重构》里说的「加功能之前先把它整理成好加的样子」——原则的落地方式是搭便车，不是专门开一场重构大会。

速查：违例信号 → 修复手法Cheat Sheet

这张表是全文的压缩版。实际工作中你不需要回忆定义，只需要认出信号。

原则一句话代码里的违例信号典型修复
SRP
单一职责		 一个类只有一个引起它变化的原因 能用两个不同主语给「这个类要改」造句；类名里带 And、Manager、Util；同一文件里出现 SQL + 邮件 + 日志 按变化原因拆类，保留一个薄编排层
OCP
开闭原则		 对扩展开放，对修改关闭 加新类型要回到同一个 switch / if-else 链加分支；else throw new NotSupportedException 抽接口 + 多态；策略 / 模板方法 / 观察者
LSP
里氏替换		 子类型必须能替换基类型 调用处出现 is / as / GetType() 判断；子类把继承来的方法抛异常或留空；覆盖方法时加强了参数校验 抽真正的共同抽象；改不可变值对象；改用组合
ISP
接口隔离		 不强迫客户端依赖它不用到的方法 实现接口时写空方法或抛异常；多个客户端依赖一个大接口但各只用其中两三个方法 按客户端角色拆接口（不是按方法逐个拆）
DIP
依赖倒置		 依赖抽象，而不是依赖具体实现 业务层里 new SqlConnection() / new HttpClient()；业务方法的签名里出现第三方 SDK 类型 高层定义接口，构造器注入实现
LoD
迪米特法则		 只和直接朋友说话 a.GetB().GetC().Do() 这种火车残骸；一个方法里点号超过两个 在中间对象上提供语义化方法；逐层委托
CRP
合成复用		 优先组合，而不是继承来复用 为了拿几个方法而继承一个语义不相关的类；子类里出现 public new 覆盖；继承层次超过三层 抽接口 + 组合注入；只在 Is-A 且过 LSP 时才用继承

反向表：先看到坏味道，再找它违反了谁

你看到的坏味道通常违反了先动哪一步
一个类几千行，改起来到处是坑SRP先按变化原因切，别急着抽接口
同一个 switch 在多个文件里重复出现OCP + SRP把它挪到一个地方，再换成多态
到处是 instanceof / is 判断LSP检查那个继承体系是否本来就该用组合
接口里的方法一半实现是空的ISP按客户端的使用情况拆接口
单元测试必须启动数据库DIP把持久化抽成接口，构造器注入
一行代码里五个点号LoD在中间那层加一个语义化方法
继承树三层以上，还在继续长CRP + LSP把变化的部分抽成可注入的组件

一页自检清单

  • 这个类里，有没有两个方法会因为不同的部门提要求而改变？（SRP）
  • 加一个新功能，我改了几个已经测试过的文件？（OCP —— 理想 0 个）
  • 有没有哪个子类，让调用方不得不回头判断「你到底是哪一种」？（LSP）
  • 实现某个接口时，我写过空方法或抛异常的方法吗？（ISP）
  • 业务代码里，有没有 new 后面跟着具体的基础设施类型？（DIP）
  • 有没有一行代码，让我知道了三个对象之间的嵌套结构？（LoD）
  • 这处继承，是因为真的 Is-A，还是只是想白拿几个方法？（CRP）
  • 这个抽象，是已经被验证过的变化逼出来的，还是我猜出来的？（YAGNI）
  • 如果我违反上面某一条，我清楚自己在向未来借什么债吗？

结语：原则是工具，不是法律Closing

如果这篇教程只留下一句话，我希望是这句：

Gather together the things that change for the same reasons. Separate those things that change for different reasons.
把因相同原因而变化的东西聚在一起，把因不同原因而变化的东西分离开——剩下六条原则，都是这句话在不同层面的展开。 —— Robert C. Martin

三个必须说清楚的提醒

  1. 它们是权衡工具，不是法律条文。Martin 自己反复强调这些是 guidelines 不是 laws。真正成熟的设计能力，不是「严格遵守所有原则」，而是知道每违反一条要付多少利息，然后选择在哪个位置付。
  2. 不要试图一次性全满足。它们之间有依赖顺序：① 先用 SRP 把单元切对（地基）→ ② 再用 DIP 把依赖方向定好（方向）→ ③ 然后才可能有 OCP（结果）。反过来做，你会得到一个「接口满天飞、但每个类还是一团乱」的系统——那比不做更难维护。
  3. 所有这一切的前提，是有测试。没有自动化测试，你既不敢重构，也无法验证「行为没变」——那么这七条原则就只是一套无法落地的美学主张。测试是设计原则的执行环境。

最后一句反直觉的话

回头看第 01 节那七个症状。你会发现，设计原则其实都没在许诺「代码会变漂亮」——它们许诺的是一件更实际的事：

让「改一处，只崩一处」成为默认状态。
每一次改动的影响范围，都在你的预期之内。这件事比优雅重要得多，因为它决定了你敢不敢继续改——而软件的生命力，就藏在「还敢改」这三个字里。
