0四个词，一根线：它们都挂在帧预算上

线程、阻塞、并发、异步，在技术书里通常是四章内容。但在游戏里，它们是同一根绳上的四个结 —— 这根绳叫「帧预算」。先把这四个词翻成白话，再看它们怎么串起来。

四个词的白话版

线程
干活的人
一个线程就是一条能独立往前走的执行流。游戏里绝大多数引擎对象只认其中那一条：主线程。
阻塞
站着干等
某个线程停在原地，等磁盘、等网络、等锁、等 GPU。期间它什么也不干，整条流水线被它堵住。
并发
多件事同时推进
多条执行流真正并行地跑。难点不在「怎么同时跑」，而在「它们共享的那份数据怎么办」。
异步
不原地等，回头给结果
发起操作后立刻返回、不占住当前线程；结果准备好时，通过回调 / await / 句柄再通知你。
四个词不是并列的技术点，而是从「谁在干」到「怎么协调」的一组视角。

你会发现这四个概念有一条清晰的因果链：为了不阻塞，我们引入异步；异步要真正利用多核，就变成并发；并发一旦发生，就必须回答「谁能在哪条线程上碰什么数据」。

而游戏的特殊性只有两句话

硬约束一：截止
每帧必须在 16.6ms（60fps）内交卷
↓
硬约束二：单店主
引擎对象基本只能由主线程碰
↓
推论
所有并发方案，最后都要把结果送回主线程这一道门
服务器的判据是「吞吐」和「延迟」，游戏的判据是「这一帧有没有按时交卷」。

在服务器或工具类软件里，多线程的收益是明确的：单位时间干更多活。但在游戏里，收益要换成一句更苛刻的话 —— 在不增加单次「卡住时间」的前提下多干活。平均帧率 60 但偶尔出现一个 500ms 的尖峰，玩家的体感远差于稳定 45 帧。这就是为什么我们后面反复强调「predictable latency（可预测延迟）」，而不是「更快的平均值」。

一句话记住全篇

游戏里的并发问题，本质都是同一个问题：有没有某条线程被堵住，导致某一帧没能按时交卷；或者有没有两条线程在同一时刻碰了同一份数据。前者表现为卡顿，后者表现为偶发崩溃。

最后这个数字值得单独说：Unity 官方在移动端优化建议里给的是「只花掉可用时间的约 65%」，也就是 30fps 目标下每帧约 22ms。原因是移动设备没有风扇，长时间满载会触发 SoC 降频，你抢到的那点时间会在几分钟后被硬件连本带利收回去。

先立个规矩

后面所有「要不要上多线程」的判断，都请你先打开 Profiler 确认瓶颈在哪。看不到数据就改并发模型，和闭着眼睛调药方差不多。CPU bound 与 GPU bound 的优化路径完全不同，前者才轮到线程上场。

1一帧 16.6 毫秒里到底发生了什么

在讨论怎么并行之前，得先有一张精确的时间地图。绝大多数「看起来是并发问题」的卡顿，最后都能在下面这张图上找到具体位置。

主线程的一帧

一帧的时间线：主线程、渲染线程、GPU 三条泳道错位并行，谁的等待被拖长，谁就是瓶颈。

这张图里有三个容易被忽略的细节，它们决定了后面所有优化的方向：

  • FixedUpdate 可能跑 0 次也可能跑好几次。物理是按固定步长追帧的，某帧渲染慢了，下一帧就要补跑两次物理 —— 卡顿会自我放大。
  • 三条泳道是错位的。主线程在提交第 N 帧命令时，渲染线程在翻译第 N-1 帧，GPU 在画第 N-2 帧。所以「主线程在等」不一定是 GPU 太慢，也可能是帧间节奏被打乱。
  • 等待点才是卡顿被看见的地方。真正让玩家皱眉的不是某一行代码慢，而是主线程在这个虚线框里待了多久。

用 Profiler 标记判断瓶颈在哪条泳道

Profiler 标记出现在哪说明该去查什么
Gfx.WaitForPresent主线程主线程干完活了，在等 GPU 把上一帧画完GPU bound：查 overdraw、材质复杂度、分辨率、后处理

判断顺序

先看 Gfx.WaitForPresent 高不高。高 → 瓶颈在 GPU，多线程救不了你，得去优化渲染。不高但主线程柱状很长 → CPU bound，才轮到「把活拆给工作线程」这一节的内容。

顺便看一眼 UE 的对照

Unity 的行话换成 UE 也很直白：GameThread 对应 Unity 主线程（UObject 世界的所有权者），RenderThread 对应渲染线程，TaskGraph 的 worker threads 对应工作线程池。两套引擎对 「谁拥有对象」这一问题的答案完全一致：引擎对象由游戏线程独占，其它线程一律不得直接触碰。区别只在于 UE 用 AsyncTask(ENamedThreads::GameThread, ...) 显式派发，而 Unity 社区习惯自己写一个 MainThreadDispatcher。

2三条泳道：主线程、渲染线程、工作线程

知道了时间分布，下一步是知道「哪些活能甩出去」。这里有个流传很广但常常出错的想法：既然要多核，那就把 AI、物理、网络各自放到一条独立线程上吧。

为什么「按系统分线程」通常是错的

按系统分线程
AI 一条、物理一条、网络一条
按任务分线程
把大活切成 N 个同构小 job，丢进线程池
↓
负载天然不均
AI 忙死时网络几乎空闲，一个核在跑，其余在围观
共享数据极多
网络要推事件给 AI，AI 要喂数据给渲染，全是交叉引用
死锁温床
系统之间互相等待，锁顺序不可控
左边是直觉，右边是正解：引擎里真正跑得起来的是「大量同构短任务 + 线程池」，而不是「几个大系统各占一条线程」。

按系统切线程的两个致命伤：一是负载无法预判 —— 你很难提前知道这一局里 AI 和网络谁更耗 CPU；二是共享数据太多 —— 网络、AI、音频、UI、渲染彼此都在读写同一批对象，交叉引用越多，race condition 和死锁的机会就越多。

正确的做法是 task-level parallelism（任务级并行）：找到那个真正耗时的计算，按数据切成一批相互无关的小任务，扔给工作线程池，跑到一个同步点（sync point）统一回收结果。举个例子：地形侵蚀计算很贵，就把世界切成 chunk，每个 chunk 一个 job，所有 job 完成后，再把结果写回全局世界状态。

这一条是所有现代引擎的共识

Unity 的 Job System、UE 的 TaskGraph、Naughty Dog 的 fiber job system，底层都是同一个模型：一组数量等于 CPU 核心数的工作线程 + 一个任务队列 + 偶尔出现的同步点。区别只在调度精度和语言糖。

三条泳道各自能干什么、不能干什么

泳道能做绝不能做
主线程

一个足够好用的心智模型

把游戏想成一家餐厅，三条泳道对应的角色是这样的：

主线程
唯一的跑堂 + 出菜口
接单、记菜单、最后把菜端上桌。他是唯一能碰菜单和与顾客说话的人。他一走神，全场都在等。
工作线程
后厨备菜班
只负责把原材料切好、算好配比，产出一盘盘半成品。他们不认识顾客，也不能决定什么时候上菜。
渲染线程
传菜电梯
把做好的东西稳定地往餐桌方向送，自己不生产内容。
派发队列
出菜窗口
备菜班把成品放到窗口，跑堂每帧过来取一次。这是跨线程结果的唯一安全出口。
餐厅模型：所有「别人算完、主线程要用」的结果，都必须经过出菜窗口，不能直接递到顾客手上。

后面第 7 节要写的「主线程派发器」，就是这个出菜窗口的具体实现。记住这个类比 —— 它能回答绝大多数「这个对象能不能在后台线程访问」的问题：顾客看不见的人，你也别让他碰。

3阻塞的四张脸

「游戏卡了一下」是很常见的反馈，但背后的原因可能有几十种。按「谁被堵住、在等谁」分类，阻塞只有四张脸。认出它们，就认出了 80% 的卡顿。

脸一：等 I/O
磁盘读、DNS、 socket、PlayerPrefs
脸二：等锁
别的线程拿着锁不撒手
脸三：等 GC
托管回收暂停所有托管线程
脸四：等 GPU
垂直同步、渲染管线反压
四类阻塞在家 Waiting 的形态不同，但在 Profiler 上都表现为「一条线程上出现一段它自己没干活的时间」。

脸一：等 I/O —— 最容易被忽视的一张

文件读取在开发者机器上通常是几毫秒，在中低端 Android 的 eMMC 上可能是几百毫秒，如果还叠加上 emmc 老化、同时被其它 app 竞争，会更糟。同理 DNS 解析在弱网下能到秒级。

// 危险清单：这些调用会原地挡住调用线程
var bytes = File.ReadAllBytes(path);                 // 同步读整个文件
var json  = File.ReadAllText(path);                  // 同上
var prefab = Resources.Load<GameObject>("Enemies/Goblin");  // 同步加载，且 Resources 全量入包
var host  = Dns.GetHostEntry("api.example.com");   // 同步 DNS，弱网下秒级
socket.Receive(buffer);                              // 同步 socket
PlayerPrefs.Save();                                  // 主线程 flush
最隐蔽的一种

你写的代码里没有任何阻塞调用，但引入的第三方 SDK 里有。统计上报、广告、支付、推送、崩溃监控，它们的 flush / init 常常是同步的。上线前最好在真机上抓一次启动 Profiler，专门看有没有意料之外的主线程长条。

脸二：等锁 —— 并发里最常见的反噬

上多线程是为了更快，但引入锁之后可能出现「线程数越多越慢」的奇观：所有线程都堵在同一把锁上，还额外付出了上下文切换的代价。第 13 节会专门讲锁的四个坑，这里先记住一个原则：锁是最后手段，不是第一手段。优先考虑的排序是：

1 · 不共享
每个线程处理数据副本，最后合并
↓
2 · 只读共享
并行阶段没人写，天然安全
↓
3 · 原子操作
Interlocked 处理标量计数
↓
4 · 无锁结构
SPSC 环形队列等
↓
5 · 加锁
兜底手段，粒度必须极小
并发保护的优先级：越往左，越应该被优先选择。锁排在最后不是因为它没用，而是因为它最容易被用错。

脸三：等 GC —— 卡顿的周期性元凶

托管语言里，new 出来的对象会在堆上分配；不再被引用的对象由垃圾回收器（GC）回收。回收过程需要遍历对象图，这段时间里托管代码是不往前走的。区别在于：Instantiate 亏损检查分配可能几百 KB，而 Update 里每帧 new 一个 List，一个月下来就是几十 MB 的稳定分配源。

常见每帧分配源替代写法
new WaitForSeconds(1f) 写在循环里缓存成一个字段复用
LINQ 表达式（Where / OrderBy / ToList）手写 for 循环 + 预分配 List
闭包与 lambda 捕获改成传值参数或缓存委托
字符串拼接 / 插值StringBuilder 或缓存，尤其是每帧执行的

Unity 的一个具体选项

Unity 支持增量式 GC（Incremental GC），它会把回收工作分摊到多帧执行，把一次大暂停拆成若干个不可见的小片。它不是「不用 GC」的许可证 —— 减小每帧分配仍然是根本手段，但作为兜底很有用。

脸四：等 GPU —— 看起来像 CPU 问题，其实不是

这一张脸最容易误诊：主线程在 Gfx.WaitForPresent 里干等，说明 CPU 早就干完活了，是 GPU 还在画。这时候你就算把逻辑并行到 16 个核上，帧率也不会变 —— 短板在另一条泳道。识别的方法很简单：看 Profiler 里这个标记的主线程占比，长期居高，就去查渲染侧（overdraw、带宽、复杂 shader、后处理、分辨率）。

4三大常规伤口：加载 / 反序列化 / Instantiate 风暴

理论讲完，看三个在实践中几乎每个人都会踩、而且都会导致「几百毫秒级尖峰」的具体场景。它们的共同点是：代码看起来完全无害。

伤口一：同步资源加载，以及藏在里面的解压

很多人的第一反应是「我用 Addressables 的异步接口了，怎么会阻塞」。问题恰恰在这里 —— 用了异步 API，不等于这一帧不会被拖住。

发起异步加载
LoadAssetAsync(handle)
↓
磁盘读取
通常在工作线程，OK
↓
解压
LZMA 必须整包解压
↓
主线程尖峰
几百毫秒，肉眼可见
「异步」管的是「谁去读完文件」，管不了「谁来解压」。压缩格式选错，异步加载照样卡主线程。

LZMA 是全量压缩：要取包里任意一个资源，都得先把整个包解压。资源越大尖峰越长。LZ4 是分块压缩：每个 chunk 独立压缩，取某个资源时只解压它所在的那些 chunk，于是尖峰被削平。

0.1s

秒级

LZ4 让包体变大 1.2~1.5 倍。手游在意下载体积时有个折中做法：远端分发用 LZMA（省流量），落地到本地缓存时转存为 LZ4，加载走 LZ4 缓存。远端省流量，本地不卡顿。

伤口二：反序列化 —— 你以为的异步，其实全是 CPU

接一个 REST 接口，await 写得漂漂亮亮，但拿到 JSON 字符串之后在主线程里跑了一个 Newtonsoft 反序列化，一张两万行的配置表解析 300ms。这里的教训是：I/O 是异步的，反序列化不是。异步只覆盖了等待网络的那部分，解析照样占满主线程。

场景典型做法建议
配置表（几 MB 的 JSON / XML）运行时 JsonConvert.DeserializeObject离线转成二进制快速格式（protobuf / MessagePack / 自定义），运行期只读 ; 并且把解析这一步挪到工作线程
存档读档主线程 File.ReadAllText + 解析后台线程 StreamReader.ReadToEndAsync，解析也在后台，只把结果对象交回主线程
Addressables 的 handle 结果处理在 Completed 回调里直接做大循环回调里只做「登记」，重活挪到下一帧或工作线程

伤口三：Instantiate 风暴 + 着色器编译

一波刷十个怪，每个 Instantiate 都要拷贝一整套组件树；更致命的是第一次用到某个 shader 变体时的编译等待，真机上可以到秒级，而且是完全不可预测地出现。

症状
第一次出现某类敌人 / 特效 / 某个技能时全场冻结
之后同样操作却完全不卡 —— 因为编译结果已经缓存在内存里。
解法
预热（warm up）：在稳定的时间点把代价先付掉
Shader Variant Collection 预先 WarmUp；对象池提前 Instantiate；过场 / 加载界面时 Preload 下一场景资源。
配套
对象池 + 拆分 Parent transform
重复出现的敌人、子弹、特效、UI 条目统统走池；复数 Instantiate 分帧摊开。
「第一次才卡」几乎是预热问题的指纹 —— 记住这个症状，能省掉一半排查时间。

5分帧与时间切片：把大象切成薄片

很多工作其实没法搬到别的线程 —— 它们要碰引擎对象。这时候剩下的办法只有一个：把它切开，每帧吃一小口。

版本一：朴素分帧（按数量）

// 每帧只处理固定个数，剩下的留给下一帧
IEnumerator SpawnWave(List<EnemyData> list)
{
    for (int i = 0; i < list.Count; i++)
    {
        SpawnOne(list[i]);
        if ((i + 1) % 8 == 0)
            yield return null;   // 交还控制权，下一帧接着干
    }
}

简单有效，但有个缺点：你并不知道 8 个会不会超时。在低端机上 8 个也可能吃掉 20ms。于是有了版本二。

版本二：时间切片（按毫秒）

// 每帧工作到预算用完就撤，不猜「几个才安全」
IEnumerator BuildLevelChunked(List<Chunk> chunks, float budgetMs = 4f)
{
    var sw = Stopwatch.StartNew();
    foreach (var c in chunks)
    {
        Build(c);
        if (sw.Elapsed.TotalMilliseconds >= budgetMs)
        {
            sw.Restart();
            yield return null;   // 预算用完，把这一帧还给渲染
        }
    }
}
预算怎么定

别把 16.6ms 全吃掉。给切片逻辑留 2~4ms 通常就够了，剩下的留给渲染提交和不可预见的抖动。目标帧预算是 16.6ms 时，整个主线程脚本最好控制在 11ms 左右（参考 Unity 对 60fps 的建议）。

版本三：加载队列 —— 把三者组合起来

真实项目里通常是一个带优先级和并发上限的加载队列，而不是到处 yield return null。

第一步
入队
所有加载请求进一个优先队列，带 priority（玩家马上要看到的 > 背景装饰）。
第二步
限并发
同时进行的异步操作数量设上限（Addressables 可用 SetNumberOfSimultaneousOperations 调节），避免同时开几十个把 I/O 和内存一起打爆。
第三步
回调进窗
handle 完成后不立刻消费资产，把结果登记到「待应用」列表。
第四步
主线程分帧应用
每帧按时间预算从列表里取出若干个做 Instantiate / 挂载，其余留到下一帧。
四步组合：并发下载可以很猛，「把资产变成场景里的东西」这一步必须慢而可控。

别忘了代价：分帧不是免费的

分帧不是万能药。它把一次 500ms 的尖峰摊成了 30 帧各 16ms —— 总工作量没变，只是不再被看见。如果这 500ms 里你要跑的内容人家必须马上看到（比如过场动画的第一帧），那就只能走「提前预热 + 加载界面」而不是分帧。

6为什么引擎 API 只能主线程调用

「Internal_CreateGameObject can only be called from the main thread」—— 这条报错几乎每个 Unity 程序员都见过。但为什么？不知道原因，就判断不了边界。

三个真正的理由

理由一
引擎内部压根没加锁
场景树、组件列表、渲染队列都是共享可变结构。给它们全加上锁，等于让每个 transform.position 都付一次锁开销 —— 引擎选择了「不加锁 + 只允许一个线程访问」。
理由二
托管对象会被搬动或回收
GC 可能移动、回收托管对象；你在后台线程持有一个 GameObject 引用并访问它，另一边主线程可能已经把它 Destroy 了。
理由三
状态是过程性的
渲染命令缓冲、动画求值、物理世界的积分，都是「有序推进」的过程。两条线程同时往里写，顺序立刻失去意义。
不是「引擎懒得支持多线程」，而是「为了性能主动放弃了内部加锁，代价是外部必须守规矩」。
最坑的一点：部署包不检查

Unity 官方文档明确写了：出于性能考虑，非 development build 不会做多线程行为检查，也不报这个错。也就是说 —— 编辑器里跑得好好的代码，打包到真机上「很可能随机崩溃或者出现不可预测的错误」。这就是那类「只在别人手机上崩」的经典来源。

对照 UE：规矩一样，说法不同

UE 里继承自 UObject 的对象（AActor、UActorComponent）绝大多数方法只能在 GameThread 调用。在 AsyncTask / TaskGraph 里不能直接操作它们，需要把操作派发回游戏线程：

// UE：把「碰 UObject 的部分」显式塞回 GameThread
Async(EAsyncExecution::ThreadPool, [WeakController, Points]()
{
    // 这里只做纯数学：评分、空间查询
    auto Best = PickBest(Points);

    AsyncTask(ENamedThreads::GameThread, [WeakController, Best]()
    {
        // 回到游戏线程，才能安全调用控制器
        if (WeakController.IsValid())
            WeakController->MoveToLocation(Best);
    });
});

注意上面用了 TWeakObjectPtr 而不是裸指针 —— 这是另一个重要习惯：跨线程传递对象时，传递弱引用，并在使用前检查有效性。因为等你拿到结果，那个对象可能早就被销毁了。

问自己一句：这个东西有没有可能同时被游戏世界的 Update 碰到？有，就必须回到主线程再动。没有疑虑时，它通常也只是个纯数据容器。

7主线程派发器：跨线程结果的唯一安全出口

后台算完了，结果怎么安全地交回主线程？答案永远是同一个形状：一条线程安全的队列 + 主线程每帧取一次的循环。这就是餐厅模型里的「出菜窗口」。

最小可用实现

public class MainThreadDispatcher : MonoBehaviour
{
    private readonly ConcurrentQueue<Action> _pending = new();
    private readonly List<Action> _drain = new(64);

    public void Enqueue(Action a) => _pending.Enqueue(a);

    void Update()
    {
        // 关键：先把队列整体搬进 _drain，再执行
        // 否则被执行的回调里若再次 Enqueue，就会重入同一个容器
        _drain.Clear();
        while (_pending.TryDequeue(out var job))
            _drain.Add(job);

        foreach (var job in _drain)
        {
            try { job(); }
            catch (Exception e) { Debug.LogException(e); }
        }
        _drain.Clear();
    }
}
为什么「先取干尽再执行」

如果写成 lock(queue){ while(queue.Count>0) queue.Dequeue()(); }，那么被执行的回调里若又调用了 Enqueue，就会试图再次获取同一把锁 —— 要么死锁，要么自旋。先整批取出、释放容器、再逐一执行，是这里唯一正确的顺序。

用法：永远是这样两半

public async Awaitable LoadAndApplyAsync(string address)
{
    // —— 后台部分：纯数据，不碰引擎 ——
    await Awaitable.BackgroundThreadAsync();
    var bytes = File.ReadAllBytes(PathFor(address));
    var table = MyBinaryParser.Parse(bytes);

    // —— 回到主线程：才开始碰引擎对象 ——
    await Awaitable.MainThreadAsync();
    ApplyToScene(table);
}

两段结构很清楚：前半段禁止任何引擎调用，后半段才对场景下手。把它当成一条硬性格式。

四种「回主线程」的常见渠道，怎么选

渠道适用注意
MainThreadDispatcher（队列 + Update）任意后台线程（Thread、Task.Run、第三方库回调）结果至少延迟一帧；必须 include 销毁时的清理
await Awaitable.MainThreadAsync()Unity 6+ 的异步方法链从后台切回主线程时，最快也要等下一帧 Update
SynchronizationContext.Post想和旧 Task 代码互操作本质就是 Unity 自己的 context，行为同上
ConcurrentQueue + 自己的 Update 泵数据流持续产生（网络包、音频样本）要给队列设上限，做背压，别让生产者跑飞
延迟是一帧，记住这件事

从后台线程把结果 post 回主线程，最快也要到下一帧的 Update 才执行。在 30fps 下这就意味着最多 33ms 的额外延迟。做实时性要求高的东西（比如网络同步）时，官方建议索性把网络那一层整个放在主线程之外，用自定义逻辑同步，而不是每条消息都来回跳线程。

8await 之后，你到底在哪个线程上

await 最违反直觉的地方是：它看起来会「另起线程」，实际上很多时候不会；而它看起来会「回到原处」，却在某些写法下不会。搞不清这两件事，就是卡死和随机崩溃的来源。

先破一个谣：async 本身不创建线程

一个只有 CPU 循环、内部一次 await 都没有的 async Task 方法，全部代码都在调用它的那个线程上跑，编译器甚至会给你一个警告。想让它真去后台，得显式用 Task.Run 或 Awaitable.BackgroundThreadAsync()。

误会
async = 多线程
事实
async 只是语法糖，真正决定「在哪跑」的是你 await 了什么
async 关键字的作用是「允许在方法里使用 await」，不是「开一条线程」。

Unity 的默认行为：await 之后会回到调用处

这和游戏引擎的特殊安排有关。Unity 用一个自定义的 UnitySynchronizationContext 替换掉了 .NET 默认的上下文，目的很明确：保证 Task 的延续无论在 Edit 模式还是 Play 模式，都跑回主线程。因为绝大多数 Unity API 只能在主线程调用，如果 await 之后随机掉到某个线程池线程上，几乎必然出事。

调用位置await 之后在哪继续说明
从主线程 await 一个 Task回到主线程延续被 post 到 UnitySynchronizationContext，在下一个 Update tick 执行 —— 这也意味着至少一帧的延迟（30fps 下约 33ms）
从后台线程 await 一个 Task线程池的某个线程这也是 Unity API 不能在这里调用的原因
ConfigureAwait(false)线程池线程（不回原上下文）省掉回主线程的开销；但后面不许碰引擎对象
await Awaitable.MainThreadAsync()主线程（无论之前在哪）Unity 6+ 推荐写法
await Awaitable.BackgroundThreadAsync()后台线程用于把重计算挪出主线程
行为一
在主线程调用 → 在主线程继续
这是最省心的情况，可以安全地接着调用 LoadSceneAsync 之类的 API。
行为二
从后台调用 → 在线程池继续
「从哪个线程发起，就在哪一类中继续」，这条规则对 Task 和 Awaitable 都成立。
行为三
内部切走不影响外部
方法内部 await BackgroundThreadAsync() 再回来与否，不影响调用者自己在哪继续 —— 作用域是局部的。
记住「从哪来回哪去」这条默认规则，90% 的「await 之后为什么崩」都能自己解释。
性能提示

每次从主线程 await 一个 Task，都要付出「捕获上下文 + 回主线程排队」的代价，且最快也要等下一帧。所以：库性质的辅助方法如果完全不碰引擎对象，统一加 ConfigureAwait(false)，可以显著减少对主线程的占用。Unity 自己的建议也是用 Awaitable 替代 Task 来规避这部分开销（Awaitable 采用对象池，且不那么依赖上下文捕获）。

三个必守的规则

规则一
别写 async void
除了 Start / 按钮点击这类顶层入口。async void 里的异常无法被捕获，会被静默吞掉 —— 表现为「代码莫名执行到一半消失了」。
规则二
Awaitable 实例不许存起来复用
Awaitable 是池化对象，await 完立刻归还。同一个实例第二次 await 是未定义行为，轻则抛异常，重则死锁。需要复用的是「封装好的方法」，不是那个实例。
规则三
Coroutine 失活不停，销毁才停
SetActive(false) 不会停止协程；只有物体销毁、脚本销毁、或手动 Stop 才会。想用「隐藏=暂停」来控制流程，一定会出 bug。
三条都是「写了不一定当场报错，但一定会在某个深夜出问题」的类型。

两种延时，别选错

WaitForSeconds 跟随游戏时间，受 Time.timeScale 影响 —— 暂停游戏时它也会停。WaitForSecondsRealtime 走真实时间，不受暂停和缩放影响。做「暂停界面上的倒计时」用前者会永远走不完，做「技能冷却」用后者会导致暂停期间冷却照走。先问自己：这个时间属于游戏世界，还是属于现实？

10.Result 死锁：Unity 最经典的翻车现场

如果你只能记住本教程里的一个 bug，记这个。它导致的症状极具迷惑性：编辑器彻底无响应、必须强制退出；或者运行到某处就永远卡住。

事故现场

// ❌ 经典死锁：在主线程上同步等待一个 Task
void Start()
{
    var data = FetchDataAsync().Result;   // 卡死在这里，永远回不来
    Debug.Log(data);
}

// ✅ 正确：让调用链一直 async 下去
async void Start()
{
    var data = await FetchDataAsync();
    Debug.Log(data);
}

为什么会死锁：两边互相等

①
主线程调用 .Result，把自己堵住
主线程进入等待状态，不再处理任何消息。
②
后台任务完成，准备跑「await 之后的部分」
延续要通过 UnitySynchronizationContext 排回主线程。
③
延续排队等主线程，主线程却在等延续
主线程要等 Task 完成；Task 要等主线程来执行它的尾巴 —— 循环等待成立。
结果
整个编辑器和游戏静止，只能强杀进程
因为它堵住的不是某个业务线程，而是驱动一切的主线程本身。
四步死锁链：主线程等 Task，Task 等主线程。两边的等待条件都握在对方手里。
铁律

永远不要在主线程上对 Task 使用 .Result 或 .Wait()。Unity 官方文档在「线程安全」段落里直接把这条写成了禁令。实在要同步等待，保证链条里已经用了 ConfigureAwait(false)（让延续去线程池，不回主线程），才可能避免。

四条看起来无害、其实也会卡死的写法

写法问题修法
asset.WaitForCompletion() 写在 Update 里把异步加载强行同步化，主线程干等改成 await handle，或用 Completed 回调
Task.Run(...).Wait()同上，且白瞎了 Task.Runawait Task.Run(...)
ConfigureAwait(false) 之后直接操作 Transform延续在线程池线程，触碰引擎对象 → 崩溃引擎操作前用 MainThreadAsync() 或派发器切回
方法标了 async 但里面只做 CPU 重活「假异步」，主线程照卡不误真的要并行就 Task.Run / Job System

死锁的通用成因对照

死锁不只有「主线程等自己」这一种。教科书上的四个必要条件（互斥、占有且等待、不可抢占、循环等待）在游戏里最常见的落地形态是循环等待：线程 A 拿着锁 1 等锁 2，线程 B 拿着锁 2 等锁 1。防范办法很朴素 —— 全局约定统一的加锁顺序，以及绝不在持有锁的时候去等另一个线程。

11取消与生命周期：切场景后还在跑的幽灵任务

异步逻辑最阴的一类 bug 不是崩溃，而是「该停的没停」—— 场景都切走了，后台任务还在跑，回调指向一个早已销毁的对象。

↓
回调回来攻打空气
给已销毁对象赋值 → 异常 / 内存异常
对象销毁不会自动取消它的异步任务 —— 这是协程与 async 之间最危险的一处差异。

标准做法：CancellationToken

public class SkinLoader : MonoBehaviour
{
    private CancellationTokenSource _cts;

    async void Start()
    {
        _cts = CancellationTokenSource.CreateLinkedTokenSource(
                   Application.exitCancellationToken);   // 退出播放/退出应用时一并取消
        try
        {
            var skin = await LoadSkinAsync(_cts.Token);
            Apply(skin);                       // 已经回到主线程
        }
        catch (OperationCanceledException)
        {
            // 干净地退出，什么都不做
        }
    }

    void OnDestroy()
    {
        _cts?.Cancel();
        _cts?.Dispose();
    }
}
一个容易被忘的参数

Unity 官方文档特别提醒：退出 Play 模式时，引擎不会自动停掉后台代码。要把它停掉，得用 Application.exitCancellationToken。上面代码里把它作为链式的父 token，一次解决「退出播放」和「对象销毁」两个场景。

1

2

12数据竞争：为什么只在别人的机器上崩

并发最折磨人的不是难写，而是——它会在你面前表现正常，在测试同事手机上崩溃，而你把代码反复读了二十遍也看不出问题。理解这一点，得从 i++ 到底做了几件事说起。

i++ 是一条指令吗

不是。它被拆成三步：

① 读
把 i 从内存读进寄存器
↓
② 加
寄存器里加一
↓
③ 写
把结果写回内存
三步之间都可能被别的线程插进来 —— 这就是「读改写」竞争的最小模型。
初始 count = 0，两个线程各执行 100 万次 count++，期望结果 200 万 可能发生的交错（坏运气的一种）： 线程 A 线程 B 内存中 count ───────── ───────── ──────────── 读 → 0 0 读 → 0 0 加 → 1 0 加 → 1 0 写 → 1 1 写 → 1 1 ← 两次自增，结果只加了 1

结果小于 200 万，而且每次跑出来的数都不一样。注意这里的关键：没有任何一行代码是错的，错的是「两个人对同一块内存的读写顺序没有被定义」。

为什么这么难复现

时序敏感
只有两条线程恰好在某个特定窗口交错才会触发
核心数敏感
4 核机器、8 核手机、你的 16 核开发机，调度完全不同
编译优化敏感
Release / Burst / IL2CPP 的指令优化与重排会改变时序
观测会改变它
加一行 Debug.Log 就可能让 bug 消失（海森堡 bug）
「只在别人机器上崩」不是玄学，是并发 bug 的正常形态。
Unity 上要额外警惕的一层

前面提过：非 development build 不做多线程行为检查。所以在编辑器里，「后台线程访问 Unity API」可能只是随机出问题而不报错；到了真机，同一个操作可能直接导致随机崩溃或不可预测行为。官方因此直接建议：别自己写多线程，用 Job System。

三条防线，按成本排序

防线做法代价
不共享每个 worker 处理自己的一份数据副本，最后合并最低，也最推荐
只读共享并行阶段没人写，数据是只读快照极低
线程安全容器ConcurrentQueue / ConcurrentDictionary / NativeContainer低，内部已实现同步
原子操作Interlocked.Increment 等，适合标量计数低，但只解决单一变量
加锁lock / FCriticalSection最高：串行化、优先级反转、死锁风险

一张值钱的经验是：volatile 不是解决办法。它只保证「可见性」（读到的不是过期值），不保证「原子性」（读改写不被打断）。volatile int count 上的 count++ 照样会丢。

如何让它「可复现」

并发 bug 的可怕在于不可复现，所以对它的第一反应应当是制造压力环境：固定不同的核心数跑、在 Release（开了优化）下跑、循环几千次、加入随机 sleep 拉宽时间窗口。把偶然变成必然，问题就解开了一半。

13锁的四个坑与本地累积模式

加锁往往比写 bug 更容易写出性能灾难 —— 它不报错，只是悄悄把你的并行度吃干净。

坑一：粒度太大，把并行变成了串行

最常见的是「一个大字典一把大锁」：所有线程抢夺同一把锁，实际执行效果是排队。正确的做法是优先考虑读写锁（读多写少时差别巨大）或者干脆按 key 分片。

坑二：加锁顺序不一致 → 死锁

经典 ABBA 死锁 线程 A： lock(装备锁) → 想去拿 lock(背包锁) 线程 B： lock(背包锁) → 想去拿 lock(装备锁) A 握着等 B 的，B 握着等 A 的 —— 两条线程从此永久静止。 防范：全局统一约定加锁顺序（例如永远「装备 → 背包」）， 并且绝不在持有锁时去等待另一个线程。

坑三：在锁里干活

// ❌ 反例：每个元素加一次锁，锁流量 = 数据量
for (int i = 0; i < 1000; i++)
{
    lock (_l) { shared.Add(i); }
}

// ✅ 正解：本地累积，最后合并一次，锁流量 = 线程数
var local = new List<int>(1000);
for (int i = 0; i < 1000; i++)
{
    local.Add(i);          // 只碰自己的内存，完全并行
}
lock (_l) { shared.AddRange(local); }   // 只锁一次
本地累积模式

先各自在本地攒着，最后合并一次。这个模式几乎适用于所有「并行累加」场景：统计、收集结果、批量记录日志。它能把锁竞争降低几个数量级，而且顺带保证了结果的可预测性。

坑四：以为加锁就万事大吉

锁保护的是「被这把锁包住的那段代码」。如果同一份数据在别处被不加锁地读写，等同于没有保护。这就是为什么要约定「数据的所有权」：谁拥有谁修改，别人只能走规定的通道。

一条贯穿全部的设计原则

缩小共享面
明确哪些数据被多线程访问
↓
明确所有权
谁产出、谁消费、什么时候交接
↓
缩小临界区
锁里只做不得不做的那几行
↓
批量交接
攒批传输，降低交互频率
四步递进：能不共享就不共享，能不频繁就不频繁，锁只用来保住最后那一点点必须共享的状态。

这个思路再往前一步，就自然走到无锁结构：既然多数情况下只有一个生产者、一个消费者，那么连这最后一点锁也可以省掉。

14伪共享：没抢数据却在抢缓存行

这是最反直觉的一个坑：两个线程写的是两个完全不同的变量，谁也没读谁的数据，性能却崩了。因为它俩恰好住在同一个缓存行里。

发生了什么

CPU 不按字节从内存取数据，而是按缓存行（cache line，常见 64 字节）整块搬运。缓存一致性协议维护的单位也是缓存行：只要行里有一个字节被改写，其它核心上对应的整行就整体失效，必须重新从别处拉取。

伪共享：两个线程写两个无关变量，因为共处同一缓存行，导致缓存行在两个核心之间反复失效。

怎么解决

手段做法适用
填充 padding在热数据之间塞无用字段，让它们各自独占一行C / C++ 与 C# struct 都能用
缓存行对齐按 64 字节对齐分配生命周期很长的热数据
本地槽位每个 worker 写自己的槽（天然拉开距离），最后汇总统计、累加速度最快
只读 + 本地副本并行阶段不写共享数据能从根上避开
要不要一开始就优化这个

不要。伪共享发生在长期、高频、多线程写相邻数据的场景 —— 每帧计数器、任务队列头尾指针、per-worker 状态数组。普通的游戏逻辑很少走到这一步。正确的顺序永远是：先把数据结构做对（连续内存、顺序访问），再看 Profiler 里有没有异常的缓存失效率，最后才轮到 padding。

15无锁环形队列：SPSC 模式

如果只有一个线程写、一个线程读（这在游戏里极其常见：网络线程收包交主线程、音频线程取样本、Job 结果回收），那么连锁都可以不要 —— 用环形缓冲区。

为什么它特别适合游戏

零分配
数组一次性分配，永久复用
可预测延迟
没有 GC 暂停，没有锁等待
有界容量
生产过快时天然背压，不会撑爆内存
缓存友好
连续内存、顺序访问
四项特性都指向同一件事：延迟可预测。对实时性而言，这比平均吞吐更有价值。
生产者只推进写指针，消费者只推进读指针，两者相向绕圈；写追不上读则满，读追不上写则空。

它的同步靠什么保证

核心
每个索引只有一个线程能改
写索引只有生产者改，读索引只有消费者改。既然没人跟自己抢，就不需要 CAS。
语义
release / acquire 配对
写完数据后用 release 存索引；读的一方用 acquire 读索引。先存数据、再发布索引；先拿到索引、再读数据 —— 顺序由内存屏障保证。
技巧
mirror 索引
各自缓存一份对方的索引值（自己的「镜像」），避免每次都跨核读对方的 volatile 变量。
技巧
容量为 2 的幂
index & (capacity - 1) 取代 % capacity。
四块拼图：独占写入 + 发布/获取语义 + 索引镜像 + 掩码取模。
写入侧（生产者线程专用） next = (write + 1) & mask; acquire 读一次对方的 readIndex，判断有没有空位 if (next == readIndex) return false; 满了：告知调用方稍后再试 / 丢弃 buffer[write] = entry; release 发布新写索引 —— 保证数据先落地，索引后可见 atomic_store(&writeIndex, next, memory_order_release); 读取侧（消费者线程专用） last = atomic_load(&writeIndex, memory_order_acquire); while (read != last) { 处理 buffer[read]; read = (read + 1) & mask; } atomic_store(&readIndex, read, memory_order_release);
别急着手写

无锁代码有句三字真言：难写、难查、难证明正确。还有 ABA 问题（一个值从 A 变 B 又变回 A，CAS 检查会误判为「没变过」）。现实建议是：优先用成熟库（如C++ 的第三方并发库、C# 的 Concurrent 系列、或者 UniTask 的 Trigger 机制），只有在 Profiler 明确指出「就是这里」时才自己实现。而且 —— 只在 SPSC 场景写无锁；多生产者多消费者的正确实现难度是另一个量级。

游戏里最值得用它的三个地方

① 网络线程 → 主线程收包队列；② 音频回调 → 引擎的样本 / 事件队列；③ Job 结果的批量回收缓冲。三者的共同特征是：单写、单读、高频、对延迟敏感 —— 正好是 SPSC 的主场。

16为什么引擎要禁止你自己开线程

Unity 文档里那句「you shouldn't use your own multithreading, use the Job System」听起来像霸道之规定，其实是经验总结。Job System 真正卖的不是「并行」，而是「安全地并行」。

自己开线程会遇到什么

线程数量失控
每个系统开一条，很快就远远超过核心数
过度订阅
线程数远超核心数，上下文切换吃掉全部收益
生命周期没人管
退出播放不会自动停，切场景回访问野对象
踩到引擎禁忌也没人提醒
Release 包不检查，直接随机崩
自己管理线程，意味着你要同时拥有：调度器作者、内存模型专家、以及一个能复现偶现 bug 的环境。

过度订阅（oversubscription）尤其值得注意：线程数不是越多越好。线程数应该大致跟得上可用核心数 —— 引擎的全局线程池已经为你做了这件事。再多就只是在给调度器添乱。

Job System 提供的三样东西

一
受控的工作线程池
数量由引擎按硬件决定，你只提交任务，不参与调度。Schedule() 不阻塞主线程，任务等空闲 worker 就开跑。
二
安全系统
通过 NativeContainer 的所有权追踪，在编译/调试期就检测出数据竞争：两个 Job 同时写一个数组会被拦下来。
三
依赖图
用 JobHandle 声明「谁依赖谁」，引擎自动排序并在同步点等待 —— 不用你手写事件、信号量。
Job System 的本质是一道填空题：你填数据和算法，它负责排线程、保安全、对依赖。
// Job System 的标准形态：纯数据进，纯数据出
[BurstCompile]
struct BoidsAccelJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<float3> Positions;
    [ReadOnly] public NativeArray<float3> Velocities;
    public NativeArray<float3> Accel;      // 只写自己那份

    public void Execute(int index)
    {
        // 这里只能碰 NativeContainer 和值类型
        // 不许 Debug.Log、不许碰 Transform、不许 new
        Accel[index] = ComputeSteering(Positions, Velocities, index);
    }
}
选型三条总结

CPU 密集 + 数据结构化 → Job System + Burst（大规模数值、AI、批量变形、粒子）。I/O 密集 → async/await（网络、文件）。像素级大规模并行 → Compute Shader。三条路互不替代，用错方向再怎么优化也到不了天花板。

17依赖图与同步点：Complete 的时机艺术

Job System 用得好不好，几乎全看一件事：你在什么时候调用 Complete()。调用太早，等于白并行；调用太晚，结果又要多等一帧。

官方给的那句话

尽早 Schedule，尽晚 Complete

手上有数据就立刻 Schedule，不到真正要用结果的那一刻绝不 Complete。中间的这段空档，就是并行度。把 Complete 一把删掉，程序通常既不崩也不错，只是慢 —— 这是最容易被忽略的性能杀手。

Schedule 之后到 Complete 之前的那段矩形，才是你真正赚到的并行时间。

延迟一帧的技巧

如果「晚一帧拿到结果」业务上可以接受，官方推荐的做法是：在帧末提交 Job，在下一帧开头取结果。这样 Job 那一整段的消耗落在帧与帧之间的空隙里，主线程完全不用停下等待。代价是数据延迟一帧 —— 对于 AI 决策、路径计算、视线检测这类东西，一帧通常毫无影响。

Profiler 里的线索

主线程上出现长时间的 WaitForJobGroup，说明它在等某个 worker 上的 Job。顺着调用链找到那个 JobHandle.Complete，看它的位置能不能往后挪 —— 这是处理 Job 性能问题最标准的一条路径。

关于 ScheduleBatchedJobs

Job 提交后会被缓存起来、不一定立刻执行。你可以用 JobHandle.ScheduleBatchedJobs() 立刻清空这笔批次让它开跑，但官方文档明确提醒这可能负向影响性能。更稳的做法是调用 Complete 来触发执行；在 ECS 里引擎会自动替你 flush，不需要手动调用。

18Job System 八条禁令

下面八条大多是「不报错但会坑你」的类型，全部来自官方文档的 troubleshooting 清单与常见的实战教训。建议当成 checklist 贴在显示器边上。

禁令一
不要在 Job 里访问静态数据
访问静态数据会绕过全部安全系统。官方文档的原话是：如果访问了错的数据，可能以各种意想不到的方式让 Unity 崩溃（例如访问 MonoBehaviour 会在 domain reload 时崩）。并且明确警告：未来版本会用静态分析禁止这种行为，届时你的代码会直接不能用。
禁令二
不要省掉 JobHandle.Complete()
只检查 IsCompleted 是不够的。必须调用 Complete 才能把 NativeContainer 的所有权交还主线程，它同时清理安全系统的状态 —— 不调用就是内存泄漏。每帧都 job 依赖上一帧的情况同样适用。
禁令三
忘记 Dispose NativeContainer
Allocator.Persistent 不会自动回收。Temp 生命周期 1 帧且不能传进 Job；TempJob 约 4 帧，是传给 Job 的常用选择。用完记得 Dispose。
禁令四
nativeArray[0]++ 是无效的
因为缺少 ref 返回，它等价于「取临时副本 → 副本加一 → 丢弃」。必须显式取出、改、写回：
var t = arr[i]; t.field = 0; arr[i] = t;
禁令五
不要在 Job 里分配托管内存
极慢，而且一分配托管内存就无法享受 Burst 编译的加成。同理，Burst 不支持 string、class、委托 —— 这些都是编译错误。
禁令六
Schedule / Complete 只能在主线程调用
Job 依赖 Job 要用 JobHandle 声明，不能「在 Job 里再 Schedule 一个 Job」。
禁令七
别在循环里塞一堆微 Job
原则是最小化 Job 数量、最大化单个 Job 的工作量。正确做法是用 IJobParallelFor 一次排一大片，而不是 for 循环里 Schedule 一百个小任务。
好事要做
用 [ReadOnly] 标记只读容器
默认是读写权限。只读标记能明显提升性能，因为它告诉引擎这些数据不会互相干扰。
七条禁令 + 一条必做建议。前两条能防止崩溃与泄漏，后面几条决定性能上限。

调试时的救命稻草

Job 里有个 Run() 方法可以替代 Schedule()，直接在主线程同步执行。Job 里的逻辑出了错时，先用 Run 在同一线程跑一遍：如果结果还是错的，那是算法问题；如果 Run 正确而 Schedule 不对，那几乎一定是并发相关的（数据竞争、容器没 Complete、跨帧生命周期）。这个二分法能省掉大量时间。

19帧同步为什么怕多线程

有些游戏不光要求「快」和「不崩」，还要求「同样的输入，在所有终端上算出一模一样的结果」。并发在这种场景下是天然的敌人。

要求是「确定性」的时候，线程调度就不允许进入你的公式

帧同步（Lockstep）同步的是玩家的输入，不是最终状态。所有客户端拿到同一帧的相同输入后各自本地推演，靠的就是「同一份输入 + 同一份逻辑 = 同一份结果」。一旦某一步的不一致，后续每一帧都会放大差异，最后彻底分叉。

原理
同步输入，不同步结果
这是帧同步的全部前提。既然结果靠本地算，那么本地算法就必须允许逐帧 bit-level 一致。
威胁
任何依赖执行顺序或浮点差异的东西
多线程让「谁先谁后」不可控 —— 累积到一定程度就是两台机器算出两条不同的人生。
边界
表现层随便并发，逻辑层寸土不让
动画、特效、UI 怎么并行都行；位置、伤害、技能命中、随机结果的计算过程必须串行且确定。
分界线很清楚：能被查看的东西可以并行，决定胜负的东西不可以。

威胁清单：这些都会悄悄破坏确定性

威胁为什么对策
浮点数不同平台 / 编译选项下浮点运算结果与精度可能不同，误差会累积放大核心逻辑用定点数或确定性数学库
随机数两边用了不同的种子或调用次数不同统一随机种子，由逻辑系统统一产出
遍历顺序Dictionary / HashSet 的迭代顺序不保证稳定（还可能被字符串哈希随机化影响）固定遍历顺序，用数组或有序容器

工程上的标准分层

逻辑层用定点数算位置、技能、碰撞、伤害；表现层根据逻辑结果驱动动画和特效。Unity 的 Transform / Rigidbody / Animator / Particle 统统归为表现层。这样你就会发现：多线程只出现在「重算一次也无所谓」的那一层。校验手段是定期对整个状态算一次 Hash，发现不一致就回滚、重算或向服务器请求修正。

20WebGL：单线程不是建议，是地板

前面所有的技术方案都有一个前提：这台机器给你开线程。WebGL 平台直接把这个前提抽走了。

约束有多硬

System.Threading 整不可用
既包括你自己写的，也包括 Unity 内部原本用来加速的那些
原本多线程的引擎子系统退化
例如 Skinning 的多线程 + SIMD 优化在 Web 上会明显变慢
后台标签页被节流
不可见时多数浏览器每秒只更新一次
异步任务的推荐写法是协程
官方原话：在 Web 上执行复杂异步任务的推荐方法是协程
WebGL 的约束不是配置问题，而是浏览器与 Wasm 运行时平台的固有属性。

Unity 文档给出了具体原因：WebAssembly 无法安全地直接访问原生堆栈，且网页上不支持抢占式线程信号（原生平台里主线程可以同步给其它线程发信号让它们暂停以便 GC，网页上没有这个机制），所以 Wasm 编译出的 C# 代码无法在多个线程上运行。

一线希望（与它昂贵的门票）

较新版本的 Web 平台在加入原生 C/C++ 多线程支持后，可以满足一个条件就开启：服务端必须返回三个特定的响应头（Cross-Origin-Opener-Policy: same-origin、Cross-Origin-Embedder-Policy: require-corp、Cross-Origin-Resource-Policy: cross-origin），把你的页面放进「安全上下文」。所以 —— 真要在 Web 上跑并发，先去确认你的 CDN 能不能配这三个头，否则连谈的资格都没有。

被节流时要特别注意的一件事

浏览器会把处于不可见标签页里的页面降频到每秒更新一次。而 Unity 的 Time.maximumDeltaTime 默认值小于一秒，这会直接导致 Time.time 的推进速度异常。所以所有「依赖时间流逝」的逻辑（计时器、离线收益、冷却恢复）在 Web 上都不要信任 Time.time，要基于服务器时间或真实时间戳。

平台的世代你还能做什么
WebGL（无多线程）协程分帧、时间切片、对象池、预加载、降复杂度
原生（含主机 / 移动 / PC）Job System + Burst、async/await、Compute Shader
一个被迫养成的好习惯

把「能不能并行」和「逻辑怎么组织」解耦开：核心逻辑写成可以按 step 推进的形式（每帧推进一次），而不是写成「开个线程一直跑」。这样单线程平台用协程驱动它、多线程平台用 Job 驱动它，业务代码不用改。这是应对多平台差异最省力的一步。

1
主线程上没有任何同步等待

Job 的所有权完整闭环
过关标准：每个 NativeContainer 有 Dispose；用到了结果的都有 Complete（而非只看 IsCompleted）；只读容器标了 [ReadOnly]。
6
每帧分配量可控
过关标准：Profiler 里非主场 GC.Alloc 列在稳定运行时接近零；Update / LateUpdate 里没有 new、LINQ、闭包、字符串拼接。

过关标准：至少跑过低配机型 + 核心数不同的设备 + Release（开满优化）版本，每个都跑过上千次关键流程。

最后：一条关于度的建议

整篇教程讲了很多并发的技术手段，但最想留下的其实是相反的一句话 —— 游戏里绝大多数「性能问题」，都不是靠加线程解决的。

先别并发
降低数据量、降低频率、对象池、预热
↓
再考虑异步
I/O 的事交给 await，别让 CPU 干等
↓
再考虑分帧
必须主线程做的事，切开慢慢吃
↓
最后才并行
结构化、批量化的数据用 Job System
↓
无锁 / 自定义线程
Profiler 指名道姓说是这里，再动手
从左到右，复杂度与风险递增。多数项目走到第三格就已经足够流畅。
一句话收尾

并发的收益是「多核」，代价是「不确定性」。做游戏最怕的就是不确定性。所以判断标准从来不是「能不能并行」，而是「这一帧能不能按时、稳定、可复现地交卷」。

✓写在最后

这篇教程整理的是「游戏开发中最常遇到的并发类问题」—— 按现象分类，按根因归位，配上可以直接照抄的结论。

如果你只记得三件事
一、主线程上的任何同步等待都是自杀 —— .Result、.Wait、WaitForCompletion 一律改成 await。
二、引擎对象归主线程独占。后台线程算完，结果只能从「派发队列」这唯一的门回到主线程。
三、先测再改。Gfx.WaitForPresent 高就别谈多线程 —— 瓶颈在 GPU，不在你手上。
