01

先问一句：什么时候不该用模式When NOT to Use

绝大多数教程从「什么是设计模式」开始。这个顺序是错的——它让人以为模式是一套应该尽量用上的好东西。事实相反：

先立一条规矩

设计模式几乎总是增加一层间接：多一个接口、多一个类、多一跳调用。你付出的是「今天更难读懂」，换来的是「以后某类改动更便宜」。如果那类改动根本不会发生，你只有付出，没有换来。

GoF 自己在书里就写了这个警告，原文的语气比后来所有转载都更谨慎：模式只有在你确实需要它提供的那种灵活性时才该用，不要过度设计。第 2 章讲 Lexi 案例时也反复强调，模式带来的是间接层，间接层是有代价的。

所以更实用的入口不是「这个模式怎么实现」，而是这三个问题：

套用任何模式之前，先过这三关
① 这里会变吗？
问的是「已经变过几次」或「需求方明确说了还会变」，不是「理论上可能变」。猜出来的变化不配消耗一个抽象。
↓
② 语言或框架已经给了吗？
事件机制、迭代器、函数是一等公民——很多模式已经是标准库里的一个关键字。自己再手写一遍是倒退。
↓
③ 更笨的写法撑得住吗？
如果一段 switch 能说清、而且半年才动一次，就让它留着。模式是重构的方向，不是起手的默认姿势。
三关里任何一关过不了，就停手。这条纪律带来的收益，比多记住十个模式更大。

真正的敌人不是「不会模式」，是「为了模式而模式」

实践里最贵的错误不是漏用模式，而是在小问题上摆大架子。典型症状：一个只有两种支付方式、且两年没变化的功能，被做成了「支付工厂 → 支付策略 → 支付适配器」三层结构，读代码的人要开六个文件才能看清一行业务逻辑。

过度设计的信号

接口的实现类永远只有一个；抽象类的子类从来没被写过第二个；某个 Factory 里只有一行 return new X()；为了加一个字段，新建了三个文件。

用得合适的信号

上一个真实需求确实只改了新增的文件，没动老文件；某个 switch 因为加了分支而被替换掉了；新同事能指着某个接口说「这是为了替换掉内部实现」。

有一种说法值得记住：模式是在重构中长出来的，不是在设计会上画出来的。先写能跑的简单代码，当同一处修改第三次找上门时，再把它提炼成模式。那时候你已经知道变化的真实形状了——而这正是所有模式真正需要的信息。

这一节最该记住的一条

判断该不该用模式，标准只有一个：这个抽象是现实里的变化逼出来的，还是我猜出来的？被逼出来的抽象会被持续使用；猜出来的抽象会成为下一批人的阅读负担。

全景：23 个模式的两条坐标轴The Map

GoF 用的是两个维度来给模式分类，理解这两个维度比记住 23 个名字有用得多。

维度取值问的是什么
目的
Purpose		创建型/结构型/行为型这个模式是管对象怎么被造出来、对象怎么拼在一起，还是对象之间怎么交互与分配职责
范围
Scope		类模式/对象模式它主要靠继承起作用（编译期定死），还是靠对象组合起作用（运行期可换）

第二个维度特别值得留意：23 个模式里绝大多数是对象模式。这不是巧合——GoF 在书里把「优先使用对象组合，而不是类继承」当作两条核心原则之一。原因很直接：继承在编译期就定死了，组合可以运行期换。

只有这两个模式靠「类」工作，其余 21 个都靠「对象」

看到「类模式」这三个字，就该意识到它的灵活性上限：它靠编译期的继承关系，做不到运行期替换。

按目的分的三组，各自管什么

创建型 · 5 个

Creational

核心动作：把「造什么对象」和「怎么用对象」分开。让系统不再依赖具体类名，也不需要知道对象是怎么造出来的。

结构型 · 7 个

Structural

核心动作：把类或对象拼成更大的结构。让新功能、新接口、新平台可以在不改（或少改）老代码的前提下接进来。

行为型 · 11 个

Behavioral

核心动作：定义对象之间怎么通信、职责怎么分。让「谁来做」和「做什么」可以各自独立地变。

注意一个数量上的事实：行为型有 11 个，几乎占了一半。这不是凑数，而是说明 GoF 认为最难、最多样的问题出在「协作」上，而不是「造对象」或「拼结构」上。初学时常觉得三个分类差不多重要，实际上是：创建型最容易懂、结构型最直观、行为型最需要花时间。

核心武器：8 类「重新设计」与对策Causes of Redesign

这一节是整本《设计模式》里最实用、却最常被跳过的部分。GoF 在第 1 章列了八类导致系统需要重新设计的原因，然后立刻给出每一类的对策模式。等于把「什么问题用什么模式」这件事，直接做成了对照表。

它的价值在于：你不需要先知道模式，只需要先认出自己踩的是第几类坑。

这张清单是从「症状」出发的。比起背 23 个模式的定义，先在这里找到自己那一行更划算。

为什么这八条能覆盖大部分场景

把它们翻译成一句人话：所有让人想重新设计的原因，都可以归结为「某个东西变了，而太多地方依赖它」。八条只是「谁在依赖什么」的八个具体样本：依赖类名、依赖操作、依赖平台、依赖内部表示、依赖算法、依赖彼此、依赖继承、依赖改不动的代码。

所以对策也永远只有三个方向：

① 把变化的地方包起来

让它单独住着，改动不外溢。策略、桥接、生成器、命令都属于这一类。

② 把依赖换成指向抽象的箭头

调用方只认识接口，实现换了它不知道。抽象工厂、观察者、模板方法属于这一类。

③ 从外面套一层，不动里面

当被改的东西你改不了，就在边界上加一层翻译或包装。适配器、装饰、代理、外观属于这一类。

这一节最该记住的一条

模式不是按「结构」选的，是按「哪种变化找上了你」选的。看到上面的表，你会发现很多模式反复出现在同一行——那不是巧合，它们本来就是同一个问题的不同解法。先确诊，再开药。

04

创建型（5）：把 new 赶出业务代码Creational Patterns

创建型模式要解决的问题只有一句话：业务代码里那句 new 具体类()，是整份代码中最硬的一根钉子。它把调用者钉死在某个具体实现上——想换成另一个实现、想在测试里换成假的、想按配置决定用哪个，都得改这一行。

创建型模式共同的动作：让「要什么」和「是什么」分开
没有模式时
var log = new FileLogger("/var/log");
调用者知道具体类、知道构造参数、知道初始化细节
↓ 把创建这件事挪走
有了模式之后
var log = factory.CreateLogger();
调用者只知道一个接口，其余全在工厂里
五种创建型模式的差别，只在于「由谁来决定造哪一个」：子类、另一个工厂对象、还是原型自己。

4.1 抽象工厂Abstract Factory

意图：提供一个接口，用于创建一系列相关或相互依赖的对象，而无需指定它们的具体类。
变化点：产品族的实现范围：对象模式关键词：一整套

它和工厂方法最容易混。一句话区分：工厂方法造「一个东西」，抽象工厂造「一套东西」。真正的画面是：我要一套按钮 + 滚动条 + 菜单，它们必须是同一个风格家族，不能出现 Windows 按钮配 Mac 滚动条。

结构：一扇门进去，出来是一整套互不串味的部件
客户端
只认识 WidgetFactory 这个接口
调 CreateScrollBar() / CreateButton()
↓ 运行期注入某一个具体工厂
三个具体工厂（同一接口）
MotifFactory · PMFactory · WindowsFactory
↓ 每个工厂只造自己这一族
产品族（同族之间保证搭配）
MotifScrollBar + MotifButton + MotifMenu
混搭在类型层面就被挡住了
最大的收益不是「能换皮肤」，而是「换皮肤时不可能漏掉某个部件」——产品族的约束被编码进了类型系统。

GoF 在 Lexi 案例里用它解决「支持多种视感标准」；在「支持多种窗口系统」那一节，作者还专门讨论过「这里能不能用抽象工厂」，结论是不能——因为窗口系统的差异不是「一套部件的风格差异」，而是「一层实现细节的差异」，那个问题属于桥接。这个对照本身就是很好的教材。

常见误用

产品族只有一个（只有一套按钮和滚动条），还是硬做了一个抽象工厂 + 一个具体工厂。只有一个实现类的抽象工厂是纯粹的噪音——它不提供任何可替换性，只提供阅读成本。

4.2 生成器Builder 日常叫「建造者」

意图：将一个复杂对象的构建过程与它的表示分离，使得同样的构建过程可以创建不同的表示。
变化点：装配步骤不变，产物形态变化范围：对象模式关键词：分步装配

它的画面感最强：一个导游（Director）拿着固定的行程单，带着不同的建造者走一遍，产出不同的东西。同一串 BuildPartA(); BuildPartB(); BuildPartC(); 调用，交给 HTML 建造者出来是 HTML，交给 PDF 建造者出来是 PDF。

结构：不变的步骤，可换的装配工
Director（导演）
只写步骤顺序：先标题 → 再正文 → 最后页脚
它不知道产物是什么格式
↓ 拿一个 Builder 走一遍步骤
Builder 接口
BuildTitle() · BuildBody() · BuildFooter() · GetResult()
↓ 换成不同实现，步骤一行不改
三种产物
HTMLBuilder → 一个字符串
PDFBuilder → 一个字节流
PlainBuilder → 一个纯文本
注意：生成器解决的是「步骤固定、产物多变」。如果步骤本身也在变，它就不合适了。

日常工程里见得最多的是它的「退化版」：链式调用构造器，也就是常说的 StringBuilder.Append(...).Append(...) 那种写法。严格说那不算 GoF 的生成器（缺了 Director），但精神是一样的：把「拼装过程」变成可读的一串动作，而不是一个塞了八个参数的构造函数。

4.3 工厂方法Factory Method

意图：定义一个用于创建对象的接口，但让子类决定实例化哪一个类。工厂方法使一个类的实例化延迟到其子类。
变化点：造哪个产品范围：类模式关键词：推迟到子类

这是三个「类模式」之一——它靠继承工作。父类里写着 var doc = CreateDocument();，CreateDocument 是个抽象方法；MyApp 子类返回自己的文档，DrawingApp 子类返回画图文档。父类的流程代码完全不用改。

结构：父类留一个洞，子类来填
Application（父类，写流程）
NewDocument() { ...; var d = CreateDocument(); ... }
CreateDocument() ← 抽象，没人知道是什么
↓ 子类实现那个洞
MyApplication → 返回 TextDocument
DrawingApplication → 返回 DrawingDocument
父类的流程代码是「一次写成、永不修改」的，变化的只是那一行返回什么。这就是开闭原则最朴素的样子。

它和生成器的区别可以用一句话记住：工厂方法管「造哪一个」，生成器管「怎么一步步造」。两者经常同时出现——生成器负责装配过程，工厂方法负责决定拿哪个生成器。

常见误用

把它和「简单工厂」混为一谈。简单工厂（一个类里放一堆 if-else 返回不同对象）不是 GoF 模式，它没有解决「新增产品要改工厂」这个问题。区别在于：加一个新类型时，简单工厂必须回去改那个 if，工厂方法只需新增一个子类。

4.4 原型Prototype

意图：用原型实例指定创建对象的种类，并且通过拷贝这些原型来创建新的对象。
变化点：从「构造」变成「克隆」范围：对象模式关键词：复制

适用场景非常具体：对象的构造过程比复制一遍贵得多，或者构造过程你根本不想知道。比如一个已经配置好的、连好连接的、缓存已预热的对象，你要的是一个「配置相同的新实例」，而不是从头 new 一遍再配一遍。

结构：把「怎么造」换成「照着抄」
客户端
调 prototype.Clone() —— 它不关心具体类
↓
原型注册表（可选但常用）
用名字查原型：registry["staff"].Clone()
新增类型 = 注册一个新原型，零代码改动
关键收益：客户端完全不需要知道 ConcreteProduct 这个类名。这也是 GoF 表里「显式指定类名创建对象」那一行的解法之一。
它真正的难点不是结构，是「深拷贝还是浅拷贝」

克隆出来的对象如果和原对象共享内部的可变对象，你改一个会神秘地影响另一个——这类 bug 极难定位。GoF 明确讨论过这个问题：成员是引用类型时必须做深拷贝，或者引入「克隆后再初始化」的钩子。所以原型模式的使用成本，主要花在克隆语义的正确性上，而不是结构上。

4.5 单件Singleton 日常叫「单例」

意图：保证一个类仅有一个实例，并提供一个访问它的全局访问点。
变化点：无范围：对象模式关键词：唯一 + 全局可达

这是 23 个模式里最简单、也最有争议的一个。它的实现只有几行，但它带来的两个后果——全局状态和隐藏依赖——恰恰是软件设计最想避免的东西。

它换来了什么，又欠下了什么
换来的
任何地方都能拿到同一个实例；构造时机可控（首次访问时创建，不像全局变量在 main 之前）；能挡住拷贝
⇅ 代价几乎等价
欠下的
类的构造函数里看不出它依赖谁（隐藏依赖）；测试之间通过单件串味（不可隔离）；任何地方都能改它（全局可变状态）
最要命的一条：「类自己决定自己依赖谁」，于是任何一个测试都没法替它换上一份假实现。

它被批评到什么程度？GoF 作者之一 Erich Gamma 在 2009 年的一次访谈里说，2005 年四位作者讨论过如果重写这本书会怎么改，他想删掉单件模式，但四人没有达成一致。同一个访谈里，他们一致认为应该补上的是另外几个当时没写的模式：extension object、dependency injection、type object、null object。

现代实践里的共识是：「唯一」应该是一个部署决策，不是一个类的设计。在 main 里构造一份，往下用构造参数传引用——类的代码里看不出任何单件痕迹，可测试性就回来了。这就是依赖注入在做的事。

那什么时候它仍然是合理的

当「唯一」是被外部约束强制的，而不是你图省事选的：一台机器上只有一个物理串口、一个进程级的硬件抽象、一个由操作系统保证唯一的资源。
判断句式是「这个领域本身就是唯一的」而不是「我只想让它有一个」。后者应该用依赖注入。

创建型的收尾：五个模式的分工

把它们排开看，五个创建型模式回答的是同一个问题的五个不同侧面：

模式由谁决定造什么它真正的卖点典型触发信号
抽象工厂注入进来的某个具体工厂产品族成套配套，混搭在类型上不可能要换一整套风格/驱动/方言
生成器调用者选的建造者装配步骤固定、产物多变构造函数参数太多，或同一个步骤序列要产出多种格式
工厂方法子类父类流程一次写成永不修改框架里留给你 override 的那个 create 钩子
原型一个现成的实例绕开昂贵或复杂的构造过程构造很贵，或你不想知道构造细节
单件没有人——它自己全局唯一且延迟创建外部约束强制唯一（谨慎使用）
这一节最该记住的一条

创建型模式的判断顺序是：先问「需要几个」，再问「由谁决定」，最后才问「怎么造」。大多数选型的困难都出在跳过前两问、直接纠结实现细节。

05

结构型（7）：不动源码，改外形Structural Patterns

结构型模式处理的是「对象怎么拼」。它们有一个共同的前提假设：有些代码你改不了，或者改了不划算。可能是第三方的库、可能是已经上线稳定的核心类、可能是改了会引爆一堆子类。于是只能从外面想办法。

七个结构型模式，三种「从外面想办法」的手段
① 加一层翻译，让不兼容的接口对上
适配器 · 外观
—— 前者一对一转换接口，后者一对多简化入口。都是接口层面的活儿，不改功能。
↓
② 加一层包装，让功能可以叠加
装饰 · 代理
—— 都是「持有被包装对象的引用」，结构几乎一模一样。差别全在意图：一个加功能，一个管访问。
↓
③ 改变组织方式，让结构本身可伸缩
组合（树形统一）· 桥接（两个维度解耦）· 享元（共享省内存）
这三个动的是结构，不是接口。
这张图的用法：客户端的报错是「接口对不上」找第一组；是「想加行为/想拦访问」找第二组；是「结构本身撑不住」找第三组。

5.1 适配器Adapter

意图：将一个类的接口转换成客户希望的另外一个接口，使原本因接口不兼容而不能一起工作的类可以一起工作。
变化点：外来接口范围：类/对象模式关键词：事后兼容

它的画面就是电源转接头。已有的类和你要用的类都在，谁都没错，只是插头对不上。适配器不做功能改造，只做形状翻译。

结构：一个会说两种话的中间人
客户端
只认 Target.Request() 这一个签名，改不了（它是我们自己的抽象）
↓
Adapter
实现 Target，同时抱一个 Adaptee 进来
Request() { adaptee.SpecificRequest(); }
↓
Adaptee（已有代码，一行不改）
它的方法名、参数顺序、返回类型都跟客户端期望的不一样
注意「一行不改」这四个字——适配器存在的唯一理由就是被适配的那一方动不了。如果两边都能改，直接统一接口就行，不需要这个模式。

它还有一个经常被忽略的用途：防腐层。当你必须依赖一个外部系统（旧系统、第三方 SDK），用它把所有丑陋的接口细节关在一个类里，其余代码只看到自己定义的干净接口。这样将来外部系统升级，只有适配器要改。

误用信号

给每一个新接入的类都写一个适配器，即使两边接口本来就差不多。适配器是「事后兼容」的工具，如果能在设计时就统一接口，那属于事前就该做好的事。

5.2 桥接Bridge

意图：将抽象部分与它的实现部分分离，使它们都可以独立地变化。
变化点：两个独立维度范围：对象模式关键词：事前解耦

它和适配器最容易混，但方向完全相反：适配器是「事后兼容」，桥接是「事前拆分」。适配器是在两个已经存在、本来不搭的东西之间架桥；桥接是在设计之初就把一个本来会长成 M×N 个类的继承树，拆成 M+N 个类。

为什么需要它：继承会让类数量相乘
不拆的话：2 个维度 → 6 个类
窗口类型（Icon / Transient / Application）× 平台实现（X / PM）
= IconX · IconPM · TransientX · TransientPM · ApplicationX · ApplicationPM
加第 3 个平台，要多写 3 个类
↓ 拆成两条独立的继承线
拆开后：2 + 2 = 4 个类
抽象侧：Window → IconWindow / TransientWindow
实现侧：WindowImp → XWindowImp / PMWindowImp
加一个平台只需 1 个类，加一种窗口只需 1 个类
↓ 两侧靠一个引用相连
这个引用就是「桥」
Window 持有一个 WindowImp，把自己的绘制请求委托下去——而不是靠继承去继承平台细节
GoF 在 Lexi 里用桥接解决「支持多种窗口系统」，用的正是这张图的 Window / WindowImp 结构。

判断要不要桥接，有一个很干脆的测试：数一数这个问题有几个会独立变化的维度。一个维度用策略就够了；两个维度用继承会爆炸，此时才轮到桥接。

5.3 组合Composite

意图：将对象组合成树形结构来表示「部分-整体」的层次，使用户对单个对象和组合对象的使用具有一致性。
变化点：结构深度范围：对象模式关键词：统一对待

它解决的是一个很具体、很常见的麻烦：「一个东西」和「一堆东西」要不要区别对待？不区别对待的话，客户端就得写「如果它是容器就遍历，如果是叶子就直接处理」这种判断，而且每加一种操作就要重写一遍。

结构：叶子和容器实现同一个接口，自己递归
Glyph（抽象基类）
Draw() · GetBounds() · Insert() · Remove()
所有节点都实现它，无论简单还是复杂
↓ 分成两种节点
叶子节点 Character
Draw() 真的画一个字符
Insert()/Remove() 是空实现——因为单个字符没有孩子
+
容器节点 Row / Column
Draw() 遍历孩子，对每个孩子调 Draw()
Insert()/Remove() 真的维护孩子列表
客户端再也不用问「你是单个还是一个组」。递归把复杂度吸收进了结构本身，上层代码保持一行。
这个模式有明确的设计代价，GoF 专门讨论过

把 Insert/Remove 放在公共基类上，会让叶子节点拥有无意义的方法——调用一个字符的 Insert 什么也不会发生，这是行为上的不一致（也常被拿来当违反里氏替换的例子）。另一条路是把它们只放在容器节点上，但那样客户端又得先判断类型。
两种做法各有代价，GoF 明确说这是个权衡，没有免费答案。实践里常见的是「基类给空实现或抛异常」，并接受这个不完美。

5.4 装饰Decorator

意图：动态地给一个对象添加一些额外的职责。就增加功能而言，装饰模式比生成子类更为灵活。
变化点：功能的组合方式范围：对象模式关键词：层层包装

要解决的问题是组合爆炸。一个窗口要能加边框、加滚动条、加阴影——用继承的话，每一种组合都是一个类；装饰把它变成「一层一层套」，每种功能只写一个类，运行期任意叠加。

结构：装饰者和被装饰者实现同一个接口，于是可以无限套
Glyph 接口
Draw() —— 装饰者和真实对象都实现它，客户端分不出差别
↓ 运行期一层层套上去
Border( Scroller( TextGlyph ) )
外层 Border.Draw() 先调 base.Draw() 画出内容，再画自己的边框
被装饰的对象始终不知道自己被套住了
↓ 加功能 = 多套一层，不动任何已有类
透明围栏（Transparent Enclosure）
GoF 在 Lexi 里叫它 MonoGlyph：它既是装饰者，也仍然是 Glyph，
所以它能被放进任意一个需要 Glyph 的位置
本质是「包装 + 接口一致 + 转发」。正是这三件事凑在一起，才让套娃成为可能。

日常见到的极端案例是 I/O 流：BufferedInputStream(DataInputStream(FileInputStream(file)))。三层包装合成了一个「带缓冲的、能读基本类型的数据流」，而每一层都是独立可复用的小类。这就是装饰模式在标准库里的样子。

5.5 外观Facade

意图：为子系统中的一组接口提供一个一致的高层接口，使子系统更加容易使用。
变化点：子系统的复杂度范围：对象模式关键词：简化入口

它最简单，也最容易被误解成「只是包装一下」。它真正的价值是提供一条捷径，同时不剥夺强者的能力：客户端想要简单就用 Compiler.Compile(code) 一行搞定，想要精细控制仍然可以绕过外观直接去调那些子系统类。

结构：给一栋楼开一个正门，但侧门没有锁上
客户端
只调 Compiler.Compile() 一行
它不知道编译涉及哪几个子系统
↓
Compiler（外观）
内部按顺序协调：Scanner → Parser → ProgramNodeBuilder → CodeGenerator
它只转发和编排，不含业务逻辑
↓ 但客户端仍然可以直接访问下面的类
子系统类（保持原样）
Scanner · Parser · CodeGenerator ……
外观不封装它们，只是给它们一个更方便的入口
和适配器的区别：适配器是「一对一转换接口」，外观是「一对多简化入口」。适配器让两个东西能协作，外观让用的人少走几步路。

它在工程里最常见的形态就是「门面」：SLF4J 统一各家日志实现、各种 SDK 把十几个零散调用包成三个方法、一个进程内模块对外只暴露一个 Service 类。这些都是标准的外观模式。

5.6 享元Flyweight

意图：运用共享技术有效地支持大量细粒度对象。
变化点：对象数量范围：对象模式关键词：共享内在状态

它是 23 个模式里目标最单一的一个：纯粹为了省内存。当你需要几十万个对象，而这些对象的大部分状态是重复的，就把重复的那部分抽出来共享。

关键动作：把对象的状态切成两半
内在状态（Intrinsic）→ 共享
不随场景变化的部分：字符的字体、字形的点阵轮廓、棋子的颜色形状
只存一份，被所有实例共用
+
外在状态（Extrinsic）→ 传参
随场景变化的部分：字符在文档中的位置、棋子在棋盘上的坐标
不存进对象，调用时当参数传进去
↓ 二者靠一个工厂拼起来
FlyweightFactory
按内在状态做池子：GetGlyph('a', font) 命中就返回已有对象，
没命中才新建。文档里几千个 'a' 可能只对应一个对象。
它需要客户端配合：调用者必须负责把外在状态传进来。这是它的使用成本，也是它常被写错的地方。

它和「缓存」的区别在于目的：缓存是为了省时间（避免重算），享元是为了省空间（避免重复对象）。两者经常一起出现——FlyweightFactory 本身就是一种缓存。

不要提前用

它的代价很实在：代码复杂度上升、客户端要自己管理外在状态、共享对象的不可变约束必须严格遵守（改了共享状态 = 所有使用者一起出 bug）。只有在测量确认「对象数量确实是瓶颈」之后才值得上。在没有数据支撑时，它是一个典型的过度优化。

5.7 代理Proxy

意图：为其他对象提供一种代理以控制对这个对象的访问。
变化点：访问的时机与权限范围：对象模式关键词：能不能访问

结构上和装饰几乎一样：都是「实现同一接口 + 持有一个真实对象 + 转发调用」。区别全在意图：装饰是加功能，代理是管访问——控制什么时候让你拿到、以什么权限拿到、要不要先做点别的。

GoF 列出的四种代理，画面各不相同
远程代理 Remote
本地对象是远方对象的替身，把网络细节藏起来
—— 调用方像调本地方法一样调远程服务
↓
虚代理 Virtual
按需创建昂贵的对象：图片没滚到可视区就先不加载
—— 延迟创建，代理先答应着，真要用时才 new
↓
保护代理 Protection
检查调用者有没有权限，没权限就拒绝
—— 权限控制塞在转发之前
↓
智能引用 Smart Reference
在访问前后做附加动作：引用计数、首次访问时加锁、写时复制
—— 现代语言里的智能指针就是这个
四种代理共用一个结构，差别在「转发之前多加了一步什么」。

结构型的收尾：三条容易走错的岔路

容易混的一对差在哪一句话判据
适配器 vs 桥接一个事后兼容，一个事前拆分两个东西是本来就有、只是不搭（适配器），还是设计时就该拆成两个独立变化的维度（桥接）
装饰 vs 代理代码结构几乎相同，意图完全不同你是想给它加能力（装饰，可以叠很多层），还是想管住访问（代理，通常一层）
装饰 vs 组合一个包装一个，一个容纳多个被包装的东西是唯一一个（装饰），还是一组、且结构是树（组合）
外观 vs 中介者都简化了关系，但方向相反外观是单向的、给外部人用的入口；中介者是双向的、内部同事之间的协调者
这一节最该记住的一条

结构型模式有一个共同前提：被组合的东西你不想改或改不了。所以判断该不该用时，先问一句「我为什么不能直接改它」——如果答案是「其实可以改」，那正确做法往往是改它，而不是套一层。

06

行为型（11）：让请求和对象脱钩Behavioral Patterns

这一类最多（11 个），也最容易学成一团浆糊——因为它们的结构彼此很像，都是「多个类 + 一层抽象 + 互相调」。真正能把它们分开的只有一个东西：它在切断哪一根耦合。

11 个行为型模式，各自切断哪一根耦合
切断「发送者 ↔ 接收者」
职责链（沿链传递）· 命令（变成对象）· 中介者（经过中间人）
↓
切断「算法 ↔ 使用它的代码」
策略（算法可换）· 模板方法（骨架与步骤分离）· 解释器（文法与求值分离）
↓
切断「状态 ↔ 行为」
状态（行为随状态自动切换）· 备忘录（状态与持有者分离）
↓
切断「集合内部 ↔ 遍历者」或「数据结构 ↔ 新操作」
迭代器（不暴露内部就能遍历）· 访问者（不改结构就能加操作）
↓
切断「发布者 ↔ 订阅者」
观察者（一对多通知，发布者不知道有谁在听）
学这一类的正确方法：先记住这根耦合，再看模式怎么切断它。只背结构，这 11 个会长得一模一样。

6.1 职责链Chain of Responsibility

意图：使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系。将这些对象连成一条链，沿着链传递请求，直到有一个对象处理它。
切断：发送者↔接收者关键词：逐级传递
结构：每个处理者只认识自己的下一个
Client
调 handler.Handle(request) 一次
它不知道最终是谁处理的
↓
Handler1 → Handler2 → Handler3
每个处理者：能处理就处理并停下，不能处理就转给后继者
转发靠的是自己持有的 successor 引用，不是知道全链
收益：链的成员可以运行期重排、增删，客户端一行都不用改。这也是它被用在 UI 事件冒泡、日志分级、审批流里的原因。
常见误用

忘记定义「没人处理会怎样」。请求走到链尾没人接，是静默丢弃还是抛异常？GoF 特别提醒了这一点：大多数实现里请求不一定被处理，这个语义必须由设计者明确下来。

6.2 命令Command

意图：将一个请求封装为一个对象，从而使你可用不同的请求对客户进行参数化；对请求排队或记录请求日志，以及支持可撤销的操作。
切断：调用者↔执行者关键词：请求变成一等公民

它的核心动作是「把一次调用变成一个东西」。一旦请求变成对象，它就能被存储、排队、序列化、重放、撤销——这些事在「一行方法调用」上是做不了的。

结构：GoF 在 Lexi 里用它实现撤销/重做
Command 接口
Execute() · Unexecute()
撤销能力和执行能力写在同一个对象里
↓
CommandHistory（命令历史）
按执行顺序压入栈：[Insert'A'][Insert'B'][Delete'A']
撤销 = 弹出并调 Unexecute()；重做 = 再压回去
↓ 谁来执行
Receiver 们
Document 自己知道怎么插入删除；Command 只负责下令
Command 对象里存的是「下令所需的全部信息」
它真正的价值：撤销功能不需要业务类支持。Document 一行撤销相关代码都没有，全靠 Command 自带 Unexecute。这就是「请求变成对象」换来的东西。

6.3 解释器Interpreter

意图：给定一个语言，定义它的文法的一种表示，并定义一个解释器，该解释器使用该表示来解释语言中的句子。
切断：文法↔求值范围：类模式关键词：规则树

它是 23 个里最少被实际使用的一个，因为它的适用条件很窄：文法本身简单、稳定，且效率要求不高。它的做法是把一条规则变成一个类——正则表达式、布尔表达式、简单查询语言都是它的主场。

结构：一句表达式长成一棵树，求值就是树的遍历
要解析的句子
(a and b) or (not c)
↓ 终结符和非终结符各自成类
非终结符节点
AndExpression · OrExpression · NotExpression
它们的 Evaluate() = 先求孩子的值，再组合
+
终结符节点
VariableExpression / Constant
它们的 Evaluate() 直接查上下文
↓
Context（上下文）
存变量取值：a=true, b=false, c=true
求值结果由结构 + 上下文共同决定
结构上它其实是组合模式 + 一个 Evaluate 操作——这正是为什么两者看起来像。
GoF 自己的警告

书里明确说：当文法变得复杂时，解释器模式会产生庞大的类层次，此时应该改用解析器生成器（如 yacc/lex 那类工具），而不是继续手工加类。不要用解释器模式去写一门真正的编程语言。

6.4 迭代器Iterator

意图：提供一种方法顺序访问一个聚合对象中的各个元素，而又不暴露该对象的内部表示。
切断：遍历↔内部结构关键词：统一的走法

它的收益有两层，第二层常被忘掉：第一层是不暴露内部结构（你不用知道它背后是数组还是链表还是树）；第二层是遍历算法本身可以换——正序、逆序、过滤、惰性求值，都不需要动集合类。

结构：把「走到哪了」这个状态从集合里搬出来
Aggregate 接口
只有一件事：CreateIterator()
↓ 造出一个遍历状态
Iterator 接口
First() · Next() · IsDone() · CurrentItem()
「当前走到哪」存在迭代器里，不存在集合里
↓ 于是
可以同时有多个遍历在进行
两个客户端各自拿着自己的迭代器，互不干扰——
如果遍历状态存在集合里，这是做不到的
这也是为什么现代语言把它做成了语法层的东西：foreach / for...of / generator 背后都是这个模式。

6.5 中介者Mediator

意图：用一个中介对象来封装一系列的对象交互。中介者使各对象不需要显式地相互引用，从而使其耦合松散，而且可以独立地改变它们之间的交互。
切断：同事↔同事关键词：网状变星形

它解决的问题用一张图就说完了：n 个对象互相引用是 n² 条线，全接到中间人身上是 n 条线。当 n 从 3 涨到 10，这个差别就是「还能维护」和「不敢维护」的区别。

结构：把网状依赖改成星形
没有中介者时
对话框里每个控件都要知道其他控件的状态：
输入框要通知按钮、按钮要通知列表、列表要通知输入框……
加一个控件要改所有控件的代码
↓ 全部接到中介者上
有了中介者之后
每个控件只认识 DialogDirector 一个对象，
变化时喊一声 director.WidgetChanged(this)，剩下交给中介者
↓
中介者持有全部协调逻辑
「输入框变空 → 禁用确定按钮」这条规则只写在一个地方
加新控件只需改中介者，不动老控件
代价同样明确：中介者会变胖。协调逻辑集中在一处，如果规则多而杂，它自己会变成一个难以维护的上帝类。

6.6 备忘录Memento

意图：在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态，以便以后将该对象恢复到原先保存的状态。
切断：状态↔持有者关键词：快照

「不破坏封装」这四个字是它的全部难点。朴素做法是把对象的所有字段暴露出来存一份，但那等于把内部结构公开了——以后改字段，所有存快照的地方都得改。备忘录的做法是：快照由对象自己生成和读取，外部只拿着一个不透明的盒子。

结构：三方分工，谁都不能多知道一点
Originator（原发器）
自己生成快照 CreateMemento()，自己恢复 SetMemento(m)
只有它知道快照里到底是什么
↓ 交出一个不透明对象
Memento（备忘录）
对原发器完全可见，对别人完全不透明
别人只能拿着它、不能读它、更不能改它
↓ 只是保管
Caretaker（负责人）
只负责存和取，不检查内容、不操作内容
它保证不破坏封装
它和命令模式经常配合：命令负责「怎么撤销」，备忘录负责「撤销到什么状态」。两者合起来才是完整的撤销系统。

6.7 观察者Observer

意图：定义对象间的一种一对多的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都得到通知并被自动更新。
切断：发布者↔订阅者关键词：广播通知

这是 23 个模式里在现代工程中出现频率最高的一个。事件监听、数据绑定、消息总线、响应式框架——底层几乎都是它。

结构：发布者只管喊，不知道谁在听
Subject（目标）
维护一个观察者列表 + Attach() / Detach()
状态一变就 foreach(o in observers) o.Update()
它不知道具体有多少人、都是谁
↓ 广播
Observer（观察者）
都实现 Update()，各自决定收到通知后干什么
新增一种反应 = 新增一个观察者，目标类一行不改
↓ GoF 在 Lexi/文档场景里的做法
一处数据，多处视图
文档数据变了，表格视图、图表视图、大纲视图各自刷新
三个视图之间互不知情
注意 push 和 pull 的取舍：推模式把细节塞进通知里，拉模式让观察者自己来取。GoF 说推模式更难复用，拉模式更灵活但要求观察者知道目标。

6.8 状态State

意图：允许一个对象在其内部状态改变时改变它的行为。对象看起来似乎修改了它的类。
切断：状态↔行为关键词：内部自动切换

它对付的是那种「一个 switch 判断自己处在哪个状态，然后每个分支里又是一大堆操作」的代码。做法是把每个状态做成一个类，把「在这个状态下能做什么」放进去；状态之间还能决定下一个状态是谁。

结构：行为随状态自动流转
Context
持有一个 State 引用，把请求转发给它
Request() { state.Handle(this); }
它自己不写任何 if 判断状态
↓ 每个状态自己决定下一步是谁
具体状态类
TCPClosed → 收到主动打开 → 把自己换成 TCPListen，并返回失败
TCPEstablished → 收到关闭 → 换成 TCPListen
「下一状态是谁」写在这一步里，不是查表
这就是它和策略模式最关键的区别：状态是对象内部自己换的，策略是外部传进来的。状态知道彼此，策略互不知情。

6.9 策略Strategy

意图：定义一系列的算法，把它们一个个封装起来，并且使它们可相互替换。本模式使得算法可独立于使用它的客户而变化。
切断：算法↔使用者关键词：可替换

它可能是所有模式里最容易理解、也最容易被滥用的一个。理解起来一句话：把那个会变的算法从类里抽出来，放到外面去，用的时候传进来。

结构：上下文不知道用的哪个算法
Context（上下文）
持有一个 Strategy 引用，需要时调 strategy.Algorithm()
它只知道「有个算法可以调」，不知道是哪个
什么时候用哪个，由客户端决定
↓
Strategy 接口 + 若干实现
每个具体策略封装一种算法，彼此完全不知道对方存在
加一种算法 = 加一个类，不改 Context 老代码
它是「对扩展开放、对修改关闭」最直观的样板：扩展是加类，修改是没有。
它的代价被低估得最严重

策略模式把算法抽离了，但也把「有哪些算法、怎么选」推给了客户端。如果选择逻辑本身复杂，这个复杂度不会消失——它会跑到调用方，变成一个更难看的 if-else。
另外两个实际问题：算法多的时候类数量膨胀；策略之间无法共享中间结果（因为互不知情），所以需要协作的算法不适合它。
还有一个前置条件：调用方必须知道不同策略的差别才能选，这本身就是一种信息泄露。GoF 提到可以用一个参数化的 Context 或把选择逻辑放进工厂/配置来缓解，但代价是把复杂度挪到别处。

6.10 模板方法Template Method

意图：定义一个操作中的算法的骨架，而将一些步骤延迟到子类中。模板方法使得子类可以不改变一个算法的结构即可重定义该算法的某些特定步骤。
切断：骨架↔步骤范围：类模式关键词：钩子

它是三个「类模式」之一，也是最古老、最普遍的设计手法——不需要任何额外的接口或类，只是一个父类里的方法调用了几个抽象的或可覆盖的方法。

结构：父类写死顺序，子类填内容
父类的模板方法（不打算被覆盖）
读输入 → 转换 → 处理（抽象） → 输出
顺序、错误处理、资源释放都写死在这里
↓ 中间那一步是钩子
子类只实现被留空的那一步
TextFileProcessor 每行转大写
CSVFileProcessor 解析成表再处理
流程一行都不用重写
GoF 特别强调这类「钩子操作」（hook operation）：父类给一个默认空实现或默认行为，子类想改才改。
这比强制抽象更灵活——不关心某个步骤的子类可以完全无视它。

它常被拿来和策略对比。区别在于变化的手段：模板方法用继承，在编译期定死步骤实现；策略用组合，运行期可换。所以策略更灵活，模板方法更简单直接——如果你的「多个变体」是明确的、有限的几个子类，模板方法往往就够了。

模板方法是最常被不知不觉用上的模式。
任何一个「父类写好了流程、留几个坑给子类填」的框架，都在用这个模式。它不需要你刻意去实现，只需要你刻意去识别。 —— 这也是它值得放在最后才讲的原因

6.11 访问者Visitor

意图：表示一个作用于某对象结构中的各元素的操作。它使你可以在不改变各元素的类的前提下定义作用于这些元素的新操作。
切断：数据结构↔操作关键词：加操作不改类

它解决的是一个具体的僵局：数据结构稳定，但需要加在它上面的操作一直在增多。如果每个操作都做成元素类里的一个方法，那每加一个操作就要改所有元素类——而它们可能来自第三方，改不了。

结构：双重分派——先看你是谁，再看你想干什么
第一步：元素接受访问者
每个元素类实现一个方法：Accept(v) { v.VisitXxx(this); }
注意它写死了自己要调哪个 Visit 重载
↓ 于是「元素类型」被确定下来
第二步：访问者按类型分派
Visitor 里为每种元素类型准备一个 VisitXxx 方法
「操作」这一维被确定下来
↓ 结果是
加一个新「操作」= 新增一个 Visitor 子类
拼写检查、断字处理、字数统计、导出……各是一个 Visitor
元素类（Character / Row / Column）一行都不用改
GoF 用它在 Lexi 里实现「拼写检查和断字处理」，并明确说：两维扩展不能同时自由——加操作容易，加元素类型则要改所有 Visitor。
它是把双刃剑，用错方向会很痛

访问者模式把「可扩展的方向」从元素类型换成了操作。也就是说：
• 加新操作 → 很爽，加一个类就行
• 加新元素类型 → 很痛，所有 Visitor 都要加一个 Visit新类型，全部重编译
如果你的元素类型还在不断增加，选它是选错了方向。这个取舍在 GoF 书里写得很清楚，但很多教程不提。

行为型的收尾：三组最容易混的

对照组差异轴一句话判据
策略 vs 状态谁来切换外部传进来的（策略）还是对象内部自己流转的（状态）。策略是「选一个」，状态是「流转起来」
策略 vs 命令生命周期只算一次、算完就完（策略）还是有「执行 / 撤销 / 排队」的生命周期（命令）
中介者 vs 观察者要不要「接下来谁干」只是广播通知大家各自知道（观察者），还是要集中决定后续动作（中介者）。观察者是一对多，中介者是多对多收敛到一处
这一节最该记住的一条

行为型模式不是按「有几个类、怎么连线」区分的，而是按「它切断了哪一根耦合」区分的。结构看起来都一样（接口 + 若干实现 + 一个持有者），但切断的耦合不同，适用场景就完全不同。

最容易选错的六组对照Confusable Pairs

23 个模式单独看都清楚，放到一起就容易选错。而选错的根源几乎永远是同一个：在看代码结构，而不是在看意图。下面六组的代码结构往往高度相似，唯一的区别是「它想干什么」。

第一组：策略 vs 状态 —— 谁在切换

两者都是「一个上下文 + 一个可替换的实现」，代码写出来几乎一样。唯一的区别是切换动作由谁发起。

对比项策略 Strategy状态 State
封装的是算法状态
谁决定用哪个客户端主动传入对象内部自动流转
这些实现彼此认识吗不认识，互不知情通常认识——状态会指定下一个状态
典型场景支付方式、排序算法、压缩算法订单状态流转、TCP 连接状态、工作流
一句话策略是「选一个」，状态是「流转起来」

第二组：装饰 vs 代理 vs 适配器 —— 三种「套一层」

这三个都是包装类持有被包装对象的引用，结构上最难区分。差别全在意图。

对比项装饰 Decorator代理 Proxy适配器 Adapter
接口变了吗不变，和被装饰者一致不变，和真实对象一致变了，转成客户端期望的接口
功能变了吗加了新功能功能不变，控制访问功能不变，只改形状
能叠多层吗可以，任意层嵌套通常一层不叠，一对一
被包装方知情吗不知情通常由代理创建/管理不知情
一句话装饰是「加能力」，代理是「管访问」，适配器是「换插头」
最容易踩的坑

装饰和代理在代码上完全无法区分——都是 class X : ISame { private ISame inner; ... }。所以判断时不要看代码，要看目的：如果你希望「用户可以自由决定加不加这一层」，那是装饰；如果「加这层是系统强制、用户不该察觉」，那是代理。

第三组：工厂方法 vs 抽象工厂 —— 一个还是一个套

对比项工厂方法抽象工厂
造几个产品一种产品一族产品（多个方法）
抽象层次一层两层（工厂的抽象 + 产品的抽象）
靠什么扩展加子类（继承）加一个具体工厂（实现接口）
加一种新产品时加一个子类，老代码不动要改接口，所有具体工厂都要实现它
一句话工厂方法造「一个东西」，抽象工厂造「一套东西」

第四组：适配器 vs 桥接 —— 事后补还是事前拆

这一组的关键词是时间点：两个不搭的东西是「本来就有，现在要凑一起」还是「设计时就该分成两个独立变化的维度」。

同一张图，两种成因
适配器：事后补救
旧日志库的 WriteLine(string, Level) 和你要的 Log(string) 对不上
两边都不想动 → 加一个翻译
对比
桥接：事前拆分
「画什么窗口」和「用哪个平台画」是两件独立的事
设计时就不该让它们长在一棵继承树上 → 拆两条线
判断句式：「这东西本来就有、只是不兼容」→ 适配器；「这东西将来会在两个方向上各自变化」→ 桥接。

第五组：中介者 vs 观察者 —— 要不要决定「接下来谁干」

对比项观察者 Observer中介者 Mediator
通信方向一对多，单向广播多对多，收敛到一处再分发
发布者知道谁在听吗不知道知道，中介者持有所有同事
协调逻辑在哪分散在各观察者里集中在中介者里
典型场景数据变了多个视图刷新、事件总线UI 控件联动、聊天室、航空管制
一句话观察者是「大家各自知道一下」，中介者是「我来安排接下来谁干」

第六组：组合 vs 装饰 —— 一个容器还是一个包装

对比项组合 Composite装饰 Decorator
持有一个还是多个多个孩子（列表）一个被装饰者
整体形状树链（一条直线）
目的让「单个」和「一组」被统一对待让功能可以逐层叠加
叶子节点有空方法吗有（Insert/Remove 无意义）没有，每个装饰者都在做事
一句话组合是「一对多、要递归」，装饰是「一对一、要叠加」
这一节最该记住的一条

选模式时，判断顺序永远是：先问意图（我要解决什么问题），再看结构（谁持有谁）。反过来做——先看结构像哪个——必然出错，因为大约有三分之一的模式共享同一套结构。

完整走一遍：Lexi 文档编辑器Case Study

GoF 书的第 2 章是一个长达 40 页的案例：设计一个所见即所得（WYSIWYG）的文档编辑器 Lexi。它的价值在于把 8 个模式放进同一个真实系统里，展示它们不是孤立的花招，而是同一个设计过程中的接力。

Lexi 面对七个设计问题，而它们正好对应用户最熟悉的那些「编辑器为什么会难做」。

七个问题 → 八个模式（GoF 第 2 章的完整映射）
① 文档结构怎么表示
要能容纳字符、图形、表格、分栏，任意嵌套，且不区分「单个」和「一组」
→ 递归组合，即组合模式 Composite
↓
② 怎么排版（把元素排成行列）
排版算法有很多种，各有质量/速度取舍，而且会换
→ Compositor 类封装算法，策略模式 Strategy
↓
③ 怎么给界面加边框、滚动条、阴影
这些装饰会随界面演进变化，且组合方式很多
→ 透明围栏（MonoGlyph），即装饰模式 Decorator
↓
④ 怎么支持多种视感标准（Motif / PM）
滚动条、按钮、菜单必须成套切换，不能混搭
→ 抽象工厂 Abstract Factory
↓
⑤ 怎么支持多种窗口系统（X / PM）
这里是「实现细节」的差异，不是「部件风格」的差异
→ Window / WindowImp 两条独立的继承线，桥接模式 Bridge
↓
⑥ 用户操作怎么统一处理并撤销
功能散落在各个对象里，菜单和按钮需要一致的触发方式和撤销能力
→ 命令模式 Command（配 CommandHistory 做撤销/重做）
↓
⑦ 拼写检查、断字这些分析怎么加
操作会不断增加，但不该每次都去改所有元素类；且分析需要遍历整个结构
→ 迭代器 Iterator（遍历）+ 访问者 Visitor（操作）
七个问题用了八个模式：注意第 ⑦ 个用了两个。问题和解法不是一一对应的，这也是为什么不能靠背「模式→场景」的一对一表。

这个案例最值得学的三个细节

  1. Glyph 这一个抽象救了整个设计。文档里的一切——单个字符、一行、一列、一张图、一个边框装饰——全部实现同一个 Glyph 接口。于是「查询光标位置」「重绘损坏区域」「做拼写检查」这些操作，都只需要对着一个接口写一次。这是「统一对待单个和一组」带来的最大红利。
  2. 同一处的差异，被拆给了两个不同的模式。「支持多种视感」用抽象工厂（换一套部件），「支持多种窗口系统」用桥接（换一层实现）。GoF 专门写了一节讨论「这里能不能用抽象工厂」，结论是不能——因为前者变的是产品族，后者变的是实现层。这个对照本身就是最好的选型训练。
  3. 装饰者也被做成了 Glyph。边框、滚动条这些「外观装饰」不是悬浮在文档之外的东西，而是文档结构里的一个节点。于是「重绘所有元素」的递归调用会顺路把它们一起画了，客户端完全不需要知道有装饰存在——这就是「透明围栏」这个名字的来历。
这一节最该记住的一条

Lexi 案例真正的教学价值不在这八个模式本身，而在于它展示了一个设计是被「一个个具体问题」推着往前走的：先有文档结构的麻烦，才有组合；排版算法会换，才有策略；界面装饰会变，才有装饰……模式是问题的产物，不是设计的起点。

代价：模式被批评，以及语言在吃掉模式Criticism

一本 1994 年的书，能统治软件设计三十年，同时也一直挨批。这一节讲清楚批评的内容和它的边界——因为知道「什么时候不用」，比多记三个模式有价值。

批评一：模式是「语言缺陷的报工单」

1996 年，当时在 NASA、后来成为 Google 研究总监的 Peter Norvig 做了一个著名演讲《Design Patterns in Dynamic Languages》。他把 23 个模式拿到 Lisp 和 Dylan 里重新审视，结论是：其中 16 个要么直接消失，要么实现起来简单得多。

他的论证角度不是「模式不好」，而是：这些模式之所以存在，是因为当时的语言缺少某些能力。他在演讲里引用过一句流传最广的概括——设计模式是对你的编程语言的缺陷报工单（design patterns are bug reports against your programming language）。

语言缺的能力被它「吃掉」的模式（6+4+2+2+1+1 = 16 个）为什么消失
类型是一等公民
6 个		抽象工厂 · 享元 · 工厂方法 · 状态 · 代理 · 职责链类和类型本身就是运行期对象，可以直接当参数传，不需要「两条平行的类层次」
函数是一等公民
4 个		命令 · 策略 · 模板方法 · 访问者一个函数变量就能替掉一整个 Command / Strategy 对象；组合替掉了继承
宏
2 个		解释器 · 迭代器语法抽象在语言层面解决了「解析」和「遍历」这两件事
方法组合
2 个		中介者 · 观察者before/after/around 钩子直接干掉了观察者的样板代码
多方法
1 个		生成器按多个参数类型分派，省掉 director / builder 那套类层次
模块
1 个		外观模块导出天然就是一个简化入口
剩下 7 个变化不大组合 · 装饰 · 备忘录 · 原型 · 单件 · 桥接 · 适配器——它们不属于「语言特性缺失」那一类，只是实现更简单

更有意思的是「被吃掉」这件事在主流语言里已经真实发生了。下面的表是 1996 年的预测，今天基本都兑现了：

模式今天被什么取代具体例子
迭代器生成器语法 / 语言内建遍历Python 的 yield、C# 的 IEnumerable、JS 的 function*
观察者事件机制 / 响应式流C# event、Go channel、RxJS
策略匿名函数 / 一等函数Java 8 lambda、JS 箭头函数——传一个函数就行
命令闭包 / thunkRust FnOnce、JS 闭包
访问者模式匹配Scala match、Java 17 switch、Rust match
装饰注解 / 特性 / mixinPython @decorator、Java Annotation
代理语言原生代理 / 拦截器ES6 Proxy、Java 动态代理
单件对象声明 / 枚举Scala object、Kotlin object

另一项研究走的是同一方向：Hannemann 和 Kiczales 用面向切面编程（AspectJ）实现了这 23 个模式，发现其中 17 个的代码级依赖可以被移除或大幅简化。结论类似——很多模式的复杂度，来自「用错误的机制去表达一个关系」。

批评二：模式变成模板复制，丢掉了原书的「为什么」

这个批评来自另一侧，更值得在意。GoF 明确说过书的灵感来自建筑学家 Christopher Alexander 的《建筑模式语言》——那本书里每个模式都有丰富的语境、力量和张力。但有评论指出：《设计模式》拿走了 Alexander 的「形式」，没有拿走他的「生成性思维」，于是传播开的是「照着模板套」，而不是「理解情境再判断」。

表现就是今天最常见的两种悲剧：面试能背出 23 个模式的定义，却在真实代码里分辨不出哪里该切一刀；或者把模式当成了「资深工程师的装饰品」，用小问题去喂大结构。

批评三：作者自己也改了主意

2009 年，Erich Gamma 在一次访谈里透露：四位作者 2005 年讨论过如果重写这本书会怎么改，结论是会重新给一些模式归类，并且补上几个当时没写的模式——扩展对象/接口（extension object / interface）、依赖注入（dependency injection）、类型对象（type object）、空对象（null object）。

另外，他个人想删掉单件模式，但四人没有达成一致。加上前面那句「依赖注入应该被补进来」——这两个动作放在一起看，含义很清楚：「唯一实例」这件事，作者更倾向于用依赖注入来做，而不是用单件模式来做。

那这套东西还值得学吗：把三种立场摆在一起
批评方的意思
很多模式是特定语言条件下的产物。换了语言，或者语言升级了，
手写这些模式就成了反模式。别把权宜之计当真理。
↓ 但
支持方的意思
模式首先是一套共享词汇。「这里需要一个访问者」比讲十行话更快，
而且它们确实是被反复验证过的解法。
↓ 合起来用
务实的结论
把它当词汇表和问题清单用，不要当施工图纸用。
学「它在防哪种变化」，别学「它的类图画成什么样」。
一个可操作的判据：当你发现语言或框架已经原生支持某件事时，用原生的，不要手写模式。用 yield 而不是手写 Iterator 类，用事件而不是手写 Observer 基类。
这一节最该记住的一条

Norvig 的批评有一个很具体的实用推论：判断一个模式该不该手写，先看语言有没有更好的表达。模式的价值在于「它指出的问题」，而不在于「它的类图」。当模式变成语言特性时，继续手写模式才是反模式。

结语：模式是词汇，不是建材Closing

如果这篇教程只留下一句话，我希望是这句：

Each design pattern lets some aspect of system structure vary independently of other aspects.
每一个设计模式，都是让系统结构中的某一个方面可以独立于其他方面而变化。 —— GoF《设计模式》第 1 章

这句话值得反复读。它把 23 个模式浓缩成了一个动作：找到那根「会单独变化」的轴，用一层边界把它圈起来。剩下的都是细节——圈在哪、用什么形状圈、圈完由谁负责。

三个必须说清楚的提醒

  1. 模式和设计原则的关系，是「答案」和「题目」。上一篇文章讲的 SOLID 七条是题面——它告诉你「哪里不对劲」；设计模式是参考答案——它告诉你「有人是这么处理的」。所以正确顺序是先学原则、再看模式：带着「开闭原则」去看策略模式，你会看到的是「加算法不改老代码」；不带原则去看，你看到的只是「三个类一个接口」，看完就忘。
  2. 不要一次把 23 个学完。真实的工程里，八成的场景落在六个模式上：策略、观察者、工厂方法、适配器、装饰、模板方法。剩下十七个是「遇到了再回来翻」的词典条目。把它们当参考手册，不要当课程表。
  3. 语言在进化，模式在退位。看到语言原生支持了某个模式，就应该用原生的，并且把这件事当成进步而不是偷懒。手写一个 Python 的 Iterator 类不是严谨，是倒退。

最后一句反直觉的话

回头看第 01 节那条规矩。整篇教程里出现的每一个模式，都需要你先付出一层间接的代价。所以学完模式之后，最该长出来的能力不是「一眼认出该用哪个模式」，而是——

能看着一段简单到「不需要任何模式」的代码，忍住不动它。
这比能在复杂代码里挑出正确的模式更难，也更有价值。因为绝大多数的「过度设计」，都不是发生在不会用模式的人手上——恰恰发生在刚学会模式、还很兴奋的人手上。
