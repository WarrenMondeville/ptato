00一句话讲清楚 WFC 在干什么

一句话：给你一堆积木和一张「谁能挨着谁」的表，WFC 负责把它拼满一整张地图，而且保证处处合法。剩下的神秘感，基本都是量子力学借来的名词。

2016 年，Maxim Gumin 开源了一个叫 Wave Function Collapse 的项目。名字听起来像是要模拟量子力学，实际上它做的事非常朴素：

输入
一组 tile
加上「tile A 的右边能不能接 tile B 的左边」这类规则。规则可以是你手写的，也可以从一张示例图里自动扫出来。
过程
一个格子一个格子地定下来
每一步都选「当前最没得选」的格子，从它还可能成为的那几种 tile 里按权重抽一个定死，然后把这个决定扩散给邻居。
输出
一张处处合法的地图
任意相邻两格都满足规则，大小随你指定，换个随机种子就换个结果。
图 0-1 · WFC 的输入输出全景

真正让它出圈的不是这篇论文式的描述，而是两个游戏。

一个是 Oskar Stålberg 的《绝境北方》（Bad North），用它在战前批量生成维京小岛；另一个是他的《城镇叠叠乐》（Townscaper），把同一套算法改成了实时、并且让玩家直接拿手戳——你在水面上点一下，一座带屋顶带窗户带晾衣绳的房子就长出来了。

这篇教程的主线

先把它当成一个约束求解器彻底吃透（第一、二部分），再学会怎么控制它输出什么（第三部分），最后拿它去解三个真问题：城镇、地牢、无限城市（第四、五、六部分）。每一部分都给能落进 Unity C# 的具体做法，而不是停在「原理很优美」。

为什么这个算法值得单独写一篇

程序生成有一整排老工具：Perlin 噪声、元胞自动机、BSP 房间切分、随机游走挖掘、马尔可夫链。它们各有擅长，但都有一个共同的软肋——它们不懂「零件」。

噪声能给你起伏地形，但给不了「这个墙角必须和那个屋顶咬合」。BSP 能给你房间布局，但房间里摆放什么、墙和地板怎么接，得靠另一套系统补齐。元胞自动机能挖出洞穴，但你没法说「这里必须是一条能通马的走廊」。

WFC 补的正是这一环：它天生工作在「预制零件 + 局部咬合关系」这一层。美术做什么样的模块，它就拼什么样的结果，而且拼出来处处咬得上。

图 0-2 · WFC 站在工具链的最后一环，负责把抽象布局落成具体零件

记住这个定位：WFC 不是万能生成器，它是「给定一块地方，选出合法零件把它填满」的那一环。后面所有工程取舍——为什么地牢要先画骨架、为什么城市要先分地块——都源于这一点。

先泼一盆冷水

WFC 不保证产物好玩，只保证产物合法。它能让每个房间的门都通向走廊，但不会关心这扇门通向的是不是死路。「看着合理」和「玩得起来」是两件事——第五部分会专门讲怎么把第二件事补上。

01把名字扔掉：它就是一个数独求解器

「波函数坍缩」这五个字，拦住了至少一半想学它的人。把量子隐喻全部删掉，剩下的东西你初三就会：数独。

先看我们面对的问题长什么样。

变量
地图上每一个格子（2D / 3D 都行）
值域
每种格子能填的取值（tile 类型 / 图案）
约束
相邻两格必须满足的二进制关系
图 1-1 · 一个约束满足问题（CSP）的三件套

这就是教科书里的 CSP（Constraint Satisfaction Problem，约束满足问题）。数独是：变量是 81 个格子，值域是 1 到 9，约束是「同行同列同宫不能重复」。WFC 是：变量是地图上的每个 cell，值域是 tile 集合，约束是「邻接合法表」。

数独里每一格开局也是「什么数字都有可能」，填下一个数就会挤掉同行同列若干格的可能性——这个挤掉别人可能性的动作，在 WFC 里叫传播；把某一格最终定成唯一一个数，在 WFC 里叫坍缩。

唯一的区别是「约束覆盖的方向数量」：数独的约束是行列宫这种跨越全图的长程约束，WFC 只用最近邻居（2D 是 4 个方向，3D 是 6 个）。约束越短程，传播越容易做增量更新，这也是它能做到实时的原因。

三个量子名词，对应三件很土的事

叠加态
Superposition
一个格子还没定，它可能是 7 种 tile 里的任意一种。就把它记作一个集合 {A,C,D,F,G,H,K}。这跟「薛定谔的猫既死又活」没有任何关系，就是一个待定集合。
波函数
Wave
整张地图上「每格当前还剩哪些可能」的总账。一个三维布尔数组 wave[x,y,t] 就够了。名字里的「波」字是说这组可能性会像水波一样在地上传开。
坍缩
Collapse
从集合里挑一个，把它变成唯一确定的值，其余全部划掉。这一步不可逆，且会立刻影响邻居。
熵
Entropy
一个格子「还剩多少不确定性」。可能性越少，熵越低。算法每次都要挑熵最低的格子下手，理由第 3 节讲。
图 1-2 · 四个术语到四件实事

把这张表对着看，你会发现所谓 WFC 的「算法核心」，其实就是一句话：维护一本总账，每次挑账上最紧张的那一格定死它，再把后果推给邻居，重复到全图定完。

为什么这个视角很重要

一旦把它认成 CSP，你立刻就知道去哪找武器了：最少剩余值启发式（MRV）、弧一致性（AC-3）、回溯搜索（DFS + backtracking） 全都是现成的成熟技术。人们口中的 WFC 各种「进阶技巧」，几乎都能在这些老概念里找到对应。算法不是魔法，只是取了个好名字。

02四步循环：初始化 → 观测 → 坍缩 → 传播

整个算法就是一个两句话的 while 循环。难的部分全在每一步的细节里。

初始化 Initialize() // 铺满：每格的可能性集合 = 全部 tile while 还有格子没坍缩: 观测 Observe() // 挑一个熵最低的格子 坍缩 Collapse() // 从它的可能性里按权重抽一个定死 传播 Propagate() // 把这个决定的后果推给邻居，反复推到不再变化

四步各管一件事，我们逐个拆。

第一步 · 初始化：把总账铺满

输出网格多大，就建多大的 possibilities 数组。开局时每个格子的可能性集合都是全集，也就是「什么都可能是」。

图 2-1 · 初始化后的总账：16 个格子，每格的可能性都是全集

这时候每格的熵都是最大值。第一轮的「观测」会发现所有格子打平，于是随便挑一个（用一点随机打破平局）。

第二步 · 观测：挑一个格子出来

观测这个名字容易误导，它其实什么都没做，只是选出一个待坍缩的目标。选择标准是「剩余可能性最少的那一格」，也就是熵最低的格子。这就是 CSP 里的 MRV（Minimum Remaining Values）启发式。

术语对照

很多中文资料把这一步叫「观察到 > 选择的最多容量的格子 > 坍缩」。记住英文 Observe = 挑格子，Collapse = 定死格子，两步是分开的，读原始实现时不会晕。

第三步 · 坍缩：抽一个确定值

从被选中格子当前的可能性集合里，按权重随机抽一个 tile，把它定为这格的最终值，把集合里其余全部剔除。这格的熵归零，并且被标记「已坍缩」，不再参与后续的观测。

权重从哪来？两种模型的答案不同（第 8、9 节讲），但用法一样：出现次数越多的 pattern，被抽中的概率越高。

第四步 · 传播：把后果扩散出去

这是全算法唯一有技术含量的部分。坍缩了一格之后，它的四（或六）个邻居就不可能维持原来的可能性集合了——那些「和被选中 tile 无法相邻」的选项必须被剔除。

剔除之后，邻居的可能性变少，邻居的邻居又要受影响……一直到没有格子再发生变化为止。整个过程用一个栈或队列维护「刚刚发生变化、需要重新检查邻居」的格子。

它的可能性从 4 降到 1
↓
② 入栈
把它的 4 个邻居压进传播栈
↓

↓
④ 若有变化
把邻居的邻居继续压栈

回到观测，挑选下一个格子
图 2-2 · 传播是坍缩之后的一轮涟漪

传播有一个非常值得注意的性质：如果一个格子的可能性被削到只剩 1 个，它就自动坍缩了，不需要你显式去抽一次，也不消耗一次随机数。这就是为什么 WFC 生成出来的地图往往有大片区域带着统一的风格——它们是被一次坍缩连锁推导出来的。

一次坍缩能走多远

在约束比较紧的 tile 集里，一次坍缩往往连带导致几十上百格被动定死。这不是 bug，这正是 WFC 生成结果「有整体感」的根本原因：一整片屋顶之所以朝向一致，是因为它们是被同一次选择连锁推出来的，不是各自独立随机的。

03熵：为什么每次挑「最没得选」的格子

如果这一步换成从上到下扫描，WFC 会退化成一个又慢又容易失败的生成器。挑格子的策略，是它能实用的关键。

朴素的想法是按顺序扫描：第一行第一列、第一行第二列……一个一个填。这在数独里叫「无启发式穷举」，代价是要试巨多次。WFC 反过来：永远优先处理最容易爆掉的格子。

从上往下扫
先处理约束松的区域，等回到紧的地方时，往往已经产生矛盾，只能推翻重来
从最紧的下手
先把「只剩两条路」的格子钉死，它的邻居随之收紧，矛盾在最早被发现，代价最小
图 3-1 · 同一个问题，两种扫描顺序的命运完全不同

熵怎么算

Gumin 的原始实现用的是香农熵，并且把权重算进去：

H(cell) = - Σ p(t) · log₂ p(t) 其中 p(t) = weight(t) / Σ weight(t') t 遍历这一格当前仍可能的所有 tile

三个性质值得留意：

  • 所有格子只剩一种可能时，H = 0。
  • 权重全部相等时，H = log₂(可能性个数)，退化成「数个数」。
  • 权重差异越大，熵越低——因为实际上你「几乎确定」会是那个大权重的 tile。

所以熵不是单纯的数量，「还剩 3 种可能但其中一种占 99%」比「还剩 3 种且均匀」不确定度更低。这个细节让 WFC 在高密度 tile 上表现更稳。

别忘了一撮噪声

Gumin 的实现里，每个格子的 entropy 都会预先加上一个极小的随机噪声（典型值 1e-6 量级）。原因是：开局时所有格子熵完全相等，如果严格取最小值，第一格永远落在同一个位置，随机种子就只能影响后续几步，生成结果的多样性会明显下降。

加噪声之后，「同等紧张」的格子随机胜出，同一套规则也能长出千变万化的结果。这是最容易被忽略、但对产出丰富度影响最大的一行代码。

挑最熵低的另一层理由：它决定了算法要不要回溯

矛盾（某一格可能性被削到 0）不是随机发生的，它几乎总是先在「快要没得选」的格子上发生。你先把这些格子处理掉，矛盾就会在它代价最小的时刻暴露——正好这块区域刚起步，改动波及面小。

如果你一直拖着它，直到周围几十格都定死了才来处理，一旦爆掉，回滚成本就是几十格。这就是为什么实践里的性能差异往往不是常数级的。

04坍缩：按权重摇号，而不是均匀掷骰子

很多人第一次实现 WFC 会得到一张「到处都有一点点」的花脸地图。病根就在这一步用了均匀随机。

假设你在做地牢，tile 集里有「墙」「走廊」「房间地板」三种，数量比例是 6 : 3 : 1。如果坍缩时均匀抽样，那么实际生成的地图里，走廊和房间会多到荒谬——因为墙本来应该是背景 filler，结果占地面积被严重高估。

均匀抽样
每种 tile 命中率相同→ 结果与示例统计无关→ 罕见 tile 被过度使用
按权重抽样
出现频率高的 tile 更容易被选中→ 输出与示例统计一致→ 罕见 tile 成为真正的点睛
权重求和 p(t)
p(t) = w(t) / Σw轮盘赌选择同时也用于算熵
图 4-1 · 权重的两个作用：决定抽谁，参与熵的计算

权重的来源自然是从示例里数出来的。一张输入图里 pattern A 出现了 50 次、B 出现 2 次，那么 A 的权重就设成 50 附近的值。这保证了「输出在统计上和输入像」——正是这一点让结果带上那种「像手盘出来的」味道。

// 权重轮盘赌 total = Σ weight[t] // 只累计仍然可能的 t r = rng.NextDouble() * total acc = 0 for t in possible do acc += weight[t] if acc >= r then return t
权重是设计者有话说的地方

你完全不必照抄示例的统计。手动改权重是最直接的一种「艺术指导」：把城墙权重调高让地牢更压抑、把水景权重调低让城镇更宜居、把某个装饰模块的权重设为 0 就是「不许出现」。比起改 tile 几何，改权重的成本近乎为零。

一个容易忽略的细节：动态权重

权重不必是常量。把权重写成位置的函数，你就得到一片低成本的「引导手艺」：

  • 距离场：离入口越远，「陷阱房」「精英怪」的权重越高。
  • 噪声图：用 Perlin 噪声给「森林」乘一个系数，森林就自然长成一簇一簇，而不是被均匀撒开。这一招几乎是所有好看的 WFC 地图的共同底子。
  • 深度/层数：地牢第 5 层的「隐藏水道」模块比第 1 层权重高。
  • 已有内容的排斥：这附近已经放了 3 座塔了，本次把塔的权重压低。

把「位置相关的权重」和「专属 tileset」配合起来，你几乎能做出任何分区效果 —— 这在第 30 节做无限城市时会是主力手法。

朴素做法：逐条比对

最直白的写法是：格子 C 刚坍缩成 tile t，就去查它的每一个邻居 N（方向 d），把 N 的可能性集合里「在方向 −d 上无法与 t 相邻」的 tile 全部划掉。

这个写法完全正确，而且对几十种 tile 的小工程来说性能已经够了。但它有个「 inefficient」的地方：每次都要把邻接表整个遍历一遍，哪怕只划掉了一个 tile。

优化做法：兼容计数（AC-4 风格）

维护一个三维计数数组 compat[x][y][t][d]，含义是：在 (x,y) 这一格、针对 tile t、在方向 d 上，还有多少个邻居 tile 是支持它的。

删掉某个 tile 时，只需要把它支持者的计数减 1；计数减到 0 时，说明这种 tile 在这个格子上也待不住了，一并删掉，并且连锁。整个过程不需要重扫邻接表。

① 删除 tile X
格子 C 的可能性少了 X
↓
② 找受益者
哪些 tile 在方向 −d 上支持 X
↓
③ 计数减一
compat[邻居][受益者][−d] --
↓
④ 计数归零
该受益者在邻居格也不可行了
↓
⑤ 继续传播
把邻居压栈，重复
图 5-2 · 兼容计数让「谁受影响」变成 O(1) 查表
什么时候才需要这个优化

tile 数量 × 地图面积 才是决定因素。一个 40 种 tile、64×64 的小地图，朴素写法毫秒级就跑完了，别过早优化。
真正需要它的是这两种场景：Overlapping 模型（pattern 轻松上千），以及实时交互（Townscaper 那种每次点击都要重算一片）。判断标准很简单：生成一次超过 100ms 才值得上。

传播的另外一个作用：它帮你免费完成了很多坍缩

再强调一次第 2 节末尾那个点。父格子坍缩 → 传播 → 某个邻居只剩 1 种可能 → 它自动坍缩 → 继续传播。你的 while 循环体实际执行的次数，通常远小于地图格子总数。

这也解释了一个反直觉的观象：规则越紧，生成往往越快。因为一次坍缩能连锁推倒一大片，观测步数变少。反过来，一个几乎「什么都能接什么」的 tile 集，反而要一格一格慢慢挑，而且结果大概率很平庸 —— 什么都能填的地方，等于什么也没设计。

06矛盾：一定会碰到，三种处理姿势

不是所有的可能性最终都有解。某一格的可能性被削到 0，就是矛盾（contradiction）。这一天一定会来，问题只在于你打算怎么收场。

为什么会矛盾？因为局部合法推不出全局有解。每一条邻接规则只管两个格子，但它叠加起来可能逼出一个无解的格局 —— 就像数独某一行被你填成无济于事的样子，后面怎么填都矛盾。

来源一
规则过紧
某个 tile 只允许一种邻居、而这种邻居又要求第三种条件……约束链越长，越容易卡死。典型症状是频繁且稳定的高失败率。
来源二
示例没覆盖过渡
输入图里从没有出现过「草 → 水」的过渡方式，输出却需要它。这在 Overlapping 模型里尤其常见，因为它只能复现已见过的 pattern。
来源三
边界与外部约束
你强制指定的那些格子（第 13 节的锚点）本身就可能互相冲突，或者和示例的统计不相容。
图 6-1 · 矛盾的三个主要来源

姿势一：整个重来（Restart）

Gumin 原始实现的做法，也是最简单最省事的做法。检测到矛盾就清空整张图，换一个随机种子从头来过。

优点
实现 10 行；结果无偏，statistically 干净；不占用内存
缺点
失败率一旦超过 20%，期望重跑次数暴涨；大图上不可接受
适用
离线预生成；小地图；调试期
图 6-2 · 最简单的方案：推倒重来

《绝境北方》用的就是这套。作者的说法很直白：「如果算法失败了，我就整个重来一次。」 因为它是在玩家登场之前离线生成小岛，几十毫秒的重试成本完全付得起。

姿势二：回溯（Backtracking）

每次坍缩前把当前总账快照压栈，遇到矛盾就弹栈回到上一个决策点，换下一个候选 tile 重试。

关键点是别全量快照。一张 128×128 地图 × 500 种 pattern 的总账，完整拷贝一次就是 8MB 级别的开销，几十次回溯下来比重启还慢。

正确做法是记「变了多少」：

// 只记录被删除的选项 struct Undo { int cellIndex; int tile; } List<Undo> changes; // 本次坍缩+传播一共删掉了哪些 (格子,tile) 对 // 回溯时按记录反向加回来，O(变化的规模) 而不是 O(总账大小)
实践建议

回溯要给深度设限。无限制的回溯在病态输入上会退化成穷举搜索，一次生成卡死几十秒。常见做法：给同一个决策点重试次数设上限（比如 3 次），超过就放弃这一支退到更上一层，或者直接降级到重启。这本质上是「有限回溯 + 重启」的混合策略，也是工程上最稳的折中。

姿势三：假装没看见（Fail Silently）

这是 Townscaper 的选择，也是最反直觉、但游戏里最有用的一种。

思路是：不是所有矛盾都值得推倒重来。如果这个格子实在找不到能完美咬合的模块，就放一个「不那么完美」的兜底模块，让画面继续下去。

代价很直观 —— Townscaper 里那些著名的悬空钢架，就是这么来的：算法发现这两块之间的支撑结构没法完美拼拢，于是选了「差一点钱」的那版，看上去就是一根没接上的钢梁。

为什么要容忍
实时交互里，重启等于画面闪烁；回溯等于卡帧
代价
偶尔出现悬空 / 穿插 /看着别扭的细节
关键前提
要有会退让的兜底模块，且产品形态容忍视觉瑕疵
图 6-3 · 假装没看见：把「正确性」换成「不中断」
怎么选

离线生成、小地图、要求严格合法 → 重启。
离线生成、大地图、规则复杂 → 有限深度回溯。
实时交互、人在旁边看着 → 兜底降级 / 静默失败。
这三种可以同时存在于一个项目里：上层分区层用重启，填充层用回溯，装饰层直接静默失败。分层的意义正在于此。

07一份能直接照着写的 C# 骨架

下面这份代码刻意写得很朴素（不用兼容计数优化），目的是让你一眼看懂结构，然后自己去优化。它能在 Unity 里直接跑。

数据定义

// Tile 定义：四条边的 socket + 权重。Unity 里建议做成 ScriptableObject
[System.Serializable]
public class WfcTile {
    public string id;
    public int[] sockets = new int[4];   // 顺序：上 右 下 左
    public float weight = 1f;
    public GameObject prefab;
}

// 方向表：上右下左，与 sockets 索引一致
static readonly int[,] DIRS = { {0,-1}, {1,0}, {0,1}, {-1,0} };
// 对面的方向：(d + 2) % 4

核心求解器

public class WfcSolver {
    readonly int W, H, T;
    readonly WfcTile[] tiles;
    readonly bool[,,] wave;          // [x, y, tileIndex]
    readonly int[,] remaining;        // 每格还剩几种可能，省得每次重数
    readonly bool[,] collapsed;
    readonly System.Random rng;

    // 邻接表：allowed[t][d] = 方向 d 上，允许与 t 相邻的 tile 索引集合
    readonly HashSet<int>[][] allowed;

    public bool Run() {
        while (true) {
            int cell = Observe();            // 挑熵最低的格子
            if (cell < 0) return true;        // 全部坍缩完毕，成功
            if (!Collapse(cell)) return false;  // 抽不出任何 tile = 矛盾
            if (!Propagate())    return false;  // 传播中出现 0 可能 = 矛盾
        }
    }

    int Observe() {
        double best = double.MaxValue;
        int bestCell = -1;
        for (int y=0; y<H; y++) for (int x=0; x<W; x++) {
            if (collapsed[x,y]) continue;
            double h = Entropy(x, y) + rng.NextDouble() * 1e-6;  // 那撮关键的小噪声
            if (h < best) { best = h; bestCell = y * W + x; }
        }
        return bestCell;
    }

    double Entropy(int x, int y) {
        double sum = 0, total = 0;
        for (int t=0; t<T; t++) {
            if (!wave[x,y,t]) continue;
            double w = tiles[t].weight;
            sum += w; total += w * Math.Log(w);
        }
        // H = log(sum) - total/sum   （等价于 -Σ p log p，少一次除法）
        return Math.Log(sum) - total / sum;
    }

    bool Collapse(int cell) {
        int x = cell % W, y = cell / W;
        double total = 0;
        for (int t=0; t<T; t++) if (wave[x,y,t]) total += tiles[t].weight;
        if (total <= 0) return false;

        double r = rng.NextDouble() * total;
        int pick = -1;
        for (int t=0; t<T; t++) {
            if (!wave[x,y,t]) continue;
            r -= tiles[t].weight;
            if (r <= 0) { pick = t; break; }
        }
        // 把这格锁死为 pick，其余全部剔除
        for (int t=0; t<T; t++) if (t != pick && wave[x,y,t]) Ban(x, y, t);
        collapsed[x,y] = true;
        return true;
    }

    bool Propagate() {
        var stack = new Stack<(int,int)>();
        // 所有刚坍缩/刚变化的格子入栈（这里简化：全部未坍缩格入栈一次）
        for (int y=0; y<H; y++) for (int x=0; x<W; x++) {
            if (remaining[x,y] == 1 && !collapsed[x,y]) { CollapseSilent(x, y); stack.Push((x,y)); }
        }
        while (stack.Count > 0) {
            var (cx, cy) = stack.Pop();
            for (int d=0; d<4; d++) {
                int nx = cx + DIRS[d,0], ny = cy + DIRS[d,1];
                if (nx<0 || ny<0 || nx>=W || ny>=H) continue;

                // (cx,cy) 在方向 d 上允许的全部 tile 的并集
                bool none = true;
                for (int t=0; t<T; t++) {
                    if (!wave[cx,cy,t]) continue;
                    if (allowed[t][d].Count > 0) { none = false; break; }
                }
                if (none) return false;   // 矛盾

                // 剔除邻居格上那些「在这个方向上没有任何支持者」的 tile
                for (int t2=0; t2<T; t2++) {
                    if (!wave[nx,ny,t2]) continue;
                    bool supported = false;
                    for (int t=0; t<T; t++)
                        if (wave[cx,cy,t] && allowed[t][d].Contains(t2)) { supported = true; break; }
                    if (!supported) {
                        wave[nx,ny,t2] = false;
                        if (--remaining[nx,ny] == 0) return false;
                        if (remaining[nx,ny] == 1) CollapseSilent(nx, ny);
                        stack.Push((nx, ny));
                    }
                }
            }
        }
        return true;
    }
}
这份骨架缺什么

为了可读性，上面省略了三样东西：① 邻接表的自动构建（第 11 节的 socket 法会自动生成 allowed）；② 回溯（第 6 节的 Undo 记录）；③ 兼容计数优化（第 5 节）。
跑通之后再一项项加，不要一上来就写最复杂的版本。

邻接表怎么自动生成

一句话：两个 tile 在方向 d 上相邻合法 ⟺ 相接的两条边 socket 相同。

void BuildAdjacency() {
    allowed = new HashSet<int>[T][];
    for (int t=0; t<T; t++) {
        allowed[t] = new HashSet<int>[4];
        for (int d=0; d<4; d++) allowed[t][d] = new HashSet<int>();

        for (int other=0; other<T; other++) {
            int od = (d + 2) % 4;   // other 面对 t 的那条边
            if (tiles[t].sockets[d] == tiles[other].sockets[od])
                allowed[t][d].Add(other);
        }
    }
}

这段 12 行代码是整个 Simple Tiled 模型的心脏。所有复杂的美术规则，最终都被压缩成了「两条边的编号是否相等」这么一个整数比较。

08Simple Tiled Model：规则自己写

第一种模型：你手里已经有一套现成的砖块，规则由你（或一个小工具）来写。游戏关卡生成几乎都用这种。

它的输入是两张清单：

tile 清单
每种零件的几何 + 四条边（或六条）的 socket 编号 + 一个权重
邻接清单
「tile A 的方向 d 上允许出现哪些 tile」——可以手写，也可以由 socket 自动生成
图 8-1 · Simple Tiled Model 的两种输入

它的三个杀手锏

一
每个 cell 就是一个模块
美术做一个「三段式房屋模块」，它在地图上就占一格。所见即所得，模块什么样，出来就是什么样，不会被算法切碎重组。
二
对称性可以自动派生
做一块「L 型转角走廊」就够了，另外三个朝向让它自己生成：复制一块 → 几何旋转 90° → socket 按方向轮回去另一侧。这一个开口就省下四倍工作量。
三
速度快、可预测
tile 数量通常在几十到几百，pattern 不需要滑动窗口提取，跑起来很轻。实时交互唯一现实的选择。
图 8-2 · Simple Tiled Model 的三大优势

代价：规矩要你自己管

所有 tile 之间的兼容关系都要声明完整。漏一条规则不会让算法报错，它会安静地少给你一些结果——直到某天你发现某个转角从来没出现过。

漏规则的典型症状

地图上某个模块永远不出现，或者出现了但很快导致矛盾。
排查方法：写个开工前的自检，枚举每种 tile 的每个方向，如果它的允许集合为空就直接报错。这一行断言能替你省掉几小时的肉眼比对。

三条立即可用的经验

  • 先从 8 ~ 15 块开始。不要一上来就做四十块的豪华套装。小 tile 集更容易看清规则有没有写错，也更容易发现「这块其实用不上」。
  • 给每块起人类可读的名字。room_corner_NE_wall 比 tile_07 好排查一百倍。
  • 留出「万能替补」。至少放一块四边都能接的 filler（实心岩 / 纯草地 / 空房间），它会在算法快撑不住的时候救场。这条到第 27 节讲地牢时会发现几乎是必需品。

Unity 里怎么落地

用 ScriptableObject 表达 tile 是最顺手的做法，配合一个编辑器脚本批量从 prefab 读 socket：

[CreateAssetMenu(menuName = "WFC/Tile")]

09Overlapping Model：让算法去偷规则

第二种模型：你给它一张示例图，它自己把规则扒下来。零规则编写，代价是慢和不可控。

做法是一个滑动窗口：

① 输入一张示例图
比如 64×64 的砖墙纹理
↓
② N×N 滑窗扫描
每个位置取一个 N×N 小图当作一个 pattern
↓
③ 去重 + 计数
得到 pattern 集合与各自出现次数（作为权重）
↓
④ 生成邻接
两个 pattern 错位一格后重叠区完全一致 → 可相邻
↓
⑤ 照常跑 WFC
只是「tile」换成了 N×N 的 pattern
图 9-1 · Overlapping Model 的五步

第 ④ 步值得停下来看一眼，它是整个模型最漂亮的地方：

图 9-2 · 邻接判定：错位一格后的重叠区域必须完全相同
这个模型真正厉害的地方

它能捕捉到「用砖块 adjacency 讲不清楚」的长程关系。比如一段螺旋楼梯、一面墙上的裂纹走向、某种特定的配色渐变——这些关系跨越多个格子，硬拆成两两邻接会丢信息，而 N×N 窗口天然把它整个打包进了一个 pattern。

N 越大，能捕捉的结构越长；但 pattern 数量也会随之爆炸。

N 选多大

Npattern 规模（典型）能捕捉的结构适用
2几十到几百最基本的两格过渡几乎没有实用价值
3几百到小几千拐角、T 型接头、小拐弯最常用的默认值
4数千更大尺度的房间布局、较大的装饰纹样需要更大尺度结构时
5+指数爆炸整块建筑立面只在离线、小地图、充足内存时用
Overlapping 的三个软肋

① 慢。pattern 数量动辄上千，wave 是「格子数 × pattern 数」的布尔数组，一张 128×128 地图配 1000 个 pattern 就是 1600 万个 bool。
② 不可控。没法说「这里必须是门」，只能靠后面第 13 节的预置格子间接引导。
③ 只能复现见过的。示例里没有的过渡形态，它永远造不出来 —— 这是50 定理，不是 bug。

混用：把它们摞起来

一个很实用并且 Townscaper 精神相通的做法是分层混用：

上层
Simple Tiled 定骨架
用几十块大模块（街区、广场、道路段）决定宏观结构。这一层块数少、快、可控。
中层
Simple Tiled 填内容
每个地块内部用专属 tileset 再跑一次，住宅区用住宅 모듈，码头区用码头模块。
下层
Overlapping 做表面
墙面罅隙、地面的磨损與污渍、草丛分布这种「没有严格功能、只求自然」的东西，丢给 Overlapping 去从样图里学。

朴素地维护一张「谁和谁能挨」的表是可怕的：10 种 tile 就是 100 个条目，100 种 tile 就是 10000 个，而且你改一个 tile 就得重查一整行。

socket 法把它彻底降维：给每条边标一个「颜色」编号，两条边能否相接，只取决于颜色是否相同。

颜色相同 ⟺ 允许相邻，一条规则覆盖全部组合。
图 11-1 · socket 配色法：把 O(T²) 的手工表压缩成一次整数比较

这套手法真正省力的地方

  • 新增一块砖不需要改任何规则。只要它的四条边涂了正确的颜色，它就自动融入了整个系统。
  • 规则成了可视化资产。你可以在 Unity 场景里把 socket 颜色画成小色块，一眼看出这块砖为什么接不上。
  • 天然支持多种互不干扰的语义。「草」和「草」是一种 socket，「路」和「路」是另一种，两者互不相干，不需要交叉判断。
进阶：双向 socket 与「匹配表」

有时候严格的「必须相同」不够用。比如你需要「任意一种水都可以接任意一种陆地边缘」。
这时把颜色相等升级成一张兼容表：CanConnect(socketA, socketB) 返回一个布尔。这是它的自然推广，简单情況下用颜色，复杂情况用表，不要一开始就上表。

给 3D 加 socket

完全同构，只是每个「面」而不是每条「边」。一个立方体模块有 6 个面，每个面一个 socket。DIRS 从 4 行扩到 6 行，(d+2)%4 换成一张方向对面表。其余算法一行都不用改。

static readonly int[][] DIRS3D = {
    {1,0,0}, {-1,0,0},   // +X, -X
    {0,1,0}, {0,-1,0},   // +Y, -Y
    {0,0,1}, {0,0,-1}    // +Z, -Z
};
static readonly int[] OPP = { 1, 0, 3, 2, 5, 4 };  // 方向 d 的对面

这也是为什么 WFC 往 Minecraft 式 voxel 世界扩展时显得格外自然——约束结构本来就没有二维假设。

12权重：唯一能调节密度的旋钮

tile 的形状说了「能拼出什么」，权重说了「多常拼出它」。WFC 里绝大部分调参，最后都落在权重上。

同一套 tile，仅仅改权重，就能得到完全不同的作品：

城墙权重高
结果压抑、狭窄、像一座要塞监狱
走廊权重高
结果像迷宫，绕且容易迷路
房间权重高
结果开阔、视野好，适合快节奏战斗
图 12-1 · 同一套 tile，不同权重 = 不同体验

这意味着一件很实用的事：你可以在运行时动态改权重来回应玩法状态，完全不用碰 tile。

调权重的三条经验

① 数量级比数值重要。把「房间」权重从 1 调到 2 变化不大，调到 10 才是质变。调权重请按倍数调，不要按步长调。
② 权重为 0 要慎用。直接归零等于删掉这块砖，可能连带把依赖它的结构也删没。想压制就用 0.01，不要给 0。
③ 罕见的东西才需要手动设高。「宝箱房」这种你想让玩家遇到的，反而应该提高权重让它多出现一些——示例里的稀有度不等于你想要的稀有度。

把权重做成一张「场」

一个非常好用又几乎零成本的做法：把权重乘以一张 float 场（noise、distance field、玩家热力图都行）。

float EffectiveWeight(WfcTile tile, int x, int y) {
    float w = tile.weight;
    // 例一：用噪声让森林成片而不是散点
    if (tile.tag == "forest") w *= forestNoise[x, y];   // 0.2 ~ 2.5
    // 例二：离入口越远，精英房越多
    if (tile.tag == "elite_room") w *= Mathf.Clamp01(distToEntrance[x,y] / 40f) * 3f;
    // 例三：靠近预先烘焙好的河流遮罩时，水体权重上升
    if (tile.tag == "water") w *= riverMask[x, y];
    return w;
}

注意这个函数同时参与熵的计算。它改变了权重的相对比例，也就改变了哪些格子会被优先坍缩。副作用是同一套种子在不同场上会产出不同布局，正合你意。

这是 WFC 里性价比最高的一招

如果你只有时间学一个调优手段，就是这个。它不需要任何新 tile、不需要改算法，五分钟就能接上，却能让「随机糊出来」变成「有意图地布局」。
第 30 节做无限城市时，我们几乎全靠它来区分住宅区、码头区、公园区。

14分层 WFC：先分地块，再填房子

单层 WFC 有个天然尺度上限：它擅长几百格，不擅长几万格。解法不是换算法，而是把它跑两遍。

单层跑大地图会遇到三个问题：

  • 失败率随面积上升。地图越大，中途踩雷的概率越高，一次重来的成本也越高。
  • 没有真正的宏观意图。即使成功，出来的也是「处处合法」而不是「有中心有郊区」。
  • 不可重启局部。改一小块就要整体重算。

分层把这些一次性解决：

第一层
宏观分区（10× 或 20× 降采样）
先用一套「用途」tile——住宅区 / 商业区 / 码头区 / 公园 / 城墙——在低分辨率网格上跑一次 WFC。这一层只决定「哪里是什么」，不管具体内容。
第二层
地块内填充
每个宏观格子对应一小片真实地图，用它自己那份 tileset 独立跑一次 WFC。住宅区的 tile 不会出现在码头区。
第三层
装饰与细节
在已成型的结构上撒门垫、窗台花盆、路灯这类不影响结构的物件。这一层允许失败、允许偷懒。
图 14-1 · 三层结构：分辨率逐级提高，约束逐级放松
分层带来的四个额外好处

① 失败可以局部化。某个地块填失败了，只重填它，不影响其他 99 个。
② 天然支持流式加载。每一个地块都是一个独立的生成单元。
③ 可以用不同的 seed。宏观层用世界种子保证世界的一致性，微观层用地块坐标派生。
④ 美术工作量可控。给每个分区做一套专属 tile，比做一套「要适配所有场景」的通吃 tile 容易得多。

分层的层数

两层通常够，三层是上限。再多就很难维护了，而且层与层之间的遗漏会被放大——上一层漏了一个可能性，下面所有层就都见不到它。

两层
分区 → 内容最常见，推荐起步
三层
分区 → 结构 → 装饰大型项目值得
四层以上
几乎总是过度设计实际效果提升不明显
图 14-2 · 层数怎么定

Townscaper 虽然不严格叫「分层」，但它的生成与装饰分离（第 19 节）本质上是分层思想的一个变体：先决定这块用哪个 건축模块，再决定怎么给它加装饰。

15六个让结果「像人做的」的经验值

算法对了不等于作品好看。下面六条是反复试出来、几乎总能见效的经验。

经验一
保证每个 socket 至少有两种 tile 可选
如果某条边只有一种东西能接，那一整条边线会变成一条死板的复制带。每种 socket 至少配 2~3 个不同的 tile，接缝处才会出现自然的交替。
经验二
给重复设上限，而不是禁止重复
「两个相同的 tile 不许相邻」太严了，会让失败率飙升。改成「相同 tile 在 3 格半径内出现次数 ≤ 2」这种软约束，或者干脆用事后检测 + 局部替换。
经验三
留一块能接任何东西的 filler
实心岩石、纯草地、空房间——它的四条边都是通配 socket。它是整个系统的安全阀，兜住了绝大多数边缘情况。
经验四
装饰层永远单独做
不要把窗户、苔藓、路牌编进结构 tile 里。它们会让 socket 数量爆炸，而且一旦结构变动就得全部重来。结构层定完之后，用一次独立的 pass 撒上去。
经验五
先看失败率，再看画面
失败率超过 20% 的 tile 集，说明规则本身有问题，这时候调权重只是在掩盖。让失败率回到 5% 以内，画面自然会变好。
经验六
把 10% 的倾斜留给「异常者」
做一两块出格的 tile——歪的塔、破的墙、长得奇怪的树——给它们很小的权重。完美的均匀会让整个作品显得假。少数异常带来的说服力，远超它们占的面积。
图 15-1 · 六条让结果脱离「程序感」的经验
一句话总结这六条

它们合起来在做同一件事：在「完全随机」和「完全确定」之间找到那个让人觉得有手的区间。纯随机看着像噪声，纯确定看着像贴纸，好看的东西永远在这两者中间。

起点：一个叫 Brick Block 的小原型

Brick Block 允许玩家在一个固定的 5×5×7 网格里堆方块，堆出来的东西会自动长成一栋栋公寓。它有两个致命问题，这两个问题直接决定了后面十年他在做什么。

问题一 · 太重复
网格一大，出来的东西就开始千篇一律。因为所有屋顶必须能互相拼接，就只能是同一种屋顶——他没有办法保证更多样的零件还能严丝合缝地咬在一起。
问题二 · 太方正

最容易被漏掉的一点

Townscaper 被讨论时，几乎所有人都在看 WFC。但没有那个不规则网格，以及没有 Marching Cubes，同样的 WFC 只能产出《绝境北方》那种方形地势。
「看起来自然有机」这件事，一半功劳不在 WFC 身上。

Townscaper 明确不是一个有目标的游戏。作者在访谈里的说法是「more of a toy than a game」。

同一个算法，用在「玩具」和用在「策略游戏」上，会有完全不同的正确解法。这一点在你自己的项目里同样成立：先想清楚失败一次会损失什么，再决定要不要做回溯。

为什么费这么大劲

作者在一次访谈里把这个取舍说得很清楚。他强调「当我给它做内容的时候，我做的是方形 tile，然后我把这些方形拼图块稍微斜一下去贴合」。

这句话是整个设计的关键

基于 tile 的流程最大的好处是：零件标准化，彼此可以互换，组合的可能性是指数级的。这是所有 tile 流方法的立身之本。

Stålberg Grid 从六边形出发，天生非周期。这是它和「扰动过的方格网」的本质区别。

18Marching Cubes 与角部片段

网格不再是方的之后，问题立刻出现：方块已经塞不进这些歪格子里了。Townscaper 的解法是换掉「tile 的最小单位」。

《Brick Block》时代，一块 tile 就是一整个完整的房间——方格里放它就是了。到了 Townscaper 的三角化网格上，这个做法不再直接可用。

问题
网格 cell 不再是立方体
它是一个被松弛过、六条边长都不相等、角度也歪斜的多面体。往里塞一个轴对齐的立方体，不是穿出去就是漏缝。
工具
Marching Cubes
原本用于把三维标量场转成多边形网格的算法。它的关键在于它关注的是「角怎么摆」——每个顶点处的标量决定这个角是实心还是空心，中间的表面由marching 插值生成。
后果
tile 从「整栋」变成「角部片段」
作者的说法是它们「不再是一整块建筑，而是一个个角部片段（corner segments）」，更容易互相拼合成贴合 cell 的形状。
图 18-1 · 从不规则网格到角部片段的三步推导

这个转变非常关键，值得单独记一笔：

改变「最小单位」往往比改算法更有效

面对「零件塞不进格子」这个问题，常见的反应是去写一个更强的贴合器。作者换了个思路：他不改怎么塞，他改什么是「零件」。
把 tile 从「一栋房子」降级成「房子的一角」，问题就消失了——因为角天然比整栋更贴合任意形状。

这条思路的通用版本是：当你的生成器反复失败时，先怀疑颗粒度，再怀疑算法。

副作用：很多东西可以从网格里「抠」出来

既然整个建筑是由 Marching Cubes 在运行时生成的网格，那么一些原本要烘焙进模型的细节就可以后置处理。最典型的是窗户。

作者的做法是把窗户用 stencil buffer 在模型生成之后「挖」出来，而不是事先做在 tile 里。理由很实在：如果窗户长在一块 tile 上，就会有无数种边缘情况——被切一半、被顶到角上、两块 tile 接缝处拼出一扇奇怪的双倍宽窗。

窗户做进 tile

19生成与装饰分离：为什么细节总是迟到

玩过 Townscaper 的人一定见过：先有一个方块冒出来，过一小会儿才会有屋顶、窗台、晾衣绳。这个「迟到」不是偷懒，是让实时成为可能的关键设计。

《绝境北方》里，WFC 是在玩家接触岛屿之前离线跑完的，慢一点没关系。Townscaper 必须在点击的瞬间响应，这就要重新组织整条流水线。

先做
识别这格能用哪些模块
玩家点下一块的瞬间，WFC 立刻把「硬的部分」做掉：根据四周约束，算出这个 cell 有哪些模块是合法的，选一个放上去。这一步必须当场给出反馈。
后做
再来装饰
屋顶样式、护栏、窗户的疏密、攀藤这些，放在下一帧乃至之后数帧慢慢填。玩家几乎注意不到它们晚了几十毫秒。
图 19-1 · 难的放前面，慢的放后面
这个模式可以照抄

凡是要实时响应式生成的地方，都值得问一句：「哪些决定必须在这一帧给出，哪些可以晚？」
一般规律是：结构必须即时，装饰可以延迟。前者影响手感和操作反馈，后者只影响观感，而人对观感的迟到容忍度远高于对操作的。

为什么城镇越大越卡

这个设计也解释了 Townscaper 里那个明显现象：建筑越复杂，从放下方块到长出细节的间隔越长。

原因是每次改动都会激起涟漪：一处改动会沿着整个连通区域扩散，因为 WFC 必须重新断言这一整片区域的所有约束仍然被满足，并为受影响的格子重新挑选合适的 tile。

图 19-2 · ripple 的范围 = 整个连通区域
工程上的应对

常见手段：① 把重算放进后台队列分帧做，前台只给即时反馈；② 限制单次传播的最大深度；③ 对「孤立的小簇」跳过全量重算，因为它们和主体不连通。
第三条尤其有效——只有连通区域内的改动才需要传播，孤立的阁楼塔怎么写都不会影响主城。

20允许悄悄失败：悬空的钢架是怎么来的

这是 Townscaper 最反直觉、也最值得学的一个决定。算法失败的时候，它选择就地认输，而不是推倒重来。

《绝境北方》里失败就整个重启；Townscaper 里不是。作者的原话大致是这样的：

我意识到这两格不可能选出完美咬合的模块了，那就当没发生，继续往下走。

为什么敢这么做？因为 Townscaper 玩家要的是立刻看到反馈。重启意味着画面闪一下、刚放的方块消失；回溯意味着这一帧卡住。相比起来，一根没接上的钢梁的代价小得多。

失败的样子
悬空、没接上的钢结构
根本原因
作者的说法：WFC 不擅长又长又细的东西
为什么可以忍
这是玩具，没有「必须走得通」的要求
图 20-1 · 悬空钢架的三层解释

「WFC 不擅长长条状物体」这句很值得展开。原因是细长结构的约束是高度耦合的长链：一根横梁横跨六个格子，那么这六个格子必须同时同意它存在，任何一格不同意，整根梁就断了。格子越多，越难凑齐。

这条经验可以直接用

别让 WFC 负责长距离连续结构。管道、缆线、城墙、长桥——这些东西交给专门的路径算法去做，让 WFC 只负责它们是「从哪个格子出发、接到哪个格子」。
判断标准很简单：如果一个东西跨越超过 3~4 个 cell 还会被看成一件东西，就別让它当 tile。

兜底策略的三个层次

「假装没发生」不是一行代码，它需要一个完整的降级阶梯：

第一层
放一个「不那么完美」的合法模块
优先找评分最高的次优解。大部分情况下这一步就够了，玩家几乎看不出。
第二层
放通配 filler
完全找不到？放一块四边都通配的兜底块。视觉上是完整的一块，只是不那么有趣。
第三层
什么都不放，留空
最后手段。宁可缺一口，也不要放一个会穿插、会 z-fighting 的错误模块。
图 20-2 · 降级阶梯：宁可平庸，不可崩坏

注意最后一层的判断：宁缺毋滥。一个穿插的模型比一个洞刺眼得多，也更容易让人第一眼觉得「这程序坏了」。

21Recipes：把彩蛋写进规则里

Townscaper 最让玩家上头的地方，是那些「不知道怎么就触发了」的惊喜——围出一圈房子，中间突然出现一座花园。这不是随机礼物，是作者设计好的。

他把这些更有趣、更独特的片段叫做 recipes（配方）。它们藏在 WFC 里，但被赋了高得多的优先级。

花园的例子被他自己讲得很清楚：

我给所有模块都排了优先级，花园模块的优先级特别高。但我手上唯一一种花园模块，它的边缘是「必须挨着墙」。
所以——除非你围出一个完全封闭的空间，否则根本放不下任何一块花园。规则就是这么来的。

↓

↓

这里有一个非常精妙的设计权衡

作者原话里有一句关键：「它的高优先级保证它足够可预测，让想要复现的玩家能够复现。」

注意这是和「随机性」相反的方向。通常我们给彩蛋设低概率让它稀有，但那种稀有是不可控的稀有 —— 玩家不知道自己是运气好还是做对了。

另一类例子是那些小石墙：作者说它们只在房屋的转角处，或者你改变了房子颜色的时候才会出现。于是同一条街、换个配色，视觉细节就自动跟着变。

22混合主动权：玩家其实只做了两件事

Townscaper 的操作界面简单到几乎没有。玩家能做三件事：加一块、删一块、选颜色。所有你看到的建筑，都是程序生成的。

这种系统有个正式名字，叫 Mixed-initiative System（混合主动权系统）：人和算法轮流掌握主动权。

为什么这个设计如此有效

一
输入成本降到极低，表达力却很高
玩家不必理解几十种建材，也不需要知道屋檐怎么处理。但他表达出来的东西刻着自己强烈的个人痕迹——因为选址是他做的。
二
系统永远给出「看起来对」的结果
因为 WFC 保证了合法性。玩家不可能做出难看的东西，因为他做不出非法的东西。这是约束求解送给人机交互的一份礼物。
三
反馈即时且可撤销
删一块，整片约束立刻重算。这种「可逆」让玩家愿意乱试，而乱试正是这一类创作工具的全部乐趣来源。

可以迁移的形态

不只是城建。任何一个「玩家做少量选择，系统补完细节」的场景都能用：
· 关卡编辑器：设计师放几个房间节点，系统把走廊、掩体、灯光补出来
· 载具 / 捏脸：玩家选几处关键来定，系统生成相匹配的过渡部件
· 对话系统：作者写关键节点，系统生成符合人设的过渡台词

代价： locality 的连锁反应

不要忘了第 19 节那张图。混合主动权的代价是每次出手都要把整片连通区域重算一遍。玩家点得很随意，系统却要为每一次点击重新断言整个连通区域的约束。

这也是为什么 Townscaper 里你建得越大、details 填得越慢。这个卡的「卡」，正是这套设计内在的成本，不是优化能完全消掉的。

约束二 · 不是每个 tile 都知道自己「能不能走」

《绝境北方》是策略游戏，敌人要从海滩走到民房，玩家单位也要能过去。所以每一块 tile 都必须携带「可通行性」信息，并且在邻接约束里体现。

作者提到一个特别漂亮的解法：那些确实走不过去的区域，直接放森林。理由是它让「走不了」这件事变得在视觉上不言自明——玩家一眼就知道那里不能去，不需要额外的 UI 提示。

「让规则肉眼可见」有时比「让规则正确」更重要。
生成器产出的每一条约束，玩家最终都会在画面上读到。如果你不得不靠 UI 去解释它，先想想能不能换成视觉语言。

约束三 · 硬约束与软约束要分开，并且必须有校验

《绝境北方》在 WFC 之外还加了一层：它有硬约束、软约束，以及生成之后的校验检查（validation check），不满足就整个重来。

硬约束
不满足就是废图
例如敌军必须能从小岛某处登陆、也必须能一路走到村子里。这些必须在 WFC 内部表达，成为 tile 的邻接或全局限制。
软约束
尽量满足，不满足也行
例如岛的形状最好有一定的高低差。通常实现为权重调节，而不是硬性限制。
校验
最后一道关
WFC 跑完之后，独立跑一遍检查：所有登陆点能否到达所有目标？不行就换种子整个重来。

24WFC 天生不懂「能不能通关」

这是 WFC 用于关卡生成时的原罪：它保证每一处都合法，但不保证整张图能玩。

先看清这个错位。WFC 的约束全是局部的——「走廊的开口必须接另一个开口」。而玩法要求全是全局的——「从入口必须能走到 Boss 房」。

WFC 能回答的
这扇门对面能不能放一段走廊？
WFC 回答不了的
这扇门通向的是一个深渊还是一间厕所？这条路是不是死路？一共生成了几个房间？
图 24-1 · 局部合法 ≠ 全局可玩

典型的失败产物有四种，全都「处处合法」：

症状一
关键房间被封死
Boss 房生成出来了，但它四周全是实心岩。因为「四周是实心岩」本身完全合法。
症状二
地图被切成互不连通的几块
两块各自都很漂亮，但中间没有路。WFC 从没被告知它们需要连通。
症状三
规模和节奏完全失控
想要十来个房间，实际生成四十个；或者刚好相反只得到三个大通铺。
症状四
关键路径没有起伏
入口出来直走二十步就到宝箱，因为没有机制被告知「应该绕一点」。

认清一件事：这不是 bug，是分工

WFC 的职责边界就到这里为止。指望它同时解决「零件咬合」和「关卡节奏」，等于指望一个贴瓷砖的师傅顺手把水电也走好。
正确的做法是：让 WFC 干它擅长的（填内容），让别的东西干它不擅长的（定结构）——这就是下一节的做法。

第一步 · 用图语法决定结构

「图语法（graph grammar）」听起来学术，做法很朴素：先写一条从入口到 Boss 的链，然后反复用几条改写规则长出分支。

规则一
把一条边替换成一个菱形回路
玩家会分岔再回合，制造回路的紧凑感。
规则二
在某条边上插入一条上锁的支路
支路尽头放奖励，需要用钥匙。这一条直接编码了「探索 → 回报」的节奏。
规则三
在后期某处插入一条捷径
打通两个原本绕远的区域。这是让玩家在二周目感到「我懂这地图」的关键。

这套方法的好处是：结构性质是构造性保证的，不需要事后校验。你从一条链开始，每一步改写都保持「入口仍能到 Boss」这个不变量。

规则不要多做

经验值是 3 ~ 7 条改写规则。规则多了反而难验证，而且你会发现很多规则产生的图长得很像。
想要多样性，靠参数（重复几次、分支概率多少）而不是靠加规则。

第三步 · 把骨架摊成格子是关键设计

这一步很多人做得太粗糙。房间并不是一个矩形框就完事了，你需要给 WFC 留下足够的信息：

预置的内容作用不做的后果
房间内部区域（含外扩一圈）保证房间一定成立房间被自身周边的随机填满吞噬
门所在的那一格及其朝向决定接什么走廊 tile门可能对着墙，或者生成出双向怪门
走廊中心线限定走廊大体走向走廊乱窜，和意图不符
房间类型标签（普通 / 宝箱 / Boss）决定该区域用哪套 tile 权重Boss 房和茅房一样大
边界一圈强制为实墙避免地图边缘破口边缘出现通往虚空的切口

注意第二行「门所在的那一格」。只标记区域是不够的，门必须精确到格子和朝向，否则 WFC 会在合法但难用的位置给你开出额外的门。

预留的空隙决定了 WFC 有多少发挥空间

骨架钉得越多，结果越可控但越呆板；钉得越少，结果越自由但越容易跑偏。
一个好用的比例是：预置格子占 30% ~ 45%。低于 30% 结果开始失控，高于 50% 你会发现直接手写更快。

26地牢 tile 集的四件套

地牢是最适合练手 WFC 的场景，因为它有非常清晰的四类零件。照着这四件套做，第一版通常就能出图。

一
房间块
每个房间块带 1~4 个开口。开口的位置与朝向就是这个块的 socket。四个开口都有的那块是「交通枢纽」，给它低权重；只有一个开口的那块是「死路」，权重中等。
二
走廊块
直道、直角、T 型、十字四种基本款。只要做其中一块，另外的靠旋转自动生成（见下文）。
三
门与门槛
门必须比普通墙厚——这是它唯一的特殊之处。把「门」做成独立的 socket 类型，并且规定只有房间块和走廊块能连接它，自动杜绝「浮空的门」。
四
万能填充
实心岩体，四边全部通配。它是整个系统的保险丝。越是靠近地图边缘、越是填缝的地方，越依赖它。
图 26-1 · 地牢 tile 的四件套

旋转与镜像：一个顶四个

这是节约美术工作量最有效的一招，也是最容易做错的一招。

原始 tile: 旋转 90°: 旋转 180°: 旋转 270°: 上=甲 右=乙 上=丁 右=甲 上=丙 右=丁 上=乙 右=丙 下=丙 左=丁 下=乙 左=丙 下=甲 左=乙 下=丁 左=甲 几何旋转的同时，socket 数组必须整体轮转一位

重点在那个易错点：光把 mesh 转 90° 是不够的，sockets 数组必须跟着轮转。忘了这一步会导致某块 tile 转完之后完全接不上任何东西，然后它会静静地永远不被使用——很难查。

哪些 tile 不能旋转

楼梯、祭坛、带方向性的壁画——这些必须显式标记 allowRotation = false。
一个反面例子：如果楼梯允许旋转，「向下」的那级台阶可能在天花板上出现。

28无限的难点在缝合，不在生成

单独生成一块城市，WFC 已经能做得很好。难的是让第 1000 块和第 1001 块接得上，而且任何时候回来它还长那样。

无限世界逼出两个 WFC 本身不关心的问题：

问题一 · 边界缝合
单独生成的两块，接缝处必然不合：路断在半空、河到边界没了。
问题二 · 幂等
玩家走远再回来，卸载过的区块要重新生成，必须和上次一模一样。

缝合的核心思路：让邻居当约束

做法其实很直接，和第 13 节的预置格子是同一个东西：

① 已生成的相邻块
它的边界一圈格子是什么，已知
↓
② 当作预置
新块生成前，把这些边界状态钉死
↓
③ 传播一次
让边界约束先扩散进新块内部
↓
④ 正常求解
接缝天然对齐

配套的还有一个必做习惯：不要按最终显示范围生成，要多生成一圈 margin 然后裁掉。

图 28-3 · 生成带 margin，裁掉边缘再使用
这条经验通用

任何局部生成算法，边缘质量都差于内部。不只是 WFC，噪声、元胞自动机也一样。
「多生成一圈再裁掉」是最廉价的解，比任何针对边界的特殊处理都划算。

缝合的深度：只缝一圈够吗

取决于你的 tile 有多大。原则是 margin 至少跨越两个 tile 的尺寸，否则相邻块内部的「半个房间」会互相打架。

tile 粒度建议 margin说明
1 格（如地砖）2 ~ 4 格约束传播通常一两格就衰减完
房间级（3~5 格）6 ~ 10 格要跨过至少一个完整房间
街区级（10 格以上）20 格以上这时更该用「宏观层全图統一定下来」的做法

最后一行点出了一个重要的分界线：当 tile 大到一定程度，「缝合」就不如「宏观层一次性决定」。这正是第 30 节要讲的分层方案。

29分块、幂等与坐标哈希

第二个问题：怎么保证任何时候重新生成，出来的东西完全一样。答案是别用随机种子，用坐标。

常见的错误做法是用一个全局递增的计数器当种子，或者依赖「第一次生成时的顺序」。这两种都会在玩家来回走动时破功。

× 顺序依赖
按访问顺序发种子第二次再来顺序变了城市跟着变了
√ 坐标派生
种子的种子由坐标算出第 (12, -7) 块永远是它自己与访问顺序无关
图 29-1 · 幂等的关键：种子从坐标派生，而不是从时间派生
// 从世界种子与区块坐标派生一个稳定种子
static uint ChunkSeed(int worldSeed, int cx, int cy) {
    uint h = (uint)worldSeed;
    h ^= (uint)cx * 0x9E3779B9u;
    h ^= (uint)cy * 0x85EBCA6Bu;
    h ^= h >> 15; h *= 0x2C1B3C6Du;
    h ^= h >> 12; h *= 0x297A2D39u;
    h ^= h >> 15;
    return h;
}

配合同一个 PRNG（推荐用 xorshift 或 PCG 这类自己实现的小 PRNG，别依赖 System.Random 在不同 Unity 版本上的行为一致），就能保证任意时刻、任意机器上，同一块永远长出同样的东西。

注意同一性陷阱

幂等还有一个藏得更深的要求：生成一块时不能依赖「邻居块的状态」来决定随机取向。
如果你先生成 A，再根据 A 的结果去决定 B 的随机选择，那么当 B 先被生成时，结果就不一样了。解决办法：相邻块的边界状态只允许作为参数传入，不允许改变这一块内部的随机序列。

三层加载环

第一环
可见区块玩家当前看得见的范围。必须已生成完毕。
第二环
缓冲区块往外 1~2 环。后台异步悄悄生成，玩家转头时它就准备好了。
第三环
待办队列更远的区域。按需入队、可按玩家的移动方向排优先级、玩家离开就取消。
图 29-2 · 加载三环：可见 / 缓冲 / 队列

关键参数只有一个：单块的生成时间预算。把生成器拆成一帧只能消耗几毫秒的形式（或者放进 Job System / 线程池），然后让每帧只处理队列里的一块。永远不要让主线程等一整块。

一个实用技巧：先给灰模范

如果某块在需要显示的那一刻还没算完，先用一个「粗糙但合法」的版本顶上——比如只用最基础的 filler tile 铺一遍。
玩家几乎不会注意到它几毫秒后就被真实内容替换了，但会更注意到画面卡住。

30先宏观后微观：一条能跑的流水线

把前面所有零件组装起来，得到一个可以真正去做「无限城市」的方案。它一共五层，每一层都用不同的工具解决不同粒度的问题。

第一层
宏观规划（低频、大尺度、纯函数）
用 Perlin / Simplex 噪声 + 一张用地配额表 决定：这一片是水还是陆，是住宅区、商业区、码头区还是城墙。
关键：这一层必须是坐标的纯函数，完全幂等、不需要 WFC。
第二层
地块切分
陆地区域上跑一次不规则网格生成（就是第 17 节的 Stålberg Grid 思路，或者退而求其次用抖动的方形网格），得到街区轮廓。
它可以按需、按 chunk 增量生成，因为它是六边形层的纯函数。
第三层
街区填充 Simple Tiled WFC
每个街区根据自己的用地类型切换 tileset：住宅区加载住宅模块包，码头区加载码头模块包。这是控制成本最低、效果最大的一步。
第四层
权重场精修
用距离场和噪声给 tile 权重再乘一次：靠水的地方码头元素权重上升、离市中心远的地方建筑变矮、道路密度随人口密度衰减。
第五层
装饰 Pass
最后一遍独立的撒点：阳台花盆、晾衣绳、路灯、行人。这一层允许失败、允许随机、允许不完美，因为它不承担任何结构责任。
图 30-1 · 无限城市的五层流水线
分层的真正价值

看第五层那一句「允许失败」。分层让每一层可以采用不同的严格程度：
· 第一 ~ 二层：必须是纯函数，绝不允许失败
· 第三层：可以重启几次
· 第四层：只是乘个系数，无所谓
· 第五层：彻底放松，失败就直接跳过
如果这五层写在一个大函数里，你只能在「全部严格」和「全部放松」之间二选一。

为什么第一层必须是纯函数

这是一个很容易忽视但代价很高的架构决定。第一层决定「这一大片区域是什么性质」，如果它也用 WFC 来做，那么每生成一个新 chunk，都要先把方圆几公里的宏观层先算一遍。

宏观层用 WFC
每块都要重算大片区域或者要把宏观结果全都缓存内存与复杂度双重上升
宏观层用噪声
f(x, y) 直接给出答案无状态、无缓存、天然幂等任何 chunk 都可以随时生成
图 30-2 · 大尺度层用纯函数，是有理由的

这条规律适用于所有无限世界：尺度越大的层，越应该用无状态的函数；有状态的求解器（WFC）留给中小尺度。

「不同区域换 tileset」这一步为什么值得强调

它是整条流水线里性价比最高的一环。原因有三：

① 降低失败率
每套 tileset 内部规则更单纯，组合更少，自然更不容易矛盾
② 提升辨识度
玩家能明确感到「这里是码头，那里是富人区」而不是均匀糊一城
③ 便于分工
美术可以一次只负责一个区的资产不必顾全所有搭配
图 30-3 · 分区 tileset 的三重收益

Townscaper 虽然没有「按区切 tileset」，但它有一个精神相通的手法：玩家选的颜色会影响后续出现哪些装饰模块（石墙只在房屋转角或你改了颜色的时候出现）。同样是「用大类切换细节规则库」。

31失败降级链：不许让玩家看见「生成失败」

在无限世界里，失败不是异常情况，是每天会发生几万次的常态。你需要一条明确的降级路线。

第一步
换种子重试（3 ~ 5 次）
最便宜的手段。实践证明绝大多数偶发失败在这一步就被吸收了。注意要用不同的种子，否则只会重复同一个失败。
第二步
放宽锚点
把这一块自己内部的预置格子按重要性排序，逐个取消。注意：邻居块给的边界约束绝不能放，那是缝合的生命线。
第三步
降低 tileset 要求
切到一套「更松」的 tileset：通常就是万能 filler 权重拉满的版本。结果会很平庸，但一定合法。
第四步
缩小到「只有边框」
只保证边界一圈与邻居对齐，中间全用 filler 平铺。玩家看到的是一片空地，不是一条裂缝。
兜底
退化为预设的手写区块
最后一道保险：放一块预先备好的「通用地块」（一片草地、一片水面）。宁可无聊，不可崩坏。
图 31-1 · 五级降级链：每往下一级，收获的质量更低但一定成功
两个必须守住的红线

① 边界不许妥协。降级可以牺牲内部质量，但不能牺牲与邻居的对齐，否则整张地图会出现肉眼可见的断层，代价远大于内部平庸。
② 兜底必须存在。哪怕它只是一片空地。永远要有最后一层会成功的东西。

把失败率摊平：不要让它聚在边界

还有一个常被忽略的现象：失败率不是均匀分布的，它会沿着某些地形集中。比如水陆交界处、(map edge)、以及多种 tileset 交汇的地方。

排查办法很简单：把每次失败的区块坐标记下来，生成一张热力图。你会很快看到某几个坐标本来就有问题——通常就是某个过渡 tile 缺失。补一块过渡 tile，往往能让全局失败率掉一半。

这条行为监控值得接上

在无限世界里，生成器的失败是沉默的——玩家不会报错，只会觉得「这游戏地图有点空」。
记录失败坐标 + 失败级别 + 触发降级到第几步，是唯一能让你知道它正在悄悄退化的方式。

32从零到跑通的十步

别急着做漂亮的模块。先用最原始的手段把算法跑通，再一层层往上加。

第 1 步
用颜色代替模型
先别管美术。五种 tile 就够：每种一个纯色方块。这一阶段你关心的唯一问题是「它跑不跑得完」。
第 2 步
手写 socket，手工邻接表
不要先写自动生成。手写一遍你才会真正理解它在表达什么。十种 tile × 四个方向，半天能写完。
第 3 步
先做最笨的版本
朴素传播（第 5 节的第一种写法）、失败就重启（第 6 节的第一种姿势）。不优化、不回溯。
第 4 步
把失败率和耗时打出来
跑 100 次，统计成功率和平均耗时。没有这两个数字，后面所有优化都是盲拍。
第 5 步
修复 tile 集，而不是调默认参数
失败率高于 5% 就回去看第 27 节那张诊断表。95% 的问题出在 tile 集本身，不在算法。
第 6 步
接入真正的美术资产
到这一步才换成好看的模块。你会发现之前调试用的界面居然可以直接变成 debug 视图保留下来。
第 7 步
加 socket 自动生成 + 旋转派生
tile 超过 20 块时补上。此时你已经有对比基准，能验证自动生成的邻接和手写的是否一致。
第 8 步
加权重场
按第 12 节把权重做成位置的场。这一步的视觉收益通常远超你的预期。
第 9 步
加全局校验 + 修复 pass
连通性、可达性、房间数量——这些 WFC 不负责的东西统统在这一层补。
第 10 步
最后才做优化
兼容计数、Job System、分块流式。把它们放在最后，因为前九步随时可能改变你的数据结构。
图 32-1 · 十步路线：每一步都有明确的完成判据
一个常见的时间分配错误

很多人把一半时间花在第 10 步（优化），却在第 5 步（修 tile 集）草草而过。而真正决定作品质量的，恰恰是第 5 步和第 8 步。
一个跑得飞快但处处平庸的生成器，不如一个慢一点但看着像人做的。

33排查手册：症状 → 原因 → 药方

把常见的坏结果按现象归类。下次遇到先看这一节，通常不用调试器。

万能的第一步

一旦出问题，先做这件事：把每一格的剩余可能性数量画成一张热力图。
熵高的区域一目了然，异常通常就出现在那里——不是某个 tile 被孤立，就是某条约束写反了。90% 的 WFC bug 用这一张图就能定位。

明确不要用 WFC 的三种情况

① 需要精确的全局控制。「必须正好三个房间」这种要求，WFC 给不了，它只有局部约束。
② 超大地图 + 毫秒级生成。它的最坏情况很难看，实时性要求高时要谨慎。
③ 从小样例求巨大多样性。样例小就必然重复，这是输入信息量的硬限制。

D附录 · 常见误区与反直觉点

这几条和初学者直觉相反，但几乎每次都被验证。

反直觉一
规则越紧，生成往往越快
直觉是「限制多 → 难找到解 → 慢」。实际上约束紧的时候，一次坍缩会连锁推倒一大片，观测步数反而减少。什么都允许的 tile 集既慢又平庸。
反直觉二
失败率高的问题通常不在算法，在 tile 集
很多人第一反应是加回溯。回溯只是让失败不那么显眼，不会让 tile 集变好。先把失败率对回看第 27 节那张诊断表。
反直觉三
问题的解法常常不在算法里，在颗粒度上
Townscaper 面临的「零件塞不进歪格子」，最后靠的是把 tile 从「一栋房」改成「一个角」。当你反复改算法无效时，试试改变问题的单位。
反直觉四
允许失败，反而可能得到更好的作品
完全不容错的生成系统通常也比较保守。能容忍局部不完美的系统，才敢生成更大胆的东西。
反直觉五
多样性往往不来自更多资产，而来自更好的权重场
加 tile 会把所有复杂度一起推高；给权重乘一张噪声图几乎零成本，视觉收益却很大。
反直觉六
「处处合法」离「好玩」还很远
WFC 的保证是数学上的，不是设计上的。永远需要一个独立的「这能不能玩」的校验层。

E附录 · 思考题

能回答前四题，说明这篇的内容你真的吃透了。

题一
去掉那撮 1e-6 的随机噪声会发生什么？
提示：注意开局时所有格子的熵是相等的。答案是：结果会极度雷同，随机种子几乎失效。
题二
为什么先坍缩低熵格子能降低总体失败cost？
提示：矛盾总是先在「快没得选」的格子上发生。答案是：让矛盾在代价最小的时刻暴露。
题三
你的 WFC 总是在地图东南角失败，可能是什么原因？
提示：看训练集 / 示例图的边界。答案通常是：某个本该存在的过渡 tile 从来没被提取到。
题四
Townscaper 的花园为什么一定要围起来才有？
提示：它不是低概率随机。答案是：花园模块的边只能接墙，唯有封闭院子满足这个硬约束。
题五
为什么 WFC 不擅长又长又细的结构？
提示：想想一根横跨六个格子的横梁需要多少格同时同意。答案是：耦合链越长，凑齐的概率越低。
题六
你的无限城市里，为什么宏观层不该用 WFC？
提示：考虑每次生成新 chunk 时要重算的范围。答案见第 30 节：大尺度就该用无状态的纯函数。

最后一句

WFC 这个名字起得太玄，但它真正想教我们的东西很朴素：把「设计」拆成一组局部规则，然后让约束传播替你把剩下的地方填满。
拆规则的能力（socket 怎么分、权重怎么给、哪里需要一个万能填充），才是这件事里真正值钱的部分。
