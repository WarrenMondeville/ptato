00技能系统为什么会烂掉

一句话：技能系统的复杂度不是线性增长的，是乘法增长的。五个技能 × 五种状态 = 不是 25 行代码，而是 25 种「这个组合是否被允许」的判断。

先描述一个几乎所有动作游戏项目都会经历的过程。

第一天，你写了一个 Fireball 类：检查蓝量够不够 → 扣蓝 → 播放动画 → 生成一个火球 → 命中后扣血。很清楚，两百行。

第二周，策划说要加冷却。你加了一个 float CooldownTimer。

第三周，要加一个「燃烧」Debuff，每秒扣血，持续 5 秒。你加了一个 List<Buff> 和一段 Tick 里的遍历。

第四周，策划问：角色被眩晕的时候能放技能吗？吟唱中被打断会怎样？两个加攻击力的 Buff 是叠加还是取最大？火球术在冷却时按钮要不要变灰？

到这里，你会发现每一个新问题都不是「新增一个功能」，而是「修改所有已存在的功能」。这就是技能系统烂掉的真正原因：不是代码写得差，而是信息散落在了错误的地方。

症状一
状态散落
「是否能放技能」这件事，被写进了技能类自己、角色类、UI 类三份代码里，且三份的判断条件会逐渐不一致。
症状二
数值有多个真相源
攻击力可能同时被装备、Buff、天赋、光环修改，每一处都在直接写 AttackPower 这个 float，谁最后写谁说了算。
症状三
表现与逻辑缠死
技能代码里直接 SpawnEmitter，于是单机跑得好好的，一上联机满屏特效重复播放两次。
症状四
改一个数值要碰代码
策划想调一个伤害系数，得改 C++、编译、重启编辑器。于是数值迭代速度被编译速度锁死。

GAS 给出的答案：把所有东西拆成数据和规则

GAS 是 Epic 用《Paragon》（MOBA）和《Fortnite》（战术竞技）的实际需求磨出来的一套框架。它没有发明什么新算法，它做的是一件更朴素的事：把「技能」这个概念拆成六个各司其职的部件，并且规定它们之间只能按固定的方式通信。

拆完之后，上面四个症状分别被这样解决：

  • 状态散落 → 状态统一用 Tag 表示，挂在角色身上。技能、UI、AI 都问同一句话。
  • 多个真相源 → 数值只能被 GameplayEffect 修改，且修改是「累加到基础值上」而不是「覆盖」。
  • 表现缠死 → 特效只能由 GameplayCue 触发，而 Cue 天然知道自己是该在客户端跑还是服务端跑。
  • 改数值要碰代码 → GameplayEffect 是纯数据资产，策划自己在编辑器里改。
最该记住的一条

GAS 的全部设计都可以归纳为一句话：能写成数据的，就不要写成代码；能靠标签判断的，就不要写 if。当你发现自己想在技能里写 if (bIsStunned) 的时候，正确做法通常是给角色挂一个 State.Stunned 标签，然后让技能的「禁用标签」栏位去处理它。

关于「GAS 很难」这件事

GAS 的口碑是两极的：一边是「我三天就跑起来了」，一边是「我看了两周 Lyra 还是不懂」。造成差异的通常不是能力，而是入手顺序。

如果你从 Lyra 源码开始读，你会同时撞上 Game Feature、Experience、Equipment、Input Mapping 四套额外系统，它们和 GAS 本身毫无关系，但混在一起看起来就像 GAS 的一部分。

01ASC：一个人的技能中枢

一句话：AbilitySystemComponent（ASC）是挂在角色身上的那个「技能背包」，它持有该角色全部的技能、生效中的效果、属性集和标签。任何 GAS 角色有且只有一个。

ASC 本身不做任何游戏逻辑。它的角色是一个容器 + 路由器：别人想改这个角色的数值，得经过它；别人想查这个角色能不能放某个技能，得问它；网络要复制什么，由它决定。

OwnerActor 和 AvatarActor：两个容易混的概念

ASC 会区分两个角色：

  • OwnerActor：真正持有 ASC 的那个 Actor。
  • AvatarActor：ASC 的物理化身，也就是你在世界里看到的那个角色。

大多数情况下两者是同一个对象（比如一个 AI 杂兵，ASC 就挂在它自己身上）。但玩家的英雄往往不是：ASC 挂在 PlayerState 上，Avatar 是那个 Character。

为什么要这么绕？因为角色会死、会重生，而 PlayerState 不会。如果 ASC 挂在 Character 上，角色一重生，身上的 Buff、冷却、属性全部清零重生——这在 MOBA 里是不可接受的（你不会希望英雄复活后身上的红 buff 没了）。放到 PlayerState 上，Pawn 可以随便销毁重建，ASC 里的数据一直活着。

方案适用代价
ASC 在 PlayerStateMOBA 英雄、会重生的玩家角色PlayerState 的 NetUpdateFrequency 默认很低，属性与标签同步到客户端会有肉眼可见的延迟，必须手动调高并开启 Adaptive Network Update Frequency。Fortnite 就是这么做的。
ASC 在 Character / PawnAI 杂兵、一次性生成的怪物、纯单机简单直接，但角色销毁后 GAS 数据一起没；死亡重生时状态全丢。

一个必踩的坑

Mixed 模式要求 OwnerActor 的 Owner 是 Controller。PlayerState 的 Owner 默认就是 Controller，但 Character 不是——所以如果你把 ASC 放在 Character 上又想用 Mixed，必须自己调 SetOwner()。从 UE 4.24 起 PossessedBy() 会自动设置 Pawn 的 Owner，这个问题缓解了不少。

02AttributeSet：数值不是一个 float

一句话：Attribute 有两个值：BaseValue（永久值）和 CurrentValue（当前值）。CurrentValue 是 BaseValue 加上所有临时修改后算出来的结果，而不是被直接改出来的。

这是 GAS 里最核心、也最容易被忽略的一个设计。平时我们写 Health -= 30，是直接改一个数字。GAS 里你永远不直接改数字，你施加一个效果，由框架去聚合出最终值。

这个设计带来一个巨大的好处：多个系统可以同时修改同一个属性，而且互相不知道对方的存在。

一个伤害数字可以被护甲减免、被 Buff 翻倍、被免疫标签完全挡下——而这三套系统之间没有一行代码互相引用。它们只是各自往同一个聚合器里丢了一个修改器。

最该记住的一条

为什么不用一个 float 自己写？因为你在复刻的不是「一个数字」，而是数字周围那条管道：谁改过它、改了多少、什么时候失效、要不要同步给客户端、客户端能不能先斩后奏。前两个 Buff 你写得出来，第五个你会开始写 GAS 的劣化版。

两个高频误区

一、不要把 BaseValue 当成最大值。「血量上限」应该是一个独立的 MaxHealth 属性，而不是 Health 的 BaseValue。否则一个 +20 上限的 Buff 会让你陷入「加血上限时当前血量要不要跟着涨」的泥潭。

二、不要在同一个 ASC 上挂两个同类型的 AttributeSet。GAS 查找时只会找到第一个实例，第二条永远读不到，而且不报错。

什么不该放进 AttributeSet

武器弹药是一个经典反例。直觉上「子弹数」是个属性，应该放进 AttributeSet。但 Fortnite 和 GASShooter 的做法都是：它就是一个普通 float，挂在物品上。

理由是：AttributeSet 的生命周期是跟着 ASC 走的，而武器会被捡起、丢弃、切换。每次换枪都要新建 / 移除一个 AttributeSet，代价高、容易崩（客户端先移除、服务器随后复制属性变化过来，客户端找不到 Set 直接崩）。

判断标准

问一句：这个值会被 Buff 修改吗？会被改 → 放进 AttributeSet；不会被改 → 用一个普通变量。攻击力会被 Buff 改，弹药不会。

03GameplayTag：把 if 换成一个标签

一句话：GameplayTag 是 GAS 的通用语。它是形如 State.Stunned、Ability.Fire.Fireball 的层级字符串，用来表达「现在是什么状态」和「允许不允许」。

GAS 里的大部分逻辑是标签匹配而不是条件分支。这一点很难在第一次读代码时体会出来，但它决定了你的项目后期能不能扛住复杂度。

举个例子。「被眩晕时不能放技能」，朴素写法是在每个技能里加一句判断：已经有了 40 个技能，你就得改 40 处，还得保证以后每个新技能都记得加。标签写法是：眩晕时角色的 ASC 上多了一个 State.Stunned，所有「动作类技能」的 Activation Blocked Tags 里填 State.Stunned。

标签的层级是真实生效的

标签不是普通字符串，它有父子关系。查询 State.Dead 时，拥有 State.Dead.ByDamage 的角色会匹配成功。这意味着你可以先粗后细：一开始只用 State.Stunned，后来需要区分「被击晕」和「被冻结」，就扩展成 State.Stunned.Knockdown 和 State.Stunned.Frozen，所有老的查询代码一行都不用改。

Effect 侧：标签还能控制「效果是否生效」

除了资产标签（纯注释用）和授予标签（Granted Tags，效果期间挂给目标），还有两个特别有用的：

  • Application Tag Requirements：目标不满足这些标签，效果根本不会被应用。比如「对已死亡目标不施加中毒」。
  • Ongoing Tag Requirements：效果应用后，标签不满足时临时失效（移除修改与标签，但效果对象还在），满足后自动恢复。比如「隐身时被光照到失效」——不用移除再重新加。
  • Remove Gameplay Effects with Tags：我生效时，把目标身上带这些标签的效果全部移除。这是「净化术」「解控」的实现方式。
  • Immunity：带某些标签的来源对我施加的一切效果免疫。「免疫所有来自 Boss 的 Debuff」一行配置搞定。
Loose Tag 的陷阱

除了由效果授予的标签，还有一种 LooseGameplayTag：直接用 AddLooseGameplayTag() 手动挂上去的。它不参与网络复制，服务器和客户端要各自维护。社区通常用它在拥有者客户端上立刻标记 State.Dead（让本地 UI 零延迟响应），但你必须记得在重生时手动清掉，否则角色会永远「死着」。

04GameplayAbility：技能是有生命周期的对象

一句话：Ability 管的是「能不能放、放完怎么收尾」，而不是「放的时候做什么」。真正的行为逻辑应当尽量下沉到 Effect 和 Task 里。

这里有个很关键的细节：CommitAbility 必须由你自己调用，而且通常写在 ActivateAbility 的开头。框架不会自动帮你扣蓝。如果你忘了调用，技能就变成了「免费无限放」。

反过来，如果你在 Commit 之前就 return 了（比如发现目标不合法），消耗和冷却不会被扣——这是特性，不是 bug：Commit 是最后一道闸门，过了这道闸门才真正付费。

最经典的一个坑

官方文档里专门举了这个例子：一个「喝血瓶」的技能没有正确调用 EndAbility()，结果角色永远处于「正在喝药」的状态——于是他再也不能喝第二瓶、不能冲刺、不能爬梯子，因为技能系统认为他还在忙着喝这瓶药。

记住：不 End，就永远占着位置。所有提前 return 的分支都要走 EndAbility()，包括失败分支。

异步怎么办：AbilityTask

技能经常需要「等一下」：等动画播完、等玩家点地面、等某个事件发生。你不能在 ActivateAbility 里写死循环，所以 GAS 提供了 AbilityTask——本质上是和技能生命周期绑定的协程。

Task用途

WaitTargetData生成一个选取器让玩家选目标（选地面、选范围、选敌人）

// 2. 等动画的「命中帧」事件（由 AnimNotify 发送）

为什么用事件而不是直接在 Notify 里写伤害

因为 AnimNotify 跑在动画线程/表现层，它不知道网络权威、不知道目标是谁、也不知道技能有没有被中断。让 Notify 只发一个「命中帧到了」的事件，由技能来决定做什么——这样被打断时，事件自然没人接收，伤害也就不会误触发。

技能等级

技能有等级概念（火球术 Lv3）。升级有两条路，区别很重要：

05GameplayEffect：改数值的唯一合法途径

一句话：GameplayEffect（GE）是纯数据。它描述「对哪个属性做什么运算、持续多久、期间挂什么标签」，里面不应该有逻辑。

把 GE 理解成一张单据：谁开了单、改什么、改多少、什么时候失效。ASC 是会计，它拿着单据去算账。

时长
Duration Policy
Instant / Duration / Infinite。选错不会报错，只会让你的游戏「闹鬼」—— 用 Instant 做 Buff 结果加成永远不掉，用 Duration 做伤害结果血自己回来了。
改什么
Modifiers
对属性做 Add / Multiply / Divide / Override。数值来源有四种：常量表（Scalable Float）、基于另一个属性（Attribute Based）、自定义计算类（MMC）、运行时传入（SetByCaller）。
复杂计算

副作用

期间挂标签、触发表现、甚至临时授予一个新技能。
周期

它不会产生任何编译错误、任何运行警告。它只会让你的游戏出现「说不清哪里不对」的手感问题：

· 用 Instant 做加速 Buff → 加速永远不消失，角色越跑越快。
· 用 Duration 做伤害 → 5 秒后血量自动涨回来，玩家看到血条诡异地弹回去。
· 用 Infinite 做 Debuff 却忘了移除 → 内存和状态永久泄漏。

运算含义典型用途

SetByCaller 本质是一个 TMap<FGameplayTag, float>：如果对应的标签不存在，它会在运行时报错并返回 0。对 Add 来说只是「没加上」，对 Divide 来说就是除以 0。用 Divide + SetByCaller 的组合一定要给默认值兜底。

除了标签，GE 还有一层直接的效果交互：

  • 堆叠（Stacking）：三个火球叠在身上是算一层还是三层？见第 8 节。
  • 移除（Remove Gameplay Effects with Tags）：净化术的实现。
  • 免疫（Immunity）：按来源标签或按效果查询整体屏蔽。

这一层意味着「驱散」「免疫」「霸体」这类高阶机制不需要写新代码，只是配置。

06GameplayCue：让表现和逻辑离婚

一句话：GameplayCue（GC）是 GAS 的表现层出口。命中特效、音效、屏幕抖动全部由它触发，而它天生知道「自己是该在客户端跑还是服务端跑」。

没有 Cue 的时候，你会怎么做？在技能代码里 SpawnEmitterAtLocation。单机没问题。一上联机，你会看到：特效在服务器上也播了一次（浪费但看不见），在客户端播了一次，而在预测失败需要回滚时——特效已经放出去了，收不回来。

Cue 解决的是这个：表现是表现，逻辑是逻辑，两者由标签连接。

这是引擎层面的强制约定：标签不以 GameplayCue. 开头，Cue 系统会直接忽略它，不报错、不警告，就是没反应。这条规则坑过非常多的人。

而且标签的层级会参与匹配：一个处理 GameplayCue.Weapon.Impact 的处理器，会自动接管 GameplayCue.Weapon.Impact.Metal 和 ...Wood，除非存在更具体的处理器。这让你可以用「泛化处理 + 特化处理」组织特效。

Cue 分两种实现：Static（一次性、无状态，性能最好，命中火花用这个）和 Actor（生成一个 Actor 持续存在，火焰、护盾用这个）。

一个重要的架构收益

Cue 不在专用服务器上运行。这意味着你可以在 Cue 里随便写粒子、音效、UI 飘字，完全不用担心浪费服务器 CPU——因为服务器上它根本不会被调用。这一条让「表现层代码会不会拖慢服务器」这个问题从根上消失了。

另外，Cue 是可以被批量和合并的（Batching），引擎会把同帧内的多个 Cue 合并成一次网络消息。在百人同屏的场景下这个功能很关键。

07聚合公式：加、乘、除的顺序

一句话：CurrentValue = ((BaseValue + 所有加法) × 所有乘法) ÷ 所有除法)。顺序是固定的，而乘法那一层有一个会让所有人算错的陷阱。

官方文档直接给出了聚合器里的那行公式：

((InlineBaseValue + Additive) * Multiplicitive) / Division

看一个具体例子。基础攻击力 100，装备 +10，Buff +30%：

CurrentValue = (100 + 10) * 1.3 = 143 // 而不是 100 + 10 + 30 = 140，也不是 100 * 1.3 + 10 = 140

这个顺序不是随意定的：先加后乘，保证百分比加成不会被固定值加成稀释。你 +10 攻击力之后，那个 +30% 依然是对「加成后的总值」生效。

陷阱：多个乘法不是连乘

这是 GAS 里最反直觉的一处实现。所有 Multiply 修改器会先合并，再一起乘上去，而不是逐个相乘。原因是乘法的 Bias（中性值）是 1：

Multiplicitive = 1 + (m1 - 1) + (m2 - 1) + ... // 一个 0.5 的减速： 1 + (0.5 - 1) = 0.5 ✅ // 两个 0.5 的减速： 1 + (0.5-1)+(0.5-1) = 0 ❌ 直接归零 // 一个 1.1 和一个 0.5： 1 + (0.1)+(-0.5) = 0.6 ✅ // 两个 ×5 的加成： 1 + (5-1) + (5-1) = 9 ❌ 你以为是 25

《Paragon》当年为此定了一条硬性设计约束，你照抄就行：

// 允许的乘法修改器组合 (最多一个值 < 1) 且 (任意多个 [1, 2) 之间的值) 或 (恰好一个值 >= 2)

如果你的项目真的需要「两个 ×5 叠成 ×25」，那不是配置能解决的——你得改动引擎里 FAggregatorModChannel::EvaluateWithBase()，把合并函数从 SumMods 换成自定义的 MultiplyMods。这是一个需要写进项目技术文档的引擎改动，因为升级引擎版本时会冲突。

还有一个更高级的开关

如果连「先加后乘」这个顺序你都想改（比如想让减速只取最狠的那个，而不是叠乘），GAS 在 OnAttributeAggregatorCreated() 里提供了自定义评估元数据。

《Paragon》的移速就是这么做的：MostNegativeMod_AllPositiveMods——所有正向加成都生效，负向减速只取最狠的那一个。这样两个 -30% 的减速不会叠成 -51%，而是 -30%。不符合条件的修改器仍然存在，只是暂时不计入结果，等最狠的那个过期后下一个会自动顶上。

08堆叠：三个火球算几层

一句话：Stacking 只对 Duration 和 Infinite 效果有效，它决定「同一个效果再次施加时，是新建一个，还是给已有的那个加一层」。

默认行为是：每次施加都是一个全新的、互不相干的实例。三个火球打在身上，就是三条独立的燃烧 Debuff，各自计时、各自到期。

开了堆叠之后，第二次施加不会新建，而是把已有的那条 Spec 的层数 +1，并按策略决定是否刷新时长。

Aggregate by Target
目标身上只有一堆，所有来源共享层数上限。PVP 里防止一个目标被全队叠爆

09消耗与冷却：不要写计时器

一句话：在 GAS 里，消耗和冷却都是 GameplayEffect。技能只是「指向」它们，判断与扣除由框架完成。

新手的本能是在技能里写：检查蓝够不够 → 减蓝 → 起一个 SetTimer。GAS 明确反对这两件事。

朴素写法
技能内 if 判断 + 手动扣蓝 + SetTimer。UI 要另写一份同样的判断，且两边会逐渐不一致
GAS 写法
技能指向一个 Cost GE（Instant）和一个 Cooldown GE（Duration + 授予 Cooldown.* 标签）。判断只有一份

运作方式非常优雅：

  • Cost GE：通常是一个 Instant 效果，减去 30 点蓝。
  • Cooldown GE：一个 Duration 效果，时长 5 秒，期间给角色授予 Cooldown.Fireball 标签。
  • 技能的 Activation Blocked Tags 填上 Cooldown.Fireball。冷却期间技能自然不能放——冷却的本质就是一个标签。
这个设计的三个连带好处

一、UI 不用另写判断。按钮变灰只需要问「这个角色身上有没有 Cooldown.Fireball」，和技能激活检查问的是同一句话，永远不会不一致。

二、Buff 可以改冷却。「减少所有冷却时间 30%」不再需要改每一个技能，它是一个新的 GE，去修改那个 Cooldown GE 的时长。

三、冷却可以被驱散和查看。它就在 ActiveGameplayEffects 列表里，调试器里能直接看到剩余时间。

Commit 的三个粒度

函数做了什么

CommitAbilityCost() / CommitAbilityCooldown()只提交其中一项。用于「技能被打断时不退冷却，但退蓝」这类设计
记住这条因果链

冷却不是计时器，是一个效果授予的标签；标签不是变量，是可被任何系统查询的状态；状态不是技能私有的，是挂在角色身上的公共事实。GAS 的每一层抽象都在做同一件事：把私有知识变成公共事实。

Meta Attribute 是什么

它是一个只存在于服务端、从不复制到客户端的临时属性。典型的名字就叫 Damage。它的生命周期极短：被 GE 写入 → 被 PostGameplayEffectExecute 读走 → 归零。

之所以要它，是因为伤害公式的输入（攻击力、护甲、暴击率）和输出（实际扣多少血）需要分开处理，而 GE 的 Modifier 只能做「一个属性改另一个属性」这种简单映射。

Execution：自定义公式的位置

UGameplayEffectExecutionCalculation 可以捕获任意多个属性，然后输出最终值。护甲减伤就写在这里：

// 一个典型的减伤公式（示意） mig = AttackPower * SkillCoef // 技能系数 reduc = Armor / (Armor + K) // 递减式护甲收益 final = mig * (1 - reduc) * CritMul

把它写在 Execution 而不是技能里，有三个理由：

  • 可被所有来源复用：普攻、火球、陷阱、反弹伤害走同一条公式，改一次全改。
  • 可被策划配置：公式里的 K 可以做成从数据表读的常量。
  • 与网络正确配合：Execution 在权威端执行，结果通过属性复制同步，天然一致。
性能要点

自定义计算类里的属性捕获定义（CaptureDefs）必须在构造函数里静态初始化，不要在每次计算时创建——GAS 内部会缓存这些定义，重复创建会让本该很便宜的计算变成分配热点。另外，公式极其复杂时，考虑用曲线表（Curve Table）替代实时计算。

11标签状态机：死亡、眩晕、吟唱

一句话：角色的「状态」应该是一组标签，而不是一个枚举变量。枚举只能表示一种状态，标签可以表示「同时又晕又中毒又在吟唱」。

这是 GAS 思路里最值得单独拿出来讲的一点，因为它能直接改善绝大多数项目的架构。

三条实践建议

一、给技能打分类标签，别只打身份标签。Ability.Fireball 是身份，Ability.Magic / Ability.Damage 是分类。封锁几乎总是按分类做。

二、状态标签统一由 GE 授予，不要手动挂。这样「解除眩晕」只要移除那个 GE，标签自动消失，不用记得清理。

三、确需手动时用 Loose Tag，但一定配对清理。Loose Tag 不复制、不会自动消失，忘了清会导致角色「永远晕着」。

  • UI：按钮变灰、Buff 图标显示，问的是同一个标签。
  • AI：行为树的条件节点直接查标签，不用去问角色类。
  • 输入：Lyra 把 Enhanced Input 的 Action 通过 InputTag.* 映射到技能，按键绑定与技能彻底解耦。

12复制模式：Full / Mixed / Minimal

一句话：复制模式回答的是「别人需要知道多少真相」。玩家角色用 Mixed（效果只给本人），AI 用 Minimal（效果完全不给），单机用 Full。

这一节是把前面所有概念放到网络环境里重新审视一遍。核心矛盾很简单：效果（GameplayEffect）是数据量最大、但对别人最没用的东西。你不需要知道敌人身上挂着 7 个 Buff 的具体数值和剩余时间，你只需要看到他冒火（Cue）和他是不是被控（Tag）。

把 ASC 放 PlayerState 时的必做项

PlayerState 的 NetUpdateFrequency 默认非常低，会导致属性和标签的改变在客户端上有明显延迟——表现是「血条明明掉了，UI 过半秒才动」。放 ASC 上去之后必须调高这个值，并开启 Adaptive Network Update Frequency（自适应更新频率）。Fortnite 用的就是这套。

Batching：把三次 RPC 压成一次

一次技能激活在传统流程里需要 2~3 次客户端到服务器的 RPC（激活请求、目标数据、结束通知）。GAS 提供了 Ability Batching 把它们合并，在高频技能（比如自动开火的枪）上收益明显。

这是个优化项，不是必做项。但如果你在做射击或 MOBA，值得在项目早期就确认它开着。

13预测：客户端先斩后奏

一句话：客户端不等服务器批准就先把动画、特效、属性变化在本地跑一遍，用一个 Prediction Key 记账；服务器回来确认就保留，否决就回滚。

Prediction Key 与预测窗口

FPredictionKey 里有两个 int16（当前 Key 和它所依赖的 Base Key）和一个「是否过期」的脏标记。它像餐厅的取餐号：客户端拿着号先坐下，服务器按号上菜，客户端按号对账。

预测窗口（FScopedPredictionWindow）是一个 RAII 作用域：构造时生成一个新 Key，析构时把它标记为失效。含义是——在这个作用域内产生的所有预测性副作用，共享同一个 Key，作为一个整体被裁决。

FScopedPredictionWindow Prediction(ASC, true);   // 开一个新 Key
ASC->TryActivateAbility(Handle);          // 窗口内的 GE / Task / Cue 全挂到这个 Key 上
// 出作用域，Key 失效，后续操作不再属于本次预测

为什么要「成批」？因为一个复杂技能包含多个子效果（瞬发伤害 + 持续治疗 + 上状态），它们必须作为一个整体被接受或拒绝。如果各自独立预测，会出现「伤害保留了但状态没上」的半吊子结果。

不可回滚
已经播出去的动画、已经放出的特效、已经响了的音效。这些是副作用，发生了就发生了

设计准则

把所有会影响游戏结果的东西放进 GE（可回滚），把所有只是好看好听的东西放进 Cue（不可回滚但代价低）。判断标准：如果这个效果被撤销会让玩家困惑，它就应该放在可回滚的一侧。蓝量被回滚玩家不会察觉，但「技能明明放了却没伤害」玩家立刻会觉得游戏坏了。

常见的预测失败来源

  • 资源不足（客户端以为有蓝，服务器说没有）
  • 被控制（客户端还没收到眩晕标签）
  • 仍在冷却（客户端对冷却的预测有天然延迟，见下节）
  • 目标不合法（客户端命中了，服务器判定没命中）

14预测不了的三件事

一句话：冷却、周期效果、效果的移除，这三件 GAS 预测不了。知道边界比知道能力更重要，因为踩到边界的表现是「说不清哪里不对」。

其一
冷却无法被正确预测
冷却依赖服务器的时间戳对账，高延迟玩家在低冷却技能上会射速低于低延迟玩家。这是官方文档列出的已知问题，不是你的配置错。
应对：对射速敏感的技能，把「能不能开下一发」的判断做成客户端本地的容错，或接受这个差异。
其二
周期效果（Periodic）不能被预测
DOT 的每一跳都只能在服务器上算。所以中毒的跳伤在客户端上会「慢半拍」出现，别把它做成需要即时反馈的机制。
其三
效果的移除无法被预测
客户端不能预测「把某个 GE 移除」。变通做法是预测性地施加一个反向效果来抵消它，但这并非总是等价，仍是官方文档列出的待解决问题。
图 14-1 · 预测能力的三条边界
还有一条隐藏边界

百分比变化（Multiply）的预测有问题。官方文档在讲 Modifier 时两次提示：百分比修改在预测环境下的对账不可靠。所以凡是「+20% 攻击力」这类效果，最好设计成只在服务端权威结算，或者接受偶尔一次的视觉跳变。

自己动手做局部预测

有些值不适合进 GAS，但仍需要本地即时反馈。官方示例项目给了一个很实用的技巧：武器弹药数用普通 float 存储，并在自动开火期间通过 PreReplication() 关掉它的复制（判断条件是角色是否拥有 IsFiring 标签）。

这样本地弹药数立刻减少，服务器的权威值不会在开火中途把本地值覆盖回去，等停火后再由服务器对齐。文档原话是：你在这里本质上是在做自己的本地预测。

这个模式可以直接推广到任何「高频变化、不参与 Buff 计算、允许短暂不一致」的数值上。

16什么时候不该用 GAS

一句话：如果你的游戏没有「多个系统同时修改同一个数值」和「多人联机」这两条需求，GAS 的前置成本收不回来。

这一点必须讲清楚，因为 GAS 的社区讨论里「该不该上」的争议远大于「怎么用」。

引入 GAS 的固定成本是实打实的：C++ 侧必须写 ASC 与 AttributeSet（没有蓝图等价物）、全队要理解六块积木、调试链路比直接写代码长一层。

休闲小游戏、两周的原型验证、纯单机且技能少于 10 个、团队没有 C++ 能力

社区里有一个很典型的迁移案例：一个中型 ARPG 项目初期用 DataAsset 方案快速上线，装备系统跑得很好；后来加入「套装效果」「传奇装备触发技能」这类需求，手动维护依赖排序变得极其痛苦，一个属性 Bug 要排查半天。最终团队花了两个月迁移到 GAS，后期技能与装备联动的开发效率提升了约三倍。

结论是：技术选型要基于产品的路线图，而不是当前的舒适区。如果你确定半年内不会加套装、不会加 Buff 联动、不做联机——那就别上 GAS，把属性重算封装成一个独立模块，预留依赖排序接口即可。

折中方案：只借鉴一半

完全不上 GAS，也可以只抄它最有价值的两个想法：

  • 基础值 / 当前值分离 + 修改器聚合：这一层的收益最大、成本最低，几乎任何项目都值得做。
  • 用标签表达状态：把 bIsStunned 换成标签容器，立刻能省掉大半的条件分支。

至于预测、堆叠、Execution 这些，等真的需要了再补。详见第 18 节的 Unity 对照。

1712 个几乎人人都会踩的坑

一句话：这些坑都不会报错。它们只是让你的游戏在某个时刻开始「说不清哪里不对」，然后耗掉你两天。

1
忘了调用 EndAbility
技能永远占用着位置，角色再也不能做它被封锁的任何事。官方文档用「喝药喝到天荒地老」举的就是这个例子。
2
忘了调用 CommitAbility
技能变成免费无限放。反过来，所有提前 return 的分支也都要 End。
3
选错 Duration Policy
Instant 做 Buff 永不消失，Duration 做伤害血量自己弹回来。
4
以为两个 Multiply 是连乘
两个 ×5 得到的是 9 而不是 25。乘法是先合并再相乘。
5
客户端没初始化 ASC
报错是「Can't activate LocalOnly or LocalPredicted ability」，但真正的原因是缺了 InitAbilityActorInfo。
6
把 BaseValue 当成血量上限
上限应该是独立的 MaxHealth 属性。
7
同一个 ASC 上挂了两个同类 AttributeSet
第二个永远读不到，且不报错。
8
Period 大于 Duration
最后一次周期永远等不到，玩家觉得「少跳了一次」。
9
SetByCaller 的标签不存在
运行时报错并返回 0。用在 Divide 上就是除以零。
10
Cue 标签没以 GameplayCue. 开头
系统静默忽略，特效永远不出现。
11
Loose Tag 忘了清理
角色永久处于某个状态，且不参与网络复制，服务器和客户端表现不一致。
12
遍历技能列表没加锁
遍历 ActivatableAbilities.Items 前必须加 ABILITYLIST_SCOPE_LOCK()，而且不要在锁的作用域内移除技能。

不要在 PreAttributeChange 里触发游戏事件。它的职责只有夹取值。要响应属性变化，用 ASC::GetGameplayAttributeValueChangeDelegate() 注册回调。在夹取函数里放逻辑，会导致「夹取被触发两次时事件也触发两次」这类极难定位的问题。

关于调试困难这件事

GAS 被抱怨最多的一点是「调试复杂，多层 Effect 嵌套」。这有一半是真的，另一半是因为没用对工具——见第 19 节。

18Unity 视角：把这套思想搬回 C#

一句话：GAS 真正值钱的不是那六个类，而是三条原则——数值只由修改器聚合、状态只用标签表达、表现只由事件触发。这三条在 Unity 里完全可以实现。

如果你是 Unity / C# 开发者，可能会觉得这一整篇讲的都是别人家的框架。但其实它对你同样有用，因为这些问题是引擎无关的：技能系统变烂的四种症状，在 Unity 项目里一模一样。

GAS 概念Unity / C# 对应实现建议
AbilitySystemComponent挂在角色 GameObject 上的一个 AbilitySystem MonoBehaviour持有技能列表、生效效果列表、属性集、标签容器。所有跨系统的读写都经过它
AttributeSetScriptableObject 定义属性集 + 运行时的 Base / Current 双值字典关键是「双值 + 修改器列表 + 脏标记重算」，不是「一个 float」
GameplayEffect纯数据 ScriptableObject描述：目标属性、运算、时长、周期、授予的标签。逻辑量为零
GameplayAbility数据用 ScriptableObject，运行时实例用一个普通 C# 对象生命周期方法照抄：CanActivate / Commit / Activate / End。配合 UniTask 做异步等待
GameplayTag层级字符串 + 运行时容器（或用静态常量表 + 位掩码）父子匹配是关键：查询 State.Dead 要能命中 State.Dead.ByDamage
GameplayCue一个表现层事件总线逻辑侧只发事件，表现侧订阅。联机时订阅方天然只在客户端存在
ExecutionCalculation策略类或委托把伤害公式从技能里抽出来，做成可替换的策略对象
客户端预测没有内建支持，需要自己写这是唯一真正缺失的一块。单机项目直接跳过
第一层
先做数值聚合（收益最大）
把 FinalValue = (Base + ΣAdd) × ΠMul 做成一个 Attribute 类，所有对数值的修改都经过它。这一步通常两三天能写完，立刻解决「Buff 互相覆盖」和「不知道谁改了我的攻击力」。
第二层
再做标签状态
一个 TagContainer + 八个语义（Required / Blocked / Granted / Cancel）。把 if (bIsStunned) 全部替换成标签查询。
第三层
再做技能生命周期
把技能拆成「数据（SO）+ 实例（运行时）」，强制 CanActivate / Commit / Activate / End 四段式，并在 End 里做统一清理。
第四层
最后才是表现解耦与联机
表现走事件总线；联机预测如果没有强需求就别做，用「服务器权威 + 客户端插值」通常够用。

最容易被忽视的移植点

不是类结构，是「效果只能由效果修改」这条纪律。在 Unity 里你随时可以直接写 player.Health -= 30，没人拦你。而一旦开了这个口子，三层之后你又会回到「不知道血是谁扣的」。建议在项目里加一条硬性约定（甚至写个 Analyzer 或 Review 检查项）：属性的 setter 只对效果系统开放。

另外，许多团队在 Unity 侧会把技能做成「时间轴 + 帧事件」的形式（类似 Timeline 或自定义轨道），这和 GAS 并不冲突：时间轴负责「什么时候发生什么」，GAS 的三层负责「发生了之后怎么结算」。两者是正交的。

19调试：看不见的系统永远调不好

一句话：GAS 的调试成本，几乎全部来自「状态看不见」。把状态可视化之后，它的调试难度会回落到和普通代码差不多的水平。

三个必用工具

工具怎么用能看到什么
showdebug abilitysystem游戏内控制台命令当前角色身上的全部属性（Base / Current 分开显示）、生效中的效果列表、剩余时间、层数
Gameplay Debugger默认按单引号键唤出同上，但是以可交互面板的形式，还能切换观察目标
Print String / 日志在关键节点打点效果的剩余时间与堆叠层数——这两个是最常算错的量
最有效的一个调试习惯

遇到「效果没生效」时，不要先去读技能蓝图。按这个顺序排查，通常两分钟内能定位：

1. 效果到底有没有被施加（看 ActiveGameplayEffects 里有没有它）
2. 施加了但被挡了（看 Application Tag Requirements / Immunity）
3. 生效了但时长策略选错（Instant 做 Buff 时会看到「属性变了但没持续」）
4. 数值不对（看聚合器的 Modifier 列表，检查 Multiply 有没有被合并）
5. 表现没出来（看 Cue 的标签前缀）

联机排查的起点

联机问题 90% 是「一边有、另一边没有」。最快的定位手段是在 AttributeSet 的 OnRep_ 回调里打断点——如果断点不触发，说明数据根本没到客户端，问题在复制模式或初始化时机；如果触发了但值不对，问题在聚合或夹取。

还有一条必须记住的配置：属性的 OnRep 里要用 GAMEPLAYATTRIBUTE_REPNOTIFY 宏，并且复制条件设为 REPNOTIFY_Always。默认情况下，如果本地值（预测值）和服务器发来的值相同，OnRep 不会触发——而这恰恰是预测成功的情况，你需要它触发来完成确认。REPNOTIFY_Always 就是为这件事存在的。

多人测试的时机

很多人把联机测试留到项目后期，这是 GAS 项目最大的风险之一。建议在项目初期就搭一个两客户端的测试环境，哪怕只是两个窗口。GAS 的复制行为需要在真实网络下跑通，单机 PIE 里「看起来对」的东西，联机后经常完全不是那么回事。

另外，用 PIE 多客户端测试时要关掉 Run Under One Process，否则非第一个客户端的世界不会正确更新（尤其是派生属性相关的逻辑）。

B从零搭建的 10 步清单

顺序很重要：属性必须早于效果，效果必须早于技能。因为效果要引用属性，技能要引用效果。顺序反了就要反复回头改。

01
启用插件
Edit → Plugins → 搜索 Gameplay Abilities，启用并重启编辑器。没启用时所有相关工具都会报错
02
注册标签
Project Settings → GameplayTags 里先把 State.*、Ability.*、Cooldown.*、GameplayCue.* 几棵树建好。标签必须先存在，技能才能引用
03
写 AttributeSet（C++）
Health / MaxHealth / Mana / MaxMana / AttackPower / Armor，每个都用 ATTRIBUTE_ACCESSORS 宏生成访问器
04
写 ASC（C++）
在 OwnerActor 的构造函数里创建，SetIsReplicated(true)，选好复制模式
05
两端初始化
服务器 PossessedBy()、客户端 OnRep_PlayerState() 各调一次 InitAbilityActorInfo
06
做三个基础 GE
GE_Damage（Instant）、GE_Cost（Instant）、GE_Cooldown（Duration + 授予标签）
07
做第一个技能 GA_Fireball
填上 Cost GE、Cooldown GE、Blocked Tags，ActivateAbility 里只做「播放动画 → 等事件 → 施加 GE → End」
08
授予技能
用 GiveAbility() 把它挂到角色身上；用 InputTag 把输入绑上去
09
加 Cue
建一个 GC_FireImpact，标签必须以 GameplayCue. 开头，挂到 GE 上
10
开调试器验证
showdebug abilitysystem，确认：属性 Base / Current 分开显示、效果在列表里、冷却标签出现过又消失

第 7 步的验收标准

第一个技能做完后，你应该能在调试器里看到：按下按键 → 蓝量减少 → 冷却标签出现 → 5 秒后标签消失 → 期间再按无效。这四件事全对，说明整条链路是通的。此时再去做伤害、Buff、联机，每一步都是局部修改。

C常见误区与反直觉点

按「反直觉程度」排序。第一条最反直觉，也最容易毁掉一整个数值体系。

反直觉 1
两个 ×5 的 Buff 叠出来是 ×9
因为乘法修改器是先合并再相乘，中性值是 1 而不是 0。要真连乘得改引擎源码。
反直觉 2
Instant 效果不会给目标挂任何标签，哪怕一帧也不会
所以「命中即眩晕」不能靠 Instant GE 的 Granted Tags 实现，要单独施加一个 Duration GE。
反直觉 3
冷却不是计时器，是一个效果授予的标签
理解了这点，「减冷却」「驱散冷却」「查看剩余冷却」全都是同一件事的不同侧面。
反直觉 4
周期效果的第一跳不在第 0 秒
Duration 3 秒、Period 1 秒，跳在 t=1、2、3。
反直觉 5
在 PreAttributeChange 里夹取，不会改掉修改器
任何重新计算当前值的地方（Execution、MMC）都要再夹一次，否则会出现「夹了但没完全夹」。
反直觉 6
预测成功时也要触发 OnRep
因为本地预测值和服务器值相同，默认的 OnRep 不会触发。必须设 REPNOTIFY_Always。
反直觉 7
武器弹药不该放进 AttributeSet
「看起来是个数值」和「应该是个属性」是两回事。判断标准是：它会被 Buff 修改吗？
反直觉 8
GAS 最难的从来不是 GAS 本身
大部分人的困难来自 Lyra 里同时存在的 Game Feature、Experience、Equipment 等额外系统。先学裸 GAS，再读 Lyra。

D思考题

能回答这六个问题，说明这套思路你已经真正内化了。建议先自己想，再回去翻对应章节。

问题涉及章节
1. 一个「+20 攻击力」和一个「+30% 攻击力」的 Buff 同时生效，基础攻击力 100，结果是多少？如果反过来先加 30% 再加 20 呢？第 7 节
2. 你要做「中毒 5 秒，每秒扣 10 血」，Duration 和 Period 分别填多少？实际会跳几次伤害？第 5、8 节
3. 三个玩家同时对同一个 Boss 上「燃烧」，你希望 Boss 最多只能叠 3 层（而不是 9 层），该选哪种堆叠类型？第 8 节
4. 「沉默」只封法术不封位移，「定身」只封位移不封施法。用标签怎么设计？需要给技能加什么标签？第 11 节
5. 一个技能预测失败了，哪些东西能被回滚，哪些不能？据此你会把「扣蓝」和「播放施法音效」分别放在哪一侧？第 13 节
6. 你的项目有 12 个技能、纯单机、三个月上线。你会上 GAS 吗？如果不上，你会照搬它的哪两层？第 16、18 节
如果只带走一句话

把「能不能」做成标签，把「改多少」做成数据，把「怎么做」留给技能。这三件事分开的那一天，你的技能系统就开始可控了——无论你用的是 GAS、Unity，还是自己撸的框架。
